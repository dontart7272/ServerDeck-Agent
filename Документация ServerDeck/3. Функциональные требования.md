# Функциональные требования

Актуализация интеграции 12 октября 2026 года: действует [дополнение по согласованным решениям Agent](<Документация ServerDeck Agent/12. Согласование с клиентом.md>). Для перечисленных там границ AFR/ASEC и дополнение заменяют прежние формулировки, включая общую политику равноправных устройств, модульный жизненный цикл, историю, аудит и localhost onboarding. Это требования, не доказательство реализации.

## Общие положения

### Область документа

Документ описывает функциональные требования к **клиенту** ServerDeck.
Требования к ServerDeck Agent (сбор данных, API, установщик, аудит, хранение
истории) описываются в отдельном документе. Требования безопасности
вынесены в документ «Требования безопасности» (`NFR-SEC-*`).

Часть разделов этого файла описывает поведение клиента при отображении данных,
которые формирует агент. Требования, относящиеся к реализации на стороне агента,
подлежат переносу в документ агента.

### Основные определения

- **Клиент** — нативное Android-приложение ServerDeck на Kotlin с интерфейсом
  Jetpack Compose. Защищённое хранение, биометрия, SSH-операции и запуск Termux
  реализуются отдельными сервисами и адаптерами Android. UI обращается к ним
  через контролируемые интерфейсы приложения.
- **ServerDeck Agent** (агент) — постоянно работающий сервис на управляемой
  Linux-системе (systemd). Предоставляет клиенту API с аутентификацией
  устройства по токену и выполняет только заранее определённые операции.
- **Модуль** — расширение возможностей ServerDeck, состоящее из клиентского
  UI-пакета (в этом документе — «плагин») и серверной части в агенте (FR-009).
- **SSH** — канал, независимый от агента. Используется клиентом для
  автоматической установки, обновления и удаления агента (FR-002), а также
  для интерактивного терминала через Termux (FR-011).

### Платформы

- Клиент: Android, Kotlin и Jetpack Compose. Поддержка других платформ
  рассматривается отдельно и не требуется от текущей реализации.
- Сервер: Linux с systemd. Raspberry Pi (arm64/armv7) поддерживается как
  Linux-система. Windows Server не входит в текущий объём.

## FR-001. Просмотр списка добавленных серверов 

**Приоритет:** Must

#### Цель

Пользователь должен иметь возможность открыть главный экран приложения и просмотреть список всех ранее добавленных серверов вместе с их текущим состоянием и ключевыми метриками.

#### Предусловия

- Пользователь ранее добавил в приложение хотя бы один сервер. 
- Для получения актуальных данных клиент имеет сетевой доступ к агенту ServerDeck. 
- Агент ServerDeck установлен и настроен на добавленном сервере.

#### Область действия

Требования группы `FR-001` описывают отображение списка серверов, сводки, карточек серверов, обновления данных, статусов, сортировки и пустых состояний.

#### Общие определения

- **ServerDeck Agent** — серверный компонент ServerDeck, устанавливаемый на управляемую Linux-систему и работающий как системный сервис.
- **Клиент** — приложение ServerDeck, которое обращается к API ServerDeck Agent для получения данных и выполнения действий.
- **Управляемый сервер** — сервер, на котором установлен и настроен ServerDeck Agent.
- **Снимок метрик** — набор данных о состоянии сервера, сформированный агентом в определённый момент времени. 
- **Последнее успешное обновление** — время последнего корректного ответа агента, содержавшего снимок метрик. 
- **Устаревшие данные** — данные, полученные раньше интервала актуальности (по умолчанию 60 секунд, настраивается в `FR-010.4`). 
- **Закреплённый сервер** — сервер, отмеченный пользователем как приоритетный для отображения в верхней части списка. 
- **Основной диск** — корневая файловая система `/`.

#### Задачи агента

Требования к задачам агента (сбор метрик, API, выполнение разрешённых операций, нормализация данных, журнал аудита) определяются в документе требований к агенту.

### FR-001.1. Отображение сохранённого списка серверов

**Приоритет:** Must  

Приложение должно отображать на главном экране все серверы, сохранённые
в локальном хранилище приложения.

Приложение не должно ожидать завершения сетевого обновления, прежде чем
показать сохранённый список серверов.

#### Критерии приёмки

- [ ] При наличии хотя бы одного сохранённого сервера пользователь видит его карточку на главном экране.
- [ ] При наличии нескольких серверов отображается карточка каждого сохранённого сервера.
- [ ] Список серверов отображается до завершения запроса к агентам.
- [ ] Ошибка сетевого обновления не скрывает сохранённые серверы из списка.

---
### FR-001.2. Запрос актуального состояния серверов

**Приоритет:** Must  

После открытия главного экрана приложение должно выполнить запрос текущего
состояния к агенту каждого сервера, сохранённого в локальном хранилище.

Запрос состояния должен включать данные, необходимые для отображения карточки
сервера: статус доступности, RX, TX, CPU, RAM, использование основного диска,
сведения о GPU при их доступности и время формирования снимка метрик.

#### Критерии приёмки

- [ ] После открытия главного экрана приложение инициирует запрос состояния для каждого сервера в списке.
- [ ] Успешный ответ агента обновляет данные только соответствующей карточки сервера.
- [ ] Запрос к одному серверу не должен блокировать запросы к другим серверам.
- [ ] При отсутствии сетевого соединения приложение не завершается аварийно.

---
### FR-001.3. Отображение времени обновления данных

**Приоритет:** Must  

Приложение должно отображать для каждого сервера время последнего успешного
получения снимка метрик от агента.

Если с момента последнего успешного обновления прошло более 60 секунд,
данные сервера должны быть помечены как устаревшие.

#### Критерии приёмки

- [ ] После успешного ответа агента приложение сохраняет время получения ответа.
- [ ] Карточка сервера отображает время последнего успешного обновления.
- [ ] Через 60 секунд после последнего успешного обновления карточка получает визуальную отметку об устаревших данных.
- [ ] При неуспешном обновлении время последнего успешного обновления не заменяется временем ошибки.

---
### FR-001.4. Сводка по состоянию серверов

**Приоритет:** Must  

Приложение должно отображать в верхней части главного экрана сводку
по состоянию всех серверов, отображаемых в текущем списке.

Сводка должна содержать:

- Общее количество серверов.
- Количество серверов со статусом `ONLINE`.
- Количество серверов со статусом `WARNING`.
- Количество серверов со статусом `OFFLINE`.
- Количество серверов со статусом `UNKNOWN`.

Сумма количества серверов по всем статусам должна быть равна общему количеству
серверов в сводке.

#### Критерии приёмки

- [ ] Сводка отображается при наличии хотя бы одного сервера.
- [ ] Сводка содержит общий счётчик серверов.
- [ ] Сводка содержит счётчик для каждого статуса.
- [ ] Сумма счётчиков статусов равна общему количеству серверов.
- [ ] После обновления статуса сервера соответствующий счётчик обновляется без повторного открытия экрана.

---
### FR-001.5. Отображение идентификационных данных сервера

**Приоритет:** Must  

Карточка каждого сервера должна отображать название сервера, заданное
пользователем при его добавлении.

Если для сервера указана локация, карточка должна отображать значение локации.
Если локация отсутствует, элемент интерфейса для неё не должен отображаться.

#### Критерии приёмки

- [ ] Карточка каждого сервера отображает его название.
- [ ] Название соответствует значению, сохранённому при добавлении или редактировании сервера.
- [ ] Локация отображается только при наличии непустого значения.
- [ ] При отсутствии локации карточка не содержит пустой подписи, пустой строки или значения `null`.

---
### FR-001.6. Отображение статуса сервера

**Приоритет:** Must  

Карточка каждого сервера должна отображать один из следующих статусов:

- `ONLINE`;
- `WARNING`;
- `OFFLINE`;
- `UNKNOWN`.

Статус должен быть представлен текстовым значением и визуальным индикатором,
не зависящим только от цвета.

#### Критерии приёмки

- [ ] Каждая карточка сервера содержит один допустимый статус.
- [ ] Для каждого статуса отображается текстовая подпись.
- [ ] Для каждого статуса отображается визуальный индикатор.
- [ ] Пользователь может различить статусы без восприятия цвета.

---
### FR-001.7. Отображение сетевого трафика

**Приоритет:** Should  

Карточка сервера должна отображать текущую скорость входящего (`RX`)
и исходящего (`TX`) сетевого трафика при наличии актуального снимка метрик.

RX и TX должны рассчитываться как суммарная скорость передачи данных по всем
сетевым интерфейсам сервера, кроме loopback-интерфейса `lo`.

Скорость должна отображаться в наиболее подходящей единице измерения:
`B/s`, `KB/s`, `MB/s` или `GB/s`.

Если данные о сетевом трафике недоступны, приложение должно отображать `—`.

#### Критерии приёмки

- [ ] При наличии метрик отображаются отдельные значения RX и TX.
- [ ] RX и TX отображаются как скорость передачи данных, а не как накопленный объём.
- [ ] Интерфейс `lo` не учитывается при расчёте RX и TX.
- [ ] Значение скорости содержит единицу измерения.
- [ ] При недоступной метрике вместо нулевого значения отображается `—`.

---
### FR-001.8. Отображение использования CPU

**Приоритет:** Must  

Карточка сервера должна отображать текущее использование CPU в процентах
в диапазоне от 0 до 100.

Если использование CPU недоступно, приложение должно отображать `—`.

#### Критерии приёмки

- [ ] При наличии метрик карточка отображает использование CPU в процентах.
- [ ] Значение CPU находится в диапазоне от 0 до 100.
- [ ] Значение CPU содержит символ `%`.
- [ ] При недоступной метрике CPU отображается `—`.

---
### FR-001.9. Отображение использования RAM

**Приоритет:** Must  

Карточка сервера должна отображать использованный и общий объём оперативной
памяти, а также процент её использования.

Объём памяти должен отображаться в подходящих единицах: `MB`, `GB` или `TB`.

Если данные об оперативной памяти недоступны, приложение должно отображать `—`.

#### Критерии приёмки

- [ ] При наличии метрик отображаются использованный и общий объёмы RAM.
- [ ] При наличии метрик отображается процент использования RAM.
- [ ] Значения объёма памяти содержат единицы измерения.
- [ ] При недоступной метрике RAM отображается `—`.

---
### FR-001.10. Отображение использования диска

**Приоритет:** Must  

Карточка сервера должна отображать использованный и общий объём основного
системного диска, соответствующего корневой файловой системе `/`, а также
процент его заполнения.

Если агент не может получить метрики корневой файловой системы, приложение
должно отображать `—`.

#### Критерии приёмки

- [ ] При наличии метрик отображаются использованный и общий объёмы диска `/`.
- [ ] При наличии метрик отображается процент заполнения диска `/`.
- [ ] Пользователь может определить, что значение относится к файловой системе `/`.
- [ ] При недоступной метрике диска отображается `—`. 

---
### FR-001.11. Отображение использования GPU

**Приоритет:** Should  

Приложение должно отображать использование GPU в процентах, если агент
обнаружил поддерживаемое графическое устройство и успешно получил его метрики.

Если сервер не содержит поддерживаемого GPU или метрики GPU недоступны,
элемент отображения GPU не должен быть показан.

Если на сервере доступно несколько GPU, приложение должно отображать
максимальное значение загрузки среди всех доступных GPU.

#### Критерии приёмки

- [ ] При наличии одного поддерживаемого GPU карточка отображает его загрузку в процентах.
- [ ] При наличии нескольких GPU отображается максимальная загрузка среди них.
- [ ] При отсутствии поддерживаемого GPU элемент GPU не отображается.
- [ ] При ошибке получения GPU-метрик элемент GPU не отображается.

---
### FR-001.12. Модель статусов сервера

**Приоритет:** Must

Приложение должно вычислять статус каждого сервера на основании результатов
обращения к его агенту. Статус является клиентской оценкой: агент не вычисляет
и не передаёт статус сервера. На модель статусов ссылаются требования
отображения, сортировки и сводок (`FR-001.4`, `FR-001.6`, `FR-001.17`).

Определения статусов:

| Статус | Условие |
|---|---|
| `UNKNOWN` | Сервер сохранён в приложении, но успешный снимок метрик от его агента ещё не получен |
| `ONLINE` | Успешный ответ агента давностью не более интервала актуальности, ни одна контролируемая метрика не достигла порога предупреждения |
| `WARNING` | Успешный ответ агента давностью не более интервала актуальности, но хотя бы одна контролируемая метрика достигла или превысила порог предупреждения |
| `OFFLINE` | Таймаут запроса к агенту, сетевая ошибка либо последний успешный снимок старше интервала актуальности |

Контролируемыми метриками являются использование CPU, RAM, диска `/`
и GPU при наличии поддерживаемого GPU. Отсутствие GPU не препятствует
присвоению статуса `ONLINE`.

Пороги предупреждений и временные интервалы являются настройками приложения
(см. FR-010) и имеют значения по умолчанию:

- CPU: не менее 90%.
- RAM: не менее 90%.
- Диск `/`: не менее 90%.
- GPU: не менее 95%, если GPU поддерживается и метрика доступна.
- Интервал актуальности успешного ответа: 60 секунд.
- Таймаут запроса к агенту: 10 секунд.

Правила переходов:

- `UNKNOWN` заменяется на `ONLINE` или `WARNING` после первого успешного
  ответа агента.
- `ONLINE` и `WARNING` переходят в `OFFLINE` при таймауте, сетевой ошибке
  или устаревании последнего снимка.
- `ONLINE` и `WARNING` могут переходить друг в друга при изменении метрик.
- При одновременном превышении нескольких порогов сервер имеет один
  статус `WARNING`.
- При переходе в `OFFLINE` приложение не должно заменять последние успешно
  полученные значения метрик нулевыми значениями; карточка отображает время
  последнего успешного обновления.

#### Критерии приёмки

- [ ] Новый сервер без успешного ответа агента получает статус `UNKNOWN`.
- [ ] После первого успешного ответа агента статус `UNKNOWN` заменяется на `ONLINE` или `WARNING`.
- [ ] Сервер с успешным ответом агента в пределах интервала актуальности получает статус `ONLINE`, если все доступные контролируемые метрики ниже порогов.
- [ ] При CPU, RAM или диске `/` не менее порога предупреждения сервер получает статус `WARNING`.
- [ ] При загрузке поддерживаемого GPU не менее порога предупреждения сервер получает статус `WARNING`.
- [ ] При одновременном превышении нескольких порогов сервер имеет один статус `WARNING`.
- [ ] Отсутствие GPU не препятствует присвоению статуса `ONLINE`.
- [ ] При отсутствии ответа агента в течение таймаута сервер получает статус `OFFLINE`.
- [ ] При сетевой ошибке сервер получает статус `OFFLINE`.
- [ ] Сервер со снимком метрик старше интервала актуальности получает статус `OFFLINE`.
- [ ] При переходе в `OFFLINE` на карточке сохраняются последние известные значения метрик и отображается время последнего успешного обновления.
- [ ] Изменение порогов и интервалов в настройках применяется к вычислению статуса без перезапуска приложения.

### FR-001.16. Закрепление серверов

**Приоритет:** Should  

Пользователь должен иметь возможность закрепить сервер.

Закреплённые серверы должны отображаться выше незакреплённых серверов
независимо от выбранного типа сортировки.

#### Критерии приёмки

- [ ] После закрепления сервер отображается в группе закреплённых серверов.
- [ ] Все закреплённые серверы отображаются выше всех незакреплённых серверов.
- [ ] Закрепление сохраняется после перезапуска приложения.
- [ ] После снятия закрепления сервер перемещается в группу незакреплённых серверов.

---
### FR-001.17. Сортировка списка серверов

**Приоритет:** Should  

Приложение должно поддерживать сортировку серверов внутри групп закреплённых
и незакреплённых серверов.

По умолчанию серверы должны сортироваться по времени добавления:
сначала недавно добавленные серверы.

Приложение должно поддерживать следующие варианты сортировки:

- По времени добавления: новые сверху / старые сверху.
- По названию: от А до Я / от Я до А.
- По статусу: `OFFLINE`, `WARNING`, `ONLINE`, `UNKNOWN`.
- По использованию CPU: по убыванию.
- По использованию RAM: по убыванию.
- По заполненности диска `/`: по убыванию.

Если значения сортировки равны, серверы должны сортироваться по названию
в алфавитном порядке.

#### Критерии приёмки

- [ ] При стандартной сортировке недавно добавленные серверы отображаются выше ранее добавленных.
- [ ] Выбранная сортировка применяется отдельно внутри закреплённой и незакреплённой групп.
- [ ] Сортировка по названию изменяет порядок серверов согласно названию.
- [ ] Сортировка по статусу использует зафиксированный порядок статусов.
- [ ] Сортировка по CPU, RAM и диску располагает серверы с наибольшим значением выше.
- [ ] При одинаковых значениях сортировки серверы упорядочены по названию.
- [ ] Выбранный тип сортировки сохраняется после повторного открытия приложения.

### FR-001.18. Пустое состояние списка серверов

**Приоритет:** Must  

Если в локальном хранилище приложения отсутствуют добавленные серверы,
приложение должно отображать пустое состояние списка.

Пустое состояние должно содержать:

- Пояснение, что серверы ещё не добавлены.
- Элемент управления для перехода к добавлению сервера.

#### Критерии приёмки

- [ ] При отсутствии серверов список не отображает пустые карточки.
- [ ] Пользователь видит понятное пояснение о причине отсутствия серверов.
- [ ] Пользователь может перейти к экрану добавления сервера из пустого состояния.

---
### FR-001.19. Независимость обновления серверов

**Приоритет:** Must  

Ошибка получения данных от одного агента не должна препятствовать отображению
списка и обновлению данных остальных серверов.

При ошибке обновления конкретного сервера приложение должно сохранить его
последнее успешное состояние, отобразить статус `OFFLINE` и время последнего
успешного обновления.

#### Критерии приёмки

- [ ] При недоступности одного сервера карточки остальных серверов остаются видимыми.
- [ ] При недоступности одного сервера приложение продолжает выполнять запросы к другим серверам.
- [ ] Успешные ответы доступных серверов обновляют их карточки независимо от ошибок других серверов.
- [ ] Ошибка одного сервера не приводит к аварийному завершению приложения.

## FR-002. Управление добавленными серверами

**Приоритет:** Must  

### Цель

Пользователь должен иметь возможность добавить сервер в ServerDeck (включая
автоматическую установку агента), изменить параметры добавленного сервера,
обновить агент и удалить сервер из приложения вместе с агентом или без него.

### Область действия

Группа требований `FR-002` определяет:

- Создание записи сервера и валидацию параметров.
- Проверку SSH-подключения и ключа сервера.
- Проверку совместимости сервера и уже установленного агента.
- Автоматическую установку агента по SSH и ручную установку как запасной сценарий.
- Выбор режима сетевого доступа к агенту.
- Pairing клиента с агентом.
- Редактирование параметров сервера.
- Обновление агента.
- Управление подключёнными устройствами.
- Удаление записи сервера и, по выбору пользователя, агента.

Требования к самому агенту (установщик, сервис, API, pairing на стороне
агента) определяются в документе требований к агенту. Здесь описано поведение
клиента.

### Общие определения

- **Сервер** — запись в приложении, описывающая управляемую Linux-систему.
- **Агент** — ServerDeck Agent: сервис на сервере, предоставляющий клиенту API.
- **Установка по SSH** — запуск установщика агента на сервере через SSH-соединение,
  которое устанавливает клиент. Клиент выполняет команды, не открывая
  интерактивный терминал.
- **SSH-данные установки** — пароль SSH, приватный SSH-ключ, парольная фраза
  и пароль `sudo`. Используются только на время операции, не сохраняются
  (см. `FR-002.5`).
- **Параметры SSH-подключения** — несекретные значения: адрес, SSH-порт,
  имя пользователя. Сохраняются в записи сервера для запуска SSH-сессии
  в Termux (см. `FR-011`).
- **Pairing** — первоначальное подключение клиента к агенту по одноразовому
  коду, после которого агент выдаёт устройству отзывной токен.
- **Токен устройства** — секретное значение, по которому агент аутентифицирует
  клиент. Хранится в защищённом хранилище платформы.
- **Отпечаток ключа сервера** — отпечаток SSH host key сервера, закрепляемый
  при первом подключении.
- **Отпечаток сертификата агента** — отпечаток TLS-сертификата агента,
  закрепляемый при pairing.
- **Режим доступа** — выбор пользователя, откуда разрешено подключение
  к порту агента (см. `FR-002.12`).
- **Состояние настройки** — состояние записи сервера в процессе добавления:
  `DRAFT`, `INSTALLING`, `AWAITING_PAIRING`, `READY`. Не путать со статусом
  сервера (`FR-001.12`).
- **Локальные данные сервера** — запись сервера, кэш метрик, временные файлы,
  настройки отображения, токен устройства и отпечатки, связанные с сервером.

Поддерживаемые серверные системы: Linux с systemd. Установщик определяет
поддерживаемые дистрибутивы и архитектуры по списку релизов агента.
Другие системы (например, Windows Server) требуют отдельных требований.

### FR-002.1. Поля конфигурации сервера

**Приоритет:** Must  

Приложение должно предоставлять форму создания и редактирования сервера.

Форма должна содержать следующие поля:

| Поле                      | Обязательность | Тип                       | Значение по умолчанию | Назначение                                                  |
| ------------------------- | -------------: | ------------------------- | --------------------- | ----------------------------------------------------------- |
| Название                  |             Да | Строка                    | `Server N`            | Отображаемое имя сервера                                    |
| Адрес                     |             Да | Строка                    | Нет                   | IPv4-адрес или hostname сервера                             |
| Порт агента               |             Да | Целое число               | Задаётся установщиком | Порт HTTPS API агента                                       |
| SSH-порт                  |             Да | Целое число               | `22`                  | Порт SSH для установки и запуска сессии в Termux            |
| Имя пользователя SSH      |             Да | Строка                    | `root`                | Пользователь SSH                                            |
| Способ аутентификации SSH |        Условно | Перечисление              | Нет                   | `PASSWORD` или `PRIVATE_KEY`; нужен только при установке    |
| Пароль SSH                |        Условно | Секретная строка          | Нет                   | Обязателен при `PASSWORD`; не сохраняется                   |
| Приватный SSH-ключ        |        Условно | Секретный файл или строка | Нет                   | Обязателен при `PRIVATE_KEY`; не сохраняется                |
| Парольная фраза ключа     |        Условно | Секретная строка          | Нет                   | Если ключ зашифрован; не сохраняется                        |
| Страна                    |            Нет | Значение из справочника   | Нет                   | Часть пользовательской локации                              |
| Город                     |            Нет | Значение из справочника   | Нет                   | Часть пользовательской локации                              |

Значение `N` в названии по умолчанию должно быть наименьшим положительным
целым числом, при котором название `Server N` отсутствует среди серверов
пользователя.

Поля способа аутентификации и секретов SSH отображаются только в сценариях,
где выполняется SSH-операция: установка, обновление и удаление агента.
В форме редактирования они не показываются.

#### Критерии приёмки

- [ ] Форма содержит все обязательные и необязательные поля.
- [ ] Название по умолчанию имеет формат `Server N`, где `N` не совпадает с существующими.
- [ ] Значение SSH-порта по умолчанию равно `22`, имени пользователя — `root`.
- [ ] Пользователь может выбрать аутентификацию по паролю или приватному ключу.
- [ ] При `PASSWORD` форма требует пароль и не требует ключ; при `PRIVATE_KEY` — наоборот.
- [ ] Поля секретов SSH не отображаются в форме редактирования.
- [ ] Поля страны и города не обязательны.

### FR-002.2. Валидация названия сервера

**Приоритет:** Must  

Перед сохранением приложение должно удалить пробелы в начале и конце
значения поля «Название».

Название должно содержать от 2 до 30 символов после обработки.
Название не должно состоять только из пробелов.

Если название не проходит валидацию, приложение не должно выполнять
SSH-проверку и не должно сохранять сервер.

#### Критерии приёмки

- [ ] Значение `  Home server  ` сохраняется как `Home server`.
- [ ] Пустое значение и значение из одних пробелов не проходят валидацию.
- [ ] Название из одного символа и более 30 символов не проходит валидацию.
- [ ] Название из 2–30 символов проходит валидацию.
- [ ] При ошибке пользователь видит сообщение о допустимой длине.
- [ ] При ошибке названия сервер не сохраняется и SSH-проверка не запускается.

### FR-002.3. Валидация адреса сервера

**Приоритет:** Must  

Поле «Адрес» является обязательным. Перед валидацией приложение удаляет
пробелы в начале и конце значения.

Адрес должен быть IPv4-адресом в точечно-десятичной записи (четыре октета
от 0 до 255) либо hostname или доменным именем:

- Одна или несколько меток, разделённых точками.
- Каждая метка от 1 до 63 символов: латинские буквы, цифры и `-`.
- Метка не начинается и не заканчивается символом `-`.
- Полная длина не более 253 символов.
- Адрес не содержит пробелов, схемы URL, пути, порта и символов
  `/`, `?`, `#`, `@`, `_`, `:`, `[`, `]`.

IPv6-адреса не поддерживаются.

Синтаксически корректный адрес не гарантирует, что сервер существует,
разрешается через DNS или доступен по сети.

#### Критерии приёмки

- [ ] Адреса `192.168.1.33`, `example-server-domain.com`, `node-01` проходят валидацию.
- [ ] Адреса `192.168.1.256`, `192.168.1`, `192.168.1.1.1` не проходят валидацию.
- [ ] Адреса `-node.example.com`, `node-.example.com` не проходят валидацию.
- [ ] Адреса `https://example.com` и `example.com:2222` не проходят валидацию.
- [ ] IPv6-адрес не проходит валидацию.
- [ ] При ошибке пользователь видит сообщение о допустимом формате.
- [ ] При ошибке адреса сервер не сохраняется и SSH-проверка не запускается.

---

### FR-002.4. Валидация портов

**Приоритет:** Must  

Порт агента и SSH-порт должны быть целыми числами в диапазоне от 1 до 65535.
Пустое значение не проходит валидацию. SSH-порт по умолчанию — `22`.

Порт агента и SSH-порт не должны совпадать.

#### Критерии приёмки

- [ ] Значения `1`, `22`, `65535` проходят валидацию.
- [ ] Значения `0`, `65536`, дробное и строковое значение не проходят валидацию.
- [ ] Совпадающие порт агента и SSH-порт не проходят валидацию.
- [ ] Без ручного изменения SSH-порт равен `22`.

### FR-002.5. Учётные данные SSH и срок их хранения

**Приоритет:** Must  

Для SSH-операций (установка, обновление, удаление агента) приложение должно
запрашивать SSH-данные установки в соответствии с выбранным способом:

- `PASSWORD`: пароль SSH не должен быть пустым.
- `PRIVATE_KEY`: ключ не должен быть пустым и должен быть распознан как
  корректный приватный SSH-ключ. Если ключ зашифрован, приложение запрашивает
  парольную фразу.

SSH-данные установки:

- Хранятся только в оперативной памяти на время операции.
- Не записываются в постоянное хранилище, кэш, журналы и отчёты об ошибках.
- Удаляются из памяти сразу после завершения, отмены или ошибки операции.
- Не отображаются в открытом виде после ввода.

При каждой следующей SSH-операции пользователь вводит их заново.

#### Критерии приёмки

- [ ] При `PASSWORD` пустой пароль не проходит валидацию.
- [ ] При `PRIVATE_KEY` отсутствие ключа или некорректный формат не проходят валидацию.
- [ ] Для зашифрованного ключа запрашивается парольная фраза.
- [ ] Поле пароля отображает маскированное значение.
- [ ] После завершения или отмены операции SSH-данные недоступны приложению.
- [ ] Повторная SSH-операция требует повторного ввода данных.
- [ ] Секреты не присутствуют в журналах и сообщениях об ошибках.

### FR-002.6. Валидация локации сервера

**Приоритет:** Could  

Пользователь может указать для сервера страну и город. Страна выбирается
из справочника, город — из списка городов выбранной страны. Если страна
не выбрана, поле города недоступно или очищено.

Локация является пользовательской метаинформацией и не влияет на параметры
подключения.

#### Критерии приёмки

- [ ] Пользователь может сохранить сервер без страны и города.
- [ ] После выбора страны доступен выбор города.
- [ ] При смене страны несоответствующий город очищается.
- [ ] Локация не используется вместо адреса сервера.

### FR-002.7. Способы добавления и состояние настройки

**Приоритет:** Must  

Приложение должно предоставлять два способа добавления сервера:

1. **Автоматическая установка** — клиент подключается по SSH и устанавливает
   агент (`FR-002.8`–`FR-002.14`).
2. **Подключение к установленному агенту** — пользователь устанавливает агент
   вручную (`FR-002.15`) и выполняет pairing (`FR-002.16`).

Незавершённая настройка может сохраняться как черновик. Черновик содержит
только несекретные данные формы и состояние настройки. Он:

- Не отображается в основном списке как управляемый сервер.
- Отображается отдельно, например в разделе «Незавершённая настройка».
- Не содержит SSH-данных установки.
- Может быть продолжен или удалён пользователем.

Запись получает состояние `READY` и появляется в основном списке только после
успешного pairing и первого ответа агента.

#### Критерии приёмки

- [ ] Пользователь может выбрать автоматическую установку или подключение к установленному агенту.
- [ ] Прерванная настройка сохраняется как черновик без секретов.
- [ ] Черновик не отображается в основном списке и не учитывается в сводке статусов.
- [ ] Пользователь может продолжить или удалить черновик.
- [ ] Запись становится `READY` только после успешного pairing и ответа агента.
- [ ] После отмены создания введённые SSH-данные удаляются из памяти.

---

### FR-002.8. Проверка SSH-подключения и ключа сервера

**Приоритет:** Must  

После успешной локальной валидации клиент должен установить SSH-соединение
с указанными параметрами и аутентифицироваться.

При первом подключении клиент должен показать пользователю отпечаток
ключа сервера и запросить подтверждение. После подтверждения отпечаток
закрепляется в записи сервера.

При последующих SSH-операциях клиент должен сравнивать ключ сервера с закреплённым
отпечатком. При несовпадении соединение блокируется, а пользователь видит
предупреждение о возможной подмене сервера. Продолжить можно только
после явного сброса закреплённого отпечатка пользователем.

Проверка завершается по тайм-ауту, заданному настройкой таймаута
(`FR-010.4`).

#### Критерии приёмки

- [ ] При корректных параметрах клиент сообщает об успешной SSH-проверке.
- [ ] При первом подключении отображается отпечаток ключа сервера и запрашивается подтверждение.
- [ ] Отказ пользователя прерывает подключение.
- [ ] Закреплённый отпечаток проверяется при каждой последующей SSH-операции.
- [ ] При несовпадении отпечатка соединение блокируется с предупреждением.
- [ ] При неверном пароле или ключе отображается ошибка аутентификации.
- [ ] При недоступном адресе или порте отображается ошибка соединения.
- [ ] При превышении тайм-аута попытка прекращается с ошибкой тайм-аута.
- [ ] Сообщение об ошибке не содержит секретных данных.
- [ ] Неуспешная SSH-проверка не создаёт готовую запись сервера.

---

### FR-002.9. Проверка совместимости сервера

**Приоритет:** Must  

После успешной SSH-аутентификации клиент должен проверить сервер,
выполнив диагностические команды через SSH. Проверка подтверждает:

- Операционную систему Linux и поддерживаемый дистрибутив.
- Наличие systemd.
- Поддерживаемую архитектуру процессора.
- Наличие прав, достаточных для установки: вход под `root`, либо пользователь
  с правом `sudo`.
- Доступность инструментов, обязательных для установщика.
- Доступность адреса загрузки агента с сервера.

Если сервер не соответствует требованиям, клиент не должен продолжать установку
и должен отобразить причину несовместимости.

#### Критерии приёмки

- [ ] Linux-сервер с systemd проходит проверку.
- [ ] Сервер без systemd не проходит проверку.
- [ ] Сервер с неподдерживаемой архитектурой не проходит проверку.
- [ ] При недостаточных правах отображается понятная причина.
- [ ] Ошибка проверки не сохраняет сервер как готовый.
- [ ] Результат проверки показывает ОС, архитектуру и способ получения прав.

### FR-002.10. Обнаружение и совместимость существующего агента

**Приоритет:** Must  

Перед установкой клиент должен проверить, установлен ли на сервере агент,
и определить его версию и версию API.

| Ситуация | Поведение клиента |
|---|---|
| Агент не установлен | Предлагает установку |
| Установлен, версия API входит в диапазон, поддерживаемый клиентом | Установка пропускается, выполняется pairing |
| Установлен, версия старее требуемой | Предлагает обновление агента (`FR-002.20`) |
| Установлен, версия новее поддерживаемой клиентом | Не понижает версию, предлагает обновить клиент |

Совместимость определяется диапазоном версий API, а не равенством версий.

#### Критерии приёмки

- [ ] При отсутствии агента предлагается установка.
- [ ] При совместимом агенте установка пропускается.
- [ ] При устаревшем агенте предлагается обновление, а не переустановка.
- [ ] Клиент не устанавливает более старую версию поверх новой.
- [ ] При несовместимо новом агенте пользователю предлагается обновить клиент.
- [ ] Существующие конфигурация и токены других устройств не изменяются при пропуске установки.

---

### FR-002.11. Получение привилегий для установки

**Приоритет:** Must  

Если установка требует прав `root` и вход выполнен не под `root`,
клиент должен запросить пароль `sudo` через интерфейс приложения.

- Перед запросом показывается экран с объяснением, зачем нужны привилегии
  и что будет выполнено.
- Пароль передаётся серверу через стандартный ввод команды `sudo`, а не как
  аргумент командной строки.
- Пароль хранится только в памяти и удаляется по завершении операции.
- Если вход выполнен под `root` или `sudo` настроен без пароля, пароль
  не запрашивается.
- Привилегии используются только на время установки. Агент после установки
  работает под непривилегированным пользователем.

#### Критерии приёмки

- [ ] При входе не под `root` отображается объяснение и запрос пароля `sudo`.
- [ ] При входе под `root` запрос пароля не отображается.
- [ ] Пароль не передаётся в аргументах команды.
- [ ] Неверный пароль `sudo` даёт понятную ошибку без раскрытия пароля.
- [ ] После завершения операции пароль недоступен приложению.
- [ ] Пароль `sudo` не записывается в журналы и отчёты об ошибках.

---

### FR-002.12. Выбор режима сетевого доступа к агенту

**Приоритет:** Must  

Перед установкой клиент должен предложить пользователю выбрать режим доступа:

| Режим | Поведение установщика |
|---|---|
| Не открывать | Правила firewall не изменяются; агент слушает только локальный интерфейс |
| Только локальная сеть | Разрешает порт агента для подсети сервера; агент слушает локальные интерфейсы |
| Любой адрес | Разрешает порт агента для всех адресов; клиент показывает предупреждение |

Значением по умолчанию является наиболее ограниченный режим. Режим «Любой адрес»
выбирается только явно и сопровождается предупреждением о доступности агента
из интернета.

Если firewall сервера не поддерживается установщиком, клиент должен сообщить об этом
и не должен утверждать, что порт открыт.

Режим доступа можно изменить позже через повторную настройку.

#### Критерии приёмки

- [ ] Пользователь выбирает режим до начала установки.
- [ ] Значение по умолчанию — наиболее ограниченный режим.
- [ ] Выбор «Любой адрес» требует предупреждения и явного подтверждения.
- [ ] Установщик не изменяет правила firewall в режиме «Не открывать».
- [ ] При неподдерживаемом firewall пользователь видит предупреждение.
- [ ] Выбранный режим отображается в итоговом подтверждении установки.

---

### FR-002.13. Подтверждение и выполнение установки агента

**Приоритет:** Must  

Перед началом установки клиент должен показать:

- Имя сервера, адрес, пользователя и закреплённый отпечаток ключа сервера.
- Устанавливаемый компонент и версию агента.
- Способ получения прав и режим доступа.
- Изменения в системе: бинарный файл, системный сервис, пользователь агента,
  правила firewall.
- Возможность отменить установку.

После подтверждения клиент запускает установщик агента на сервере через SSH.
Установщик должен проверять контрольную сумму и подпись загружаемого
дистрибутива (`NFR-SEC-017`). Клиент отображает ход установки по этапам и
читает результат установщика: версию агента, отпечаток TLS-сертификата,
порт, pairing-код.

Установка успешна, если агент запущен как системный сервис и отвечает
на тестовый запрос.

При неуспешной установке клиент показывает этап ошибки и предлагает повторить
или отменить. Отмена или ошибка не оставляют сервер в состоянии `READY`.

#### Критерии приёмки

- [ ] Перед установкой пользователь видит подтверждение со списком изменений.
- [ ] Пользователь может отменить установку до изменений на сервере.
- [ ] Клиент отображает прогресс установки по этапам.
- [ ] Успешная установка завершается запуском агента как системного сервиса.
- [ ] Клиент получает от установщика версию, порт, отпечаток сертификата и pairing-код.
- [ ] При ошибке отображается этап, на котором она произошла.
- [ ] Ошибка установки не создаёт сервер в состоянии `READY`.
- [ ] Установка с нарушенной подписью или контрольной суммой прерывается.

---

### FR-002.14. Проверка доступности агента после установки

**Приоритет:** Must  

После установки клиент должен проверить, что агент доступен с устройства
пользователя по выбранному адресу и порту, а не только с сервера.

Если агент недоступен, клиент должен показать возможные причины и не утверждать
об успехе:

- Закрыт firewall облачного провайдера.
- Отсутствует проброс порта на роутере.
- Устройство находится в другой сети, чем сервер.
- Выбран режим доступа «Не открывать».

#### Критерии приёмки

- [ ] Клиент выполняет проверку подключения к агенту с устройства пользователя.
- [ ] При недоступности отображаются причины и действия.
- [ ] Пользователь может повторить проверку после исправления сети.
- [ ] Недоступность агента не приводит к состоянию `READY`.

---

### FR-002.15. Ручная установка агента

**Приоритет:** Must  

Клиент должен предоставлять сценарий ручной установки как для серверов
без SSH-доступа, так и как запасной вариант:

- Отображать команду установки, которую можно скопировать или выполнить
  с другого устройства (например, показать как QR-код).
- Использовать тот же установщик, что и автоматическая установка.
- Ожидать появления агента и затем переходить к pairing.

#### Критерии приёмки

- [ ] Клиент отображает команду установки с возможностью копирования.
- [ ] Ручная установка не требует ввода SSH-данных в клиенте.
- [ ] После установки пользователь вводит pairing-код и адрес агента в клиенте.
- [ ] Автоматическая и ручная установка используют один и тот же установщик.

---

### FR-002.16. Pairing и регистрация сервера

**Приоритет:** Must  

Клиент должен завершить добавление сервера через pairing:

1. Клиент подключается к агенту по HTTPS и закрепляет отпечаток его
   TLS-сертификата. При автоматической установке отпечаток сверяется
   со значением, полученным от установщика по SSH.
2. Клиент передаёт pairing-код. При автоматической установке код подставляется
   автоматически, при ручной — вводится пользователем.
3. Агент выдаёт токен устройства.
4. Клиент сохраняет токен в защищённом хранилище платформы.
5. Клиент запрашивает первый снимок метрик.

После успеха запись получает состояние `READY` и появляется в основном списке.

Если отпечаток сертификата не совпадает с полученным по SSH, pairing
прерывается с предупреждением.

#### Критерии приёмки

- [ ] Pairing выполняется только по HTTPS.
- [ ] При автоматической установке отпечаток сверяется с полученным по SSH.
- [ ] При несовпадении отпечатков pairing прерывается.
- [ ] Токен устройства сохраняется в защищённом хранилище, а не в открытом виде.
- [ ] После pairing клиент сохраняет идентификатор агента и время первого ответа.
- [ ] Сервер появляется в списке только после успешного pairing и первого снимка.
- [ ] Неверный, использованный или истёкший pairing-код отклоняется с понятной ошибкой.
- [ ] Сервер получает статус `ONLINE` или `WARNING` после первого снимка.

---

### FR-002.17. Открытие формы редактирования сервера

**Приоритет:** Must  

Пользователь должен иметь возможность открыть форму редактирования
ранее добавленного сервера из карточки или меню.

Форма заполняется текущими несекретными параметрами:

- Название.
- Адрес.
- Порт агента.
- SSH-порт.
- Имя пользователя SSH.
- Страна и город.

Форма не содержит SSH-секретов и токена устройства.

#### Критерии приёмки

- [ ] Пользователь может открыть редактирование из карточки или меню.
- [ ] Форма содержит текущие несекретные параметры.
- [ ] Токен устройства и SSH-секреты не отображаются.
- [ ] Пользователь может отменить редактирование без изменений.

---

### FR-002.18. Изменение параметров сервера

**Приоритет:** Must  

Пользователь должен иметь возможность изменить название, адрес, порт агента,
SSH-порт, имя пользователя SSH, страну и город.

Изменённые значения проходят валидацию `FR-002.2`–`FR-002.6`.

Правила повторной проверки:

- Изменение названия или локации не требует проверки.
- Изменение адреса или порта агента требует проверки доступности агента
  и совпадения закреплённого отпечатка его сертификата.
- Изменение адреса или SSH-порта сбрасывает закреплённый отпечаток ключа сервера
  и запрашивает его подтверждение при следующей SSH-операции.
- Изменение SSH-порта и имени пользователя не требует проверки SSH,
  если SSH-операция не выполняется.

До успешной проверки рабочие параметры не заменяются новыми.

#### Критерии приёмки

- [ ] Пользователь может изменить каждый поддерживаемый параметр.
- [ ] Для изменённых полей применяется валидация добавления.
- [ ] Некорректные значения не сохраняются.
- [ ] Изменение названия или локации не запускает проверку.
- [ ] Изменение адреса или порта агента проверяет доступность и отпечаток сертификата.
- [ ] При ошибке проверки сохранённые рабочие параметры остаются без изменений.
- [ ] Изменённые значения применяются после сохранения и перезапуска приложения.
- [ ] Карточка в списке обновляется без перезапуска.

---

### FR-002.19. Повторная настройка и смена доверия

**Приоритет:** Must  

Если после изменения параметров агент недоступен, клиент должен предложить:

- Повторить проверку.
- Выполнить повторную настройку агента через SSH (установка или обновление).
- Подключиться заново (новый pairing).

Если агент доступен, но отпечаток его сертификата изменился, клиент должен
блокировать подключение и показывать предупреждение. Принять новый
отпечаток можно только через явное подтверждение и новый pairing.

Режим сетевого доступа (`FR-002.12`) может быть изменён при повторной
настройке через SSH.

#### Критерии приёмки

- [ ] При недоступном агенте пользователь видит варианты повторной настройки.
- [ ] Отмена сохраняет ранее рабочие параметры.
- [ ] При смене отпечатка сертификата подключение блокируется с предупреждением.
- [ ] Принятие нового отпечатка требует нового pairing.
- [ ] Ошибка повторной настройки не удаляет запись сервера.
- [ ] Пользователь может изменить режим сетевого доступа.

---

### FR-002.20. Обновление агента

**Приоритет:** Should  

Клиент должен сообщать пользователю, что для сервера доступна новая версия
агента или что текущая версия несовместима с клиентом.

Обновление выполняется через SSH с теми же требованиями, что и установка
(`FR-002.5`, `FR-002.8`, `FR-002.11`):

- Обновляется только программный файл агента. Конфигурация, токены других
  устройств, TLS-сертификат и данные агента сохраняются.
- Замена выполняется атомарно, с откатом к предыдущей версии при ошибке
  (`NFR-SEC-017`).
- Перед обновлением показывается версия «было → станет».
- После обновления клиент проверяет доступность агента и совместимость.

#### Критерии приёмки

- [ ] Клиент показывает доступное обновление или причину несовместимости.
- [ ] Перед обновлением пользователь видит версии и подтверждает действие.
- [ ] Обновление не изменяет сертификат и токены устройств.
- [ ] При ошибке обновления агент откатывается к предыдущей версии.
- [ ] После обновления выполняется проверка доступности агента.

---

### FR-002.21. Подключённые устройства

**Приоритет:** Must  

Для выбранного сервера пользователь должен видеть список устройств,
подключённых к агенту, и иметь возможность отозвать токен любого из них
(`NFR-SEC-007`).

Для каждого устройства отображаются название, время подключения и время
последнего использования. Текущее устройство помечается отдельно.

Отзыв токена текущего устройства эквивалентен отключению от сервера
и требует подтверждения.

#### Критерии приёмки

- [ ] Пользователь видит список подключённых устройств сервера.
- [ ] Текущее устройство отмечено отдельно.
- [ ] Пользователь может отозвать токен другого устройства.
- [ ] После отзыва устройство теряет доступ к агенту.
- [ ] Отзыв токена текущего устройства требует подтверждения.

---

### FR-002.22. Запрос удаления сервера

**Приоритет:** Must  

Пользователь должен иметь возможность инициировать удаление сервера.

Диалог подтверждения должен содержать название сервера и варианты:

- **Удалить только запись** (значение по умолчанию): клиент отзывает токен
  текущего устройства на агенте, удаляет локальные данные. Агент остаётся
  на сервере.
- **Также удалить агент с сервера**: дополнительно запускает удаление агента
  через SSH (`FR-002.24`) и требует ввода SSH-данных.
- **Также удалить данные агента**: доступно при удалении агента; определяет,
  будут ли удалены данные (история метрик, журнал аудита).

Если у агента есть другие подключённые устройства, диалог должен предупредить,
что удаление агента отключит их, и показать их количество.

До подтверждения ничего не удаляется. Кнопки: «Удалить» и «Отмена».

#### Критерии приёмки

- [ ] Пользователь может открыть действие удаления для сервера.
- [ ] Диалог отображает название сервера и варианты удаления.
- [ ] По умолчанию выбрано удаление только записи.
- [ ] При других подключённых устройствах диалог предупреждает об их отключении и показывает их количество.
- [ ] До подтверждения сервер и данные не изменяются.
- [ ] При выборе «Отмена» всё остаётся без изменений.

---

### FR-002.23. Удаление локальных данных сервера

**Приоритет:** Must  

После подтверждения клиент должен:

1. Отозвать токен текущего устройства на агенте, если агент доступен.
2. Удалить локальную запись сервера и все связанные данные:
   - Параметры подключения и закреплённые отпечатки.
   - Токен устройства.
   - Кэш метрик и снимков состояния.
   - Локально сохранённые логи и временные файлы.
   - Настройки отображения, закрепление, сортировку и переопределения
     настроек (`FR-010.1`).

Если агент недоступен, клиент всё равно удаляет локальные данные и сообщает,
что токен остался активным на сервере и может быть отозван через CLI агента
(`NFR-SEC-007`).

После удаления сервер не отображается в списке, сводке, уведомлениях и поиске,
а запланированные проверки прекращаются.

#### Критерии приёмки

- [ ] После подтверждения сервер исчезает из списка.
- [ ] Токен устройства отзывается на агенте, если агент доступен.
- [ ] Если агент недоступен, пользователь видит предупреждение об активном токене.
- [ ] Удаляются кэш метрик, логи, токен, отпечатки и настройки сервера.
- [ ] После удаления сервер не учитывается в сводке статусов.
- [ ] После удаления прекращаются запланированные проверки сервера.
- [ ] После перезапуска сервер не появляется снова.

---

### FR-002.24. Удаление агента с сервера

**Приоритет:** Should  

Если пользователь выбрал удаление агента, клиент должен запустить
деинсталлятор на сервере через SSH с теми же требованиями, что и установка
(`FR-002.5`, `FR-002.8`, `FR-002.11`).

Деинсталлятор должен удалить:

- Системный сервис и бинарный файл агента.
- Пользователя агента.
- Правила firewall, созданные установщиком.
- Данные агента, если пользователь выбрал их удаление.

Если сервер недоступен или SSH отказал, клиент должен предложить команду
ручного удаления и завершить удаление локальной записи только после выбора
пользователя.

#### Критерии приёмки

- [ ] Для удаления агента клиент запрашивает SSH-данные и проверяет отпечаток ключа сервера.
- [ ] Деинсталлятор удаляет сервис, бинарный файл, пользователя агента и правила firewall.
- [ ] Данные агента удаляются только при явном выборе пользователя.
- [ ] При недоступном сервере отображается команда ручного удаления.
- [ ] Результат удаления агента отображается пользователю.
- [ ] Ошибка удаления агента не удаляет локальную запись без решения пользователя.

## FR-003. Просмотр подробной информации о сервере

**Приоритет:** Must  

### Цель

Пользователь должен иметь возможность открыть подробную информацию
о добавленном сервере, просмотреть его системные характеристики,
текущее состояние ресурсов, сетевые параметры, наиболее ресурсоёмкие процессы
и сведения о доступных дополнительных компонентах.

### Область действия

Группа требований `FR-003` определяет:

- Открытие экрана подробностей сервера.
- Обновление и отображение снимка метрик.
- Информацию об операционной системе и оборудовании.
- Метрики CPU, RAM, swap, дисков и сети.
- Топ процессов.
- Дополнительные блоки GPU, Docker и безопасности.
- Обработку отсутствующих, устаревших и недоступных данных.

### Общие определения

- **Снимок метрик** — набор данных о сервере, сформированный ServerDeck Agent
  в определённый момент времени.
- **Время сбора** — время, когда агент завершил сбор данных для снимка.
- **Устаревшие данные** — данные, собранные более 60 секунд назад.
- **Основной диск** — файловая система, смонтированная в `/`.
- **Логический CPU / vCPU** — процессор, доступный операционной системе как
  отдельная единица выполнения; его количество соответствует числу CPU,
  доступных планировщику ОС.
- **Load average** — среднее количество задач, готовых выполняться или
  ожидающих непрерываемого I/O, за интервалы 1, 5 и 15 минут.
- **Недоступная метрика** — метрика, которую агент не смог получить или
  которая не поддерживается на сервере.
- **Неустановленный компонент** — Docker, GPU-драйвер, firewall или иной
  компонент, отсутствующий на сервере.

### FR-003.1. Открытие подробностей сервера

**Приоритет:** Must  

Пользователь должен иметь возможность открыть экран подробной информации
для любого сервера из списка добавленных серверов.

При открытии экрана приложение должно отобразить название сервера,
его текущий или последний известный статус и время последнего успешного
получения данных.

#### Критерии приёмки

- [ ] Пользователь может открыть подробности нажатием на карточку сервера.
- [ ] На экране отображается название выбранного сервера.
- [ ] На экране отображается статус сервера.
- [ ] На экране отображается время последнего успешного обновления.
- [ ] Открытие деталей одного сервера не показывает данные другого сервера.

### FR-003.2. Запрос актуального снимка подробностей

**Приоритет:** Must  

После открытия экрана подробностей приложение должно запросить у ServerDeck Agent
актуальный снимок данных выбранного сервера.

Приложение должно отображать последнее успешно сохранённое состояние до получения
нового ответа агента.

Ошибка обновления не должна очищать ранее успешно полученные данные.

#### Критерии приёмки

- [ ] При открытии экрана инициируется запрос подробных данных у агента.
- [ ] До получения ответа отображаются последние сохранённые данные, если они существуют.
- [ ] Успешный ответ обновляет только данные открытого сервера.
- [ ] Ошибка запроса не удаляет ранее сохранённые данные.
- [ ] При отсутствии сохранённых данных и ошибке запроса отображается состояние ошибки.

### FR-003.3. Ручное обновление подробностей

**Приоритет:** Should  

Пользователь должен иметь возможность вручную повторить запрос актуальных данных
выбранного сервера с экрана подробностей.

Во время выполнения запроса приложение должно отображать индикатор обновления
и не должно допускать одновременный запуск нескольких одинаковых запросов.

#### Критерии приёмки

- [ ] Пользователь может запустить ручное обновление.
- [ ] При ручном обновлении отправляется новый запрос к агенту.
- [ ] Во время обновления виден индикатор выполнения.
- [ ] Повторное нажатие не создаёт параллельные одинаковые запросы.
- [ ] После успеха обновляются данные и время последнего обновления.

### FR-003.4. Отображение недоступных и устаревших данных

**Приоритет:** Must  

Если отдельная метрика недоступна, приложение должно отображать `—`
или иной единый индикатор отсутствия данных.

Если агент недоступен, приложение должно отображать статус `OFFLINE`,
время последнего успешного обновления и последние известные данные, если они есть.

Если снимок данных собран более 60 секунд назад, приложение должно
визуально отмечать данные как устаревшие.

#### Критерии приёмки

- [ ] Недоступная метрика не отображается как `0`, если ноль не был реально получен от агента.
- [ ] При недоступном агенте последние полученные метрики остаются видимыми.
- [ ] При недоступном агенте отображается статус `OFFLINE`.
- [ ] Снимок старше 60 секунд получает признак устаревших данных.
- [ ] Отсутствие Docker или GPU не считается ошибкой получения данных.

### FR-003.5. Отображение системной информации

**Приоритет:** Must  

Приложение должно отображать следующую информацию об операционной системе
и аппаратной платформе сервера:

- Static hostname.
- Machine ID.
- Версию ядра Linux.
- Архитектуру процессора.
- Название и версию операционной системы.
- Часовой пояс сервера.
- Время работы сервера с момента последней загрузки.

Machine ID должен отображаться в сокращённом виде по умолчанию.
Приложение должно предоставить возможность скопировать полное значение Machine ID.

#### Критерии приёмки

- [ ] На экране отображается static hostname сервера.
- [ ] На экране отображается версия ядра Linux.
- [ ] На экране отображается архитектура процессора.
- [ ] На экране отображается название и версия ОС.
- [ ] На экране отображается часовой пояс сервера.
- [ ] На экране отображается uptime сервера.
- [ ] Machine ID по умолчанию не занимает чрезмерное место на экране.
- [ ] Пользователь может скопировать полный Machine ID.

### FR-003.6. Отображение характеристик CPU

**Приоритет:** Must  

Приложение должно отображать следующие характеристики CPU:

- Модель процессора.
- Количество логических CPU / vCPU, доступных операционной системе.
- Текущую общую загрузку CPU в процентах.
- Load average за 1, 5 и 15 минут.
- Количество процессов, доступных операционной системе.

Значение текущей загрузки CPU должно отображаться в диапазоне от 0 до 100%.

Load average должен отображаться тремя числовыми значениями в формате
`LA1 / LA5 / LA15`.

#### Критерии приёмки

- [ ] На экране отображается модель CPU.
- [ ] На экране отображается количество доступных логических CPU / vCPU.
- [ ] На экране отображается общая загрузка CPU в процентах.
- [ ] На экране отображаются значения load average за 1, 5 и 15 минут.
- [ ] На экране отображается количество процессов.
- [ ] Значение load average не обозначается символом `%`.
- [ ] При недоступности отдельной CPU-метрики отображается `—`.

### FR-003.7. Интерпретация нагрузки CPU

**Приоритет:** Should  

Приложение должно отображать краткую интерпретацию состояния CPU,
если обнаружена потенциальная проблема с нагрузкой.

Интерпретация должна быть основана на фиксированных правилах и не должна
выдаваться за точный диагноз причины проблемы.

После реализации истории метрик рекомендуется использовать правила:

- Если загрузка CPU не менее 90% в двух последовательных снимках,
  отображать предупреждение «Высокая загрузка CPU».
- Если `LA1` превышает количество логических CPU и `LA1` не меньше `LA5`,
  отображать предупреждение «Очередь задач превышает доступные CPU».
- Если `LA1` меньше `LA5`, отображать справочную подпись
  «Нагрузка снижается».
- Если `LA1` больше `LA5`, отображать справочную подпись
  «Нагрузка растёт».

#### Критерии приёмки

- [ ] При выполнении правила высокой загрузки CPU отображается предупреждение.
- [ ] При превышении LA1 количества логических CPU отображается предупреждение.
- [ ] Интерпретация содержит формулировку «возможная причина» или не утверждает причину как факт.
- [ ] При отсутствии условий предупреждение не отображается.

### FR-003.8. Отображение частоты и температуры CPU

**Приоритет:** Should  

Если агент может получить соответствующие данные, приложение должно отображать:

- Минимальную и максимальную текущую частоту CPU.
- Температуру CPU или доступных температурных датчиков.

Если на сервере отсутствуют поддерживаемые датчики температуры или данные
частоты недоступны, соответствующий блок не должен отображаться как ошибка.

#### Критерии приёмки

- [ ] При доступных данных отображается диапазон частоты CPU.
- [ ] При доступных температурных датчиках отображается температура с единицей `°C`.
- [ ] При отсутствии датчиков температуры отображается `—` или блок скрывается согласно единому правилу интерфейса.
- [ ] Отсутствие температуры не влияет на статус доступности сервера.

### FR-003.9. Мини-график загрузки CPU

**Приоритет:** Could  

Приложение должно отображать мини-график общей загрузки CPU за выбранный период,
если доступны исторические снимки метрик.

Мини-график должен содержать не менее 10 точек данных и отображать период,
к которому относятся данные.

#### Критерии приёмки

- [ ] При наличии достаточной истории метрик отображается график CPU.
- [ ] При отсутствии достаточного числа точек вместо графика отображается сообщение об отсутствии истории.
- [ ] На графике указан временной период данных.
- [ ] График не строится из вымышленных или нулевых значений.

### FR-003.10. Отображение оперативной памяти и swap

**Приоритет:** Must  

Приложение должно отображать:

- Использованный объём оперативной памяти.
- Общий объём оперативной памяти.
- Свободный или доступный объём оперативной памяти.
- Процент использования оперативной памяти.
- Использованный объём swap.
- Общий объём swap.
- Процент использования swap, если swap доступен.

Объёмы памяти должны отображаться в `MB`, `GB` или `TB`.

Если swap не настроен на сервере, приложение должно отображать
`Swap отсутствует` или значение `0 / 0`, но не считать это ошибкой.

#### Критерии приёмки

- [ ] Отображаются использованный и общий объёмы RAM.
- [ ] Отображается доступный объём RAM.
- [ ] Отображается процент использования RAM.
- [ ] При наличии swap отображаются использованный и общий объёмы swap.
- [ ] При отсутствии swap пользователь видит понятное состояние.
- [ ] Значения памяти содержат единицы измерения.

### FR-003.11. Отображение файловых систем и дисков

**Приоритет:** Must  

Приложение должно отображать список смонтированных файловых систем,
доступных для мониторинга.

Для каждой файловой системы должны отображаться:

- Точка монтирования.
- Устройство или источник монтирования.
- Тип файловой системы.
- Общий размер.
- Использованный объём.
- Доступный объём.
- Процент использования пространства.
- Процент использованных inode, если метрика доступна.
- Статус файловой системы.

Приложение должно отображать файловую систему `/` при доступности данных, в том числе для типов `overlay` и `squashfs` (AFR-016).

Временные, служебные и псевдофайловые системы должны быть исключены
из списка по политике агента. Минимально должны исключаться `proc`, `sysfs`,
`tmpfs`, `devtmpfs`, `cgroup`, `overlay` и `squashfs`, если пользователь
не включил их отображение отдельно. Это исключение не применяется к корневому монтированию `/`.

#### Критерии приёмки

- [ ] Файловая система `/` отображается при наличии доступа к данным.
- [ ] Для каждой отображаемой файловой системы показаны тип, размер, использование и точка монтирования.
- [ ] Процент использования диска отображается отдельно от числа занятых байт.
- [ ] Процент inode отображается при доступности метрики.
- [ ] При недоступности inode отображается `—`.
- [ ] Псевдофайловые системы не засоряют основной список.
- [ ] Ошибка получения одной файловой системы не скрывает остальные.

---

### FR-003.12. Определение статуса файловой системы

**Приоритет:** Should  

Приложение должно определять статус каждой отображаемой файловой системы
на основании процента использования пространства и, если доступно,
процента использования inode.

Используются следующие значения по умолчанию:

- `NORMAL`: использование пространства и inode менее 85%.
- `WARNING`: использование пространства или inode от 85% до 94.99%.
- `CRITICAL`: использование пространства или inode не менее 95%.
- `UNKNOWN`: метрики файловой системы недоступны.

#### Критерии приёмки

- [ ] При использовании диска 84% статус равен `NORMAL`.
- [ ] При использовании диска 85% статус равен `WARNING`.
- [ ] При использовании диска 95% статус равен `CRITICAL`.
- [ ] При использовании inode 95% статус равен `CRITICAL`, даже если место на диске доступно.
- [ ] При отсутствии метрик статус равен `UNKNOWN`.

### FR-003.13. Обнаружение и сводка GPU

**Приоритет:** Should  

Если ServerDeck Agent обнаружил хотя бы одно поддерживаемое GPU-устройство,
приложение должно отображать блок GPU.

Блок GPU должен содержать:

- Количество обнаруженных GPU.
- Суммарный доступный объём VRAM.
- Строку предупреждения, если хотя бы одно GPU находится в состоянии предупреждения или критическом состоянии.

Если поддерживаемые GPU не обнаружены, блок GPU не должен отображаться.

#### Критерии приёмки

- [ ] При отсутствии поддерживаемого GPU блок GPU не отображается.
- [ ] При наличии одного или нескольких GPU отображается их количество.
- [ ] При наличии VRAM отображается суммарный объём VRAM.
- [ ] При проблеме хотя бы одного GPU в сводке отображается предупреждение.

---

### FR-003.14. Отображение информации по каждому GPU

**Приоритет:** Should  

Для каждого поддерживаемого GPU приложение должно отображать:

- Порядковый номер GPU.
- Модель GPU.
- Текущую загрузку GPU в процентах.
- Использованный и общий объём VRAM.
- Процент использования VRAM.
- Температуру GPU, если доступна.
- Текущую потребляемую мощность в ваттах, если доступна.
- Количество процессов, использующих GPU, если доступно.

Если отдельная метрика GPU недоступна, приложение должно отображать `—`
для этой метрики, не скрывая остальные доступные данные GPU.

#### Критерии приёмки

- [ ] Для каждого обнаруженного GPU отображается номер и модель.
- [ ] Отображаются использование GPU и VRAM при доступности метрик.
- [ ] Отображается температура с единицей `°C`, если она доступна.
- [ ] Отображается мощность с единицей `W`, если она доступна.
- [ ] Отображается количество GPU-процессов, если агент может его определить.
- [ ] Недоступность температуры не скрывает VRAM и загрузку GPU.

### FR-003.15. Статус GPU

**Приоритет:** Could  

Приложение должно определять статус GPU по доступным метрикам.

Рекомендуемые значения:

- `WARNING`: загрузка GPU не менее 95%, VRAM не менее 90% или температура не менее 85°C.
- `CRITICAL`: VRAM не менее 98% или температура не менее 92°C.
- `UNKNOWN`: отсутствуют данные, необходимые для оценки.
- `NORMAL`: ни одно условие предупреждения или критического состояния не выполнено.

Значения порогов должны быть настраиваемыми (см. FR-010).

### FR-003.16. Отображение общей сетевой информации

**Приоритет:** Must  

Приложение должно отображать следующую общую сетевую информацию сервера:

- Состояние сетевой доступности, определённое по доступности ServerDeck Agent.
- Маршрут по умолчанию, если агент может его определить.
- Локальные IPv4-адреса, доступные на сетевых интерфейсах.
- Настроенные DNS-серверы, если агент может их определить.

Публичный IPv4-адрес должен отображаться только если агент успешно определил его
через явно настроенный механизм внешней проверки.

Если публичный IPv4 определить не удалось, приложение должно отображать `—`.

#### Критерии приёмки

- [ ] При доступном агенте отображается состояние сетевой доступности.
- [ ] При доступности маршрута по умолчанию отображается его адрес или интерфейс.
- [ ] Отображаются обнаруженные локальные IPv4-адреса.
- [ ] Отображаются DNS-серверы, если доступны.
- [ ] Невозможность определить публичный IPv4 не делает сервер `OFFLINE`.

### FR-003.17. Отображение сетевых интерфейсов

**Приоритет:** Must  

Приложение должно отображать список физических и виртуальных сетевых интерфейсов,
кроме loopback-интерфейса `lo`.

Для каждого интерфейса должны отображаться:

- Название интерфейса.
- Состояние подключения: `UP`, `DOWN`, `UNKNOWN`.
- Текущая скорость входящего трафика RX.
- Текущая скорость исходящего трафика TX.
- Скорость линка, если она доступна.
- IPv4-адрес или список IPv4-адресов, если они назначены.
- Краткий статус ошибок интерфейса.

Краткий статус ошибок должен учитывать счётчики ошибок приёма и передачи
пакетов, если агент может их получить.

#### Критерии приёмки

- [ ] Интерфейс `lo` не отображается в основном списке интерфейсов.
- [ ] Для каждого интерфейса отображается название.
- [ ] Для интерфейса отображаются RX и TX как скорости, а не накопленные байты.
- [ ] При доступности отображается скорость линка.
- [ ] При наличии отображается IPv4-адрес интерфейса.
- [ ] При ненулевых ошибках RX или TX отображается предупреждение об ошибках.
- [ ] При недоступных счётчиках ошибок отображается `—` или `Нет данных`.

### FR-003.18. Проверка сетевой задержки и потерь

**Приоритет:** Could  

Пользователь должен иметь возможность указать цель проверки сети:
IPv4-адрес или hostname.

Если цель проверки задана, ServerDeck Agent должен выполнять проверку
сетевой доступности до этой цели и возвращать:

- Среднюю задержку в миллисекундах.
- Процент потерь пакетов.
- Время выполнения проверки.
- Статус ошибки, если проверка не была выполнена.

Цель проверки не должна иметь фиксированное имя `monitor-01`.

#### Критерии приёмки

- [ ] Пользователь может задать цель проверки сети.
- [ ] При успешной проверке отображаются задержка и процент потерь.
- [ ] При ошибке DNS отображается понятное сообщение.
- [ ] При невозможности выполнить ICMP-проверку отображается статус недоступности проверки.
- [ ] Агент ограничивает количество пакетов и время выполнения проверки.

### FR-003.19. Обнаружение Docker Engine

**Приоритет:** Should  

Приложение должно отображать блок Docker только если ServerDeck Agent обнаружил
установленный Docker Engine и может получить доступ к Docker daemon.

Блок Docker должен отображать состояние Docker Engine:

- `RUNNING`;
- `STOPPED`;
- `UNAVAILABLE`;
- `NOT_INSTALLED`;
- `UNKNOWN`.

#### Критерии приёмки

- [ ] При отсутствии Docker Engine блок Docker не отображается или показывает `NOT_INSTALLED` согласно единому правилу интерфейса.
- [ ] При запущенном Docker daemon отображается `RUNNING`.
- [ ] При установленном, но остановленном Docker daemon отображается `STOPPED`.
- [ ] При отсутствии прав доступа к Docker API отображается `UNAVAILABLE`.
- [ ] Ошибка Docker не влияет на отображение базовых метрик сервера.

### FR-003.20. Сводка Docker-контейнеров

**Приоритет:** Should  

При доступном Docker Engine приложение должно отображать:

- Общее количество контейнеров.
- Количество контейнеров в состояниях `running`, `restarting`, `paused`,
  `exited` и `dead`, если состояние поддерживается Docker Engine.
- Количество контейнеров с проблемами.
- Суммарное использование CPU и RAM запущенными контейнерами, если метрики доступны.

Контейнер считается проблемным, если его состояние равно `restarting`,
`paused`, `dead` или если он завершился с ненулевым кодом выхода.

#### Критерии приёмки

- [ ] Отображается общее количество контейнеров.
- [ ] Отображаются счётчики по состояниям контейнеров.
- [ ] Контейнер `restarting` учитывается как проблемный.
- [ ] Контейнер `dead` учитывается как проблемный.
- [ ] Контейнер с ненулевым exit code учитывается как проблемный.
- [ ] CPU и RAM отображаются только для запущенных контейнеров.
- [ ] Остановленный контейнер не получает вымышленное значение CPU или RAM.

### FR-003.21. Отображение проблемных и активных Docker-контейнеров

**Приоритет:** Should  

Приложение должно отображать не более пяти Docker-контейнеров на экране
подробностей сервера.

Приоритет отображения контейнеров:

1. Контейнеры с проблемами.
2. Контейнеры в состоянии `restarting`.
3. Запущенные контейнеры с наибольшим потреблением CPU.
4. Остальные контейнеры.

Для каждого отображаемого контейнера приложение должно показывать:

- Имя контейнера.
- Текущий статус.
- Имя Docker Compose-проекта или сервиса, если оно доступно.
- Краткую причину проблемы, если она доступна.
- CPU и RAM только для контейнера в состоянии `running`.
- Время работы для `running` или время остановки для неработающего контейнера.

#### Критерии приёмки

- [ ] Отображается не более пяти контейнеров.
- [ ] Проблемные контейнеры имеют приоритет над обычными.
- [ ] Для `running` контейнера отображаются CPU и RAM при доступности метрик.
- [ ] Для остановленного контейнера CPU и RAM не отображаются.
- [ ] При доступности Compose-метаданных отображается проект или сервис.
- [ ] Контейнер с проблемой показывает краткую причину, если агент может её определить.

### FR-003.22. Отображение топа процессов

**Приоритет:** Must  

Приложение должно отображать не более 10 процессов, потребляющих наибольшее
количество ресурсов на сервере.

Пользователь должен иметь возможность переключать сортировку топа процессов:

- По использованию CPU, по убыванию.
- По использованию оперативной памяти, по убыванию.

Для каждого процесса должны отображаться:

- PID.
- Имя процесса.
- Использование CPU в процентах.
- Использование оперативной памяти в байтах с форматированием в `MB` или `GB`.

Если процесс завершился между сбором данных и отображением, приложение должно
показать полученный снимок как историческое значение и не должно считать это
ошибкой.

#### Критерии приёмки

- [ ] На экране отображается не более 10 процессов.
- [ ] При сортировке по CPU процессы упорядочены по убыванию CPU.
- [ ] При сортировке по RAM процессы упорядочены по убыванию памяти.
- [ ] Для каждого процесса отображаются PID и имя.
- [ ] Для каждого процесса отображаются CPU и используемая RAM.
- [ ] При отсутствии процессов или метрик отображается понятное пустое состояние.

### FR-003.23. Отображение сводного статуса безопасности

**Приоритет:** Should  

Приложение должно отображать сводный статус безопасности сервера
в одном из состояний:

- `NORMAL`;
- `WARNING`;
- `CRITICAL`;
- `NO_DATA`.

Сводный статус должен рассчитываться только по поддерживаемым и доступным
проверкам. Если ни одна проверка не выполнена или данные недоступны,
должен отображаться статус `NO_DATA`.

#### Критерии приёмки

- [ ] При отсутствии данных безопасности отображается `NO_DATA`.
- [ ] Статус `CRITICAL` имеет приоритет над `WARNING`.
- [ ] Статус `WARNING` имеет приоритет над `NORMAL`.
- [ ] Приложение не отображает `NORMAL`, если безопасность не была проверена.

- [ ] При отключённом поддерживаемом firewall отображается `INACTIVE`.
- [ ] При отсутствии поддерживаемого firewall отображается `NOT_INSTALLED`.

### FR-003.25. Отображение SSH-событий безопасности

- [ ] Успешные входы отображаются отдельно от неудачных.
- [ ] При отсутствии доступа к журналам отображается `Нет данных`.
- [ ] Отсутствие событий SSH не считается ошибкой.

### FR-003.27. Отображение критических событий безопасности

#### Критерии приёмки

- [ ] При отсутствии доступа к источнику событий отображается `Нет данных`.

## FR-004. Просмотр подробной информации о конкретном GPU

**Приоритет:** Should  

### Цель

Пользователь должен иметь возможность открыть экран подробной информации
о конкретном GPU, установленном на управляемом сервере, просмотреть его
статические характеристики, текущие метрики, процессы, использующие GPU,
и историю доступных показателей.

### Область действия

Группа требований `FR-004` определяет:

- Открытие подробностей конкретного GPU.
- Отображение статической информации о GPU.
- Отображение текущих метрик GPU.
- Отображение процессов, использующих GPU.
- Отображение истории метрик и графиков.
- Отображение событий, связанных с GPU.
- Обработку отсутствующих и устаревших данных.

### Общие определения

- **Поддерживаемый GPU** — GPU, для которого ServerDeck Agent может получить
  идентификационные данные и хотя бы одну метрику состояния через поддерживаемый
  источник, например NVML, `nvidia-smi`, AMD SMI или ROCm SMI.
- **GPU ID** — стабильный идентификатор GPU в ServerDeck Agent.
  В качестве внешнего идентификатора рекомендуется использовать UUID GPU.
- **Текущий снимок GPU** — набор текущих метрик конкретного GPU, собранный
  ServerDeck Agent в определённый момент времени.
- **История метрик** — сохранённые временные точки метрик GPU.
- **Недоступная метрика** — метрика, которую драйвер, устройство или агент
  не поддерживает либо не может получить в момент сбора.
- **GPU-процесс** — процесс операционной системы, использующий вычислительные,
  графические или memory-ресурсы конкретного GPU.
- **VRAM** — видеопамять GPU.
- **Диапазон графика** — период истории метрик, выбранный пользователем:
  `15m`, `1h`, `6h`, `24h` или `7d`.

### FR-004.1. Открытие подробностей выбранного GPU

**Приоритет:** Should  

Пользователь должен иметь возможность открыть экран подробной информации
о конкретном GPU из блока GPU на экране подробностей сервера.

При открытии экрана приложение должно передать идентификатор выбранного GPU
и отобразить данные именно этого устройства.

#### Критерии приёмки

- [ ] При наличии нескольких GPU пользователь может выбрать конкретное устройство.
- [ ] Экран подробностей отображает данные выбранного GPU, а не агрегированные данные всех GPU.
- [ ] На экране отображаются сервер и GPU, к которым относятся данные.
- [ ] При удалении GPU или невозможности его обнаружить приложение отображает понятное состояние ошибки.

---

### FR-004.2. Загрузка и обновление данных GPU

**Приоритет:** Should  

При открытии экрана подробностей GPU приложение должно запросить у ServerDeck Agent
актуальный снимок выбранного устройства.

До завершения запроса приложение должно отображать последние сохранённые
данные GPU, если они существуют.

Пользователь должен иметь возможность вручную обновить данные GPU.

#### Критерии приёмки

- [ ] При открытии экрана выполняется запрос текущих данных выбранного GPU.
- [ ] Успешный ответ обновляет данные только выбранного GPU.
- [ ] Во время обновления отображается индикатор выполнения.
- [ ] Повторное нажатие обновления не запускает параллельные идентичные запросы.
- [ ] При ошибке обновления ранее полученные данные не очищаются.

---

### FR-004.3. Отображение времени обновления и устаревших данных

**Приоритет:** Must  

Экран подробностей GPU должен отображать время последнего успешного получения
снимка выбранного GPU.

Если снимок старше 60 секунд, данные должны быть визуально обозначены
как устаревшие.

Если отдельная метрика недоступна, приложение должно отображать `—`
или иной единый индикатор отсутствия данных. Недоступная метрика не должна
заменяться нулевым значением.

#### Критерии приёмки

- [ ] Экран отображает время последнего успешного обновления.
- [ ] Снимок старше 60 секунд имеет признак устаревших данных.
- [ ] Недоступная температура не отображается как `0°C`.
- [ ] Недоступная мощность не отображается как `0 W`.
- [ ] Ошибка одной метрики не скрывает остальные доступные данные GPU.

### FR-004.4. Отображение основной информации о GPU

**Приоритет:** Should  

Приложение должно отображать следующие идентификационные данные выбранного GPU:

- Название устройства.
- Производитель GPU.
- Модель GPU.
- Версию установленного драйвера.
- Версию CUDA, если она применима и доступна.
- UUID GPU.
- PCIe Bus ID или PCIe-адрес устройства.
- Текущую и максимальную поддерживаемую версию PCIe, если доступны.
- Текущую и максимальную ширину PCIe-линии, если доступны.

UUID должен отображаться в сокращённом виде по умолчанию.
Пользователь должен иметь возможность скопировать полное значение UUID.

Если CUDA не применима или её версия недоступна, приложение должно
отображать `Не используется` или `—`.

#### Критерии приёмки

- [ ] Отображаются производитель, модель и название выбранного GPU.
- [ ] Отображается версия драйвера, если она получена агентом.
- [ ] Для NVIDIA GPU с доступной CUDA отображается версия CUDA.
- [ ] Для GPU без CUDA приложение не отображает ошибку.
- [ ] Отображается UUID GPU.
- [ ] Пользователь может скопировать полный UUID.
- [ ] При доступности отображается PCIe-адрес.
- [ ] При доступности отображаются поколение и ширина PCIe-линии.

### FR-004.5. Отображение текущей загрузки и VRAM

**Приоритет:** Must  

Приложение должно отображать для выбранного GPU:

- Текущую загрузку GPU-чипа в процентах.
- Использованный объём VRAM.
- Общий объём VRAM.
- Процент использования VRAM.

Загрузка GPU должна отображаться в диапазоне от 0 до 100%.

Объём VRAM должен отображаться в `MB`, `GB` или `TB`.

Если GPU поддерживает отдельную метрику загрузки memory interface,
она может отображаться дополнительно как «Загрузка памяти GPU», но не должна
заменять основную загрузку GPU-чипа.

#### Критерии приёмки

- [ ] При доступной метрике отображается загрузка GPU-чипа в процентах.
- [ ] При доступной метрике отображаются использованный и общий объёмы VRAM.
- [ ] При доступной метрике отображается процент использования VRAM.
- [ ] Значения VRAM содержат единицы измерения.
- [ ] Метрика GPU utilisation не подменяется процентом использования VRAM.
- [ ] Недоступность одной метрики не скрывает другие текущие показатели.

### FR-004.6. Отображение температуры, мощности и вентиляторов

**Приоритет:** Should  

Приложение должно отображать следующие метрики выбранного GPU, если они
поддерживаются устройством и доступны через драйвер:

- Текущую температуру GPU-чипа в градусах Цельсия.
- Текущую потребляемую мощность в ваттах.
- Скорость вентиляторов в процентах или RPM.
- Единицу измерения скорости вентилятора.

Если GPU имеет пассивное охлаждение либо драйвер не предоставляет данные
о вентиляторах, приложение должно отображать `Нет данных` или `Пассивное
охлаждение`, если агент может определить этот факт.

#### Критерии приёмки

- [ ] При доступности температура отображается с единицей `°C`.
- [ ] При доступности мощность отображается с единицей `W`.
- [ ] При доступности отображается скорость вентилятора.
- [ ] Скорость вентилятора содержит единицу `%` или `RPM`.
- [ ] Отсутствие вентилятора не отображается как ошибка GPU.
- [ ] Недоступная метрика отображается единым индикатором отсутствия данных.

### FR-004.7. Определение статуса GPU

**Приоритет:** Should  

Приложение должно определять текущий статус выбранного GPU:

- `NORMAL`;
- `WARNING`;
- `CRITICAL`;
- `UNKNOWN`.

Статус определяется по доступным метрикам:

| Условие                            | Статус     |
| ---------------------------------- | ---------- |
| Нет данных, достаточных для оценки | `UNKNOWN`  |
| VRAM не менее 98%                  | `CRITICAL` |
| Температура не менее 92°C          | `CRITICAL` |
| VRAM от 90% до 97.99%              | `WARNING`  |
| Температура от 85°C до 91.99°C     | `WARNING`  |
| Загрузка GPU не менее 95%          | `WARNING`  |
| Ни одно условие выше не выполнено  | `NORMAL`   |

Если одновременно выполнены условия разных уровней, используется статус
с наибольшей критичностью.

Пороговые значения в будущей версии должны быть доступны для настройки.

#### Критерии приёмки

- [ ] При VRAM 98% статус равен `CRITICAL`.
- [ ] При температуре 92°C статус равен `CRITICAL`.
- [ ] При VRAM 90% статус равен `WARNING`.
- [ ] При температуре 85°C статус равен `WARNING`.
- [ ] При загрузке GPU 95% статус равен `WARNING`.
- [ ] При температуре 92°C и VRAM 90% итоговый статус равен `CRITICAL`.
- [ ] При отсутствии всех проверяемых метрик статус равен `UNKNOWN`.

### FR-004.8. Отображение процессов, использующих GPU

**Приоритет:** Should  

Приложение должно отображать список процессов, использующих выбранный GPU,
если ServerDeck Agent может получить данные о GPU-процессах.

Для каждого процесса должны отображаться:

- PID процесса.
- Имя процесса.
- Имя пользователя, запустившего процесс, если оно доступно.
- Используемый объём VRAM.
- Время работы процесса, если агент может его определить.
- GPU utilisation процесса, только если драйвер или API предоставляет
  достоверную метрику на уровне процесса.

Список процессов по умолчанию должен быть отсортирован по использованию VRAM
в порядке убывания.

Приложение не должно отображать или вычислять «потребляемую мощность GPU
процесса», если эта метрика не предоставляется достоверно источником данных.

#### Критерии приёмки

- [ ] При наличии GPU-процессов отображается список процессов.
- [ ] Для процесса отображаются PID и имя.
- [ ] При доступности отображается имя пользователя.
- [ ] При доступности отображается использованная VRAM.
- [ ] Список по умолчанию отсортирован по VRAM в порядке убывания.
- [ ] При доступности отображается время работы процесса.
- [ ] GPU utilisation процесса отображается только при получении достоверного значения от агента.
- [ ] Приложение не показывает вымышленную мощность GPU для отдельного процесса.
- [ ] При отсутствии GPU-процессов отображается состояние «GPU-процессы не обнаружены».

### FR-004.9. Сбор истории GPU-метрик

**Приоритет:** Could  

ServerDeck Agent должен периодически сохранять историю метрик каждого
поддерживаемого GPU.

Для каждой точки истории должны сохраняться:

- Время сбора в UTC.
- Загрузка GPU-чипа в процентах.
- Использованный объём VRAM.
- Общий объём VRAM.
- Температура GPU, если доступна.
- Потребляемая мощность, если доступна.
- Скорость вентилятора, если доступна.

Частота сбора, срок хранения и правила агрегации должны быть определены
в отдельном требовании к истории метрик.

#### Критерии приёмки

- [ ] Каждая сохранённая точка содержит время сбора.
- [ ] История сохраняется отдельно для каждого GPU.
- [ ] Отсутствие отдельной метрики не препятствует сохранению других метрик точки.
- [ ] Система не сохраняет пароль, ключи, командные строки процессов и другие секреты в точках метрик.

### FR-004.10. Выбор диапазона истории GPU-метрик

**Приоритет:** Could  

Пользователь должен иметь возможность выбрать общий диапазон истории
для графиков GPU:

- `15m`;
- `1h`;
- `6h`;
- `24h`;
- `7d`.

Выбранный диапазон должен применяться ко всем графикам на текущем экране GPU.

Если данных недостаточно для выбранного диапазона, приложение должно показать
доступный период данных и не должно заполнять отсутствующие интервалы
вымышленными значениями.

#### Критерии приёмки

- [ ] Пользователь может выбрать каждый поддерживаемый диапазон.
- [ ] После выбора диапазона обновляются все графики текущего GPU.
- [ ] При отсутствии данных за часть периода приложение сообщает о неполной истории.
- [ ] На графиках отображается фактический временной интервал данных.
- [ ] Выбор диапазона не изменяет данные других GPU.

### FR-004.11. График загрузки GPU

Вертикальная ось графика должна иметь диапазон от 0 до 100%.

- [ ] Значения графика не выходят за диапазон от 0 до 100%.

### FR-004.12. График использования VRAM

#### Критерии приёмки

- [ ] График показывает исторические точки использованной VRAM.
- [ ] Значения VRAM имеют единицы измерения.
- [ ] График соответствует выбранному диапазону времени.

### FR-004.13. Графики температуры, мощности и вентиляторов

**Приоритет:** Could  

Приложение должно отображать отдельные графики следующих метрик,
если соответствующие данные доступны:

- Температура GPU.
- Потребляемая мощность GPU.
- Скорость вентиляторов.

Каждый график должен содержать подпись единицы измерения:

- Температура: `°C`.
- Мощность: `W`.
- Вентиляторы: `%` или `RPM`.

Если метрика не поддерживается GPU либо отсутствует в истории, соответствующий
график не должен отображаться как ошибка.

#### Критерии приёмки

- [ ] При наличии истории температуры отображается график температуры.
- [ ] При наличии истории мощности отображается график мощности.
- [ ] При наличии истории вентилятора отображается график скорости вентилятора.
- [ ] Графики содержат корректные единицы измерения.
- [ ] Отсутствие одной истории не скрывает другие доступные графики.

### FR-004.14. Журнал значимых событий GPU

**Приоритет:** Could  

ServerDeck Agent должен формировать журнал значимых событий выбранного GPU
на основании доступных метрик и фиксированных правил.

После реализации журнала должны поддерживаться как минимум события:

- GPU обнаружен.
- GPU перестал быть доступен.
- Не удалось получить данные драйвера.
- Переход статуса GPU в `WARNING`.
- Переход статуса GPU в `CRITICAL`.
- Возврат статуса GPU из `WARNING` или `CRITICAL` в `NORMAL`.
- Превышение порога температуры.
- Превышение порога использования VRAM.
- Появление ошибки GPU-драйвера, если агент может её надёжно определить.

Для каждого события должны отображаться:

- Время события.
- Тип события.
- Уровень: `INFO`, `WARNING`, `CRITICAL`.
- Краткое понятное описание.
- Техническая причина без секретов, если она доступна.

#### Критерии приёмки

- [ ] При переходе GPU в `WARNING` создаётся событие уровня `WARNING`.
- [ ] При переходе GPU в `CRITICAL` создаётся событие уровня `CRITICAL`.
- [ ] При возвращении к нормальному состоянию создаётся информационное событие.
- [ ] Каждое событие содержит время и понятное описание.
- [ ] В описании и технических данных нет токенов, паролей, SSH-ключей и другого секрета.
- [ ] При отсутствии событий отображается понятное пустое состояние.

## FR-005. Подробная информация о CPU

**Приоритет:** Must  

### Цель

Пользователь должен иметь возможность открыть подробный экран CPU выбранного
сервера, просмотреть характеристики процессора, текущее состояние,
исторические графики нагрузки, нагрузку по логическим ядрам и процессы,
создающие наибольшую нагрузку на CPU.

### Область действия

Группа требований `FR-005` определяет:

- Открытие экрана CPU выбранного сервера.
- Отображение статических характеристик CPU.
- Отображение текущих CPU-метрик.
- Получение и отображение исторических CPU-метрик.
- Выбор временного диапазона графиков.
- Отображение загрузки по логическим CPU.
- Отображение частот, температур и throttling при доступности данных.
- Отображение CPU pressure.
- Отображение топа процессов по потреблению CPU.

### Общие определения

- **Логический CPU / vCPU** — единица выполнения, доступная планировщику ОС.
  Число логических CPU может отличаться от числа физических ядер из-за SMT,
  Hyper-Threading или виртуализации.
- **Физическое ядро** — аппаратное ядро процессора, если сервер и ОС позволяют
  достоверно определить это значение.
- **Общая загрузка CPU** — доля времени, в течение которого CPU не находился
  в состоянии idle за интервал между двумя измерениями, выраженная в процентах.
- **User time** — время выполнения кода пользовательских процессов.
- **System time** — время, затраченное ядром Linux на обработку системных вызовов,
  прерываний и системных задач.
- **I/O wait** — время ожидания операций ввода-вывода, учитываемое ядром.
- **Steal time** — время, в течение которого vCPU виртуальной машины был готов
  к выполнению, но фактически выполнялись задачи другой гостевой системы.
- **Idle time** — время простоя CPU.
- **Load average** — среднее число задач, готовых к выполнению или ожидающих
  непрерываемого I/O, за интервалы 1, 5 и 15 минут.
- **CPU pressure** — доля времени, в течение которого задачи ожидали
  процессорного времени из-за нехватки CPU-ресурсов.
- **Throttling** — ограничение производительности CPU из-за температуры,
  лимита мощности, политики гипервизора или иной причины.
- **Историческая точка метрики** — значение CPU-метрик с временем формирования.
- **Недоступная метрика** — метрика, которую агент не может получить
  на конкретном сервере.

### FR-005.1. Открытие подробной информации о CPU

**Приоритет:** Must  

Пользователь должен иметь возможность открыть экран подробной информации
о CPU для выбранного сервера с экрана подробностей сервера.

При открытии экрана приложение должно отображать название сервера,
время последнего успешного получения CPU-метрик и текущий статус доступности
сервера.

#### Критерии приёмки

- [ ] Пользователь может открыть экран CPU для выбранного сервера.
- [ ] Экран CPU отображает название выбранного сервера.
- [ ] Экран CPU отображает время последнего успешного обновления CPU-данных.
- [ ] Экран CPU отображает текущий статус сервера.
- [ ] При недоступном сервере отображаются последние известные данные, если они существуют.

### FR-005.2. Обновление CPU-данных

**Приоритет:** Must  

При открытии экрана CPU приложение должно запросить у ServerDeck Agent
актуальные CPU-метрики и доступные исторические данные для выбранного диапазона.

Пользователь должен иметь возможность вручную обновить текущие CPU-метрики.

Ошибка обновления не должна очищать ранее успешно полученные текущие данные
или исторические точки.

#### Критерии приёмки

- [ ] При открытии экрана приложение запрашивает актуальные CPU-метрики.
- [ ] При открытии экрана приложение запрашивает историю для выбранного диапазона.
- [ ] Пользователь может вручную повторить запрос текущих метрик.
- [ ] Во время обновления отображается индикатор процесса.
- [ ] Ошибка обновления не удаляет ранее отображённые данные.
- [ ] При отсутствии сохранённых данных отображается понятное состояние ошибки.

### FR-005.3. Отображение характеристик CPU

**Приоритет:** Must  

Приложение должно отображать следующие статические характеристики CPU:

- Название и модель процессора.
- Архитектуру процессора.
- Количество физических ядер, если агент может определить его достоверно.
- Количество логических CPU / vCPU.
- Поддерживаемый или текущий диапазон частот CPU, если данные доступны.

Если количество физических ядер определить невозможно, приложение должно
отображать `—` и не подменять это значение количеством логических CPU.

#### Критерии приёмки

- [ ] На экране отображается модель CPU.
- [ ] На экране отображается архитектура CPU.
- [ ] На экране отображается количество логических CPU / vCPU.
- [ ] При доступности отображается количество физических ядер.
- [ ] При недоступности количества физических ядер отображается `—`.
- [ ] При доступности отображается частота или диапазон частот с единицей MHz или GHz.

### FR-005.4. Отображение текущей общей загрузки CPU

**Приоритет:** Must  

Приложение должно отображать текущую общую загрузку CPU в процентах
в диапазоне от 0 до 100%.

Значение общей загрузки CPU должно рассчитываться агентом по разнице счётчиков
CPU-времени между двумя последовательными измерениями.

Приложение не должно отображать общую загрузку CPU как сумму процентных
значений отдельных процессов.

#### Критерии приёмки

- [ ] Общая загрузка CPU отображается в процентах.
- [ ] Значение находится в диапазоне от 0 до 100.
- [ ] При успешном обновлении значение соответствует актуальному снимку.
- [ ] При первом запуске агента до получения двух измерений приложение отображает `—` или статус `Сбор данных`.
- [ ] Значение не рассчитывается суммированием CPU-процентов процессов.

### FR-005.5. Отображение структуры CPU-времени

**Приоритет:** Must  

Приложение должно отображать распределение CPU-времени по следующим
состояниям:

- `user`;
- `system`;
- `iowait`;
- `steal`;
- `idle`.

Каждое значение должно отображаться в процентах за интервал между двумя
последовательными измерениями.

Сумма отображаемых категорий может быть меньше 100%, если агент не объединяет
в них значения `nice`, `irq`, `softirq`, `guest` и другие состояния ядра.

Если часть состояний не включается в отображение, агент должен передавать
дополнительную категорию `other` либо документировать правило агрегации.

#### Критерии приёмки

- [ ] На экране доступны значения `user`, `system`, `iowait`, `steal` и `idle`.
- [ ] Все значения отображаются в процентах.
- [ ] Значения относятся к одному интервалу измерения.
- [ ] `steal` отображается как отдельная категория, если он доступен.
- [ ] При отсутствии данных о категории отображается `—`, а не вымышленный ноль.
- [ ] Правило обработки `nice`, `irq`, `softirq` и других состояний зафиксировано в контракте API агента.

### FR-005.6. Отображение load average

**Приоритет:** Must  

Приложение должно отображать load average за интервалы:

- 1 минута (`LA1`);
- 5 минут (`LA5`);
- 15 минут (`LA15`).

Значения должны отображаться как числовые показатели без символа `%`.

На графике load average приложение должно отображать горизонтальную контрольную
линию, соответствующую количеству логических CPU / vCPU сервера.

Контрольная линия должна быть подписана количеством логических CPU / vCPU.

#### Критерии приёмки

- [ ] На экране отображаются `LA1`, `LA5` и `LA15`.
- [ ] Load average не отображается как процент.
- [ ] График load average содержит линию количества логических CPU / vCPU.
- [ ] Контрольная линия имеет понятную подпись.
- [ ] Если количество логических CPU недоступно, контрольная линия не рисуется, а пользователь видит `Нет данных о vCPU`.

---

### FR-005.7. Отображение CPU pressure

**Приоритет:** Should  

Если ядро Linux предоставляет CPU pressure через `/proc/pressure/cpu`,
приложение должно отображать CPU pressure типа `some`:

- Среднее значение за 10 секунд (`avg10`);
- Среднее значение за 60 секунд (`avg60`);
- Среднее значение за 300 секунд (`avg300`).

CPU pressure должен отображаться в процентах времени ожидания CPU.

Если PSI не поддерживается ядром или недоступен агенту, блок CPU pressure
должен отображать `Не поддерживается` или не отображаться в соответствии
с единым правилом интерфейса.

#### Критерии приёмки

- [ ] При доступном PSI отображаются `avg10`, `avg60` и `avg300`.
- [ ] Значения CPU pressure отображаются в процентах.
- [ ] При отсутствии `/proc/pressure/cpu` приложение не показывает ошибку сервера.
- [ ] При недоступности PSI отображается `Не поддерживается` либо блок скрывается согласно правилу интерфейса.

---

### FR-005.8. Сбор исторических CPU-метрик

**Приоритет:** Must  

ServerDeck Agent должен собирать исторические CPU-метрики для построения
графиков.

Агент должен сохранять исторические точки, содержащие:

- Время сбора метрики в UTC.
- Общую загрузку CPU.
- Распределение CPU-времени: `user`, `system`, `iowait`, `steal`, `idle`.
- Load average: `LA1`, `LA5`, `LA15`.
- CPU pressure `some.avg10`, `some.avg60`, `some.avg300`, если доступно.
- Минимальную, максимальную и среднюю частоту CPU, если доступно.
- Температуру CPU и статус throttling, если доступно.

Периоды хранения должны поддерживать отображение диапазонов:
15 минут, 1 час, 6 часов, 24 часа и 7 дней.

#### Критерии приёмки

- [ ] Агент сохраняет CPU-историю с отметками времени в UTC.
- [ ] В истории присутствует общая загрузка CPU.
- [ ] В истории присутствует load average.
- [ ] При доступности в истории присутствуют CPU pressure, частота, температура и throttling.
- [ ] История поддерживает получение данных за период до 7 дней.
- [ ] Метрики старше срока хранения удаляются или агрегируются согласно политике хранения.

---

### FR-005.9. Политика хранения и агрегации CPU-метрик

**Приоритет:** Must  

ServerDeck Agent должен хранить CPU-метрики не менее 7 суток.

Чтобы ограничить объём локального хранилища на сервере, агент должен
использовать следующую политику хранения:

- Детальные точки с периодом 15 секунд хранятся не менее 1 часа.
- Агрегированные точки с периодом 1 минута хранятся не менее 24 часов.
- Агрегированные точки с периодом 5 минут хранятся не менее 7 суток.

При агрегации должна сохраняться следующая информация:

- Среднее значение для загрузки CPU, CPU-состояний, CPU pressure и частоты.
- Максимальное значение для температуры CPU.
- Максимальное значение для статуса throttling.
- Последнее значение для load average.

#### Критерии приёмки

- [ ] Диапазон 15 минут получает точки с разрешением не хуже 15 секунд.
- [ ] Диапазон 1 час получает точки с разрешением не хуже 15 секунд.
- [ ] Диапазон 6 часов получает точки с разрешением не хуже 1 минуты.
- [ ] Диапазон 24 часа получает точки с разрешением не хуже 1 минуты.
- [ ] Диапазон 7 дней получает точки с разрешением не хуже 5 минут.
- [ ] Температурные пики не теряются при агрегации.
- [ ] Событие throttling не теряется при агрегации.
- [ ] Агент не хранит бесконечное количество необработанных точек.

---

### FR-005.10. Выбор временного диапазона графиков

**Приоритет:** Must  

Приложение должно предоставлять единый селектор временного диапазона
для всех графиков CPU.

Доступные диапазоны:

- `15M` — последние 15 минут.
- `1H` — последний час.
- `6H` — последние 6 часов.
- `24H` — последние 24 часа.
- `7D` — последние 7 суток.

Выбранный диапазон должен применяться ко всем графикам CPU на экране.

При открытии экрана диапазон по умолчанию должен быть `1H`.

#### Критерии приёмки

- [ ] Пользователь видит все пять вариантов диапазона.
- [ ] При первом открытии выбран диапазон `1H`.
- [ ] После выбора диапазона обновляются все CPU-графики.
- [ ] На каждом графике отображается выбранный период.
- [ ] Выбранный диапазон сохраняется при повороте экрана и повторном отображении UI-состояния.

---

### FR-005.11. Отображение графика общей загрузки CPU

**Приоритет:** Must  

Приложение должно отображать график общей загрузки CPU за выбранный временной
диапазон.

График должен:

- Использовать ось Y в диапазоне от 0 до 100%.
- Содержать временную ось.
- Показывать время и значение выбранной точки при взаимодействии пользователя
  с графиком.
- Отображать отсутствие данных в промежутках, где агент не собрал метрику,
  а не соединять точки через пропущенный период.

#### Критерии приёмки

- [ ] График использует значения общей загрузки CPU.
- [ ] Ось Y ограничена диапазоном 0–100%.
- [ ] На графике видна временная шкала.
- [ ] Пользователь может получить время и значение отдельной точки.
- [ ] Пропуски данных визуально отличаются от нулевой загрузки CPU.

---

### FR-005.12. Отображение графика структуры CPU-времени

**Приоритет:** Must  

Приложение должно отображать историческое распределение CPU-времени
по категориям `user`, `system`, `iowait`, `steal` и `idle`.

График должен позволять различить вклад каждой категории в общую загрузку CPU.

Если категории агрегируются согласно правилам `FR-005.5`, приложение должно
использовать одинаковые правила для текущего отображения и исторического графика.

#### Критерии приёмки

- [ ] На графике доступны категории user, system, iowait, steal и idle.
- [ ] Легенда графика объясняет обозначение каждой категории.
- [ ] Категории отображаются в процентах.
- [ ] Правила агрегации совпадают с текущими CPU-метриками.
- [ ] При отсутствии одной категории она не подменяется нулём.

---

### FR-005.13. Отображение графика load average

**Приоритет:** Must  

Приложение должно отображать график load average за выбранный диапазон.

График должен содержать линии:

- `LA1`;
- `LA5`;
- `LA15`;
- Количество логических CPU / vCPU как контрольную линию.

Ось Y должна автоматически подбираться так, чтобы были видны максимальное
значение load average и контрольная линия количества логических CPU / vCPU.

#### Критерии приёмки

- [ ] График содержит линии LA1, LA5 и LA15.
- [ ] График содержит контрольную линию vCPU.
- [ ] Ось Y не обрезает максимум load average.
- [ ] Контрольная линия vCPU видна даже при низком load average.
- [ ] При отсутствии данных load average отображается понятное состояние.

---

### FR-005.14. Отображение графика CPU pressure

**Приоритет:** Should  

Если CPU pressure доступен, приложение должно отображать график CPU pressure
типа `some.avg10` за выбранный диапазон.

Приложение может дополнительно отображать `some.avg60` и `some.avg300`.

Ось Y графика должна использовать диапазон от 0 до 100%.

#### Критерии приёмки

- [ ] При доступном PSI отображается график CPU pressure.
- [ ] График содержит как минимум `some.avg10`.
- [ ] Значения отображаются в диапазоне 0–100%.
- [ ] При недоступном PSI график не отображается как ошибка.

---

### FR-005.15. Отображение графика частоты CPU

**Приоритет:** Should  

Если агент получает данные CPUFreq, приложение должно отображать исторический
график средней частоты CPU за выбранный период.

При доступности данных по отдельным логическим CPU приложение должно позволять:

- Переключиться на отображение частоты по отдельным ядрам.
- Либо отобразить минимальную, среднюю и максимальную частоты как диапазон.

Если CPUFreq не поддерживается аппаратной платформой, ядром Linux или
виртуальной машиной, график не должен отображаться как ошибка.

---

### FR-005.16. Отображение графика температуры и throttling CPU

**Приоритет:** Should  

Если агент получает данные датчиков температуры CPU, приложение должно
отображать график температуры CPU за выбранный период.

Если агент обнаружил throttling, приложение должно отображать событие
ограничения производительности на графике температуры или отдельной шкале событий.

Для каждой точки throttling должны быть доступны:

- Время обнаружения.
- Тип throttling, если агент может определить его.
- Текущее или зафиксированное значение температуры, если доступно.

Если датчики или сведения о throttling отсутствуют, приложение не должно
отображать ошибку сервера.

---

### FR-005.17. Отображение нагрузки по логическим CPU

**Приоритет:** Should  

Приложение должно отображать текущую загрузку каждого доступного логического CPU.

Для каждого логического CPU должны отображаться:

- Номер логического CPU.
- Текущая загрузка в процентах.
- Визуальный индикатор загрузки.

При количестве логических CPU более 32 приложение должно использовать
сворачиваемое представление или постраничную загрузку, чтобы экран оставался
читаемым.

#### Критерии приёмки

- [ ] Для каждого доступного логического CPU отображается номер и загрузка.
- [ ] Нагрузка каждого CPU отображается в диапазоне 0–100%.
- [ ] Для сервера с количеством CPU до 32 все CPU отображаются на экране.
- [ ] Для сервера с количеством CPU более 32 интерфейс не становится непригодным для использования.
- [ ] При недоступности данных отдельного CPU отображается `—`.

---

### FR-005.18. Отображение частоты CPU по ядрам

**Приоритет:** Should  

Если частота доступна по отдельным логическим CPU, приложение должно
отображать частоту для каждого CPU или диапазон частот по всем CPU.

Пользователь должен иметь возможность выбрать один из режимов:

- «По ядрам».
- «Диапазон: минимум / среднее / максимум».

При отсутствии частотных данных элемент управления выбором режима не отображается.

---

### FR-005.19. Отображение температур CPU по датчикам

**Приоритет:** Should  

Если агент обнаружил несколько температурных датчиков CPU, приложение должно
отображать список датчиков.

Для каждого датчика должны отображаться:

- Название датчика.
- Текущая температура.
- Максимальная температура за выбранный период, если доступна история.
- Порог предупреждения и критический порог, если они предоставлены источником данных.

Если конкретный датчик не содержит порогов, приложение должно отображать `—`
вместо вымышленного порога.

### FR-005.20. Отображение топа процессов по CPU

**Приоритет:** Must  

Приложение должно отображать не более 10 процессов, потребляющих наибольшее
количество CPU-ресурсов на момент формирования текущего снимка.

Для каждого процесса должны отображаться:

- PID.
- Имя процесса.
- Имя пользователя-владельца процесса, если доступно.
- Использование CPU в процентах.
- Использование RAM в байтах с форматированием в MB или GB.

Процессы должны сортироваться по использованию CPU в порядке убывания.
При одинаковом использовании CPU процессы должны сортироваться по PID
в порядке возрастания.

#### Критерии приёмки

- [ ] Отображается не более 10 процессов.
- [ ] Процессы отсортированы по CPU в порядке убывания.
- [ ] Для каждого процесса отображаются PID и имя.
- [ ] Для каждого процесса отображается CPU-потребление.
- [ ] При доступности отображается имя владельца процесса.
- [ ] При одинаковом CPU процессы упорядочены по PID.
- [ ] Завершение процесса после формирования снимка не приводит к ошибке экрана.

### FR-005.21. Отображение состояния исторических данных

**Приоритет:** Must  

Если для выбранного диапазона отсутствует полная история CPU-метрик,
приложение должно отображать доступную часть истории и указывать период,
за который данные отсутствуют.

Приложение не должно создавать точки графика с нулевыми значениями
для заполнения пропусков.

Если сервер был добавлен менее выбранного временного диапазона назад,
приложение должно отображать данные с момента первого сбора метрик.

#### Критерии приёмки

- [ ] Для нового сервера график показывает историю с первого доступного снимка.
- [ ] При пропусках связи на графике видны пропуски, а не ложные нулевые значения.
- [ ] При отсутствии истории пользователь видит понятное объяснение.
- [ ] При недоступном агенте ранее сохранённая история остаётся доступной.

---

### FR-005.22. Ограничение объёма ответа истории

**Приоритет:** Must  

ServerDeck Agent не должен возвращать более 2 000 исторических точек
на один запрос одного графика.

Если выбранный диапазон содержит больше точек, агент должен агрегировать
данные согласно `FR-005.9` до количества не более 2 000 точек.

#### Критерии приёмки

- [ ] Ответ истории для одного графика содержит не более 2 000 точек.
- [ ] При большом объёме истории используется агрегация.
- [ ] Агрегация сохраняет максимальную температуру.
- [ ] Агрегация сохраняет факт throttling.
- [ ] Мобильное приложение не зависает при загрузке диапазона 7 дней.

## FR-006. Подробная информация о сетевом интерфейсе

**Приоритет:** Must  

### Цель

Пользователь должен иметь возможность открыть подробную информацию
о конкретном сетевом интерфейсе выбранного сервера, просмотреть его
состояние, адресацию, параметры линка, текущий и исторический трафик,
ошибки передачи и предупреждения.

### Область действия

Группа требований `FR-006` определяет:

- Открытие экрана выбранного сетевого интерфейса.
- Отображение текущего состояния и свойств интерфейса.
- Отображение IPv4, IPv6, MTU и маршрута по умолчанию.
- Отображение текущих скоростей RX и TX.
- Отображение исторических графиков трафика.
- Отображение использования пропускной способности канала.
- Отображение ошибок и отброшенных пакетов.
- Проверку latency и packet loss для маршрута или настроенной цели.
- Состояния отсутствующих, устаревших и неподдерживаемых данных.

### Общие определения

- **Сетевой интерфейс** — сетевое устройство Linux, имеющее имя, например
  `eth0`, `ens18`, `enp3s0`, `wlan0`, `wg0`, `docker0`.
- **Loopback-интерфейс** — интерфейс `lo`, используемый для локального
  взаимодействия внутри сервера.
- **RX** — скорость приёма данных сетевым интерфейсом.
- **TX** — скорость передачи данных сетевым интерфейсом.
- **Текущая скорость трафика** — скорость RX или TX, вычисленная по разнице
  счётчиков байт между двумя последовательными снимками агента.
- **Скорость линка** — скорость физического сетевого соединения, доступная
  драйверу интерфейса, например `100 Mbps`, `1 Gbps` или `10 Gbps`.
- **Duplex** — режим передачи данных физического линка: `FULL`, `HALF`,
  `UNKNOWN` или `NOT_APPLICABLE`.
- **MTU** — максимальный размер IP-пакета, который интерфейс передаёт без
  фрагментации на канальном уровне.
- **Default route** — маршрут, используемый сервером для адресов, для которых
  отсутствует более специфичный маршрут.
- **Default gateway** — следующий узел маршрута по умолчанию, если он указан.
- **Ошибки интерфейса** — счётчики ошибок RX/TX, предоставленные ядром,
  драйвером или системной утилитой.
- **Dropped packets** — количество пакетов, отброшенных до обработки
  или передачи из-за нехватки ресурсов, очередей или иных причин.
- **Настроенная цель проверки** — IPv4-адрес или hostname, выбранный
  пользователем для измерения задержки и потерь.
- **Историческая точка** — значение сетевой метрики с временем сбора в UTC.

### FR-006.1. Открытие подробной информации об интерфейсе

**Приоритет:** Must  

Пользователь должен иметь возможность открыть экран подробной информации
о выбранном сетевом интерфейсе с экрана подробностей сервера.

При открытии экрана приложение должно отображать название выбранного интерфейса,
название сервера, статус доступности сервера и время последнего успешного
получения данных интерфейса.

#### Критерии приёмки

- [ ] Пользователь может открыть подробности выбранного интерфейса.
- [ ] На экране отображается имя выбранного интерфейса.
- [ ] На экране отображается название сервера.
- [ ] На экране отображается время последнего успешного обновления данных.
- [ ] Открытие интерфейса `eth0` не отображает метрики `wlan0` или другого интерфейса.

### FR-006.2. Запрос актуальных данных интерфейса

**Приоритет:** Must  

При открытии экрана интерфейса приложение должно запросить у ServerDeck Agent
актуальные данные выбранного интерфейса и исторические данные для выбранного
временного диапазона.

Пользователь должен иметь возможность вручную обновить текущие данные.

Ошибка обновления не должна удалять последние успешно полученные сведения
об интерфейсе и историю его метрик.

#### Критерии приёмки

- [ ] При открытии экрана выполняется запрос текущих данных интерфейса.
- [ ] При открытии экрана выполняется запрос истории трафика для выбранного диапазона.
- [ ] Пользователь может выполнить ручное обновление.
- [ ] Во время обновления отображается индикатор выполнения.
- [ ] Ошибка обновления не очищает ранее полученные данные.
- [ ] Повторное нажатие на обновление не запускает несколько одинаковых запросов одновременно.

---

### FR-006.3. Отображение устаревших и недоступных данных

**Приоритет:** Must  

Если последний снимок интерфейса был собран более 60 секунд назад,
приложение должно визуально обозначить данные как устаревшие.

Если сервер или агент недоступен, приложение должно отображать последние
известные данные интерфейса, если они существуют, вместе со статусом `OFFLINE`
сервера и временем последнего успешного обновления.

Если отдельная метрика интерфейса недоступна, приложение должно отображать `—`,
`Нет данных` или `Не поддерживается` в зависимости от причины отсутствия.

#### Критерии приёмки

- [ ] Данные старше 60 секунд помечаются как устаревшие.
- [ ] При недоступном агенте ранее полученные данные остаются видимыми.
- [ ] Отсутствующая метрика не заменяется нулевым значением.
- [ ] Отсутствие link speed для виртуального интерфейса не считается ошибкой.
- [ ] Отсутствие IPv6 не считается ошибкой.

---

### FR-006.4. Отображение названия и типа интерфейса

**Приоритет:** Must  

Приложение должно отображать название и тип выбранного сетевого интерфейса.

Агент должен передавать тип интерфейса в одном из нормализованных значений:

- `ETHERNET`;
- `WIFI`;
- `LOOPBACK`;
- `BRIDGE`;
- `BOND`;
- `VLAN`;
- `TUNNEL`;
- `VPN`;
- `VIRTUAL`;
- `OTHER`;
- `UNKNOWN`.

Если точный тип определить невозможно, приложение должно отображать `UNKNOWN`
или `OTHER`, но не подменять неизвестный интерфейс типом Ethernet.

#### Критерии приёмки

- [ ] На экране отображается имя интерфейса.
- [ ] На экране отображается нормализованный тип интерфейса.
- [ ] Неизвестный тип не отображается как Ethernet без подтверждающих данных.
- [ ] Виртуальный интерфейс может отображаться как `VIRTUAL`, `BRIDGE`, `VLAN` или иной корректный тип.

---

### FR-006.5. Отображение статуса подключения интерфейса

**Приоритет:** Must  

Приложение должно отображать состояние интерфейса в одном из значений:

- `CONNECTED`;
- `DISCONNECTED`;
- `NO_CARRIER`;
- `DISABLED`;
- `UNKNOWN`;
- `NO_DATA`.

Правила определения статуса:

- `CONNECTED` — интерфейс административно включён и имеет carrier,
  если carrier применим к данному типу интерфейса.
- `DISCONNECTED` — интерфейс доступен, но физическое или логическое
  подключение отсутствует.
- `NO_CARRIER` — интерфейс включён, но не обнаруживает физический линк.
- `DISABLED` — интерфейс административно выключен.
- `UNKNOWN` — агент не смог определить статус.
- `NO_DATA` — информация об интерфейсе ещё не была успешно получена.

Для виртуальных, VPN- и туннельных интерфейсов, у которых понятие carrier
неприменимо, агент должен использовать логическое состояние интерфейса.

#### Критерии приёмки

- [ ] Интерфейс с доступным физическим линком получает статус `CONNECTED`.
- [ ] Интерфейс без carrier получает статус `NO_CARRIER` или `DISCONNECTED`.
- [ ] Административно выключенный интерфейс получает статус `DISABLED`.
- [ ] Невозможность определить состояние приводит к `UNKNOWN`.
- [ ] Для VPN-интерфейса отсутствие физического carrier не приводит автоматически к `NO_CARRIER`.

---

### FR-006.6. Отображение адресации и MTU

**Приоритет:** Must  

Приложение должно отображать для выбранного интерфейса:

- Основной IPv4-адрес с длиной префикса, если он назначен.
- Дополнительные IPv4-адреса, если они назначены.
- IPv6-адреса с длиной префикса, если они назначены.
- MTU.

Основным IPv4-адресом считается первый глобальный IPv4-адрес интерфейса,
определённый агентом. Если глобальный адрес отсутствует, может отображаться
адрес другого scope с указанием его типа.

IPv6-адреса link-local должны иметь явную подпись `link-local`.

Если IPv4 или IPv6 не назначены, соответствующее поле должно отображать `Нет адреса`.

#### Критерии приёмки

- [ ] При наличии IPv4 отображается основной IPv4-адрес и длина префикса.
- [ ] При наличии нескольких IPv4 доступен просмотр дополнительных адресов.
- [ ] При наличии IPv6 отображаются IPv6-адреса.
- [ ] Link-local IPv6 адрес имеет соответствующую подпись.
- [ ] При отсутствии IPv6 не отображается ошибка.
- [ ] MTU отображается как целое числовое значение.

---

### FR-006.7. Отображение default route и default gateway

**Приоритет:** Must  

Приложение должно определить, используется ли выбранный интерфейс
для маршрута по умолчанию.

Если маршрут по умолчанию использует выбранный интерфейс, приложение должно
отображать:

- Адрес default gateway, если он указан.
- Имя интерфейса.
- Метрику маршрута, если она доступна.

Если выбранный интерфейс не используется для маршрута по умолчанию,
приложение должно отображать `Не используется для default route`.

Если на сервере отсутствует маршрут по умолчанию, приложение должно
отображать `Default route отсутствует`.

#### Критерии приёмки

- [ ] Для интерфейса default route отображается адрес gateway.
- [ ] Для интерфейса default route отображается имя интерфейса.
- [ ] Для интерфейса без default route отображается понятное состояние.
- [ ] При отсутствии default route на сервере отображается соответствующее сообщение.
- [ ] Default gateway не отображается ошибочно на всех интерфейсах сервера.

---

### FR-006.8. Отображение текущих RX и TX

**Приоритет:** Must  

Приложение должно отображать текущую скорость входящего трафика RX
и исходящего трафика TX выбранного интерфейса.

RX и TX должны рассчитываться ServerDeck Agent по разнице накопительных
счётчиков байт интерфейса между двумя последовательными измерениями.

Скорость должна отображаться в подходящей единице:

- `B/s`;
- `KB/s`;
- `MB/s`;
- `GB/s`.

Для сетевых графиков и расчёта загрузки канала агент должен передавать
скорость в битах в секунду или значения байт в секунду, из которых клиент
однозначно может вычислить биты в секунду.

#### Критерии приёмки

- [ ] RX и TX отображаются отдельными значениями.
- [ ] RX и TX являются скоростями, а не накопленными объёмами.
- [ ] Скорость содержит единицу измерения.
- [ ] При первом измерении без предыдущего счётчика отображается `Сбор данных` или `—`.
- [ ] При недоступности счётчиков отображается `—`.

---

### FR-006.9. Отображение скорости линка и duplex

**Приоритет:** Should  

Если скорость линка и duplex доступны, приложение должно отображать:

- Скорость линка.
- Режим duplex.

Duplex должен отображаться в одном из значений:

- `FULL`;
- `HALF`;
- `UNKNOWN`;
- `NOT_APPLICABLE`.

Если скорость линка неизвестна, отрицательна, равна нулю или неприменима
к типу интерфейса, приложение должно отображать `Нет данных`.

Для виртуальных, туннельных, VPN- и loopback-интерфейсов скорость линка
и duplex могут быть неприменимы.

#### Критерии приёмки

- [ ] Для Ethernet-интерфейса с доступными данными отображаются скорость и duplex.
- [ ] Значение скорости линка содержит единицу Mbps или Gbps.
- [ ] При `FULL` отображается значение full duplex.
- [ ] При неизвестном duplex отображается `UNKNOWN`.
- [ ] Для виртуального интерфейса отсутствие скорости линка не считается ошибкой.

---

### FR-006.10. Расчёт загрузки канала

**Приоритет:** Should  

Если скорость линка интерфейса известна и больше нуля, приложение должно
рассчитывать загрузку канала отдельно для RX и TX.

Загрузка канала рассчитывается по формулам:

\[
RX\ Utilization = \frac{RX\ bits/s}{Link\ speed\ bits/s} \times 100\%
\]

\[
TX\ Utilization = \frac{TX\ bits/s}{Link\ speed\ bits/s} \times 100\%
\]

Приложение должно отображать текущую скорость и процент загрузки,
например: `RX: 820 Mbps из 1 Gbps (82%)`.

Если скорость линка неизвестна или неприменима, процент загрузки канала
не должен отображаться.

#### Критерии приёмки

- [ ] При известной скорости линка отображаются RX и TX utilization.
- [ ] Utilization рассчитывается отдельно для RX и TX.
- [ ] Значение utilization отображается в процентах.
- [ ] При скорости линка 1 Gbps и RX 820 Mbps отображается примерно 82%.
- [ ] При неизвестной скорости линка приложение не выводит ложный процент загрузки.

---

### FR-006.11. Сбор исторических сетевых метрик

**Приоритет:** Must  

ServerDeck Agent должен собирать исторические метрики для каждого сетевого
интерфейса, доступного для мониторинга.

Каждая историческая точка должна содержать:

- Время сбора в UTC.
- RX bytes per second.
- TX bytes per second.
- RX errors.
- TX errors.
- RX dropped packets.
- TX dropped packets.
- Скорость линка, если доступна.

Исторические данные должны позволять отображать диапазоны:

- 15 минут;
- 1 час;
- 6 часов;
- 24 часа;
- 7 дней.

Политика хранения, агрегации и максимального количества точек должна
соответствовать общему требованию хранения исторических метрик.

#### Критерии приёмки

- [ ] Для каждого отслеживаемого интерфейса агент сохраняет RX и TX историю.
- [ ] В истории сохраняются счётчики ошибок и dropped packets.
- [ ] Исторические точки содержат время в UTC.
- [ ] История доступна как минимум за 7 дней.
- [ ] При отсутствии интерфейса новые исторические точки для него не создаются.

---

### FR-006.12. Выбор временного диапазона графиков

**Приоритет:** Must  

Приложение должно предоставлять единый селектор временного диапазона
для всех графиков выбранного сетевого интерфейса.

Доступные диапазоны:

- `15M` — последние 15 минут.
- `1H` — последний час.
- `6H` — последние 6 часов.
- `24H` — последние 24 часа.
- `7D` — последние 7 суток.

Выбранный диапазон должен применяться ко всем доступным графикам интерфейса.

Диапазон по умолчанию должен быть `1H`.

#### Критерии приёмки

- [ ] Пользователь может выбрать все пять диапазонов.
- [ ] По умолчанию выбран диапазон `1H`.
- [ ] После смены диапазона обновляются все графики интерфейса.
- [ ] Выбранный диапазон сохраняется при пересоздании UI-состояния экрана.

---

### FR-006.13. График RX и TX

**Приоритет:** Must  

Приложение должно отображать график входящего и исходящего трафика
выбранного интерфейса за выбранный временной диапазон.

График должен:

- Отображать RX и TX как отдельные серии данных.
- Использовать единицы скорости передачи данных.
- Содержать временную ось.
- Отображать значение и время выбранной точки.
- Визуально отличать отсутствие данных от нулевого трафика.

#### Критерии приёмки

- [ ] На графике отображаются отдельные серии RX и TX.
- [ ] Значения графика являются скоростями, а не накопленными байтами.
- [ ] На графике присутствует временная шкала.
- [ ] Пользователь может просмотреть значение выбранной точки.
- [ ] Пропуски метрик не заменяются искусственными нулями.

---

### FR-006.14. График загрузки канала

**Приоритет:** Should  

Если для интерфейса известна скорость линка, приложение должно отображать
график загрузки канала для RX и TX в процентах за выбранный период.

График должен использовать диапазон оси Y от 0 до 100%.

Если скорость линка изменялась в выбранном периоде, агент должен передать
скорость линка для соответствующих исторических точек или признак изменения
скорости. Приложение должно отображать изменение как событие или пересчитать
utilization для каждого интервала с соответствующей скоростью линка.

Если скорость линка недоступна для всего диапазона, график загрузки канала
не должен отображаться.

#### Критерии приёмки

- [ ] При известной link speed отображается график загрузки RX и TX.
- [ ] Ось Y графика ограничена 0–100%.
- [ ] При изменении скорости линка utilization не рассчитывается по устаревшему значению.
- [ ] При отсутствии link speed график не отображается.

---

### FR-006.15. График ошибок и dropped packets

**Приоритет:** Must  

Приложение должно отображать исторический график изменений счётчиков:

- RX errors;
- TX errors;
- RX dropped packets;
- TX dropped packets.

Поскольку ошибки и dropped packets являются накопительными счётчиками,
агент должен передавать для графика количество новых ошибок и dropped packets
за каждый интервал сбора, а не абсолютное значение счётчика с момента загрузки.

При перезапуске интерфейса, сбросе счётчика или уменьшении накопительного
значения агент должен корректно обработать сброс и не формировать
отрицательные значения.

#### Критерии приёмки

- [ ] График показывает прирост RX/TX errors за интервал.
- [ ] График показывает прирост RX/TX dropped packets за интервал.
- [ ] График не отображает отрицательные значения.
- [ ] После сброса интерфейсного счётчика график корректно продолжает сбор данных.
- [ ] При нулевом приросте ошибок отображается нулевая линия, а не отсутствие данных.

---

### FR-006.16. Определение предупреждений сетевого интерфейса

**Приоритет:** Must  

Приложение должно отображать статус интерфейса:

- `NORMAL`;
- `WARNING`;
- `CRITICAL`;
- `UNKNOWN`.

Статус определяется по следующим правилам:

- `CRITICAL` — интерфейс является интерфейсом default route и имеет статус
  `DISCONNECTED`, `NO_CARRIER` или `DISABLED`.
- `WARNING` — за последний интервал сбора обнаружен ненулевой прирост
  RX errors, TX errors, RX dropped packets или TX dropped packets.
- `WARNING` — загрузка RX или TX канала составляет не менее 90%,
  если известна скорость линка.
- `NORMAL` — данные доступны и не выполнено ни одно правило `WARNING`
  или `CRITICAL`.
- `UNKNOWN` — невозможно определить необходимые данные или статус интерфейса.

При наличии нескольких условий должен отображаться наиболее серьёзный статус:
`CRITICAL` выше `WARNING`, `WARNING` выше `NORMAL`.

#### Критерии приёмки

- [ ] Отключение интерфейса default route приводит к `CRITICAL`.
- [ ] Появление новых RX/TX errors приводит к `WARNING`.
- [ ] Появление новых dropped packets приводит к `WARNING`.
- [ ] Загрузка канала 90% или выше приводит к `WARNING`, если известна link speed.
- [ ] При нескольких условиях отображается наиболее серьёзный статус.
- [ ] При отсутствии данных отображается `UNKNOWN`.

---

### FR-006.17. Настройка цели проверки latency и packet loss

**Приоритет:** Could  

Пользователь должен иметь возможность выбрать цель сетевой проверки для сервера:

- Default gateway выбранного интерфейса, если он существует.
- Пользовательский IPv4-адрес.
- Пользовательский hostname.

Цель проверки должна храниться отдельно для каждого сервера.

Если пользовательская цель отсутствует, приложение не должно автоматически
считать произвольный публичный хост обязательной целью проверки.

#### Критерии приёмки

- [ ] Пользователь может выбрать default gateway как цель проверки.
- [ ] Пользователь может задать IPv4-адрес.
- [ ] Пользователь может задать hostname.
- [ ] При отсутствии цели блок latency и packet loss показывает `Цель не настроена`.
- [ ] Настройка одной цели не изменяет параметры другого сервера.

---

### FR-006.18. Отображение latency и packet loss

**Приоритет:** Could  

Если цель проверки сети настроена и агент может выполнить проверку,
приложение должно отображать:

- Среднюю задержку в миллисекундах.
- Минимальную и максимальную задержку, если доступны.
- Процент потерь пакетов.
- Время последней проверки.
- Статус ошибки проверки, если она не выполнена.

Агент должен ограничивать проверку не более чем пятью пакетами
или временем выполнения не более 10 секунд.

Невозможность выполнить ICMP-проверку не должна автоматически означать,
что выбранный интерфейс или сервер недоступен.

#### Критерии приёмки

- [ ] При успешной проверке отображаются latency и packet loss.
- [ ] Задержка отображается в миллисекундах.
- [ ] Потери отображаются в процентах.
- [ ] При недоступности ICMP пользователь видит ошибку проверки, а не ложный `OFFLINE`.
- [ ] Проверка не работает бесконечно и завершается не позднее 10 секунд.

---

### FR-006.19. История latency и packet loss

**Приоритет:** Could  

Если настроена цель проверки и агент регулярно выполняет измерения,
приложение должно отображать графики latency и packet loss за выбранный
временной диапазон.

Исторические точки должны содержать:

- Время проверки в UTC.
- Среднюю задержку.
- Процент потерь.
- Статус выполнения проверки.

Пропущенная или неуспешная проверка должна отображаться как отсутствие данных
или ошибка проверки, а не как значение latency `0 ms`.

## FR-007. Просмотр и управление файлами

**Приоритет:** Must  

### Цель

Авторизованный пользователь должен иметь возможность просматривать
разрешённые файловые системы и каталоги управляемого сервера, получать
метаданные файлов, выполнять разрешённые операции с файлами и каталогами,
а также просматривать и редактировать поддерживаемые текстовые файлы
в пределах назначенных прав доступа.

### Область действия

Группа требований `FR-007` определяет:

- Просмотр подключённых и смонтированных файловых систем.
- Навигацию по разрешённым каталогам.
- Просмотр метаданных файлов и каталогов.
- Просмотр и редактирование текстовых файлов.
- Создание, переименование и перемещение файлов и каталогов.
- Загрузку и скачивание файлов.
- Удаление файлов и каталогов.
- Ограничение доступа разрешёнными корневыми каталогами.
- Разделение файловых разрешений.
- Защиту от выхода за разрешённые корневые каталоги.
- Обработку ошибок файловой системы.
- Журнал аудита файловых операций.

### Границы модуля

Файловый менеджер реализуется после готовности ядра мониторинга, поскольку
функционально зависит от агента, модели прав и аутентификации.

Зависимости реализации:

- ServerDeck Agent с аутентификацией и аудитом.
- Модель прав доступа ServerDeck.
- Явно настроенные разрешённые корневые каталоги.
- Безопасный механизм разрешения путей и обработки символических ссылок.
- API загрузки и скачивания с лимитами размера.
- Защита от конфликтов редактирования.
- Тесты на path traversal, symlink escape, удаление и отказ в доступе.nn### Общие определения

- **Разрешённый корневой каталог** — абсолютный путь на сервере,
  явно разрешённый политикой ServerDeck для конкретного пользователя и сервера.
  Пример: `/home/alex/projects` или `/mnt/data`.
- **Разрешённая область** — разрешённый корневой каталог и все объекты,
  доступные внутри него с учётом реального пути, символических ссылок,
  прав ОС и прав ServerDeck.
- **Реальный путь** — канонический путь объекта после разрешения `.` , `..`
  и символических ссылок.
- **Path traversal** — попытка получить доступ за пределами разрешённого
  корневого каталога через конструкции наподобие `../`, абсолютный путь,
  некорректное кодирование или символическую ссылку.
- **Символическая ссылка** — объект файловой системы, указывающий на другой путь.
- **Текстовый файл** — файл, который допускается к просмотру или редактированию
  по политике расширений, размера, кодировки и содержимого.
- **Бинарный файл** — файл, не соответствующий правилам текстового файла
  или содержащий бинарные данные.
- **Версия файла** — значение, позволяющее определить, изменился ли файл
  между открытием и сохранением: ETag, хеш содержимого, сочетание inode,
  размера и времени изменения либо другой серверный идентификатор версии.
- **Операция изменения** — создание, загрузка, сохранение, переименование,
  перемещение, удаление, восстановление или окончательное удаление объекта.
- **Корзина** — отдельное безопасное место хранения удалённых объектов,
  из которого файл может быть восстановлен до окончательного удаления.

### FR-007.1. Просмотр доступных файловых систем

**Приоритет:** Must  

Приложение должно отображать список смонтированных файловых систем сервера,
доступных текущему пользователю согласно политике доступа ServerDeck.

Для каждой файловой системы должны отображаться:

- Точка монтирования.
- Устройство или источник монтирования.
- Тип файловой системы.
- Общий размер.
- Занятое пространство.
- Свободное пространство.
- Процент использования пространства.
- Статус доступности.
- Режим монтирования: `READ_ONLY` или `READ_WRITE`.
- Признак наличия хотя бы одного разрешённого корневого каталога внутри
  данной файловой системы.

Приложение не должно отображать файловую систему как доступную для навигации,
если в ней нет разрешённого корневого каталога для текущего пользователя.

#### Критерии приёмки

- [ ] Пользователь видит только файловые системы, в которых есть хотя бы один разрешённый корневой каталог.
- [ ] Для каждой файловой системы отображается точка монтирования.
- [ ] Для каждой файловой системы отображаются общий, занятый и свободный объёмы.
- [ ] Для каждой файловой системы отображается тип файловой системы.
- [ ] Для каждой файловой системы отображается режим `READ_ONLY` или `READ_WRITE`.
- [ ] Недоступный или размонтированный том получает понятный статус.
- [ ] Файловая система без разрешённых каталогов не раскрывает своё содержимое пользователю.

---

### FR-007.2. Отображение разрешённых корневых каталогов

**Приоритет:** Must  

Приложение должно отображать список разрешённых корневых каталогов,
доступных текущему пользователю на выбранном сервере.

Для каждого разрешённого корневого каталога должны отображаться:

- Отображаемое название.
- Абсолютный путь.
- Режим доступа пользователя: `READ_ONLY` или `READ_WRITE`.
- Набор разрешённых операций, если он ограничен политикой.
- Статус доступности каталога.

Пользователь должен начинать навигацию только из списка разрешённых
корневых каталогов.

#### Критерии приёмки

- [ ] Пользователь видит список доступных корневых каталогов.
- [ ] Пользователь не может вручную открыть произвольный путь сервера вне списка разрешённых корней.
- [ ] Для каждого корня отображается режим доступа.
- [ ] При недоступности точки монтирования пользователь видит понятную ошибку.

---

### FR-007.3. Навигация по разрешённым каталогам

**Приоритет:** Must  

Пользователь должен иметь возможность:

- Просматривать содержимое разрешённого корневого каталога.
- Переходить в дочерние каталоги.
- Возвращаться к родительскому каталогу.
- Возвращаться к списку разрешённых корневых каталогов.
- Обновлять содержимое текущего каталога вручную.

Агент должен проверять доступ к каждому запрашиваемому пути до выполнения
операции чтения каталога.

Переход к родительскому каталогу не должен позволять выйти за пределы
выбранного разрешённого корневого каталога.

#### Критерии приёмки

- [ ] Пользователь может открыть разрешённый корневой каталог.
- [ ] Пользователь может открыть дочерний каталог внутри разрешённой области.
- [ ] Пользователь может вернуться на один уровень вверх внутри разрешённой области.
- [ ] При нахождении в корневом разрешённом каталоге переход выше него недоступен.
- [ ] Пользователь может обновить содержимое текущего каталога.
- [ ] Попытка открыть путь вне разрешённой области завершается отказом в доступе.

---

### FR-007.4. Отображение содержимого каталога

**Приоритет:** Must  

Приложение должно отображать содержимое разрешённого каталога постранично.

Для каждого файла или каталога должны отображаться:

- Имя объекта.
- Тип объекта: `FILE`, `DIRECTORY`, `SYMLINK`, `OTHER`.
- Размер в байтах с форматированием в KB, MB, GB или TB.
- Время последнего изменения.
- Владелец, если данные доступны.
- Группа, если данные доступны.
- Права доступа ОС в символьном виде, например `rw-r-----`.
- Признак режима read-only, если объект или файловая система недоступны для записи.
- Признак символической ссылки и её целевой путь, если он доступен и безопасен для отображения.

Размер каталога не должен вычисляться рекурсивно при обычном просмотре,
если это требует обхода вложенной структуры.

Каталог должен отображать `—` или `Не рассчитан` вместо рекурсивного размера,
если размер не был предварительно рассчитан агентом.

#### Критерии приёмки

- [ ] Для каждого объекта отображаются имя и тип.
- [ ] Для файлов отображается размер.
- [ ] Для объектов отображается дата изменения.
- [ ] При доступности отображаются владелец, группа и права ОС.
- [ ] Символическая ссылка визуально отличается от обычного файла или каталога.
- [ ] Просмотр каталога не запускает рекурсивный расчёт размера всех вложенных объектов.
- [ ] Большой каталог загружается постранично.

### FR-007.5. Сортировка содержимого каталога

**Приоритет:** Should  

Пользователь должен иметь возможность сортировать содержимое текущего каталога:

- По имени.
- По дате изменения.
- По размеру.
- По типу.

Для каждого типа сортировки пользователь должен иметь возможность выбрать
порядок по возрастанию или убыванию.

По умолчанию объекты должны сортироваться по имени в алфавитном порядке,
при этом каталоги отображаются выше файлов.

Если значения сортировки равны, объекты должны сортироваться по имени
в алфавитном порядке.

#### Критерии приёмки

- [ ] Пользователь может выбрать каждый поддерживаемый тип сортировки.
- [ ] Пользователь может изменить направление сортировки.
- [ ] При стандартной сортировке каталоги отображаются выше файлов.
- [ ] При одинаковом размере, дате или типе применяется сортировка по имени.
- [ ] Выбранная сортировка применяется ко всем страницам текущего каталога.

---

### FR-007.6. Просмотр подробных метаданных объекта

**Приоритет:** Should  

Пользователь должен иметь возможность открыть подробную информацию
о файле или каталоге в пределах разрешённой области.

Для файла должны отображаться:

- Полный путь относительно разрешённого корневого каталога.
- Тип объекта.
- Размер.
- Время создания, если доступно.
- Время последнего изменения.
- Время последнего доступа, если доступно.
- Владелец и группа, если доступны.
- Права доступа ОС.
- Режим монтирования файловой системы.
- MIME-тип или предполагаемый тип содержимого, если агент может его определить.
- Версия файла, пригодная для защиты от конфликтов редактирования.

Для каталога должны отображаться те же доступные метаданные, кроме MIME-типа.

#### Критерии приёмки

- [ ] Пользователь может открыть метаданные файла.
- [ ] Пользователь может открыть метаданные каталога.
- [ ] Метаданные содержат путь, тип и дату изменения.
- [ ] Для файла отображается размер.
- [ ] Для файла доступна версия для последующего безопасного сохранения.
- [ ] Отсутствующие метаданные отображаются как `—`, а не как вымышленные значения.

### FR-007.7. Определение текстовых и бинарных файлов

**Приоритет:** Must  

ServerDeck Agent должен определять возможность текстового просмотра и редактирования
файла на основании нескольких условий:

- Файл находится в разрешённой области.
- Пользователь имеет право просмотра или редактирования.
- Размер файла не превышает установленный лимит.
- Файл не содержит признаков бинарного содержимого.
- Расширение файла входит в список поддерживаемых для текстовой работы
  либо пользователь явно выбрал расширенный режим просмотра.

Список поддерживаемых текстовых расширений:

- `.txt`;
- `.md`;
- `.yaml`;
- `.yml`;
- `.json`;
- `.toml`;
- `.ini`;
- `.conf`;
- `.env`;
- `.py`;
- `.js`;
- `.ts`;
- `.sh`;
- `.log`;
- `.service`.

Расширение файла не должно быть единственным критерием определения текстового файла.

Файлы, содержащие NUL-байты или не прошедшие проверку текстового содержимого,
должны считаться бинарными, если не выбран расширенный режим.

#### Критерии приёмки

- [ ] Поддерживаемый текстовый файл может быть открыт для просмотра при наличии права просмотра.
- [ ] Файл с неподдерживаемым расширением не открывается автоматически как текст.
- [ ] Бинарный файл не отображается как текст.
- [ ] Файл с NUL-байтом определяется как бинарный.
- [ ] Расширение `.txt` не является единственным основанием для текстового открытия.
- [ ] При отсутствии права просмотра содержимое файла не передаётся на клиент.

---

### FR-007.8. Просмотр содержимого текстового файла

**Приоритет:** Should  

Пользователь должен иметь возможность просматривать содержимое поддерживаемого
текстового файла, если:

- Файл находится в разрешённой области.
- Пользователь имеет право `VIEW`.
- Размер файла не превышает лимит просмотра.
- Файл распознан как текстовый.

Максимальный размер полного текстового просмотра должен быть
не более 1 MB или другого явно настроенного лимита.

По умолчанию агент и приложение должны использовать кодировку UTF-8.

Если UTF-8-декодирование невозможно, приложение должно сообщить о проблеме
кодировки и предложить выбрать кодировку в расширенном режиме, если такая
возможность реализована.

#### Критерии приёмки

- [ ] Пользователь с правом `VIEW` может открыть поддерживаемый текстовый файл.
- [ ] Файл размером не более лимита загружается целиком.
- [ ] Файл размером выше лимита не загружается целиком на устройство.
- [ ] UTF-8 файл отображается корректно.
- [ ] При ошибке декодирования пользователь видит понятное сообщение.
- [ ] При отсутствии права просмотра содержимое файла не отображается.

---

### FR-007.9. Просмотр больших текстовых файлов и логов

**Приоритет:** Should  

Если текстовый файл превышает лимит полного просмотра, приложение должно
предложить режим частичного просмотра.

Режим частичного просмотра должен поддерживать:

- Получение последних N строк файла.
- Выбор количества строк: 100, 500 или 1 000.
- Ручную загрузку более ранних строк порциями.
- Отображение факта, что показана только часть файла.

Режим постоянного streaming `tail -f` не входит в текущий объём. Вместо него пользователь
может вручную обновить последние строки файла.

#### Критерии приёмки

- [ ] Большой файл не передаётся на устройство клиента целиком.
- [ ] Пользователь может просмотреть последние 100, 500 или 1 000 строк.
- [ ] Пользователь видит, что отображается только хвост файла.
- [ ] Пользователь может запросить более ранние строки.
- [ ] Ручное обновление загружает новую порцию последних строк.
- [ ] Режим частичного просмотра не позволяет редактировать файл.

---

### FR-007.10. Редактирование текстового файла

**Приоритет:** Could  

Пользователь должен иметь возможность редактировать поддерживаемый текстовый файл,
если одновременно выполняются условия:

- Файл находится в разрешённой области.
- Пользователь имеет право `EDIT`.
- Файловая система смонтирована в режиме `READ_WRITE`.
- Пользователь имеет право записи на уровне ОС.
- Размер файла не превышает лимит редактирования.
- Файл распознан как текстовый.
- Файл не открыт в режиме частичного просмотра.

Максимальный размер файла для редактирования должен быть
не более 512 KB или другого явно настроенного лимита.

Перед отправкой изменений приложение должно получить версию файла.

При сохранении приложение должно передавать ожидаемую версию файла.
Агент должен сохранить изменения только при совпадении ожидаемой и текущей версии.

#### Критерии приёмки

- [ ] Пользователь с правом `EDIT` может перейти к редактированию поддерживаемого файла.
- [ ] Пользователь без права `EDIT` не видит действие сохранения.
- [ ] Файл на read-only файловой системе не может быть отредактирован.
- [ ] Файл больше лимита не открывается в режиме редактирования.
- [ ] При открытии агент возвращает версию файла.
- [ ] При сохранении приложение передаёт ожидаемую версию файла.
- [ ] Агент не сохраняет изменения при несовпадении версий.

---

### FR-007.11. Защита от конфликта редактирования

**Приоритет:** Must  

Агент должен предотвращать молчаливую перезапись файла, изменённого после его
открытия пользователем.

Если текущая версия файла на сервере не совпадает с версией, полученной
при открытии файла, агент должен отклонить сохранение с ошибкой `FILE_CONFLICT`.

При конфликте приложение должно:

- Сообщить, что файл был изменён на сервере или другим пользователем.
- Не перезаписывать текущую версию файла автоматически.
- Предложить обновить содержимое с сервера.
- Предложить сравнение локальной и серверной версий, если функция сравнения доступна.
- Позволить пользователю сохранить локальный текст отдельно, не заменяя файл.

#### Критерии приёмки

- [ ] Изменение файла на сервере после открытия вызывает `FILE_CONFLICT`.
- [ ] При конфликте серверная версия не перезаписывается молча.
- [ ] Пользователь видит понятное сообщение о конфликте.
- [ ] Пользователь может повторно загрузить текущую серверную версию.
- [ ] Ошибка конфликта фиксируется в журнале аудита как неуспешная операция сохранения.

---

### FR-007.12. Атомарное сохранение текстового файла

**Приоритет:** Must  

При сохранении изменений текстового файла агент должен использовать атомарную
замену содержимого в пределах той же файловой системы, если это поддерживается
операционной системой и правами доступа.

Агент должен:

- Записать новые данные во временный файл в том же каталоге.
- Применить необходимые права доступа в соответствии с политикой.
- Проверить версию исходного файла непосредственно перед заменой.
- Атомарно заменить исходный файл временным после успешной проверки.
- Удалить временный файл при неуспешной операции.

Агент не должен оставлять частично записанный файл при сетевом обрыве,
ошибке записи или конфликте версий.

#### Критерии приёмки

- [ ] Ошибка записи не приводит к частично перезаписанному исходному файлу.
- [ ] Конфликт версий не изменяет исходный файл.
- [ ] После успешного сохранения файл содержит полную новую версию.
- [ ] Временный файл удаляется после неуспешной операции.
- [ ] Успешное сохранение создаёт запись аудита.

---

### FR-007.13. Создание файлов и каталогов

**Приоритет:** Could  

Пользователь должен иметь возможность создать пустой каталог или текстовый файл
в текущем разрешённом каталоге, если имеет право `CREATE`, файловая система
доступна для записи и права ОС позволяют операцию.

Имя создаваемого объекта должно:

- Быть непустым после удаления начальных и конечных пробелов.
- Не содержать символы `/` и NUL.
- Не содержать путь, включая `..`, абсолютный путь или разделители каталогов.
- Не совпадать с существующим объектом в целевом каталоге.
- Не превышать ограничение длины имени, поддерживаемое файловой системой.

При создании файла пользователь может выбрать только поддерживаемый текстовый
шаблон или пустой файл.

#### Критерии приёмки

- [ ] Пользователь с правом `CREATE` может создать каталог в разрешённой области.
- [ ] Пользователь с правом `CREATE` может создать пустой текстовый файл.
- [ ] Имя с `/`, `..` или NUL не проходит валидацию.
- [ ] При совпадении имени с существующим объектом создание не выполняется.
- [ ] При отсутствии прав ОС пользователь получает понятную ошибку.
- [ ] Успешное создание фиксируется в аудите.

---

### FR-007.14. Загрузка файлов на сервер

**Приоритет:** Could  

Пользователь должен иметь возможность загрузить файл с устройства клиента
в выбранный разрешённый каталог, если имеет право `UPLOAD`, а файловая система
доступна для записи.

Перед загрузкой агент должен проверить:

- Право `UPLOAD` пользователя.
- Принадлежность целевого пути разрешённой области.
- Доступность файловой системы для записи.
- Доступное место на файловой системе.
- Лимит размера файла.
- Корректность имени файла.
- Конфликт с существующим объектом.

Максимальный размер одного загружаемого файла должен быть 50 MB, если на сервере не задан другой лимит.

При совпадении имени с существующим файлом приложение должно предложить:

- Отменить загрузку.
- Переименовать загружаемый файл.
- Перезаписать существующий файл, если пользователь имеет право `EDIT`
  и прошёл отдельное подтверждение.

Загрузка должна выполняться во временный файл с последующей атомарной заменой.

#### Критерии приёмки

- [ ] Пользователь с правом `UPLOAD` может выбрать файл для загрузки.
- [ ] Файл больше 50 MB не начинает загружаться.
- [ ] При недостатке места пользователь получает понятную ошибку.
- [ ] При конфликте имени приложение предлагает варианты разрешения.
- [ ] Перезапись требует отдельного подтверждения.
- [ ] Неуспешная загрузка не оставляет частичный итоговый файл.
- [ ] Успешная загрузка фиксируется в аудите.

---

### FR-007.15. Скачивание файлов с сервера

**Приоритет:** Should  

Пользователь должен иметь возможность скачать файл из разрешённой области,
если имеет право `DOWNLOAD`.

Перед скачиванием агент должен проверить, что файл:

- Находится в разрешённой области.
- Не является каталогом.
- Доступен для чтения текущему пользователю.
- Не превышает лимит скачивания за одну операцию.

Максимальный размер скачиваемого файла должен быть 100 MB, если на сервере не задан другой лимит.

Скачивание должно поддерживать возобновление передачи, если платформа клиента
и API агента предоставляют такую возможность. Если возобновление не поддержано,
приложение должно явно сообщать об этом при прерывании операции.

#### Критерии приёмки

- [ ] Пользователь с правом `DOWNLOAD` может скачать разрешённый файл.
- [ ] Пользователь не может скачать каталог как обычный файл.
- [ ] Файл больше лимита не скачивается без отдельного механизма.
- [ ] При отсутствии права чтения скачивание не начинается.
- [ ] При ошибке сети пользователь получает понятный результат операции.
- [ ] Успешное скачивание фиксируется в аудите, если политика аудита включает чтение.

---

### FR-007.16. Переименование объектов

**Приоритет:** Could  

Пользователь должен иметь возможность переименовать файл или каталог
в пределах текущей разрешённой области, если имеет право `RENAME`
и права ОС позволяют операцию.

Новое имя должно проходить те же правила валидации, что и имя при создании.

Если объект с новым именем уже существует, агент не должен выполнять
переименование без явного подтверждения пользователя и права перезаписи.

#### Критерии приёмки

- [ ] Пользователь с правом `RENAME` может переименовать файл.
- [ ] Пользователь с правом `RENAME` может переименовать каталог.
- [ ] Некорректное имя не сохраняется.
- [ ] Конфликт имени требует отдельного подтверждения.
- [ ] Попытка переименования вне разрешённой области отклоняется.
- [ ] Успешное переименование фиксируется в аудите.

---

### FR-007.17. Перемещение объектов

**Приоритет:** Could  

Пользователь должен иметь возможность переместить файл или каталог между
разрешёнными каталогами одного сервера, если имеет право `MOVE` на исходный
объект и право `CREATE` или `MOVE` в целевом каталоге.

Агент должен проверять доступность исходного и целевого путей, права ОС,
политику ServerDeck, конфликт имён и принадлежность обоих путей
разрешённым областям.

Если перемещение происходит между разными файловыми системами, агент должен
явно определить, поддерживается ли операция как копирование с последующим
удалением. Перемещение между разными файловыми системами не должно
выполняться автоматически.

#### Критерии приёмки

- [ ] Пользователь может переместить объект внутри одной разрешённой файловой системы.
- [ ] Пользователь не может переместить объект в неразрешённый каталог.
- [ ] При конфликте имени пользователь получает понятное сообщение.
- [ ] Перемещение между разными файловыми системами не запускается молча.
- [ ] Успешное перемещение фиксируется в аудите.

---

### FR-007.18. Подтверждение удаления объекта

**Приоритет:** Must  

Пользователь должен иметь возможность удалить файл или каталог только при наличии
права `DELETE` и после явного подтверждения операции.

Диалог подтверждения должен содержать:

- Имя удаляемого объекта.
- Полный путь относительно разрешённого корневого каталога.
- Тип объекта.
- Предупреждение о последствиях операции.
- Информацию о том, будет ли объект перемещён в корзину или удалён необратимо.

Удаление непустого каталога должно требовать отдельного усиленного подтверждения.

#### Критерии приёмки

- [ ] Удаление не начинается без подтверждения.
- [ ] Диалог содержит имя и путь объекта.
- [ ] Пользователь может отменить удаление без изменения данных.
- [ ] Для непустого каталога используется отдельное усиленное подтверждение.
- [ ] В интерфейсе явно указано, обратима ли операция.

---

### FR-007.19. Удаление файлов и каталогов в корзину

**Приоритет:** Could  

Если для разрешённой файловой системы настроена корзина, приложение должно
перемещать удаляемые файлы и каталоги в корзину вместо окончательного удаления.

Для каждого объекта в корзине должны сохраняться:

- Исходный путь.
- Время удаления.
- Идентификатор пользователя, выполнившего удаление.
- Размер объекта, если доступен.
- Срок хранения.

Срок хранения должен быть настраиваемым на сервере и по умолчанию
составлять 7 дней.

При перемещении объекта в корзину агент должен предотвращать конфликт имён
и сохранять исходный путь для восстановления.

#### Критерии приёмки

- [ ] При настроенной корзине удалённый файл перемещается в неё.
- [ ] При настроенной корзине удалённый каталог перемещается в неё.
- [ ] Для объекта сохраняется исходный путь.
- [ ] Корзина не создаёт конфликт имён между объектами с одинаковым названием.
- [ ] Пользователь видит, что объект может быть восстановлен.
- [ ] Удаление в корзину фиксируется в аудите.

---

### FR-007.20. Восстановление объекта из корзины

**Приоритет:** Could  

Пользователь с правом `RESTORE` должен иметь возможность восстановить объект
из корзины в исходный путь или в другой разрешённый каталог.

Перед восстановлением агент должен проверить:

- Доступность целевой файловой системы.
- Права ServerDeck и права ОС.
- Конфликт с существующим объектом в целевом пути.
- Принадлежность целевого пути разрешённой области.

При конфликте имени приложение должно предложить переименование,
выбор другого пути или отмену восстановления.

#### Критерии приёмки

- [ ] Пользователь с правом `RESTORE` может восстановить объект.
- [ ] По умолчанию предлагается исходный путь.
- [ ] При конфликте имени восстановление не перезаписывает существующий объект молча.
- [ ] Восстановление в неразрешённую область запрещено.
- [ ] Успешное восстановление фиксируется в аудите.

---

### FR-007.21. Окончательное удаление

**Приоритет:** Could  

Пользователь с правом `PURGE` должен иметь возможность окончательно удалить
объект из корзины только после явного подтверждения.

Окончательное удаление является необратимой операцией.

Ручной PURGE объектов корзины входит в согласованный объём (AFR-048). Объекты также могут удаляться по серверному сроку хранения. Оба пути соблюдают аудит: без надёжной записи начала удаление не начинается.

---

### FR-007.22. Ограничение файлового доступа разрешёнными корнями

**Приоритет:** Must

Политика корней общая для конкретного Agent и всех его равноправных сопряжённых устройств. По умолчанию доступен home runtime-пользователя. Доверенное устройство может изменить общую политику версионированной аудируемой операцией; добавление `/` требует предупреждения. Политика не расширяет права ОС и не отменяет защиту объектов/предков Agent. Вложенные монтирования включаются явно, пути передаются как root_id и относительные компоненты.

Проверки применяются к чтению, созданию, сохранению, rename/move, upload/download, корзине, restore и PURGE (AFR-042/043, ASEC-014/015). Строкового префикса недостаточно; невозможность безопасного разрешения/изменения даёт отказ.

#### Критерии приёмки

- [ ] Каждая файловая операция проверяет текущую общую политику, версию и фактические права.
- [ ] Подмена пути, ссылки, aliases и mount не обходят корни/защищённые объекты, в том числе при root.
- [ ] Изменение политики другим телефоном не затирается молча; ожидаемая версия обязательна.
- [ ] Политики разных Agent независимы; у устройств одного Agent нет скрытых разных списков корней.
- [ ] При недоказанной безопасности операция отклонена и доступность действия отражена честно.

---

### FR-007.23. Защита от path traversal и symbolic link escape

**Приоритет:** Must  

ServerDeck Agent должен предотвращать выход за пределы разрешённой области
через:

- Последовательности `..`.
- Абсолютные пути.
- URL-кодирование и двойное кодирование пути.
- Нулевые байты.
- Символические ссылки.
- Символические ссылки в промежуточных каталогах.
- Гонки времени проверки и использования пути (TOCTOU).

Агент не должен выполнять файловые операции, полагаясь только на строковую
проверку вида `path.startsWith(allowedRoot)`.

Перед операцией агент должен разрешить путь относительно дескриптора
разрешённого корневого каталога и убедиться, что все разрешённые компоненты
пути остаются внутри этого корня.

Переход по символической ссылке должен быть запрещён для всех операций,
кроме отображения метаданных самой ссылки.

#### Критерии приёмки

- [ ] Путь с `../` не позволяет выйти за разрешённый корень.
- [ ] Абсолютный путь вне разрешённой области отклоняется.
- [ ] URL-кодированный вариант `..` отклоняется.
- [ ] Путь с NUL-байтом отклоняется.
- [ ] Символическая ссылка на объект вне разрешённого корня не может быть открыта.
- [ ] Символическая ссылка внутри промежуточного каталога не позволяет выйти из разрешённой области.
- [ ] При попытке обхода пользователь получает ошибку `ACCESS_DENIED`.

---

### FR-007.24. Файловые разрешения ServerDeck

**Приоритет:** Should  

ServerDeck должен поддерживать следующие файловые разрешения:

- `VIEW` — просмотр списка объектов, метаданных и содержимого текстовых файлов.
- `DOWNLOAD` — скачивание файлов.
- `UPLOAD` — загрузка файлов.
- `CREATE` — создание файлов и каталогов.
- `EDIT` — изменение содержимого существующих текстовых файлов.
- `RENAME` — переименование файлов и каталогов.
- `MOVE` — перемещение файлов и каталогов.
- `DELETE` — перемещение объекта в корзину.
- `RESTORE` — восстановление объекта из корзины.
- `PURGE` — окончательное необратимое удаление.

Разрешения должны назначаться как минимум для комбинации:

- Пользователь ServerDeck.
- Сервер.
- Разрешённый корневой каталог.

Допускается одна роль `OWNER`, обладающая всеми разрешениями
в пределах настроенных корневых каталогов.

#### Критерии приёмки

- [ ] У агента есть отдельная проверка разрешения для каждой операции.
- [ ] Наличие права `VIEW` не предоставляет право `EDIT`.
- [ ] Наличие права `EDIT` не предоставляет право `DELETE`.
- [ ] Разрешения действуют только в пределах назначенного корневого каталога.
- [ ] Владелец сервера может выполнять полный набор разрешённых операций.

---

### FR-007.25. Обработка ошибок файловой системы

**Приоритет:** Must  

Приложение должно отображать понятное сообщение при ошибке файловой операции.

Агент должен возвращать машиночитаемый код ошибки как минимум для состояний:

- `ACCESS_DENIED` — запрещено политикой ServerDeck.
- `OS_PERMISSION_DENIED` — отказ прав операционной системы.
- `NOT_FOUND` — объект не найден.
- `ALREADY_EXISTS` — объект с таким именем уже существует.
- `READ_ONLY_FILESYSTEM` — файловая система доступна только для чтения.
- `NO_SPACE_LEFT` — недостаточно свободного места.
- `VOLUME_UNAVAILABLE` — том или точка монтирования недоступны.
- `PATH_INVALID` — путь или имя объекта некорректны.
- `SYMLINK_NOT_ALLOWED` — операция с символической ссылкой запрещена политикой.
- `FILE_TOO_LARGE` — превышен лимит размера.
- `FILE_CONFLICT` — файл был изменён после открытия.
- `UNSUPPORTED_FILE_TYPE` — файл не поддерживается операцией.
- `OPERATION_TIMEOUT` — операция превысила разрешённое время выполнения.
- `INTERNAL_ERROR` — непредвиденная ошибка агента.

Сообщение, отображаемое пользователю, не должно содержать пароли, токены,
содержимое файлов, закрытые абсолютные пути вне разрешённой области
или внутренние stack trace.

#### Критерии приёмки

- [ ] Каждая ошибка API содержит машиночитаемый код.
- [ ] Пользователь видит понятное описание ошибки.
- [ ] При отсутствии места отображается ошибка `NO_SPACE_LEFT`.
- [ ] При read-only файловой системе отображается `READ_ONLY_FILESYSTEM`.
- [ ] При конфликте версии отображается `FILE_CONFLICT`.
- [ ] Сообщения об ошибках не содержат секреты и stack trace.

---

### FR-007.26. Аудит изменяющих файловых операций

**Приоритет:** Must  

ServerDeck Agent должен создавать запись аудита для каждой файловой операции,
изменяющей состояние:

- Создание файла.
- Создание каталога.
- Загрузка файла.
- Сохранение изменений файла.
- Переименование.
- Перемещение.
- Удаление в корзину.
- Восстановление из корзины.
- Автоматическое окончательное удаление после истечения срока хранения.
- Ручное окончательное удаление, если оно будет реализовано.

Каждая запись аудита должна содержать:

- Время операции в UTC.
- Идентификатор операции.
- Идентификатор пользователя ServerDeck.
- Имя пользователя для отображения, если доступно.
- Идентификатор сервера.
- Имя сервера для отображения, если доступно.
- Тип операции.
- Исходный путь относительно разрешённого корня, если применимо.
- Целевой путь относительно разрешённого корня, если применимо.
- Идентификатор разрешённого корневого каталога.
- Размер объекта до и после операции, если применимо.
- Результат: `SUCCESS` или `FAILURE`.
- Код ошибки при неуспехе.
- Причину отказа или ошибки без раскрытия секретов.

Аудит должен фиксировать как успешные, так и неуспешные попытки
изменяющих операций.

#### Критерии приёмки

- [ ] Создание файла создаёт запись аудита.
- [ ] Загрузка файла создаёт запись аудита.
- [ ] Сохранение текста создаёт запись аудита.
- [ ] Переименование и перемещение создают записи аудита.
- [ ] Удаление и восстановление создают записи аудита.
- [ ] Неуспешная операция изменения также создаёт запись аудита.
- [ ] Запись содержит время, пользователя, сервер, операцию и результат.
- [ ] Аудит не содержит содержимого файла, паролей, токенов и SSH-ключей.

---

### FR-007.27. Отображение записи аудита файловой операции

**Приоритет:** Should  

Приложение должно отображать человеку понятное представление записи аудита
файловой операции.

Пример отображения:

```text
26.09.2026 10:31 UTC
alex изменил файл

Сервер: home-server-01
Путь: /mnt/data/projects/serverdeck/docker-compose.yml
Операция: SAVE
Размер: 2.4 KB → 2.8 KB
Результат: Успешно
```

Если операция была неуспешной, приложение должно отображать итог
`Не выполнено` и понятную причину без технического stack trace.

## FR-008. Просмотр процессов сервера

**Приоритет:** Must  

### Цель

Пользователь должен иметь возможность просмотреть список процессов,
запущенных на выбранном сервере, определить процессы с наибольшим
потреблением CPU или оперативной памяти и получить базовую информацию
о каждом процессе.

### Область действия

Группа требований `FR-008` определяет:

- Получение списка процессов от ServerDeck Agent.
- Отображение базовой информации о процессах.
- Отображение текущего потребления CPU и RAM.
- Поиск процесса по имени и PID.
- Сортировку процессов.
- Обработку завершившихся, недоступных и устаревших данных.
- Отображение необязательной связи процесса с systemd, Docker или cgroup.

### Границы модуля

Модуль процессов поддерживает просмотр информации и завершение процессов
(см. FR-008.14).

Не входит в текущий объём:

- Приостановка и возобновление процессов.
- Изменение приоритета, `nice` и `ionice`.
- Отображение дерева процессов.
- Отображение открытых файлов.
- Отображение сетевых сокетов процесса.
- Отображение окружения процесса.
- Детализированные метрики дискового I/O.
- Экспорт списка процессов.

Отображение аргументов командной строки исключено из соображений
безопасности (см. FR-008.13).nn### Общие определения

- **Процесс** — экземпляр выполняемой программы в операционной системе Linux.
- **PID** — уникальный числовой идентификатор процесса в пределах текущего
  PID namespace.
- **PPID** — идентификатор родительского процесса.
- **Процесс-родитель** — процесс, создавший рассматриваемый процесс.
- **Статус процесса** — текущее состояние выполнения процесса.
- **Uptime процесса** — время, прошедшее с момента запуска процесса
  до момента формирования снимка метрик.
- **CPU процесса** — доля процессорного времени, потреблённая процессом
  за интервал между двумя измерениями, выраженная в процентах.
- **RAM процесса** — объём физической оперативной памяти, занятый процессом
  в момент формирования снимка.
- **RSS** — Resident Set Size, объём памяти процесса, находящийся
  в физической оперативной памяти.
- **Связь с systemd unit** — информация о unit systemd, если агент может
  определить принадлежность процесса.
- **Связь с Docker-контейнером** — информация о контейнере, если агент может
  определить принадлежность процесса через cgroup или Docker runtime.
- **cgroup** — механизм Linux для группировки и ограничения ресурсов процессов.
- **Снимок процессов** — набор информации о процессах на момент сбора агентом.

### FR-008.1. Получение списка процессов

**Приоритет:** Must  

При открытии экрана процессов приложение должно запросить у ServerDeck Agent
актуальный снимок процессов выбранного сервера.

Приложение должно отображать время формирования снимка процессов.

Если агент недоступен, приложение должно отобразить последнее успешно
полученное состояние списка процессов, если оно существует, с отметкой
об устаревших данных.

#### Критерии приёмки

- [ ] При открытии экрана процессов приложение отправляет запрос к агенту.
- [ ] После успешного ответа отображается список процессов выбранного сервера.
- [ ] На экране отображается время формирования снимка.
- [ ] При недоступном агенте ранее сохранённый список остаётся доступным.
- [ ] Данные старше 60 секунд помечаются как устаревшие.
- [ ] При отсутствии сохранённого снимка и недоступном агенте отображается понятное состояние ошибки.

---

### FR-008.2. Постраничное отображение процессов

**Приоритет:** Must  

Приложение должно отображать список процессов постранично.

ServerDeck Agent должен возвращать не более 100 процессов в одном ответе.

Приложение должно поддерживать загрузку следующей страницы процессов
без потери текущих параметров поиска и сортировки.

Если количество процессов превышает размер одной страницы, приложение должно
отобразить возможность загрузить следующую страницу.

#### Критерии приёмки

- [ ] Агент не возвращает более 100 процессов в одном ответе.
- [ ] При количестве процессов более 100 пользователь может загрузить следующую страницу.
- [ ] После загрузки следующей страницы ранее отображённые процессы не исчезают.
- [ ] Поиск и сортировка сохраняются при переходе к следующей странице.
- [ ] При количестве процессов не более 100 элемент загрузки следующей страницы не отображается.

---

### FR-008.3. Отображение идентификационных данных процесса

**Приоритет:** Must  

Для каждого процесса в списке приложение должно отображать:

- PID.
- Имя процесса.
- Текущий статус.
- Имя пользователя-владельца процесса, если доступно.
- UID владельца процесса.

Имя процесса должно отображаться в безопасном виде и не должно включать
полную командную строку, аргументы запуска, переменные окружения, пароли,
токены или иные секреты.

Если имя пользователя определить не удалось, приложение должно отображать
UID и значение `Неизвестный пользователь`.

#### Критерии приёмки

- [ ] Для каждого процесса отображается PID.
- [ ] Для каждого процесса отображается имя.
- [ ] Для каждого процесса отображается статус.
- [ ] Для каждого процесса отображается UID.
- [ ] При доступности отображается имя пользователя.
- [ ] Если имя пользователя недоступно, отображается UID и понятная подпись.
- [ ] Полная командная строка процесса не отображается.

---

### FR-008.4. Нормализация статуса процесса

**Приоритет:** Must  

ServerDeck Agent должен преобразовывать системные статусы процессов
в следующие нормализованные значения:

- `RUNNING` — процесс выполняется или готов к выполнению.
- `SLEEPING` — процесс ожидает событие.
- `DISK_SLEEP` — процесс ожидает непрерываемую операцию ввода-вывода.
- `STOPPED` — процесс остановлен сигналом или отладчиком.
- `ZOMBIE` — процесс завершён, но ещё не обработан родительским процессом.
- `DEAD` — процесс завершён и находится в переходном состоянии.
- `UNKNOWN` — состояние не удалось определить.

Приложение должно отображать человекочитаемую подпись статуса
и визуальный индикатор, не зависящий только от цвета.

#### Критерии приёмки

- [ ] Каждый процесс получает один нормализованный статус.
- [ ] Для статуса отображается текстовая подпись.
- [ ] `ZOMBIE` визуально отличается от обычного sleeping-процесса.
- [ ] Неизвестный системный статус преобразуется в `UNKNOWN`.
- [ ] Приложение не показывает пользователю необъяснённые однобуквенные статусы Linux.

---

### FR-008.5. Отображение времени запуска и uptime процесса

**Приоритет:** Should  

Для каждого процесса приложение должно отображать:

- Время запуска процесса в часовом поясе пользователя или сервера
  согласно единому правилу приложения.
- Uptime процесса в относительном формате, например `Запущен 3 ч 14 мин назад`.

Если время запуска невозможно определить, приложение должно отображать `—`.

Значение uptime процесса не должно быть отрицательным.

#### Критерии приёмки

- [ ] При доступности отображается время запуска процесса.
- [ ] При доступности отображается относительный uptime процесса.
- [ ] Uptime процесса не имеет отрицательного значения.
- [ ] При недоступности времени запуска отображается `—`.

---

### FR-008.6. Отображение родительского процесса и потоков

**Приоритет:** Should  

Для каждого процесса приложение должно отображать:

- PPID.
- Имя процесса-родителя, если агент может его определить в пределах текущего снимка.
- Количество потоков процесса.

Если родительский процесс завершился до формирования снимка или недоступен,
приложение должно отображать PPID и значение `Родитель не найден`.

Если число потоков определить невозможно, приложение должно отображать `—`.

#### Критерии приёмки

- [ ] Для каждого процесса отображается PPID.
- [ ] При доступности отображается имя процесса-родителя.
- [ ] При отсутствии родителя отображается понятная подпись.
- [ ] При доступности отображается число потоков.
- [ ] Недоступность числа потоков не скрывает другие данные процесса.

---

### FR-008.7. Отображение использования CPU процессом

**Приоритет:** Must  

Приложение должно отображать текущее использование CPU каждым процессом
в процентах.

Значение CPU процесса должно рассчитываться ServerDeck Agent по разнице
процессорного времени процесса между двумя последовательными измерениями.

Для процессов, появившихся после предыдущего измерения, приложение должно
отображать `—`, `Новый процесс` или иное единое состояние до получения
второго измерения.

Значение CPU процесса может превышать 100% на многоядерной системе,
если агент использует суммарное потребление нескольких логических CPU.
Выбранная модель расчёта должна быть единой для всех экранов приложения.

#### Критерии приёмки

- [ ] Для процесса с двумя измерениями отображается CPU-потребление.
- [ ] Для нового процесса до второго измерения не отображается вымышленный процент CPU.
- [ ] Значение CPU содержит символ `%`.
- [ ] Правило обработки значений выше 100% документировано в контракте агента.
- [ ] Ошибка расчёта CPU одного процесса не скрывает остальные процессы.

---

### FR-008.8. Отображение использования памяти процессом

**Приоритет:** Must  

Приложение должно отображать использование оперативной памяти процессом
как значение RSS.

RSS должен передаваться агентом в байтах и форматироваться клиентом
в KB, MB или GB.

При недоступности RSS приложение должно отображать `—`.

Приложение не должно суммировать RSS процессов для представления общего
использования памяти сервера, так как страницы памяти могут разделяться
между несколькими процессами.

#### Критерии приёмки

- [ ] Для каждого процесса при доступности отображается RSS.
- [ ] Размер памяти отображается в подходящей единице измерения.
- [ ] При недоступности RSS отображается `—`.
- [ ] В интерфейсе RSS не называется «точным суммарным потреблением памяти всеми процессами».

---

### FR-008.9. Отображение связи процесса с systemd, Docker и cgroup

**Приоритет:** Should  

Если ServerDeck Agent может определить принадлежность процесса, приложение
должно отображать одну или несколько связей:

- Имя systemd unit.
- Имя или идентификатор Docker-контейнера.
- Путь или идентификатор cgroup.

Приоритет отображения:

1. Docker-контейнер, если процесс принадлежит контейнеру.
2. systemd unit, если процесс принадлежит service unit.
3. cgroup, если более понятная связь не определена.

Если связь определить невозможно, приложение не должно отображать ошибку
и не должно предполагать принадлежность процесса к systemd или Docker.

#### Критерии приёмки

- [ ] Для процесса Docker-контейнера при доступности отображается контейнер.
- [ ] Для процесса systemd service при доступности отображается имя unit.
- [ ] При отсутствии Docker не отображается ошибка.
- [ ] При невозможности определить связь элемент не отображается.
- [ ] Неверно определённая связь не отображается как достоверная.

---

### FR-008.10. Поиск процессов

**Приоритет:** Must  

Пользователь должен иметь возможность искать процессы по:

- Имени процесса.
- PID.
- Имени пользователя.
- Имени systemd unit, если связь определена.
- Имени Docker-контейнера, если связь определена.

Поиск должен выполняться агентом до применения пагинации.

Поиск по текстовым полям должен быть регистронезависимым.

#### Критерии приёмки

- [ ] Пользователь может найти процесс по точному PID.
- [ ] Пользователь может найти процесс по части имени.
- [ ] Поиск не зависит от регистра.
- [ ] При поиске по имени пользователя отображаются процессы этого пользователя.
- [ ] При пустом запросе отображается полный список.
- [ ] При отсутствии результатов отображается пустое состояние поиска.

---

### FR-008.11. Сортировка списка процессов

**Приоритет:** Must  

Пользователь должен иметь возможность сортировать процессы по следующим полям:

- Использование CPU.
- Использование RAM.
- Имя процесса.
- PID.
- Время запуска.

По умолчанию процессы должны сортироваться по использованию CPU
в порядке убывания.

При одинаковом значении основного поля сортировки процессы должны
сортироваться по PID в порядке возрастания.

#### Критерии приёмки

- [ ] По умолчанию процессы с большим CPU отображаются выше.
- [ ] Пользователь может выбрать сортировку по RAM.
- [ ] Пользователь может выбрать сортировку по имени.
- [ ] Пользователь может выбрать сортировку по PID.
- [ ] Пользователь может выбрать сортировку по времени запуска.
- [ ] При одинаковых значениях применяется сортировка по PID.
- [ ] Выбранная сортировка сохраняется при загрузке следующей страницы.

---

### FR-008.12. Обработка завершившихся процессов

**Приоритет:** Must  

Если процесс завершился после формирования снимка, приложение должно
отображать данные процесса как сведения на момент снимка и не должно
считать это ошибкой.

При попытке загрузить следующую страницу или обновить список завершившийся
процесс может отсутствовать в новом снимке.

Приложение не должно сохранять завершившийся процесс как активный после
успешного обновления списка.

#### Критерии приёмки

- [ ] Завершившийся после снимка процесс не вызывает ошибку отображения.
- [ ] После обновления завершившийся процесс исчезает из актуального списка.
- [ ] Новый процесс может появиться после обновления.
- [ ] Список не содержит дубликаты PID внутри одного снимка.

---

### FR-008.13. Защита чувствительной процессной информации

**Приоритет:** Must  

Приложение и ServerDeck Agent не должны передавать или отображать:

- Полную командную строку процесса.
- Аргументы командной строки.
- Переменные окружения.
- Содержимое открытых файлов.
- Секреты, токены, пароли или ключи.
- Пути, содержащие конфиденциальные данные, если они не требуются
  для отображения имени процесса.

Агент должен передавать только минимально необходимый набор процессных данных,
определённый требованиями `FR-008.3`–`FR-008.9`.

#### Критерии приёмки

- [ ] В ответе API списка процессов отсутствует полная командная строка.
- [ ] В ответе API отсутствуют environment variables.
- [ ] В ответе API отсутствуют секреты и токены.
- [ ] На карточке процесса отображается только безопасное имя процесса.

---
---

### FR-008.14. Завершение процесса

**Приоритет:** Should

Пользователь должен иметь возможность отправить выбранному процессу сигнал
завершения после явного подтверждения.

- Поддерживаются операции `TERM` (SIGTERM) и `KILL` (SIGKILL) как отдельные
  именованные действия; `KILL` требует отдельного предупреждения о
  принудительном завершении.
- Завершение процесса с PID 1 не допускается.
- Операция выполняется через API агента как именованная операция с параметром
  PID и требует права `processes:control`.
- Результат операции должен корректно обрабатывать ситуацию, когда процесс
  завершился между отображением списка и подтверждением пользователя.
- Операция записывается в аудит агента.

#### Критерии приёмки

- [ ] Пользователь с правом `processes:control` может отправить SIGTERM выбранному процессу после подтверждения.
- [ ] Пользователь без права `processes:control` не видит доступного действия завершения.
- [ ] Попытка завершения PID 1 отклоняется.
- [ ] Завершённый процесс исчезает из списка или отображает статус завершения.
- [ ] Процесс, завершившийся до подтверждения, даёт понятную ошибку без ложного сообщения об успехе.

## FR-009. Модульная система и плагины

**Приоритет:** Must  

### Цель

ServerDeck должен предоставлять модульную архитектуру, позволяющую расширять
возможности управления сервером для сторонних утилит и сервисов, которые
не входят в базовую поставку.

Модуль состоит из двух связанных частей:

- **Клиентский UI-пакет (плагин)** — JSON-описание страниц, схем и локализации.
  Устанавливается в клиент локально и отрисовывается встроенными компонентами.
- **Серверный модуль** — реализация в агенте: получение данных и выполнение
  разрешённых действий.

Части связаны общим `module_id` и версионируемыми контрактами. Плагин не может
выполнять действий без серверного модуля.

Плагин позволяет добавить к ServerDeck:

- Страницы и разделы пользовательского интерфейса.
- Отображение статусов, метрик и событий сторонней утилиты.
- Формы настройки.
- Разрешённые действия управления.
- Интеграцию с API агента.
- Локализацию текстов.
- Описание требуемых разрешений.

Плагины не содержат и не исполняют произвольный код на устройстве клиента.
Интерфейс описывается декларативно и интерпретируется ядром клиента
в пределах Plugin SDK.

Основным источником интерфейса во время работы является локально установленный
пакет. Получение пакета (из файла, каталога или от агента) — отдельная операция
установки, а не часть обновления метрик. Установленный пакет не удаляется
автоматически по истечении срока.

### Область действия

Группа требований `FR-009` определяет:

- Формат и состав клиентского UI-пакета.
- Установку, проверку и удаление пакета.
- Модель декларативного интерфейса.
- Ограниченный набор действий и API-вызовов.
- Разрешения.
- Совместимость пакетов с версиями клиента и агента.
- Подпись, целостность и происхождение пакетов.
- Серверные модули в агенте.
- Изоляцию данных и аудит.

### Границы модуля

Каталог модулей сообщества (маркетплейс), публикация модулей, рейтинги
и автоматическое обновление внешних модулей не входят в текущий объём.
Архитектура должна допускать их появление в будущем без изменения
контрактов ядра.

Требования к текущей архитектуре:

- Базовые экраны ServerDeck (подключение, секреты, установка модулей,
  подтверждение опасных операций) встроены в клиент и не описываются
  импортируемыми пакетами.
- Ядро клиента отделено от модулей экранов и API-контрактов.
- API агента поддерживает регистрацию возможностей.
- Схемы данных и UI версионируются.
- Один встроенный демонстрационный модуль может быть добавлен для проверки
  Plugin SDK.
- Один пакет может быть установлен в нескольких версиях, если разные серверы
  требуют несовместимых версий серверного модуля.

---

### FR-009.1. Формат пакета плагина

**Приоритет:** Must  

Плагин ServerDeck должен распространяться как пакет с декларативными
ресурсами и манифестом:

```text
module-package/
    manifest.json
    pages/
    schemas/
    locales/
    assets/
```

Пакет плагина не должен содержать исполняемый код, включая:

- сценарии и разметку, требующие исполнения или интерпретации как код;
- APK, DEX, JAR и нативные библиотеки `.so`;
- исполняемые shell-скрипты.

Пакет может содержать:

- Манифест.
- Описания страниц и UI-компонентов.
- Описания API-операций.
- JSON Schema входных и выходных данных.
- Локализацию.
- Иконки и статические ресурсы.
- Подпись разработчика и контрольные суммы файлов.
- Документацию.

#### Критерии приёмки

- [ ] Плагин содержит манифест.
- [ ] Плагин не содержит исполняемого кода.
- [ ] Манифест содержит идентификатор, версию и информацию о совместимости.
- [ ] Манифест содержит перечень требуемых разрешений.
- [ ] Пакет может содержать только разрешённые типы файлов.
- [ ] Пакет с запрещённым исполняемым файлом отклоняется при установке.

---

### FR-009.2. Манифест плагина

**Приоритет:** Must  

Манифест должен содержать:

- `module_id` — уникальный идентификатор в формате reverse-domain,
  например `org.serverdeck.postgres`; общий для UI-пакета и серверного модуля.
- Отображаемое название и краткое описание.
- Версию пакета по Semantic Versioning.
- Версию схемы UI (`ui_schema_version`) и версию Plugin SDK.
- Требуемый диапазон версий API серверного модуля.
- Диапазон совместимых версий клиента и агента.
- Список используемых UI-компонентов.
- Идентификатор разработчика или издателя.
- Список требуемых разрешений.
- Описание страниц и доступных API-операций.
- Схемы входных и выходных данных.
- Контрольные суммы ресурсов и информацию о подписи.

#### Критерии приёмки

- [ ] Плагин без `module_id` не устанавливается.
- [ ] Плагин без версии не устанавливается.
- [ ] Плагин без указания версии Plugin SDK или `ui_schema_version` не устанавливается.
- [ ] Несовместимый с клиентом плагин не активируется.
- [ ] Плагин, чей диапазон API не поддерживается агентом, не активируется для этого сервера.
- [ ] Некорректный манифест возвращает понятную ошибку валидации.

---

### FR-009.3. Декларативный пользовательский интерфейс плагина

**Приоритет:** Must  

Плагин должен описывать интерфейс только декларативными компонентами из закрытого
реестра клиента. JSON-описание страницы задаёт структуру, порядок компонентов
и привязки к данным (`data_key`). Реализация компонентов находится в приложении
и использует Jetpack Compose и общую тему ServerDeck.

Описание интерфейса устанавливается локально в составе UI-пакета. Значения для
отображения поступают отдельно через API агента и не изменяют реестр компонентов
или реализацию интерфейса. Добавление нового типа компонента требует обновления
клиента; пакет модуля не может поставлять его исполняемую реализацию.

Plugin SDK должен предоставлять ограниченный набор компонентов:

- Заголовок и описание.
- Текстовое значение.
- Статус.
- Карточка.
- Список.
- Таблица (в том числе ключ–значение).
- Индикатор загрузки и прогресса.
- Кнопка действия.
- Поле ввода.
- Переключатель.
- Выпадающий список.
- Поле пароля.
- Диалог подтверждения.
- Блок ошибки.
- Пустое состояние.
- График временного ряда.

Плагин не должен:

- Содержать или исполнять программный код из UI-пакета или ответов агента.
- Загружать собственные классы, библиотеки или исполняемую реализацию компонентов.
- Получать прямой доступ к Android API, защищённому хранилищу, SSH-транспорту и файловой системе устройства.
- Самостоятельно выполнять сетевые запросы.
- Использовать сетевые адреса, отличные от адреса управляемого сервера.

Кнопка указывает `action_id`, а не адрес запроса. Клиентский диспетчер
действий сопоставляет `action_id` с зарегистрированной операцией текущего сервера
и модуля.

Строки, пришедшие в данных, отображаются как текст (`NFR-SEC-016`).

#### Критерии приёмки

- [ ] UI плагина формируется только из поддерживаемых декларативных компонентов.
- [ ] Неподдерживаемый компонент не отображается и вызывает ошибку совместимости.
- [ ] Плагин не получает доступ к нативным возможностям платформы.
- [ ] Плагин не может загрузить собственную исполняемую реализацию UI-компонента.
- [ ] Все сетевые запросы выполняются через контролируемый клиент ServerDeck.
- [ ] Действие кнопки выполняется только через зарегистрированный `action_id`.

---

### FR-009.4. Взаимодействие плагина с ServerDeck Agent

**Приоритет:** Must  

Плагин должен взаимодействовать с сервером только через зарегистрированные
операции API ServerDeck Agent, вызываемые по `action_id`.

Каждая операция должна содержать:

- Уникальный идентификатор операции.
- HTTP-метод или тип RPC-вызова.
- Версионированный маршрут API.
- JSON Schema входных параметров.
- JSON Schema ответа.
- Список требуемых разрешений.
- Признак изменения состояния сервера.
- Настройку тайм-аута.
- Набор нормализованных кодов ошибок.

Плагин не должен передавать агенту произвольную shell-команду или текст,
предназначенный для исполнения командной оболочкой.

#### Критерии приёмки

- [ ] Каждое действие плагина связано с зарегистрированной API-операцией.
- [ ] Неподдерживаемая операция не отправляется агенту.
- [ ] Входные параметры валидируются до отправки и агентом после получения.
- [ ] Операция без необходимых разрешений отклоняется.
- [ ] Плагин не может передать произвольную shell-команду.
- [ ] Ошибки агента преобразуются в безопасные пользовательские сообщения.

---

### FR-009.5. Подтверждение опасных действий плагина

**Приоритет:** Must  

Если API-операция плагина изменяет состояние сервера, пользователь должен
подтвердить действие перед его выполнением.

Перед подтверждением приложение должно отобразить:

- Название плагина.
- Название операции.
- Целевой сервер.
- Параметры операции без секретных значений.
- Возможные последствия.
- Действия «Подтвердить» и «Отмена».

Агент должен дополнительно проверять, что операция разрешена политикой
и соответствует объявленной схеме плагина.

#### Критерии приёмки

- [ ] Операция изменения состояния не выполняется без подтверждения.
- [ ] Диалог содержит название сервера и операции.
- [ ] Секретные параметры не отображаются в диалоге.
- [ ] Отмена не изменяет состояние сервера.
- [ ] Успешное и неуспешное действие записываются в аудит.

---

### FR-009.6. Разрешения плагина

**Приоритет:** Must  

Плагин должен явно объявлять требуемые разрешения в манифесте.

Plugin SDK должен поддерживать как минимум следующие разрешения:

- `server:read` — чтение базовой информации о сервере.
- `metrics:read` — чтение метрик.
- `processes:read` — чтение списка процессов.
- `services:read` — чтение статуса сервисов.
- `services:control` — управление разрешёнными сервисами.
- `logs:read` — чтение разрешённых логов.
- `files:read` — чтение файлов в разрешённых каталогах.
- `files:write` — изменение файлов в разрешённых каталогах.
- `network:read` — чтение сетевой информации.
- `modules:<id>:storage` — доступ к изолированному хранилищу плагина.
- `modules:<id>:<action>` — выполнение разрешённых действий плагина.

При установке плагина пользователь должен увидеть список запрошенных разрешений
и подтвердить их выдачу отдельно для каждого сервера.

Плагин не должен получать доступ к разрешениям, которые не были выданы
пользователем и не разрешены политикой агента.

#### Критерии приёмки

- [ ] Манифест содержит список требуемых разрешений.
- [ ] Пользователь видит запрашиваемые разрешения перед активацией.
- [ ] Разрешения выдаются отдельно для каждого сервера.
- [ ] Плагин без `files:read` не может запрашивать файловые данные.
- [ ] Плагин без `services:control` не может выполнять управление сервисом.
- [ ] Отзыв разрешения прекращает доступ плагина к соответствующей операции.

---

### FR-009.7. Изоляция данных плагинов

**Приоритет:** Must  

Каждый плагин должен иметь изолированное локальное хранилище.

Плагин не должен иметь доступ к:

- Токенам API других плагинов.
- SSH-учётным данным.
- Приватным ключам.
- Локальным данным других серверов без явно выданного разрешения.
- Данным других плагинов.
- Системным журналам приложения, содержащим чувствительную информацию.

Плагин может получать только данные, возвращённые разрешёнными API-операциями,
и собственные данные из изолированного хранилища.

#### Критерии приёмки

- [ ] Один плагин не может прочитать локальные данные другого плагина.
- [ ] Плагин не получает SSH-ключи и пароли.
- [ ] Плагин не получает прямой доступ к токенам агента.
- [ ] Плагин получает данные только через разрешённые операции API.
- [ ] Удаление плагина удаляет его изолированное локальное хранилище после подтверждения пользователя.

---

### FR-009.8. Проверка подписи и целостности плагина

**Приоритет:** Must  

Перед установкой или обновлением плагина приложение должно проверить:

- Целостность пакета по контрольным суммам.
- Цифровую подпись пакета.
- Доверенность сертификата разработчика.
- Совместимость с версией приложения, Plugin SDK и ServerDeck Agent.
- Отсутствие запрещённых типов файлов.
- Корректность манифеста и схем.

Приложение не должно активировать плагин, если любая обязательная проверка
не пройдена.

#### Критерии приёмки

- [ ] Плагин с изменённым файлом не проходит проверку целостности.
- [ ] Неподписанный плагин не устанавливается в production-режиме.
- [ ] Плагин с недоверенной подписью не активируется.
- [ ] Несовместимый плагин не активируется.
- [ ] Пакет с запрещённым исполняемым файлом не устанавливается.
- [ ] Пользователь получает понятную причину отказа в установке.

---

### FR-009.9. Установка и активация плагина

**Приоритет:** Should  

Пользователь должен иметь возможность импортировать подписанный пакет плагина
из файла. Установка из доверенного каталога или предложения агента допускается
как дополнительный источник: полученный пакет сначала проверяется и устанавливается
локально.

Перед установкой приложение должно отобразить:

- Название и версию плагина.
- Имя разработчика.
- Источник получения плагина.
- Список запрашиваемых разрешений.
- Поддерживаемые версии клиента и агента.
- Список серверов, для которых будет активирован плагин.

После установки плагин должен быть отключён, пока пользователь явно
не активирует его для одного или нескольких серверов.

#### Критерии приёмки

- [ ] Пользователь видит информацию о плагине до установки.
- [ ] Пользователь подтверждает установку.
- [ ] Плагин не получает доступ к серверу без отдельной активации.
- [ ] Пользователь может активировать плагин для одного выбранного сервера.
- [ ] Плагин отображается в интерфейсе только после успешной активации.

---

### FR-009.10. Удаление и отключение плагина

**Приоритет:** Should  

Пользователь должен иметь возможность отключить плагин для конкретного сервера
или удалить плагин из приложения.

Отключение плагина не должно изменять состояние сторонней утилиты на сервере.

Удаление плагина из клиента не должно автоматически удалять
серверную интеграцию или стороннюю утилиту с сервера.

Перед удалением плагина приложение должно предупредить пользователя
об удалении локальных настроек и кэша плагина.

#### Критерии приёмки

- [ ] Пользователь может отключить плагин для одного сервера.
- [ ] После отключения экран плагина не доступен для данного сервера.
- [ ] Отключение не останавливает сторонний сервис на сервере.
- [ ] Пользователь может удалить плагин из приложения.
- [ ] Перед удалением пользователь видит предупреждение.
- [ ] Удаление очищает локальный кэш и изолированное хранилище плагина.

---

### FR-009.11. Серверные интеграционные модули

**Приоритет:** Must  

Плагин, требующий взаимодействия со сторонней серверной утилитой, должен
использовать серверный интеграционный модуль ServerDeck Agent.

Серверный интеграционный модуль должен:

- Регистрировать поддерживаемые возможности.
- Предоставлять типизированные API-операции.
- Проверять входные параметры.
- Проверять права пользователя.
- Выполнять только заранее определённые действия.
- Ограничивать время выполнения внешних команд.
- Не исполнять произвольный shell-текст, переданный клиентом.
- Записывать изменяющие операции в журнал аудита.
- Возвращать нормализованные ошибки.

Системные модули компилируются в общий процесс/выпуск Agent и не отключаются/удаляются отдельно. Дополнительные серверные модули вручную регистрируются через CLI, работают отдельными управляемыми процессами либо через доверенный внешний IPC. Подпись/манифест не являются sandbox или автоматической выдачей прав ОС; общий UID не обеспечивает изоляцию. Серверный код и клиентский UI имеют независимые жизненные циклы (AFR-003, AFR-051–AFR-059, NFR-SEC-012).

#### Критерии приёмки

- [ ] Серверный модуль регистрирует список поддерживаемых операций.
- [ ] Агент отклоняет запрос к незарегистрированной операции.
- [ ] Агент валидирует входные параметры.
- [ ] Агент проверяет разрешения до выполнения операции.
- [ ] Агент ограничивает время выполнения внешней команды.
- [ ] Агент не передаёт пользовательский ввод напрямую в shell.
- [ ] Изменяющая операция создаёт запись аудита.

---

### FR-009.12. Каталог плагинов сообщества

**Приоритет:** Could  

ServerDeck должен предоставлять каталог плагинов сообщества после появления
инфраструктуры проверки, публикации и отзыва плагинов.

Для каждого плагина каталог должен отображать:

- Название.
- Описание.
- Разработчика.
- Версию.
- Дату обновления.
- Совместимые версии ServerDeck и Agent.
- Список запрашиваемых разрешений.
- Инструкции по установке серверного интеграционного модуля.
- Статус проверки или верификации.
- Исходный код или ссылку на исходный репозиторий.
- Лицензию.

Каталог должен поддерживать отзыв плагина при обнаружении уязвимости,
нарушении политики или компрометации ключа разработчика.

#### Критерии приёмки

- [ ] Пользователь видит разработчика и версию до установки.
- [ ] Пользователь видит необходимые разрешения.
- [ ] Пользователь видит совместимость с текущими версиями приложения и агента.
- [ ] Отозванный плагин не может быть установлен.
- [ ] Пользователь получает уведомление о критичном отзыве уже установленного плагина.

---

### FR-009.13. Совместимость и обновление плагинов

**Приоритет:** Should  

Плагин должен указывать версии Plugin SDK, клиента и ServerDeck Agent,
с которыми он совместим.

Приложение не должно активировать плагин, если он требует неподдерживаемую
версию Plugin SDK или агента.

Перед обновлением плагина приложение должно проверить подпись, целостность,
совместимость и список изменённых разрешений.

Если новая версия запрашивает дополнительные разрешения, она не должна
активироваться до отдельного подтверждения пользователя.

Обновление устанавливается целиком и не заменяет работающую версию частично.
Предыдущая версия сохраняется для отката. Если два сервера требуют несовместимых
версий серверного модуля, клиент может хранить несколько версий пакета.

#### Критерии приёмки

- [ ] Несовместимый плагин не активируется.
- [ ] Обновление проходит проверку подписи и целостности.
- [ ] Новые разрешения требуют повторного подтверждения.
- [ ] При неудачном обновлении сохраняется работоспособная предыдущая версия плагина.
- [ ] Пользователь может откатиться к предыдущей версии пакета.
- [ ] Пользователь видит причину несовместимости.

## FR-010. Настройки приложения

**Приоритет:** Must

### Цель

Пользователь должен иметь возможность настраивать поведение, внешний вид
и параметры безопасности приложения. Настройки относятся к клиенту
и не требуют изменений на сервере.

### Область действия

Группа требований `FR-010` определяет:

- Структуру настроек: глобальные значения и переопределения на уровне сервера.
- Пороги статусов и интервалы обновления.
- Таймауты и параметры подключения к агенту.
- Внешний вид приложения.
- Безопасность и биометрию.
- Управление модулями.
- Управление локальным хранилищем данных.

---

### FR-010.1. Структура настроек

**Приоритет:** Must

Настройки разделены на два уровня:

- **Глобальные настройки** — применяются ко всем серверам.
- **Настройки сервера** — переопределяют отдельные глобальные значения
  для конкретного сервера.

Переопределяемыми являются параметры, зависящие от характеристик сервера:
интервалы опроса, таймауты и пороги статусов. Для каждого переопределяемого
параметра настройка сервера должна показывать, используется значение сервера
или глобальное, и позволять сбросить переопределение к глобальному значению.

#### Критерии приёмки

- [ ] Глобальные настройки применяются ко всем серверам без переопределений.
- [ ] Переопределение интервала опроса для одного сервера не влияет на остальные.
- [ ] Для каждого переопределения отображается его источник и доступен сброс к глобальному значению.

---

### FR-010.2. Пороги статусов сервера

**Приоритет:** Must

Пользователь должен иметь возможность изменять пороги предупреждения
статуса `WARNING` (см. FR-001.12) для метрик CPU, RAM, диска `/` и GPU,
глобально и на уровне отдельного сервера.

- Диапазон допустимых значений порога: от 50% до 100%.
- Значения по умолчанию: CPU 90%, RAM 90%, диск `/` 90%, GPU 95%.
- Изменение применяется к вычислению статуса без перезапуска приложения.

#### Критерии приёмки

- [ ] Пользователь может изменить порог каждой метрики глобально.
- [ ] Пользователь может переопределить порог для отдельного сервера.
- [ ] Значение вне допустимого диапазона отклоняется с понятной ошибкой.
- [ ] Изменённые пороги применяются к статусам без перезапуска.

---

### FR-010.3. Интервалы обновления

**Приоритет:** Must

Пользователь должен иметь возможность настраивать интервалы опроса агента:

- Интервал обновления карточек списка серверов. Значение по умолчанию: 5 секунд.
- Интервал обновления экрана подробностей открытого сервера. Значение по умолчанию: 2 секунды.
- Минимальный допустимый интервал ограничивается приложением, чтобы
  исключить избыточную нагрузку на агент и сеть.

Интервалы настраиваются глобально и переопределяются на уровне сервера.

#### Критерии приёмки

- [ ] Пользователь может изменить интервал обновления карточек и подробностей.
- [ ] Интервал меньше минимально допустимого отклоняется с понятной ошибкой.
- [ ] Переопределение интервала для сервера не влияет на остальные серверы.

---

### FR-010.4. Таймауты и устаревание данных

**Приоритет:** Must

Пользователь должен иметь возможность настраивать:

- Таймаут запроса к агенту. Значение по умолчанию: 10 секунд.
- Интервал актуальности успешного ответа, после которого сервер получает
  статус `OFFLINE` (см. FR-001.12). Значение по умолчанию: 60 секунд.

Оба параметра настраиваются глобально и переопределяются на уровне сервера.

#### Критерии приёмки

- [ ] Пользователь может изменить таймаут и интервал актуальности.
- [ ] Слишком малый интервал актуальности относительно интервала опроса предупреждается пользователем.
- [ ] Изменённые значения применяются к вычислению статуса без перезапуска.

---

### FR-010.5. Внешний вид

**Приоритет:** Should

Пользователь должен иметь возможность настраивать:

- Тему оформления: светлая, тёмная, системная.
- Единицы отображения сетевого трафика: байты или биты.
- Единицы отображения температуры: Цельсий или Фаренгейт.
- Формат времени и язык интерфейса.

#### Критерии приёмки

- [ ] Смена темы применяется без перезапуска приложения.
- [ ] Выбранные единицы применяются ко всем экранам с соответствующими метриками.
- [ ] Настройки внешнего вида не влияют на данные, получаемые от агента.

---

### FR-010.6. Безопасность и биометрия

**Приоритет:** Must

Пользователь должен иметь возможность включать биометрическую защиту:

- Блокировка приложения при запуске.
- Подтверждение чувствительных действий, выбираемых пользователем:
  - Завершение процесса (FR-008.14).
  - Операции управления сервисами и модулями.
  - Файловые операции изменения и удаления (FR-007).
  - Просмотр секретов и токенов.
  - Запуск SSH-сессии в Termux (FR-011).

- Отключение биометрии должно требовать альтернативной защиты блокировки
  устройства и явного предупреждения.
- При недоступности биометрии приложение должно предлагать ввод кода
  блокировки устройства.

#### Критерии приёмки

- [ ] Пользователь может включить блокировку приложения при запуске.
- [ ] Пользователь может выбрать, какие действия требуют биометрического подтверждения.
- [ ] При включённой защите чувствительное действие не выполняется без успешного подтверждения.
- [ ] При недоступности биометрии доступен альтернативный способ разблокировки.

---

### FR-010.7. Управление модулями

**Приоритет:** Must

В настройках приложения пользователь должен видеть:

- Список установленных клиентских UI-пакетов модулей с версиями.
- Версию серверного контракта, с которой совместим каждый пакет.
- Возможность отката к предыдущей версии пакета.
- Возможность удаления пакета.

Управление установкой и обновлением пакетов определяется требованиями
модульной системы (FR-009); FR-010 определяет только экран управления.

#### Критерии приёмки

- [ ] Отображается список установленных пакетов с версиями.
- [ ] Пользователь может откатиться к предыдущей версии пакета.
- [ ] Пользователь может удалить установленный пакет.

---

### FR-010.8. Локальное хранение данных

**Приоритет:** Should

Пользователь должен иметь возможность:

- Видеть объём локального кэша метрик и истории на устройстве.
- Задавать лимит кэша и очищать его.

#### Критерии приёмки

- [ ] Отображается объём, занимаемый локальными данными.
- [ ] Пользователь может задать лимит кэша.
- [ ] Очистка кэша не удаляет настройки, записи серверов и секреты.

---

### FR-010.9. Хранение и перенос настроек

**Приоритет:** Should

- Настройки хранятся локально на устройстве и переживают обновление приложения.
- Секреты и токены не входят в состав переносимых настроек.
- Настройки не содержат данных, требующих синхронизации с сервером.

#### Критерии приёмки

- [ ] Настройки сохраняются между запусками приложения.
- [ ] Обновление приложения не сбрасывает настройки.
- [ ] Экспорт настроек, если он реализован, не содержит секретов и токенов.

## FR-011. SSH-терминал сервера через Termux

**Приоритет:** Should  

### Цель

Пользователь должен иметь возможность открыть интерактивную SSH-сессию
выбранного сервера из карточки сервера, не вводя адрес вручную.

### Область действия

На Android терминал реализуется через запуск SSH-сессии во внешнем приложении
Termux. SSH-терминал является каналом, независимым от агента: он работает
и при недоступном агенте.

Встроенный SSH-терминал внутри клиента не входит в текущий объём. Архитектура
должна допускать его появление: клиент работает с терминалом через абстрактный
интерфейс транспорта (`SshTransport`), а запуск Termux является одной из его
реализаций («внешний терминал»).

### Общие определения

- **Termux** — внешнее Android-приложение с командной строкой и SSH-клиентом.
- **Запуск сессии** — передача Termux команды `ssh` с параметрами сервера
  через `RUN_COMMAND` Intent.
- **Параметры запуска** — адрес, SSH-порт и имя пользователя из записи сервера.

---

### FR-011.1. Запуск SSH-сессии в Termux

**Приоритет:** Should  

Клиент должен предоставлять действие «Открыть SSH в Termux» в карточке
и меню сервера.

При запуске клиент:

1. Показывает название сервера и параметры запуска.
2. Запрашивает биометрическое или иное локальное подтверждение, если оно
   включено в настройках (`FR-010.6`).
3. Передаёт Termux программу `ssh` и массив аргументов: порт, пользователь
   и адрес.
4. Termux открывает интерактивную сессию с подключением к этому серверу.

Клиент передаёт программу и аргументы раздельно и не использует
промежуточную командную строку `sh -c "..."`. Перед передачей адрес,
пользователь и порт проходят валидацию, соответствующую `FR-002.2`–`FR-002.4`.

Клиент не передаёт в Termux пароли, приватные ключи и парольные фразы.
Аутентификацию и проверку ключа сервера выполняет SSH-клиент Termux.

Биометрия подтверждает запуск сессии из ServerDeck; она не защищает сам Termux
и уже открытые в нём сессии.

#### Критерии приёмки

- [ ] Действие запуска доступно для сервера с заполненными параметрами SSH.
- [ ] Перед запуском отображаются название сервера и параметры подключения.
- [ ] При включённой защите запуск требует успешного локального подтверждения.
- [ ] Отказ или ошибка подтверждения не запускают сессию.
- [ ] Termux получает программу `ssh` и массив аргументов без интерполяции в командную строку.
- [ ] Intent не содержит пароля, ключа и парольной фразы.
- [ ] Некорректные параметры запуска отклоняются до отправки в Termux.

---

### FR-011.2. Проверка готовности Termux

**Приоритет:** Should  

Перед запуском клиент должен определить, что Termux установлен и интеграция
разрешена: приложение доступно, выдано разрешение `com.termux.permission.RUN_COMMAND`,
в настройках Termux включена внешняя интеграция (`allow-external-apps=true`).

Если условия не выполнены, клиент должен показать пошаговую инструкцию,
а не молча завершить действие.

Клиент должен описывать, что SSH-ключ для сервера настраивается в Termux
пользователем, а пароль или парольная фраза вводятся в Termux.

#### Критерии приёмки

- [ ] При отсутствии Termux клиент предлагает его установить и показывает инструкцию.
- [ ] При отсутствии разрешения или настройки интеграции отображается инструкция.
- [ ] Клиент объясняет, что SSH-данные вводятся в Termux, а не в ServerDeck.
- [ ] Недоступность Termux не влияет на остальные функции клиента.

---

### FR-011.3. Интерфейс SSH-транспорта

**Приоритет:** Should  

Клиент должен обращаться к SSH-возможностям через интерфейс платформенного
адаптера, не привязанный к конкретной реализации:

- Выполнение команды на сервере (для установки, обновления и удаления агента,
  `FR-002`).
- Запуск внешнего терминала (Termux).
- Открытие встроенной интерактивной сессии — зарезервировано для будущей
  реализации.

#### Критерии приёмки

- [ ] Функции установки и удаления агента используют общий интерфейс SSH-транспорта.
- [ ] Запуск Termux вынесен в отдельную реализацию интерфейса.
- [ ] Добавление встроенного терминала не требует изменения функций FR-002.
