# Требования безопасности

Актуализация 12 октября 2026 года: для серверных границ действуют [ASEC Agent](<Документация ServerDeck Agent/4. Требования безопасности.md>) и [дополнение клиентских контрактов](<Документация ServerDeck Agent/12. Согласование с клиентом.md>). Согласованные root/права/общая политика/модули/аудит/обновление не переопределяются старыми клиентскими формулировками. Испытания реализации ещё не выполнены.

## Область действия документа

Требования безопасности являются сквозными для всей системы и охватывают
клиент, ServerDeck Agent и их взаимодействие. Для каждого требования указана
область: **Клиент**, **Агент** или **Обе стороны**. Требования к агенту,
относящиеся к его функциональному поведению, детализируются в отдельном
документе агента; здесь фиксируются только требования безопасности.

Клиент реализуется как нативное Android-приложение на Kotlin и Jetpack Compose.
Работа с секретами, биометрией, SSH и системными Intent выполняется встроенными
сервисами приложения. Внешние JSON-описания модулей не получают прямого доступа
к этим сервисам.

Документ ссылается на функциональные требования: `FR-007.24` (файловые
разрешения), `FR-008.13` (защита процессной информации), `FR-008.14`
(завершение процесса), `FR-010.6` (биометрия).

## Модель угроз

Защищаемые активы:

- Токены устройств и доступ к управлению серверами.
- Метрики, логи, списки процессов и файловая структура сервера.
- Целостность установки агента и клиентских пакетов модулей.

Рассматриваемые злоумышленники:

- Похититель разблокированного или заблокированного устройства.
- Злоумышленник в локальной сети или на пути трафика (MITM).
- Скомпрометированный или враждебный сервер, к которому подключился клиент.
- Враждебный автор модуля.
- Вредоносное содержимое в данных сервера: имена процессов, строки логов,
  имена файлов (инъекции в интерфейс).

Границы доверия:

- Клиент ↔ Агент (сеть, TLS).
- Клиент ↔ Termux (Intent, без передачи секретов).
- Клиент ↔ сервер по SSH при установке, обновлении и удалении агента (проверка ключа сервера).
- Агент ↔ серверный модуль (межпроцессное взаимодействие).
- Источник пакета модуля ↔ установленный пакет (проверка целостности).

Базовые допущения:

- Устройство пользователя может быть потеряно.
- Сервер может быть скомпрометирован независимо от ServerDeck.
- Локальная сеть не считается доверенной.

## Хранение секретов на устройстве

### NFR-SEC-001. Хранение учётных данных

**Приоритет:** Must
**Область:** Клиент

Клиент должен хранить отзывные токены устройств агента только в зашифрованном
виде: записи шифруются ключом, размещённым в Android Keystore.

SSH-пароли, приватные SSH-ключи, парольные фразы и пароль `sudo` клиентом
не сохраняются. Они вводятся пользователем для конкретной операции установки,
обновления или удаления агента и существуют только в памяти на время операции
(NFR-SEC-020, NFR-SEC-021). Интерактивные SSH-сессии выполняются в Termux,
и их учётные данные обслуживаются Termux (NFR-SEC-015).

Секретные значения не должны записываться:

- В открытый вид в локальной базе или настройках приложения.
- В незашифрованные файлы, настройки и другие локальные хранилища приложения.
- В логи приложения и отчёты об ошибках.
- В кэш интерфейса.
- В резервные копии в пригодном к использованию виде: ключи Android Keystore
  не входят в резервные копии ОС, поэтому зашифрованные записи
  невосстановимы на другом устройстве. После смены устройства требуется
  повторный pairing.

Приложение должно маскировать секретные поля интерфейса и не передавать
секреты в сообщениях об ошибках.

#### Критерии приёмки

- [ ] Токен устройства не присутствует в открытом виде в хранилище приложения.
- [ ] Клиент не сохраняет SSH-пароли, приватные ключи, парольные фразы и пароль `sudo` в постоянном хранилище.
- [ ] Сообщение об ошибке подключения не содержит токен или парольную фразу.
- [ ] Восстановление приложения из резервной копии не восстанавливает работоспособные токены устройств.
- [ ] После удаления сервера его токен недоступен приложению.

---

### NFR-SEC-002. Отсутствие секретов в сборке клиента

**Приоритет:** Must
**Область:** Клиент

Клиентская сборка не должна содержать встроенных секретов, ключей, токенов
или паролей, включая отладочные и тестовые значения. Допускаются только
публичные значения: список известных endpoint’ов обновлений, публичные ключи
для проверки подписей пакетов.

#### Критерии приёмки

- [ ] Сборка клиента не содержит строк, похожих на секреты, при проверке сканером секретов.
- [ ] Публичный ключ проверки подписей в сборке не позволяет подписывать пакеты.

## Транспорт и подключение

### NFR-SEC-003. Обязательный TLS

**Приоритет:** Must
**Область:** Обе стороны

Все соединения клиента с агентом должны использовать HTTPS и WSS.
Незашифрованные HTTP/WS-соединения не допускаются, включая локальную сеть.

Клиент должен проверять валидность сертификата агента и отклонять соединение
при ошибках проверки. Интерфейс не должен содержать опции «игнорировать
ошибки сертификата».

Для самоподписанных сертификатов допускается закрепление отпечатка
сертификата при первом подключении (pairing): отпечаток сохраняется
в записи сервера и проверяется при всех последующих соединениях. Неожиданная
смена отпечатка блокирует подключение с явным предупреждением.

#### Критерии приёмки

- [ ] Соединение по HTTP или WS отклоняется клиентом.
- [ ] Соединение с недействительным сертификатом отклоняется без возможности обхода.
- [ ] Смена отпечатка закреплённого сертификата блокирует подключение с предупреждением.

---

### NFR-SEC-004. Проверка доступа к API

**Приоритет:** Must
**Область:** Агент

Агент должен проверять действующий токен устройства перед предоставлением
доступа к защищённым операциям API и подпискам WSS. Идентификатор приложения,
версия клиента и другие описательные заголовки не являются доказательством
подлинности устройства и не заменяют токен или проверку прав.

Для первичного pairing действует отдельная проверка одноразового кода
по NFR-SEC-006. Отсутствие регистрации устройства не открывает доступ
к метрикам или управляющим операциям.

#### Критерии приёмки

- [ ] Запрос к защищённому API без действующего токена отклоняется до выполнения операции.
- [ ] Подстановка идентификатора или версии официального клиента не даёт доступа без токена.
- [ ] Pairing до регистрации устройства не предоставляет доступ к защищённым операциям.

---

### NFR-SEC-005. Лимиты и защита от перегрузки

**Приоритет:** Must
**Область:** Агент

Агент должен применять:

- Ограничение частоты запросов на токен и на адрес.
- Ограничение размера тела запроса и ответа.
- Ограничение количества одновременных WebSocket-соединений и подписок.
- Ограниченные очереди сообщений: при переполнении подписка отбрасывается
  или закрывается, а не накапливает метрики в памяти бесконечно.

#### Критерии приёмки

- [ ] Превышение частоты запросов возвращает ограничение с кодом ошибки.
- [ ] Слишком большое тело запроса отклоняется.
- [ ] Превышение числа WebSocket-соединений отклоняет новые соединения.
- [ ] Переполнение очереди подписки не приводит к неограниченному росту памяти.

## Pairing и устройства

### NFR-SEC-006. Pairing через одноразовый код

**Приоритет:** Must
**Область:** Обе стороны

Первое подключение клиента к агенту должно выполняться через pairing:

- Агент отображает одноразовый короткоживущий код (ограниченное число
  попыток и срок действия).
- Клиент передаёт код по защищённому соединению (NFR-SEC-003).
- Агент создаёт отдельную учётную запись устройства и выдаёт отзывной токен.
- Код не допускает повторного использования.

Аутентификация устройства токеном обязательна для всех API и WebSocket.

#### Критерии приёмки

- [ ] Повторное использование pairing-кода отклоняется.
- [ ] Истёкший код отклоняется.
- [ ] Превышение числа неудачных попыток аннулирует код.
- [ ] API без аутентификации недоступен, кроме эндпоинта pairing.

---

### NFR-SEC-007. Отзыв устройств и сессий

**Приоритет:** Must
**Область:** Обе стороны

Пользователь должен иметь возможность просмотреть активные устройства
и отозвать токен конкретного устройства.

Отзыв должен:

- Немедленно запрещать дальнейшие API-запросы и закрыть активные
  WebSocket-соединения отозванного устройства.
- Быть доступен не только из клиента: при потере единственного устройства
  отзыв выполняется на самом сервере через CLI агента.

#### Критерии приёмки

- [ ] Список устройств показывает активные токены со временем последнего использования.
- [ ] После отзыва API-запросы отклоняются.
- [ ] После отзыва WebSocket-соединение закрывается агентом.
- [ ] Отзыв возможен через CLI агента без клиента.

## Авторизация и аудит

### NFR-SEC-008. Проверка прав на каждую операцию

**Приоритет:** Must
**Область:** Агент

Агент должен проверять право на каждую запрошенную операцию на стороне
сервера. Скрытие кнопки в интерфейсе не является контролем доступа.

Права разделяются по областям, например: `metrics:read`, `processes:read`,
`processes:control`, `services:control`, `files:read`, `files:write`,
`modules:<id>:<action>`.

WebSocket-сообщения должны проходить ту же проверку прав, что и REST-запросы.

#### Критерии приёмки

- [ ] Запрос операции без права отклоняется агентом.
- [ ] Права проверяются отдельно для каждого сообщения WebSocket.
- [ ] Клиент с правом только на чтение не может выполнить управляющую операцию, обратившись к API напрямую.

---

### NFR-SEC-009. Аудит операций

**Приоритет:** Must
**Область:** Агент

Агент должен записывать в журнал аудита все управляющие операции:
кто, когда, какое устройство, какая операция, над каким объектом, результат.

Журнал аудита не должен содержать секреты: токены, пароли, содержимое
ключей, аргументы команд с чувствительными значениями.

#### Критерии приёмки

- [ ] Управляющая операция отражается в аудите с устройством-инициатором.
- [ ] Операции чтения метрик не заполняют журнал целиком.
- [ ] В аудите нет секретных значений.

## Изоляция удалённого кода и модули

### NFR-SEC-010. Декларативный интерфейс без исполняемого кода

**Приоритет:** Must
**Область:** Клиент

Клиент должен воспринимать внешние описания (JSON-пакеты модулей, данные
агента) как данные, а не как код.

Запрещено:

- Исполнять программный код, полученный от агента или из пакета модуля.
- Загружать из пакета собственные классы, байткод, нативные библиотеки
  или реализации UI-компонентов.
- Интерпретировать внешние строки как команды, выражения или инструкции
  построения интерфейса вне проверенной схемы.
- Предоставлять внешним описаниям прямой доступ к Android API, защищённому
  хранилищу, SSH-транспорту, файловой системе устройства и сетевым адресам,
  отличным от адреса управляемого сервера.

JSON-описание может ссылаться только на компоненты Jetpack Compose из встроенного
реестра клиента. Оно проходит проверку схемы и совместимости до отображения.
Данные агента подставляются в разрешённые привязки `data_key` и не изменяют
исполняемую реализацию компонентов. Действия указываются идентификатором
`action_id` и выполняются диспетчером клиента в контексте текущего сервера
и модуля.

#### Критерии приёмки

- [ ] UI-пакет с исполняемыми ресурсами или неподдерживаемым типом компонента отклоняется.
- [ ] Поля, содержащие программный код или разметку, не исполняются; допустимые строковые значения отображаются как текст.
- [ ] Имя процесса или строка лога, содержащие разметку, отображаются как текст.
- [ ] Внешнее описание не может вызвать произвольный API-запрос, минуя диспетчер действий.

---

### NFR-SEC-011. Подпись и целостность пакетов модулей

**Приоритет:** Must
**Область:** Обе стороны

Установка и обновление пакетов модулей (клиентских UI-пакетов и серверных
модулей) должны проверять подпись и целостность пакета.

Обновление, запрашивающее новые разрешения, не активируется до отдельного
подтверждения пользователя. При неудачном обновлении сохраняется работоспособная
предыдущая версия.

#### Критерии приёмки

- [ ] Пакет с нарушенной подписью или контрольной суммой не устанавливается.
- [ ] Обновление с новыми разрешениями требует повторного подтверждения.
- [ ] Неудачное обновление оставляет предыдущую версию работоспособной.

---

### NFR-SEC-012. Изоляция серверных модулей

**Приоритет:** Must
**Область:** Агент

Дополнительные серверные модули выполняются отдельно от ядра, обычно под выбранным пользователем Agent. Внешний запуск другим пользователем допускается при доверенном IPC и фактических правах. Выделенный пользователь автоматически не создаётся. Общий UID и отдельный процесс не являются sandbox; capabilities ограничивают маршрутизацию ядра, а не все действия кода. При доступной делегации cgroup применяются согласованные лимиты, при отсутствии явно показывается отсутствие изоляции ресурсов. Системные модули работают в процессе Agent (AFR-003/051–AFR-057/070, ASEC-020–ASEC-022).

#### Критерии приёмки

- [ ] Сторонний модуль не выполняется в процессе ядра агента.
- [ ] Контракт/IPC отклоняют невыданные операции; ограничения ОС и отсутствие sandbox описаны честно.
- [ ] Обработанный сбой/зависание дополнительного IPC не останавливает остальные функции; очереди/рестарты ограничены, общий UID не объявляется защитой от злонамеренного кода.

## Операционная безопасность агента

### NFR-SEC-013. Минимальные привилегии агента

**Приоритет:** Must
**Область:** Агент

Agent работает под существующим выбранным пользователем ОС. Root допустим по явному выбору с предупреждением. Штатные действия используют фактические права процесса/групп и серверную политику; автоматическое sudo и постоянный helper отсутствуют (AFR-004, ASEC-001). Служебный пользователь автоматически не создаётся.

API агента не должен содержать операций выполнения произвольных команд
или скриптов: доступны только именованные операции с параметрами.

#### Критерии приёмки

- [ ] Runtime user соответствует выбору; root имеет предупреждение, sudo установщика не меняет этот выбор.
- [ ] В API нет операции передачи произвольной командной строки.
- [ ] Недостаток прав даёт отказ без sudo/helper; файловые/аудитные guards действуют также при root.

---

### NFR-SEC-014. Изоляция сервиса агента

**Приоритет:** Should
**Область:** Агент

Hardening systemd применяется после проверки совместимости с выбранными файловыми корнями, процессами и GPU. Нельзя незаметно скрыть согласованные ресурсы или выдать новые capabilities. Ограничения API действуют независимо от ОС-профиля; профиль не объявляется полной sandbox.

#### Критерии приёмки

- [ ] Профиль службы проверен с разрешёнными корнями/источниками; ограничения и отсутствие изоляции отражены явно.
- [ ] Агент функционирует без избыточных capabilities.

## Termux и SSH-терминал

### NFR-SEC-015. Передача параметров в Termux без секретов

**Приоритет:** Must
**Область:** Клиент

При запуске SSH-сессии в Termux клиент должен передавать только
адрес, имя пользователя и порт.

Запрещено передавать:

- Пароли и парольные фразы.
- Приватные ключи.
- Командные строки оболочки (`sh -c "..."`) с интерполяцией параметров.

Параметры Intent могут попадать в журналы Termux и сообщения об ошибках,
поэтому секреты в них недопустимы. Проверка ключа сервера и аутентификация
SSH выполняются средствами Termux.

Секреты, введённые для установки агента (NFR-SEC-020), не передаются в Termux.

Запуск SSH-сессии из клиента подтверждается биометрией согласно `FR-010.6`;
биометрия защищает запуск из ServerDeck и не является защитой самого Termux.

#### Критерии приёмки

- [ ] Intent содержит только программу, адрес, пользователя и порт.
- [ ] Парольная фраза запрашивается внутри Termux, а не передаётся клиентом.
- [ ] Передача параметров в Termux требует биометрического подтверждения при включённой защите.

## Отображение данных

### NFR-SEC-016. Безопасное отображение внешних данных

**Приоритет:** Must
**Область:** Клиент

Все строки, полученные от агента (имена процессов, строки логов, имена
файлов и каталогов, сообщения модулей), должны отображаться как обычный текст
в компонентах Compose. Разметка, командные последовательности и выражения
в этих строках не интерпретируются и не меняют поведение интерфейса.

Чувствительная процессная информация ограничивается согласно `FR-008.13`.

#### Критерии приёмки

- [ ] Строка лога с разметкой или программным кодом отображается как обычный текст.
- [ ] Имя файла с управляющими символами не ломает разметку экрана.

## Установка и обновление

### NFR-SEC-017. Целостность дистрибутива агента

**Приоритет:** Must
**Область:** Обе стороны

Установка и обновление агента должны проверять целостность и подлинность
дистрибутива: контрольные суммы и подписи опубликованных артефактов.

Скрипт установки не должен выполняться в обход проверки целостности
загружаемого пакета. Обновление агента не должно оставлять систему
в полурабочем состоянии: применяется атомарная замена с возможностью
отката к предыдущей версии.

#### Критерии приёмки

- [ ] Установка пакета с нарушенной подписью или суммой прерывается с понятной ошибкой.
- [ ] Неудачное обновление откатывает агента к работоспособной версии.

---

### NFR-SEC-018. Резерв идентификатора

Идентификатор не задаёт действующего требования и сохранён для стабильности
нумерации. Защита секретов нативного Android-клиента определяется NFR-SEC-001,
NFR-SEC-003 и NFR-SEC-020–023.

---

## Утерянное устройство

### NFR-SEC-019. Действия при потере устройства

**Приоритет:** Must
**Область:** Обе стороны

При потере устройства пользователь должен иметь возможность отозвать
все его токены без доступа к самому устройству (NFR-SEC-007), а данные
на устройстве должны быть защищены блокировкой ОС и шифрованием хранилища.

Приложение не должно увеличивать поверхность атаки по сравнению
с базовой защитой устройства: не выводить секреты на экран блокировки,
не показывать адреса серверов и метрики в системных уведомлениях
без явной настройки.

#### Критерии приёмки

- [ ] Отзыв всех токенов устройства возможен с сервера через CLI.
- [ ] Уведомления приложения не содержат адресов серверов и секретных данных.

## Установка, обновление и удаление агента по SSH

### NFR-SEC-020. Жизненный цикл SSH-данных установки

**Приоритет:** Must
**Область:** Клиент

SSH-данные установки (пароль, приватный ключ, парольная фраза, пароль `sudo`):

- Хранятся только в оперативной памяти на время операции.
- Не записываются в постоянное хранилище, кэш, журналы, отчёты об ошибках
  и резервные копии.
- Удаляются из памяти сразу после завершения, отмены или ошибки операции.
- Не передаются в Termux, модули и плагины.
- Не отображаются в открытом виде после ввода.

Любая следующая SSH-операция требует повторного ввода данных.

#### Критерии приёмки

- [ ] После завершения операции SSH-данные недоступны приложению.
- [ ] Повторная операция запрашивает данные заново.
- [ ] Секреты отсутствуют в журналах и сообщениях об ошибках.
- [ ] Приватный ключ не передаётся в Termux и не доступен плагинам.

---

### NFR-SEC-021. Передача привилегий (sudo)

**Приоритет:** Must
**Область:** Клиент

Пароль `sudo` вводится только в интерфейсе клиента после экрана с объяснением
назначения привилегий. Пароль передаётся серверу через стандартный ввод
команды `sudo`, а не как аргумент командной строки, и не выводится в журналы.

Привилегии используются только на время установки, обновления или удаления.
Штатная работа агента не требует `sudo` (NFR-SEC-013).

#### Критерии приёмки

- [ ] Пароль не присутствует в аргументах выполняемой на сервере команды.
- [ ] Пароль не логируется ни клиентом, ни установщиком.
- [ ] При входе под `root` пароль не запрашивается.
- [ ] Ошибка `sudo` не раскрывает введённый пароль.

---

### NFR-SEC-022. Проверка и закрепление ключа SSH-сервера

**Приоритет:** Must
**Область:** Клиент

Клиент должен показывать отпечаток ключа сервера при первом SSH-подключении
и закреплять его после подтверждения пользователя. При несовпадении ключа
последующее подключение блокируется с предупреждением о возможной подмене.
Продолжение возможно только после явного сброса отпечатка пользователем.

Отключение проверки ключа сервера не допускается.

#### Критерии приёмки

- [ ] При первом подключении отображается отпечаток и запрашивается подтверждение.
- [ ] Отпечаток проверяется при каждой SSH-операции.
- [ ] При несовпадении подключение блокируется.
- [ ] В интерфейсе нет опции «не проверять ключ сервера».

---

### NFR-SEC-023. Доверие к TLS-сертификату агента при автоматической установке

**Приоритет:** Must
**Область:** Клиент

При автоматической установке клиент должен получить отпечаток TLS-сертификата
агента по SSH-каналу с проверенным ключом сервера (NFR-SEC-022) и сверить его
с сертификатом, предъявленным агентом при pairing. Несовпадение прерывает
pairing. При ручной установке отпечаток подтверждается пользователем при
первом подключении (NFR-SEC-003).

#### Критерии приёмки

- [ ] Отпечаток сертификата, полученный по SSH, сверяется при pairing.
- [ ] Несовпадение отпечатков прерывает pairing с предупреждением.
- [ ] При ручной установке пользователь явно подтверждает отпечаток.

---

### NFR-SEC-024. Режим сетевого доступа по умолчанию

**Приоритет:** Must
**Область:** Обе стороны

Установщик не должен открывать порт агента без явного выбора пользователя.
Значением по умолчанию является наиболее ограниченный режим. Режим
«Любой адрес» требует предупреждения и явного подтверждения.

Правила firewall, созданные установщиком, должны удаляться при удалении агента.
Установщик не должен утверждать, что порт открыт, если правило не удалось
создать или firewall не поддерживается.

Для режима «Любой адрес» усиливаются ограничения pairing: короткий срок
действия кода и лимит попыток (NFR-SEC-006).

#### Критерии приёмки

- [ ] Без явного выбора правила firewall не изменяются.
- [ ] Режим «Любой адрес» требует подтверждения с предупреждением.
- [ ] При удалении агента созданные правила firewall удаляются.
- [ ] При неподдерживаемом firewall пользователь получает явное сообщение.

---

### NFR-SEC-025. Безопасное обновление и удаление агента

**Приоритет:** Must
**Область:** Обе стороны

Обновление агента не должно изменять конфигурацию, TLS-сертификат и токены
других устройств. Удаление агента должно предупреждать, что другие
подключённые устройства потеряют доступ. Клиент не должен понижать версию
агента без явного подтверждения пользователя.

При удалении сервера из клиента токен текущего устройства отзывается на агенте,
если агент доступен. Если он недоступен, пользователь получает предупреждение
об активном токене и инструкцию отзыва через CLI агента (NFR-SEC-007).

#### Критерии приёмки

- [ ] Обновление сохраняет сертификат и токены других устройств.
- [ ] Перед удалением агента отображается число других подключённых устройств.
- [ ] При удалении записи токен отзывается, если агент доступен.
- [ ] При недоступном агенте отображается предупреждение об активном токене.
