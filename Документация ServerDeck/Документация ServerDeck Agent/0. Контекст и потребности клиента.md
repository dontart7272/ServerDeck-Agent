## 1. Зачем нужен этот документ

Пользователь спроектировал основную часть мобильного приложения ServerDeck и хочет перейти к документации серверного агента. Перед проектированием API необходимо установить, какие данные требуются экранам, какие действия выполняет клиент и как обновляются результаты.

Текущий запрос пользователя:

> Разобраться, какие данные нужно запрашивать по API для каждого экрана. Пока не проектировать само API, а определить необходимые операции и то, какие данные они должны отдавать или принимать.

В новом чате следует использовать этот документ как отправную точку, проверяя подробности по исходным требованиям. Конкретные URL, HTTP-методы, JSON-схемы, сообщения WebSocket и внутреннее устройство агента пока не согласованы.

Обозначения статуса решений:

- **Принято** — решение пользователя или правило, уже закреплённое в действующих документах без отмеченного противоречия.
- **Предложение** — вариант из последнего обсуждения обмена данными, который ещё предстоит уточнить.
- **Открытый вопрос** — недостаток определения или противоречие, которое нельзя молча превратить в обязательное поведение.

## 3. Контекст и принятые решения

### 3.1. Продукт и платформа

- ServerDeck — мобильное приложение для мониторинга и управления собственными Linux-серверами и установленными на них утилитами.
- Проектируется полный запланированный продукт. Пользователь отказался от ограничения документации рамками MVP. Порядок проектирования и реализации допустим, сокращение требований под видом MVP — нет.
- Клиент: нативный Android, Kotlin и Jetpack Compose.
- Клиент распространяется подписанным APK через GitHub Releases. Публикация в Google Play и App Store не является целью текущего проекта.
- Поддержка других мобильных платформ не входит в обязательства текущей архитектуры.
- Агент: постоянно работающий сервис Linux с systemd. Требования упоминают Raspberry Pi и архитектуры ARM; точную матрицу дистрибутивов и архитектур нужно определить.
- Python + FastAPI указан как предпочтение, требующее сравнения с Go по распространению и эксплуатации. Это не окончательно выбранный стек агента.
- Обязательного центрального аккаунта и регистрации ServerDeck нет. Встроенный ИИ-помощник не предусмотрен.

### 3.2. Интерфейс и этап проектирования

- Дизайн создаётся в Stitch, реализация — общими компонентами Compose. Экспортированный HTML не является реализацией клиента.
- Актуальное визуальное направление — светлый полумультяшный стиль; подробности находятся в DESIGN.md и согласованных макетах.
- Пользователь считает допустимым начинать реализацию клиента без отрисовки всех экранов: недостающий интерфейс можно собрать из общей визуальной системы, используя документацию для поведения.
- Пользователю нужна практичная документация, по которой ИИ-агент сможет написать код. Не следует добавлять документы исключительно ради полноты формального комплекта.

### 3.3. Каналы взаимодействия

- Клиент обращается непосредственно к агенту выбранного сервера. Список сохранённых серверов находится на телефоне.
- Обмен с агентом использует HTTPS и WSS. REST API и подписки WebSocket должны иметь аутентификацию и проверку прав.
- SSH — независимый канал для установки, обновления, удаления и обслуживания агента.
- Интерактивный SSH-терминал запускается в Termux. Встроенный терминал не требуется.
- API агента предоставляет именованные разрешённые операции с параметрами. Передача произвольных shell-команд или скриптов не допускается.

### 3.4. Модульная система

- Модуль состоит из клиентского UI-пакета и серверной части, связанных `module_id` и версионированным контрактом.
- UI-пакет содержит декларативный JSON: структуру страницы, порядок встроенных компонентов, привязки к данным и действиям.
- Клиент отрисовывает описание встроенными компонентами Compose. Исполняемый код интерфейса от сервера или пакета не принимается.
- Описание интерфейса устанавливается локально. Данные страницы запрашиваются отдельно у агента.
- Действия вызываются через зарегистрированные `action_id` с проверкой схемы, прав, ограничений и результата.
- Установка клиентского пакета, активация для сервера, установка серверного модуля и установка сторонней утилиты — разные операции.
- Удаление клиентского пакета не означает удаление утилиты с Linux-сервера.
- Клиентские пакеты проверяются по подписи, целостности и совместимости. Дополнительные разрешения новой версии требуют подтверждения.
- По требованиям безопасности сторонние серверные модули изолируются от ядра отдельным процессом и непривилегированным пользователем ОС. Встроенные доверенные модули могут выполняться внутри агента.

## 4. Граница ответственности

| Клиент | Агент |
|---|---|
| Отображает экраны и локальные JSON-описания модулей | Собирает и нормализует системные данные |
| Хранит список серверов, их пользовательские названия и локации | Предоставляет идентичность сервера, версии и возможности |
| Хранит оформление, таймауты, интервалы обновления и клиентские пороги | Соблюдает собственные пределы нагрузки, частоты и размера ответа |
| Вычисляет клиентские ONLINE/WARNING/OFFLINE/UNKNOWN | Возвращает измерения, состояние источников и результаты операций |
| Сохраняет кэш, время получения и состояние сетевых попыток | Передаёт время измерения; хранит серверную историю согласно политике |
| Показывает права и подтверждения действий | Независимо проверяет права на каждый запрос и подписку |
| Инициирует известные операции | Выполняет операции, проверяет ОС/файловые ограничения, ведёт аудит |
| Инициирует SSH-обслуживание и запускает Termux | Работает как сервис и предоставляет локальные средства восстановления доступа |

Скрытая кнопка или клиентское подтверждение не заменяют серверную авторизацию. Изменение клиентского интервала доставки не должно автоматически менять серверную частоту сбора истории. Отношение этих частот предстоит определить отдельно.

## 5. Подключение, pairing и безопасность

### 5.1. Согласованный жизненный цикл подключения

1. Пользователь выбирает автоматическую установку по SSH, ручную установку или подключение к готовому агенту.
2. До доверенного обмена проверяются SSH-ключ и/или TLS-идентичность соответствующего канала. При ручном подключении предусмотрено подтверждение TLS-отпечатка; детали bootstrap нужно определить.
3. Pairing использует одноразовый короткоживущий код с ограничением попыток. Агент регистрирует устройство и выдаёт отзывной токен.
4. Клиент получает первый корректный снимок метрик. Только после этого создаётся готовая запись сервера в основном списке.
5. Ошибка первого запроса метрик не отменяет успешный pairing: пока мастер открыт, запрос повторяется с уже полученным токеном.
6. Черновики незавершённых форм и мастеров не сохраняются. Закрытие очищает ввод; переход между шагами открытого мастера не считается закрытием.
7. Токен после pairing временно хранится защищённо и не считается черновиком. При закрытии незавершённого мастера клиент пытается отозвать его, затем удаляет локально. Если отзыв не подтверждён, пользователь получает объяснение и инструкцию отзыва через CLI агента.
8. Отмена до подтверждённого начала установки не изменяет сервер. Отмена после начала не обещает откат уже сделанных изменений или остановку удалённой операции.

### 5.2. Обязательные ограничения

- Токены устройств хранятся на Android зашифрованно, с ключом в Android Keystore.
- SSH-пароли, приватные SSH-ключи, парольные фразы и пароль sudo не сохраняются; существуют в памяти на время конкретной операции.
- Доверие к TLS-сертификату не заменяется автоматически после ошибки. Новый pairing не запускается автоматически из обычного просмотра.
- Права проверяются на каждую API-операцию и WSS-подписку. Отозванному устройству запрещаются новые запросы и закрываются активные соединения.
- Отзыв должен быть возможен через CLI агента, в том числе при потере единственного телефона.
- Агент штатно работает непривилегированно. Повышенные права предоставляются через ограниченный helper или фиксированные системные правила.
- Нужны ограничения запросов, размеров, времени выполнения, соединений, подписок и очередей; конкретные значения ещё не выбраны.
- Аудит изменяющих операций фиксирует успехи и отказы, не содержит содержимое файлов, токены, SSH-секреты и stack trace.
- Полные командные строки процессов, аргументы и окружение не передаются клиенту. Имя процесса и разрешённые структурированные сведения допустимы.

## 6. Общая модель данных и состояния

### 6.1. Клиентский статус сервера

| Статус | Согласованное значение |
|---|---|
| ONLINE | Есть актуальный корректный снимок, доступные контролируемые метрики не достигли порогов предупреждения |
| WARNING | Есть актуальный корректный снимок и хотя бы один достигнутый порог предупреждения |
| OFFLINE | Соединение с агентом завершилось ошибкой или тайм-аутом, последующая успешная проверка ещё не получена |
| UNKNOWN | Состояние нельзя достоверно оценить: нет сети на телефоне, утрачен доступ, не пройдена проверка доверия, нет пригодного снимка либо данные устарели без актуальной проверки |

- OFFLINE не доказывает выключение физического сервера.
- При установленном отсутствии сети телефона или проблеме доступа используется UNKNOWN с причиной.
- Старение снимка само по себе не отменяет ранее установленный OFFLINE. Оценка изменяется при новом результате или новой известной причине.
- Повторная проверка — отдельный признак выполнения, а не пятый статус.
- Клиентские статусы соединения, предупреждения отдельных ресурсов и сводка безопасности — разные сущности.

### 6.2. Свежесть и частичные результаты

- Различаются время измерения агентом, время успешного получения клиентом и время последней попытки.
- Повторное получение прежнего измерения не делает его свежим. Ошибка не обновляет время успешных данных.
- После ошибки сохраняется последний корректный снимок с исходным временем и признаком устаревания.
- Ошибка отдельного датчика, истории или блока не означает недоступность всего агента.
- Отсутствие оборудования, неподдерживаемая метрика, недостаточные права, пустой результат и ошибка источника должны различаться.
- Недоступное значение не подменяется нулём, а пропуск истории — вымышленной точкой.
- Запоздалый ответ не должен заменять новый выбор сервера, периода или поиска и восстанавливать удалённую запись.
- Объекты идентифицируются по устойчивым идентификаторам, а не по положению в списке.

### 6.3. Предложение для будущего формата данных

Для каждого набора данных определить: идентичность объекта, время измерения, значения и единицы, доступность полей, состояние источника и безопасную причину неполноты. Конкретные поля и оболочку ответа пока не фиксировать.

Числа передавать в согласованных базовых единицах, а не строками вида «2.4 GB». Время агента — UTC; формат отображения выбирает клиент. Для сетевых счётчиков определить интервалы измерений, сбросы и переполнение. Для процентов определить знаменатель и правила нормализации.

| EX-006 | GPU; SCR-010 | Идентификатор GPU | Модель, производитель, UUID/PCIe, драйвер/CUDA при применимости; загрузка, VRAM, температура, мощность, вентиляторы, связанные процессы с достоверными GPU-метриками |
| EX-007 | Сетевая сводка; SCR-011 | Запрос сетевых данных | Интерфейсы, адреса, маршруты, DNS, RX/TX, скорости линков, состояния и счётчики ошибок |
| EX-008 | Интерфейс; SCR-012 | Идентификатор экземпляра интерфейса | Тип, адреса/префиксы, MTU, маршрут, состояние, link speed/duplex, RX/TX, загрузка канала, ошибки и dropped packets |

Основания: FR-001, FR-003–FR-006, UC-002–UC-005. Топ CPU-процессов может использовать EX-011 вместо отдельной реализации; GPU-процессы имеют дополнительные поля и не должны подменяться обычным списком процессов.

Обзор не обязательно должен быть одним тяжёлым ответом. Разбиение на независимо обновляемые блоки и краткое/подробное представления — предложение, которое нужно проверить по нагрузке и согласованности данных.

Список всех сохранённых серверов и счётчики ONLINE/WARNING/OFFLINE/UNKNOWN формирует клиент. Каждый агент отдаёт сведения только о своём сервере; общего облачного API списка серверов не предполагается.

### 7.3. Процессы и сетевые проверки

| ID | Назначение / экраны | Входные данные | Выходные данные |
|---|---|---|---|
| EX-011 | Список процессов и топ; SCR-013/008/009 | Поиск, фильтры, сортировка, размер страницы, продолжение выборки | PID, идентичность экземпляра, имя, владелец/UID, состояние, CPU, RSS, время запуска; доступные связи с systemd/Docker/cgroup; данные продолжения |
| EX-012 | Процесс; SCR-014 | Идентичность конкретного экземпляра процесса | Подробности, родитель, потоки, время работы, доступные операции и причины ограничений |
| EX-013 | Завершение; SCR-013/014 | Идентичность экземпляра и разрешённый сигнал TERM/KILL | Отказ или результат отправки сигнала; завершение подтверждается отдельно, если его удалось установить |
| EX-014 | Конфигурация и результаты проверки; SCR-012 | Запрос текущих настроек/результата | Цель, время проверки, задержка, потери, состояние и причина ошибки |
| EX-015 | Изменение цели; DLG-011 | Gateway, IPv4 или hostname | Принятая конфигурация либо причина отказа |
| EX-016 | Запуск проверки; SCR-012 | Выбранная цель или ссылка на конфигурацию | Результат либо идентификатор длительной операции |

Основания: FR-008, FR-006.17–FR-006.19, UC-005–UC-006.

- Поиск и сортировка процессов выполняются до пагинации по всей разрешённой выборке. Ответы разных версий списка нельзя незаметно склеивать.
- Одного PID недостаточно для опасного действия из-за повторного использования номера. Точный идентификатор экземпляра ещё не определён.
- TERM и KILL требуют права управления, явного подтверждения и аудита. Завершение PID 1 запрещено требованиями.
- Первое измерение CPU процесса может быть недоступно: для скорости нужны два измерения. Не подменять его нулём.
- Проверку задержки выполняет сервер, а не телефон. Выбор gateway интерфейса в качестве цели не гарантирует выход пакетов через этот интерфейс.
- Где хранится цель проверки и общая ли она для устройств, пока не определено.
- Публичный IP допустим только через явно настроенный механизм внешней проверки. Отдельный запрос его запуска не включён в 40 позиций как согласованная операция.

Основание: FR-007. Операции и ограничения исходного требования важнее укрупнённых формулировок этой таблицы.

- Доступ определяется одновременно политикой агента, выданными правами, правами ОС и режимом монтирования. «ФС доступна для записи» не означает «этому устройству разрешена запись».
- Корень и относительный путь ограничивают область работы. Проверка канонического пути и symlink escape выполняется агентом, включая изменяющие операции.
- Размер каталогов не требует рекурсивного обхода при каждом отображении списка.
- Полный просмотр и редактирование требуют проверки текстового содержимого и размера. Расширение само по себе не доказывает, что файл текстовый.
- Частичный просмотр больших файлов: последние 100/500/1000 строк, загрузка более ранних порций и ручное обновление. Постоянный `tail -f` требованиями исключён.
- Сохранение проверяет ожидаемую версию и выполняется атомарно. Конфликт не разрешается автоматической перезаписью.
- Загрузка и скачивание передают поток файла; обязательное кодирование всего файла в JSON/Base64 не предлагается.
- Перемещение между файловыми системами не должно незаметно превращаться в копирование с удалением.
- Корзина условна: доступна там, где предусмотрена серверной политикой. Автоматическое удаление по сроку и ручной PURGE — разные возможности.

## 9. Обновление данных: предложение для согласования

| Тип | Предлагаемое поведение |
|---|---|
| Текущие показатели | Первый снимок при открытии, затем WSS-подписка на данные активного экрана; ручное обновление остаётся доступным |
| История | Запрос при открытии и смене периода; способ добавления новых точек уточнить отдельно |
| Характеристики оборудования | При подключении/открытии и после значимых изменений; не обязательно передавать при каждом измерении |
| Возможности и разрешения | При подключении и изменениях; способ уведомления об изменениях требуется определить |
| Каталоги, тексты, корзина, устройства | При открытии, вручную и после связанных действий |
| Пакеты и выпуски | Через отдельные внешние источники согласно их правилам |

Предлагается одно WSS-соединение с каждым активно наблюдаемым агентом и подписки внутри соединения, а не отдельный сокет для каждого графика. Количество одновременно наблюдаемых агентов, фоновые режимы и лимиты соединений ещё не определены.

Необходимые вопросы протокола: получение начального состояния, идентичность/порядок обновлений, обнаружение пропуска, восстановление после разрыва, ограничение очередей и завершение подписок. Конкретные сообщения пока не проектировать.

По действующим требованиям интервалы по умолчанию: карточки — 5 секунд, подробности — 2 секунды; тайм-аут — 10 секунд; свежесть — 60 секунд. Это параметры клиента из FR-010, которые нужно согласовать с доставкой по WSS. Они не определяют автоматически частоту сбора и хранения всех метрик.

| Upload / download | По умолчанию 50 MB / 100 MB, если сервер не задал иной лимит | FR-007.14–FR-007.15 |
| Частичный текст | Последние 100/500/1000 строк и более ранние порции | FR-007.9; постоянного tail -f нет |
| Корзина | Срок настраивается на сервере, по умолчанию 7 дней | FR-007.19; ручной PURGE противоречив |

Единицы KB/MB в исходных требованиях необходимо уточнить до контракта: десятичные или двоичные и точное количество байтов. Нельзя незаметно выбрать одну трактовку в клиенте, другую в агенте.

Ограничения ответа не должны приводить к потере смысла: пропуски не превращаются в нули, температурные пики и throttling сохраняются согласно правилам агрегации. История хранится на сервере независимо от того, открыт ли экран телефона.

## 11. Внешние источники и SSH: отдельно от API агента

Для полного продукта могут потребоваться:

- Каталог UI-пакетов: поиск, описания, версии, совместимость, права, сведения о проверке/отзыве.
- Получение подписанного пакета и данных проверки целостности.
- Источник выпусков агента: доступные версии, совместимость и установочные артефакты.
- Источник выпусков клиента при наличии соответствующей функции; конкретный механизм не утверждён.

Каталог сообщества зависит от инфраструктуры проверки, публикации и отзыва пакетов. Не следует автоматически добавлять центральный сервер в обязательную архитектуру или считать каталог уже существующим сервисом.

Установка, обновление и удаление агента выполняются по SSH. Требования обновления предусматривают атомарную замену, откат при ошибке и сохранение конфигурации, TLS, токенов других устройств и данных. После обслуживания клиент проверяет доступность и совместимость агента.

Для документации агента всё равно нужно описать установщик, CLI, systemd unit, конфигурацию, восстановление доступа, обновление и удаление. Отсутствие HTTP-пути не означает отсутствие серверного требования.

## 12. Открытые вопросы и противоречия

| Вопрос | Почему влияет на проектирование | Как трактовать до решения |
|---|---|---|
| Опрос и WSS | FR-010 описывает интервалы опроса, а архитектура предусматривает подписки | Не фиксировать автоматический fallback, частоту доставки или частоту коллектора без решения |
| Старые определения OFFLINE | FR-010.4 и связанные FR смешивают устаревание и недоступность | Использовать согласованную модель из сценариев; запланировать синхронизацию FR |
| Черновики и момент создания записи | В старых FR остаются прежние формулировки | Следовать решениям раздела 5: без черновиков, запись после первого корректного снимка |
| Доступность EX-001 до pairing | Нужны проверки совместимости, но NFR-SEC-006 допускает без аутентификации только pairing | Определить безопасный bootstrap и минимальные сведения; не открывать публично все capabilities/права |
| Где хранится цель сетевой проверки | От этого зависят запись конфигурации, права и влияние на другие телефоны | EX-014/015 — предварительное разбиение, не утверждённые серверные ресурсы |
| Публичный IP | Требуется явно настроенная внешняя проверка; режим запуска и хранения не задан | Не запускать обязательный внешний запрос при каждом обновлении карточки |
| Инициатор аудита и корзины | Упоминается пользователь ServerDeck, но центральных аккаунтов нет | Определить идентичность зарегистрированного устройства и системных действий; не добавлять аккаунты |
| Ручной PURGE | FR-007.21 одновременно описывает возможность и исключает её из текущего объёма | EX-030 условен; автоматическое удаление по политике рассматривать отдельно |
| Дублирование FR-007.22 | В требованиях два одинаково пронумерованных раздела | Уточнить при синхронизации ссылок; не создавать две независимые функции |
| Устойчивые идентификаторы | PID переиспользуется; интерфейсы и GPU могут исчезнуть/появиться заново | Определить идентичность экземпляров, поколений и отношение истории к ним |
| Согласованность страниц | Список процессов и каталоги меняются во время дозагрузки | Определить снимок/курсор, устаревание и перезапуск выборки |
| История GPU/сети и событий | CPU имеет более подробную политику, другие ресурсы — нет | Дополнить отдельно, не объявлять CPU-политику универсальной без согласования |
| Настройки и серверная политика | Клиентские пороги/интервалы локальны, но лимиты, корзина и сбор истории принадлежат агенту | Разделить эти настройки; не добавлять API редактирования всей серверной конфигурации по умолчанию |
| Права устройств и модулей | Требуется проверка прав, но администратор/владелец и порядок выдачи не определены | Уточнить первичную выдачу, изменение и отзыв без обязательных облачных аккаунтов |
| Наблюдение за длительной операцией | Тайм-аут или закрытие экрана не подтверждают отмену | Определить состояния, повтор, хранение результата и поведение после перезапуска |
| Жизненный цикл серверных модулей | UI-пакет не устанавливает серверную часть, но детали её установки/обновления ещё не описаны | Не считать EX-035 универсальным установщиком; описать жизненный цикл отдельно |
| Docker/безопасность в обзоре | Это сводки, а не разрешение добавить полноценное управление Docker/firewall | Соблюдать FR-003.19–FR-003.27 и границы карты экранов |
| Место чтения аудита | Требование отображения есть, самостоятельного экрана в карте нет | Уточнить точку доступа без автоматического расширения карты |
| Стек и поддерживаемые системы | Python/FastAPI — предпочтение; способ доставки и совместимость не определены | Сначала сравнить по требованиям, затем зафиксировать выбор |

Эти вопросы не требуют останавливать всё проектирование. Независимые требования можно оформлять, отмечая зависимые решения как открытые. Новые рекомендации не следует автоматически записывать в раздел «Принято».

## 13. Что оформить в документации агента

Рекомендуемый порядок работы — предложение, а не сокращение состава продукта:

2. Согласовать спорные пункты раздела 12, необходимые для начала требований.
3. Сформировать функциональные требования агента: сбор данных, история, процессы, файлы, диагностика, устройства, аудит, модули, CLI и жизненный цикл.
4. Уточнить реестр обменов и связать каждую операцию с FR/UC/SCR, правами, ограничениями и ошибками.
5. После этого проектировать REST API, JSON-схемы, ошибки, пагинацию и протокол WSS.
