# ServerDeck Agent — рабочие заметки и решения

Дата создания: 11 октября 2026 года. Последнее обновление: 12 октября 2026 года.

Это рабочая запись обсуждения проектирования Agent. Здесь собраны принятые решения, предложения и вопросы, которые ещё нужно разобрать. Документ не заменяет функциональные требования и окончательный контракт API.

**Актуальный статус:** пользователь принял все пункты Р01–Р25. Они оформлены в [описании проекта](<1. Краткое описание.md>), [функциональных требованиях AFR-001–AFR-072](<2. Функциональные требования.md>) и [требованиях безопасности ASEC-001–ASEC-031](<4. Требования безопасности.md>). Пакет решений приведён в [отдельном файле](<Предложения по оставшимся вопросам.md>). Ранние пометки «предложение», «не выбрано» и «открыто» в исторических разделах ниже не отменяют принятый пакет; при реализации использовать актуальные требования и их трассировку. Технические схемы API/IPC/UI, конфигурация, архитектура, план и журнал оформлены 12 октября 2026 года: [техническая основа](<10. Противоречия и готовность.md>). Результаты испытаний реализации отсутствуют; исторические записи ниже сохраняют прежний контекст.

## 1. Исходная основа

Источники: [контекст и потребности клиента](<0. Контекст и потребности клиента.md>), [краткое описание Agent](<1. Краткое описание.md>), [требования безопасности](<../4. Требования безопасности.md>) и текущий диалог.

**Принято ранее, по контекстному документу:**

- Проектируется полный запланированный продукт. Последовательность реализации допустима, сокращение требований под видом MVP — нет.
- Нативный Android-клиент обращается непосредственно к Agent выбранного Linux-сервера. Обязательных центральных аккаунтов нет.
- HTTPS/WSS используются для взаимодействия с Agent; SSH — отдельный канал установки и обслуживания.
- API предоставляет именованные разрешённые операции с проверяемыми параметрами. Произвольные shell-команды и скрипты через API не принимаются.
- Подключение устройств использует pairing, отзывные токены и явную проверку доверия. Авторизацию нельзя заменять скрытыми кнопками клиента.
- Клиентские UI-пакеты декларативны. Серверный модуль и клиентский UI-пакет — разные устанавливаемые части.

Предварительные EX-001–EX-040 из контекстного документа не являются утверждёнными маршрутами API. Частоты сбора и общие правила доставки согласованы; детальные схемы HTTP/WSS ещё оформляются.

## 3. Запуск, установка и обслуживание

**Принято, последнее решение пользователя:** Agent устанавливается непосредственно на хост. Одна systemd-служба запускает один основной процесс под существующим Linux-пользователем, указанным в клиенте при настройке сервера. В этом процессе работают ядро и все системные модули; дополнительные модули работают в отдельных процессах.

Docker первоначально предложен ради упрощения доставки и совместимости. Пользователь подтвердил, что Docker не является принципиальным требованием и допустим другой способ. Контейнерный запуск не выбран основным способом; обязательство разработать альтернативный Docker-вариант также не принималось.

Причина выбора направления: Agent должен работать с ресурсами хоста, включая процессы и файлы. Контейнерная упаковка не устраняет необходимость проектировать такой доступ, права, совместимость драйверов и безопасное обслуживание.

**Принято в текущем диалоге:**

- При автоматическом добавлении сервера клиент подключается по SSH и запускает установку.
- Подключение допускается как под root, так и под обычным пользователем с правами sudo.
- При первой установке устанавливаются утилиты, необходимые для корректной работы системных модулей. Конкретный перечень и правила проверки уже установленных зависимостей согласовываются отдельно.
- Обновление пока запускается только вручную. Клиент должен сообщать о наличии новой версии, совместимой с конкретным сервером. Это не означает разрешение на автоматическую установку.

**Предложения по деталям установки:**

- Сначала проверять ОС, архитектуру, права и существующую установку, затем формировать план изменений.
- Запрашивать пароль sudo только при необходимости. Ввод пароля не заменяет проверку разрешённых пользователю действий.
- Размещать конфигурацию, TLS-ключи, регистрации устройств и историю отдельно от файлов выпуска.
- Принятый порядок обновления с сохранением данных, подготовкой восстановления и автоматическим возвратом после провала проверки описан в разделе 6.1; конкретный механизм ещё предстоит определить.

**Принято по правам исполнения:** отдельная служебная учётная запись для основного Agent не выбирается. Он получает обычные права выбранного пользователя и его групп в пределах ограничений службы. Запуск под root разрешён по выбору пользователя; клиент сообщает о рисках этого выбора. SSH-секреты и пароль sudo по-прежнему не сохраняются; наличие sudo не означает автоматического повышения прав процесса.

**Принято для недостатка прав:** Agent сообщает, что операция недоступна выбранному пользователю. Автоматический sudo или привилегированный helper для обхода отказа ОС в штатных операциях не выбирается. Получение прав при SSH-установке и обслуживании остаётся отдельным сценарием.

**Открыто:** язык и стек, формат поставки, состав зависимостей и технический механизм обновления ядра и модулей. Нужны источник сведений о выпусках, правила определения совместимости и частота проверки. Python/FastAPI остаётся исходным предпочтением, а не окончательным выбором. NFR-SEC-013 о запрете штатного запуска от root и применении helper требует синхронизации с новыми прямыми решениями пользователя.

## 4. NVIDIA и зависимости GPU-мониторинга

**Позиция пользователя:** на сервере с используемым NVIDIA GPU предполагается установленный драйвер. Для получения данных можно использовать nvidia-smi, при необходимости доустановив утилиту при инициализации Agent.

**Предложения, ещё не зафиксированные как окончательная реализация:**

- Для постоянного сбора рассмотреть NVML; nvidia-smi использовать для диагностики и, при необходимости, как альтернативный источник.
- Отдельно различать отсутствие GPU, отсутствие доступа, неисправный/отсутствующий драйвер и неподдерживаемую метрику.
- Недоступность GPU-мониторинга не должна останавливать остальные функции Agent. Не подменять недоступные значения нулями.
- Возможную установку утилит выполнять с учётом существующего драйвера. Установка или замена самого драйвера — отдельное решение, которое нельзя незаметно включать в установку Agent.

**Открыто:** обязательные метрики и модели GPU, способ сбора, разрешённые изменения пакетов, поддержка NVIDIA на ARM и поведение при несовместимых версиях.

## 5. Модульность стандартных функций

**Принято:** стандартные функциональные наборы тоже являются модулями. Пользователь прямо назвал GPU-мониторинг и файловый менеджер. Модули делятся на системные и дополнительные.

- Системные модули нельзя отключать или удалять средствами Agent/клиента. Это ограничение продукта, а не обещание запретить администратору ОС менять установку вручную.
- Дополнительные модули можно отключать в клиенте или удалять; остальные функции должны продолжать корректно работать.
- Системными считаются все возможности клиента из коробки: CPU, GPU, RAM, диски, процессы, сеть и остальные штатные функции, включая файловый менеджер. Они входят в основной процесс Agent; отдельного файлового исполнителя нет. Полную трассировку этого правила по клиентским требованиям ещё нужно оформить.
- Серверные модули пока устанавливаются вручную на сервер. После корректной установки модуль автоматически появляется на соответствующем экране клиента, где доступны разрешённые действия с учётом его типа.

**Принято, последнее решение пользователя о процессах:**

- Один основной процесс Agent под выбранным пользователем охватывает ядро и все системные модули.
- Дополнительные модули запускаются в отдельных процессах.
- Предыдущие варианты с отдельным служебным пользователем ядра, общим процессом мониторинга отдельно от ядра и отдельным файловым исполнителем заменены этим решением.

**Следствия для проектирования, не дополнительные обещания:** обычное обновление системного модуля может потребовать перезапуска всего основного процесса и временно прервать API, подписки и остальные системные функции. Ошибка, завершающая основной процесс, также затрагивает их все. Прежнее требование независимого обновления каждого системного модуля без влияния на ядро больше не используется как гарантия. Горячая перезагрузка кода не выбрана.

**Принято по отключению и удалению дополнительных модулей:**

- Отключение останавливает процесс, сбор данных и выполнение действий. Настройки и накопленная история сохраняются для повторного включения.
- Обычное удаление убирает код модуля и сохраняет настройки/историю. Полное удаление данных — отдельный явный выбор.
- Удаление интеграционного модуля не означает автоматического удаления управляемой им сторонней программы.

Эти действия выполняются только при наличии необходимых прав. Если Agent не вправе остановить процесс или удалить установленный код, клиент получает отказ с понятной причиной, а не сообщение об успешном отключении/удалении.

**Открыто:** начальная комплектация дополнительными модулями, правила обнаружения и проверки ручной установки, доверие к пакету, расположение сохраняемых данных. Установка серверных модулей через клиент в текущем решении не предусмотрена. Способ запуска их ручного обновления ещё нужно определить.

**Предложение по зависимостям:** системные функции не должны зависеть от удаляемого дополнительного модуля. Для зависимостей между дополнительными модулями нужно заранее определить последствия отключения/удаления. Автоматическое обнаружение пакета не должно означать запуск непроверенного кода.

**Принятые общие функции внутри основного процесса:**

- Идентичность Agent, HTTPS/WSS, pairing и управление устройствами.
- Общая авторизация, ограничения запросов и аудит.
- Регистрация модулей, проверка совместимости и управление их жизненным циклом.
- Общие механизмы хранения истории и наблюдения за длительными операциями. Политики хранения и контракты операций требуют дальнейшего проектирования.

**Принято по пользователям дополнительных модулей:** пользователь вручную выбирает способ установки и запуска. Модуль может работать под той же учётной записью, что Agent, либо под другой, если обеспечен корректный обмен данными. Автоматическое создание отдельной ограниченной учётной записи для каждого модуля больше не является принятым обязательством.

**Принят основной способ управления дополнительными модулями:** Agent запускает их отдельными дочерними процессами под своей учётной записью и управляет жизненным циклом; подробности — в разделе 5.4. Ранее разрешённый выбор другой учётной записи администратором не отменён, но внешний запуск не принят как обязательный второй режим.

**Открыто для дополнительных модулей:** точные схемы принятого JSON-RPC-обмена через Unix-сокет, аутентификация локальных процессов, детали остановки и ограниченных повторов запуска, переживание перезапуска основного Agent. Общие правила обмена и отслеживания действий приняты в разделе 5.6. Доступ к каналу под разными пользователями и взаимодействие с внешним supervisor/systemd остаются отдельными вопросами внешнего запуска. Внешний supervisor не должен незаметно запускать снова модуль, который клиент считает отключённым. Процессы с одним UID не получают полную изоляцию друг от друга только за счёт раздельного запуска.

NFR-SEC-012 о выделенном непривилегированном пользователе для стороннего модуля требует синхронизации: пользователь явно разрешил самостоятельный выбор учётной записи запуска.

| Процессы | Список, поиск и сортировка до пагинации, топ; PID и идентичность экземпляра, имя, владелец, состояние, CPU/RSS, запуск/uptime, родитель, потоки и доступные связи с systemd/Docker/cgroup; TERM/KILL как именованные действия | SCR-008/009/013/014; FR-003.22, FR-005.20, FR-008 | PID 1 защищён даже при запуске от root. Проверять тот же экземпляр процесса, а не только PID. Отправка сигнала не доказывает завершение. Недостаток прав — понятный отказ и аудит; аргументы/окружение и полную командную строку не передавать |
| Файлы и корзина | Корни, каталоги и метаданные; текстовый и частичный просмотр, редактирование с проверкой версии и атомарным сохранением; создание, upload/download, переименование, перемещение, удаление, корзина и восстановление | SCR-015–019 и файловые диалоги; FR-007 | Обычные права выбранного пользователя, ограничения путей и ФС; без автоматического sudo. Сохраняются ограничения размеров, защита от конфликтов и symlink escape. Ручной PURGE остаётся открытым из-за FR-007.21; постоянный tail -f не добавляется |
| Сводка Docker | Обнаружение Engine, доступность daemon, состояния и количества контейнеров, проблемные/активные контейнеры, доступные CPU/RAM и Compose-метаданные для обзора | SCR-008; FR-003.19–003.21 | Штатная функция наблюдения, даже если Docker не установлен. Отсутствие Engine/прав не останавливает Agent. Не устанавливать Docker только ради этой сводки и не добавлять start/stop/remove контейнеров без отдельного требования |
| Мониторинг безопасности | Состояние поддерживаемого firewall; доступные SSH-сессии и события входа за заданный период; состояние Fail2ban, jail и блокировки при доступности; классифицированные события по фиксированным правилам | SCR-008; FR-003.23–003.27 | Отсутствие источников/прав не означает безопасное состояние. Успешный SSH-вход сам по себе не предупреждение. Секреты не выдаются. Настройка firewall/Fail2ban и автоматическое устранение проблем этим модулем не добавляются |

Наличие системного модуля не означает наличие оборудования или стороннего сервиса на каждом сервере. GPU, Docker и Fail2ban могут отсутствовать: модуль остаётся частью поставки, но сообщает о доступности источника. Установщик должен различать обязательные инструменты сбора и приложения, состояние которых Agent лишь наблюдает.

### 5.2. Общие функции основного процесса

Принято: следующие обязанности реализовать как общие части ядра в том же процессе, без отдельных отключаемых модулей для каждого пункта. Детальные контракты и параметры их работы предстоит спроектировать.

| Общая часть | Обязанности и связь с модулями |
|---|---|
| HTTPS/WSS и контракты | Приём запросов, аутентификация каждого запроса/подписки, версии API, схемы, ограничения размеров/частоты и доставка данных. Модули не открывают собственные публичные порты по умолчанию |
| Идентичность, устройства и доступ | Версия/идентичность Agent, регистрация и отзыв устройств, pairing-коды, равные права телефонов и проверка политики операций. Отзыв закрывает активные соединения устройства |
| Планирование сбора и состояние источников | Ограниченная частота работы коллектора, отметки времени, ошибки отдельных блоков, недоступные поля. Клиентская частота доставки не должна автоматически менять серверную политику истории |
| История и события | Общий механизм хранения/чтения и лимитов. Каждый ресурсный модуль определяет метрики и правила агрегации; CPU-политику не переносить автоматически на GPU/сеть. История сохраняется без открытого экрана телефона |
| Аудит и длительные операции | Записи изменяющих действий и отказов без секретов; идентичность инициатора-устройства; состояние операций, безопасность повтора после тайм-аута и правила перезапуска. Формат и сроки хранения ещё не выбраны |
| Реестр дополнительных модулей | Обнаружение корректной ручной установки, проверка контракта/совместимости, регистрация разрешённых чтений и действий, локальный обмен, состояние, отключение/удаление при наличии прав |
| Сборка сводок | Карточка сервера и обзор переиспользуют результаты перечисленных модулей; не запускают второй независимый сбор всех метрик. Время и полнота данных сохраняются по блокам; одинаковый момент измерения всех блоков не обещается без отдельного решения |

Локальный список серверов, ONLINE/WARNING/OFFLINE/UNKNOWN, клиентские пороги отображения и настройки интерфейса остаются в клиенте. Общие серверные правила формирования событий и индивидуальный показ уведомлений приняты в разделе 5.7; клиентские пороги статуса не становятся автоматически серверными правилами. Для сводки безопасности классификация событий агентом и итоговый статус клиентом должны быть явно разделены при проектировании формата.

Установка, обновление, удаление Agent и восстановление доступа относятся к установщику/CLI и SSH-обслуживанию, а не к новому публичному API произвольных команд. Установщик создаёт выбранную systemd-службу; CLI обеспечивает локальные действия восстановления и выдачу pairing-сведений. Обязательные исполняемые файлы и их упаковка пока не определены.

### 5.3. Что уточнить по перечню

- Связь прав ОС с разрешёнными корнями и общая защита собственных файлов Agent приняты в разделе 8.2. Точные защищённые объекты и механизмы проверок ещё проектируются. Запуск от root не отменяет фиксированные запреты продукта и проверку параметров.
- Частоты сбора, хранения и доставки разделяются; базовые интервалы и уровни истории GPU/сети приняты в разделе 9.1. Лимиты и детальные правила агрегации GPU/сети ещё уточняются. Обязательная история RAM/дисков не добавлена.
- FR-003.11 одновременно требует показывать `/` и исключать overlay/squashfs по умолчанию. Нужен приоритет правил, если корневая ФС имеет такой тип.
- Правила размещения и хранения сетевой цели между устройствами остаются открытыми. Ограничение FR-006.18: не более пяти пакетов либо десяти секунд; точный алгоритм проверки ещё не выбран.
- FR-007.21 противоречиво описывает ручной PURGE, FR-007.22 продублирован. Эти пункты не превращены в два новых модуля или утверждённые операции.
- Краткое описание Agent упоминает службы и журналы шире текущих экранов. Сейчас системные связи процессов, события безопасности, аудит и чтение лог-файлов покрыты; отдельное управление systemd-службами и универсальный просмотр журналов не добавлены без уточнения требований.
- В одном процессе обработанная ошибка коллектора должна возвращать частичный результат; аварийное завершение процесса затрагивает весь Agent. Порядок запуска, тайм-ауты внешних операций и ограничение объёма работы требуют проектирования; отдельная строка таблицы не даёт процессной изоляции.
- Перечень утилит установки будет согласован после выбора источников и стека. Сам факт наличия метрики не означает обязательную установку утилиты для каждого показателя.

### 5.4. Обнаружение и управление дополнительными модулями

Статус: **основной способ запуска принят пользователем** — Agent запускает модуль отдельным дочерним процессом под своей учётной записью, наблюдает состояние, останавливает/включает и перезапускает после сбоев с ограничением повторов. Ручная установка, отдельные процессы и отказ при недостатке прав остаются принятыми решениями. Отдельная systemd-служба для каждого дополнительного модуля не требуется. Ранее разрешённый администратору выбор другой учётной записи не отменён; реализация внешнего запуска остаётся отдельным вопросом, не обязательным вторым режимом. Остальные детали ниже сохраняют статус предложений, если отдельно не приняты в других разделах.

**Установка и обнаружение:** установщик модуля, запускаемый администратором вручную, размещает код и регистрирует описание модуля в известном Agent реестре. Описание содержит устойчивый идентификатор, название, версию, совместимые версии протокола модулей/Agent, требования ОС/архитектуры и зависимостей, способ подключения и управления процессом, пути к коду и отдельно сохраняемым данным. Точные формат и пути ещё не выбраны. Agent обнаруживает изменение реестра без полного перезапуска, проверяет описание и сообщает о модуле клиентам. Простое появление произвольного исполняемого файла не даёт разрешения на запуск; регистрация и разрешение запуска должны быть явной частью доверенной ручной установки. Наличие манифеста не доказывает безопасность кода.

| Способ запуска | Предлагаемое поведение Agent | Ограничения |
|---|---|---|
| Управляемый Agent — принят как основной | Запускает зарегистрированный модуль отдельным дочерним процессом под своей учётной записью, наблюдает состояние, останавливает/включает и выполняет ограниченные повторы после аварии | Внутрипроцессный импорт стороннего кода не нужен; права удаления кода проверяются отдельно. Поведение дочерних процессов при остановке/аварии основной systemd-службы ещё проектируется; независимость от перезапуска Agent не обещается |
| Внешний запуск — рассматриваемая возможность | Администратор запускает модуль через systemd или другой механизм, в том числе под другим пользователем, и настраивает локальный обмен и разрешённое управление | Не утверждён как обязательный режим. Agent не меняет UID и не получает sudo автоматически. Остановка, запуск и удаление доступны только при настроенном контроле и реальных полномочиях; иначе соответствующие действия недоступны с причиной |

**Канал данных:** принят JSON-RPC 2.0 через локальный Unix-сокет, подробности — в разделе 5.6. Публичный HTTPS/WSS-порт остаётся у Agent; клиент обращается к модулям через него. Нужны проверка зарегистрированной идентичности модуля, согласование версии и возможностей протокола, ограничения сообщений/частоты/очередей и тайм-ауты. Разным пользователям установщик вручную предоставляет необходимый доступ к каналу; доверять любому локальному процессу без проверки нельзя. Обрамление сообщений, организация сокетов и схема аутентификации пока не утверждены.

**Совместимость и состояние:** проверять не только номер выпуска Agent, но и версию контракта обмена и необходимые возможности. Несовместимый или некорректно установленный модуль показывать в управлении модулями с причиной, без рабочих операций. Различать желаемое состояние «включён/отключён», наблюдаемое состояние процесса и готовность протокола. Примеры отображаемых состояний: установлен и отключён; запускается; готов; недоступен/ошибка; останавливается; несовместим. Отсутствие ответа не означает успешную остановку и само по себе не доказывает завершение процесса.

**Отключение:** сначала сохранить намерение отключения и закрыть новые действия, затем остановить работу штатным управлением и подтвердить результат. При внешнем supervisor нужно согласовать состояние с ним: убийство PID не заменяет остановку службы, которая может перезапустить процесс. При отказе/тайм-ауте показывать фактическое либо неизвестное состояние и причину, не обещать завершение уже начатых изменяющих операций. После подтверждённого отключения модуль не запускается при перезапуске Agent/сервера без нового включения; конкретные настройки внешнего запуска должны обеспечивать это правило.

**Аварии:** обрыв связи одного модуля не останавливает системные функции; клиент получает состояние недоступности, устаревшие данные и разрывы истории. Для управляемых процессов предложены повторы с задержкой и конечным бюджетом; после повторяющихся сбоев остановить цикл и показать ошибку. Отдельный процесс сам по себе не ограничивает потребление CPU/RAM и не изолирует процессы с одинаковым UID; конкретные ресурсные ограничения ещё выбрать.

**Удаление:** остановить процесс, предотвратить повторный запуск и только затем удалять зарегистрированный код с проверкой прав/принадлежности путей. Частичные ошибки удаления показывать явно. Настройки и история сохраняются по принятому правилу, их полное удаление — отдельный явный выбор. Не принимать произвольный путь удаления из ответа модуля. Если внешним запуском или файлами управляет другой администратор, вернуть причину недоступности и инструкцию для ручного действия.

**Появление в клиенте:** принят декларативный UI-пакет из встроенных компонентов клиента, подробности — в разделе 5.5. Карточка модуля появляется автоматически, полноценный экран — при наличии установленного совместимого UI-пакета. Серверную совместимость и наличие поддерживаемого клиентского интерфейса различать.

Принято: управляемые Agent отдельные процессы как основной способ запуска; общая модель интерфейсов — в разделе 5.5, внутреннего обмена — в разделе 5.6, обновления — в разделе 6.1. На согласование: техническая регистрация описания при ручной установке. Точные схемы сообщений, тайм-ауты, бюджеты повторов, безопасная аутентификация IPC, технический механизм обновлений, детальный UI-контракт и объём поддержки внешнего запуска остаются открытыми.

Основания: документация upstream systemd описывает [политику перезапусков служб](https://github.com/systemd/systemd/blob/main/man/systemd.service.xml) и [проверку полномочий управления службами](https://github.com/systemd/systemd/blob/main/man/org.freedesktop.systemd1.xml). Поэтому управление внешним процессом нельзя обещать по одному факту наличия его PID или локальной связи с ним. Совместимость конкретных параметров с Ubuntu 22.04 проверять отдельно, без переноса возможностей текущего upstream как гарантированных.

### 5.5. Интерфейс дополнительных модулей

Статус: **принято пользователем** — декларативные UI-пакеты из встроенных компонентов клиента без загружаемого исполняемого кода, автоматическое появление карточки серверного модуля, получение UI-пакета через Agent с проверкой подписи/совместимости и отдельным подтверждением установки. Также приняты независимые жизненные циклы UI-пакета и серверного процесса, отдельное обновление данных и изоляция ошибки интерфейса модуля от остальных экранов. Подход соответствует существующим FR-009 и NFR-SEC-010; точная схема, доверие к издателям и технические детали ещё проектируются.

**Две части:** серверный процесс получает данные и выполняет именованные операции, клиентский UI-пакет содержит JSON-описание страниц/полей/локализации и привязки к данным и действиям. Общий устойчивый `module_id` связывает части. Клиентская реализация компонентов остаётся встроенной в приложение. Серверный процесс, его контракт обмена с Agent, API модуля для клиента и версия UI-схемы — разные границы совместимости, не один общий номер выпуска.

**Принято по возможностям интерфейса:** использовать реестр встроенных компонентов клиента; исходный набор описан в FR-009: заголовки, карточки значений/статусов, списки/таблицы, временные графики, поля форм/переключатели/выбор значений, кнопки, подтверждения, прогресс, ошибки и пустые состояния. Страницы и привязки можно менять обновлением совместимого UI-пакета без выпуска приложения. Новый тип компонента или поведение, не выражаемое поддерживаемой схемой, требует обновления клиента; произвольную Android-реализацию из пакета не загружать. Сам по себе JSON не безопасен: нужны проверка схемы, версии, размеров/сложности, допустимых привязок и изоляция ошибки отображения. Детальные правила этих проверок и пределы компонентов ещё определить.

**Принятый общий сценарий получения UI:**

1. Администратор вручную устанавливает серверный модуль; Agent сообщает клиенту зарегистрированную идентичность, возможности и состояние.
2. Карточка модуля автоматически появляется в управлении модулями независимо от наличия его UI-пакета. Системные действия жизненного цикла выполняются средствами ядра клиента с проверкой прав на Agent, без обязательной загрузки интерфейса стороннего модуля.
3. Если локальный пакет уже есть и совместим, становится доступен функциональный экран. Если его нет, показать состояние «Требуется интерфейс модуля» и предложить установку.
4. UI-пакет можно получить через Agent. Предложение по упаковке: включать его в ручную серверную поставку. Перед установкой клиент проверяет подпись доверенного издателя, целостность, идентичность и совместимость, показывает источник/версию/запрашиваемые возможности и получает подтверждение пользователя. Источник через Agent не заменяет доверие к издателю; сам факт подписи неизвестным ключом недостаточен. Конкретная модель доверия и формат поставки ещё не определены.
5. После установки локального пакета экран строится встроенными компонентами; значения поступают отдельно от структуры UI. Обновление метрик не устанавливает новый UI-пакет незаметно. Импорт из файла, уже предусмотренный FR-009, сохраняется. Каталог распространения, доверенные ключи и обновление пакетов ещё проектируются.

**Граница действий:** кнопка ссылается на проверяемый идентификатор операции конкретного модуля текущего сервера, а не передаёт shell-команду или произвольный URL. Agent и серверный модуль проверяют доступность и параметры независимо от видимости кнопки. Изменяющие действия используют общие правила подтверждения, аудита и отслеживания длительных операций; точная классификация опасных действий ещё требует контракта. UI-пакет не получает прямого доступа к токенам устройств, SSH, Android API или самостоятельным сетевым запросам.

**Неоднозначности и ошибки:** серверная часть может быть совместима с Agent, но требовать более новой UI-схемы; это отдельная причина недоступности экрана, не повод прекращать мониторинг сервера. Ошибка пакета затрагивает его интерфейс, не остальные экраны. При отключении модуля не представлять старые значения как текущие; при отсутствии серверной части не выполнять её действия. Удаление локального UI-пакета не удаляет серверный процесс. Серверное удаление не должно автоматически удалять общий локальный пакет, используемый для других серверов. Версии пакетов для разных серверов и политика выбора совместимой версии требуют детализации согласно FR-009.

Принято: декларативные экраны из встроенных компонентов как основной вариант, получение подписанного UI-пакета через Agent с отдельным подтверждением установки и автоматическая карточка состояния до установки UI. Новая функциональность в рамках поддерживаемых компонентов не требует обновления клиента; новые компоненты требуют. Открыто: точная схема, пределы компонентов, доверие к издателям, формат поставки и механизм обновления.

Источники: [FR-009](<../3. Функциональные требования.md>) и [NFR-SEC-010](<../4. Требования безопасности.md>); [Android Developers о динамической загрузке кода](https://developer.android.com/privacy-and-security/risks/dynamic-code-loading) рекомендует избегать её без необходимости, [Google Play](https://support.google.com/googleplay/android-developer/answer/16559646?hl=en) ограничивает загрузку исполняемого кода из внешних источников. Это основание сохранять декларативную схему, а не утверждение, что любой JSON-пакет автоматически безопасен или соответствует всем правилам публикации.

### 5.6. Обмен Agent с дополнительными модулями

Статус: **принято пользователем** — JSON-RPC 2.0 через локальный Unix-сокет, согласование версии/возможностей при запуске, обмен состоянием/данными/событиями/действиями, отдельные идентификаторы и отслеживание изменяющих операций без слепого повтора после потери связи. Также приняты явное неизвестное состояние результата, устаревание данных при обрыве и ограничения сообщений/очередей/ожидания как обязательный принцип. Описывается внутренняя граница отдельных процессов, а не окончательный публичный HTTPS/WSS API или маршруты EX-001–EX-040. Технические детали и отдельно отмеченные предложения ещё требуют проектирования.

**Транспорт и сообщения:** принят JSON-RPC 2.0 поверх локального Unix-сокета. Клиент телефона общается только с Agent; отдельные публичные порты модулей не требуются. Каждый управляемый процесс получает выделенный контекст подключения, связанный с зарегистрированным модулем и текущим экземпляром запуска. Конкретная организация сокетов, обрамление сообщений потока, лимиты и установление доверия ещё проектируются. JSON-RPC задаёт запросы/ответы/ошибки и уведомления, но сам не задаёт аутентификацию, границы сообщений в потоке, сохранение операций или гарантии доставки.

**Начало работы:** после запуска модуль согласует с Agent идентификатор, экземпляр запуска, поддерживаемые версии внутреннего протокола, возможности и схему предоставляемых данных/операций. Agent сверяет это с доверенной регистрацией, не доверяет одному заявленному `module_id`. До успешного согласования рабочие действия не маршрутизируются. Версия выпуска модуля и версия контракта различаются; неподдерживаемый контракт даёт диагностируемую несовместимость, не аварийное завершение Agent.

| Группа обменов | Предлагаемая ответственность |
|---|---|
| Состояние и возможности | Готовность, доступные источники/операции, признаки деградации, подтверждение связи и согласованное завершение |
| Текущие данные | Типизированные значения с единицами, идентичностью ресурса, временем измерения и причинами недоступности; Agent переиспользует снимки для всех телефонов |
| История и события | Модуль объявляет поддерживаемые ряды/события, Agent согласует расписание и лимиты хранения. Неподтверждаемые уведомления нельзя использовать как единственную гарантию записи важных событий |
| Операции | Именованное действие, проверенные параметры, идентичность устройства-инициатора, идентификатор операции, состояние/результат и структурированная ошибка |

**Сбор и история:** предлагается, чтобы Agent задавал политику сбора и сохранял разрешённые ряды дополнительных модулей через общий механизм истории. Это не означает автоматического применения CPU-интервалов/сроков ко всем сторонним метрикам. У модуля собственное пространство идентификаторов/версий метрик; изменения единиц или смысла ряда не должны смешиваться со старой историей. Передача параметров и снимков не должна запускать повторный сбор по числу телефонов. Частота, максимальное число рядов, бюджет дополнительных модулей и источник времени ещё требуют решения.

**Изменяющие действия:** Agent проверяет устройство, состояние модуля и допустимость вызова; модуль повторно проверяет свои параметры, текущие условия и права ОС. Модуль не получает токен мобильного устройства. Идентификатор JSON-RPC-запроса связывает ответ с запросом, но не является гарантией однократного выполнения. Приняты отдельный устойчивый идентификатор изменяющей операции и получение её состояния. При обрыве после отправки, когда результат неизвестен, не повторять действие автоматически. Пример: повторное создание резервной копии после потерянного ответа может создать второй объект. Срок хранения результатов/защиты повторов и восстановление состояния после аварии ещё проектируются; выполнение ровно один раз без таких механизмов не обещается.

**Потеря связи:** сохранять отдельно желаемое состояние, факт существования процесса и готовность протокола. Нет ответа — данные устаревают, новые действия недоступны, незавершённые операции могут иметь неизвестный результат. Отправленный запрос остановки без подтверждения не равен остановленному процессу. После переподключения сверять экземпляр запуска и состояния операций; старые сообщения другого экземпляра не принимать как новые результаты. Ошибки одного соединения не должны останавливать системные коллекторы или другие модули.

**Защита и ограничения:** ограничить размер/глубину JSON, число одновременных запросов, очереди, время обработки и частоту сообщений. Разделить политику заменяемых текущих снимков и сохраняемых событий/операций. Аутентификация соединения должна быть привязана к ожидаемому дочернему процессу и конкретному запуску; одно совпадение UID недостаточно для различения модулей под общим пользователем. Проверка peer credentials, права сокета и способ передачи параметров запуска — кандидаты, не готовая гарантия изоляции. Процессы с тем же UID или root по принятой архитектуре не считаются полностью изолированными. Ошибки и журналы не должны раскрывать токены, ключи или другие секреты.

**Разработка модулей:** контракт не должен требовать языка реализации Agent. Предлагается выпустить описание схем и небольшой SDK/пример подключения, чтобы модуль можно было реализовать на подходящем языке. Исходные пользовательские имена операций и точный JSON пока не фиксируются; это следующий уровень детализации после согласования обязанностей.

Принято: локальный JSON-RPC 2.0 через Unix-сокет, согласование версии/возможностей при запуске, единые правила времени/ошибок и отслеживание изменяющих операций без слепого повтора после потери связи. Общая запись истории дополнительных модулей — отдельное предложение; интервалы/бюджеты ещё открыты. Фрейминг, аутентификация, точные схемы и гарантии восстановления требуют проектирования.

Источники: [JSON-RPC 2.0](https://www.jsonrpc.org/specification) определяет корреляцию запросов/ответов и отсутствие подтверждения уведомлений; [Linux man-pages: unix(7)](https://man7.org/linux/man-pages/man7/unix.7.html) описывает локальные сокеты, их права и получение учётных данных другой стороны. Ни один из этих механизмов сам по себе не обеспечивает сохранение операций или изоляцию модулей под одним UID.

### 5.7. События, уведомления и аудит

**Статус: принято пользователем.** Нужны уведомления при закрытом приложении, без внешнего сервиса доставки; задержки допустимы. Agent формирует события по общим серверным правилам независимо от телефонов и ведёт отдельный аудит; правила редактируются через клиент с одинаковыми правами устройств. Телефон периодически догружает события и самостоятельно выбирает показ уведомлений; позиции чтения и настройки звука/показа индивидуальны. Для фоновых проверок принят WorkManager, точный интервал ещё не выбран. Обязательный облачный backend, push-relay и FCM не вводятся. Своевременная доставка и немедленное обнаружение остановки сервера не гарантируются; технические детали и открытые вопросы перечислены ниже.

**Принятое разделение:**

| Сущность | Назначение |
|---|---|
| Событие | Зафиксированный факт: изменение доступности источника, сбой драйвера/модуля, начало/завершение проблемы по правилу, результат обновления. Событие существует независимо от показа уведомления |
| Состояние проблемы | Текущее состояние конкретного правила/ресурса и связанная последовательность возникновения, изменений и восстановления; не новый алерт на каждый снимок |
| Уведомление | Представление события на конкретном телефоне с учётом его настроек и разрешения Android; доставка данных не равна факту показа уведомления |
| Аудит | Кто, когда, с какого зарегистрированного устройства выполнил управляющую операцию, над каким объектом и с каким результатом; это не журнал всех измерений |

**Серверное обнаружение:** Agent регистрирует события и оценивает согласованные серверные правила без подключённых телефонов. Для CPU/GPU/памяти/диска приняты настраиваемые порог, минимальная длительность нарушения, условие устойчивого восстановления и ограничение повторного оповещения. Численные значения пока не выбираются. Пример для обсуждения: высокая нагрузка CPU считается проблемой только после удержания порога заданное время; возврат требует устойчивого снижения, а не одного колебания. Отсутствие свежих измерений переводит оценку в недоступность/неизвестность, а не в подтверждённое восстановление. Сам по себе высокий процент использования GPU может быть ожидаемой работой, поэтому правила должны настраиваться, а не объявлять любую полную загрузку критической.

FR-010.2 задаёт локальные клиентские пороги статуса с глобальными настройками/переопределением сервера; CPU/GPU/безопасность имеют также собственные правила событий. **Принято:** серверные правила формирования событий общие для сервера, редактируются через клиент с одинаковыми правами устройств и действуют без телефона. Каждый телефон отдельно выбирает, какие события показывать уведомлениями. Локальные пороги отображения сохраняются, не переносятся автоматически на сервер и не подменяют правила событий. Клиент должен различать порог отображаемого статуса и правило, по которому сформировано событие; конкретный интерфейс этих настроек ещё проектируется.

**Фоновая доставка без внешнего сервиса:** принят WorkManager для периодической проверки доступности и чтения новых событий с Agent. Минимальный период повторяющейся задачи Android — 15 минут; фактический запуск может существенно задерживаться, в частности в Doze. Это не гарантия доставки за 15 минут. При открытом приложении новые события можно получать через согласованный HTTPS/WSS-обмен; фон не должен требовать постоянного двухсекундного опроса. При отсутствии сети телефона не сообщать «сервер упал». Если сам Agent/хост остановился, он не сможет отправить своё состояние; недоступность обнаруживается клиентом только при выполненной проверке. Отличать отсутствие ответа от доказанного выключения хоста. Сценарий немедленных оповещений при полном отказе сервера этой схемой не гарантируется.

**Догрузка и несколько устройств:** события получают устойчивые идентификаторы и порядок/курсор, каждый телефон хранит собственную позицию чтения и показанные уведомления. Прочтение на одном устройстве не удаляет события для других. При восстановлении связи клиент догружает доступные события, подавляет повторные уведомления и предлагает сводку старых событий вместо шквала сообщений. Если период отсутствия клиента превысил хранение событий либо часть потеряна, явно показать неполное покрытие. Получение страницы событий, её локальное сохранение и подтверждение позиции согласовать так, чтобы сбой не скрывал непрочитанные события. Отказ Android в показе уведомлений отражать в настройках, сохраняя события доступными внутри приложения. Настройки звука/показа локальны для телефона, просмотр не означает устранение серверной проблемы.

**Аудит по NFR-SEC-009:** записывать изменяющие действия с устройством-инициатором, стабильным идентификатором операции, временем, типом/идентификатором объекта, итогом или неизвестным результатом и безопасной причиной отказа. Системный процесс, обновляющая утилита и локальная CLI требуют собственных достоверных типов инициатора; нельзя доверять произвольному имени из запроса. Обычное чтение метрик не создаёт запись на каждый запрос. Не записывать токены, пароли, ключи, содержимое файлов или чувствительные параметры; имена/пути объектов минимизировать по согласованной политике. Отзыв устройства не должен удалять его идентичность из существующего аудита. Локальный журнал не является неизменяемым доказательством против администратора root/процесса с тем же UID.

**Хранение и отказы:** события и аудит требуют отдельных сроков/бюджетов, не скрыто занимают лимит истории CPU/GPU/сети. Ротация, частота, переполнение и потерянное покрытие должны быть наблюдаемыми. Фиксировать переходы и объединять повторы; служебный сбой записи нельзя рекурсивно логировать бесконечно. **Принято пользователем:** если Agent не может надёжно сохранить запись о начале изменяющего действия в аудит, он отказывается начинать это действие; мониторинг продолжает работать по возможности. См. раздел 5.8. Автоматическое исправление проблем, завершение процессов по порогу и перезапуск сторонних приложений этим предложением не разрешаются.

Приняты: общий серверный журнал событий и отдельный аудит, серверные правила с длительностью/восстановлением, периодическая фоновая догрузка с локальными уведомлениями и независимые позиции чтения телефонов. Также приняты отсутствие внешнего сервиса, допустимость задержек и разделение общих правил событий с индивидуальными настройками показа. Отказ начинать изменяющее действие при невозможности записать его начало в аудит принят отдельно в разделе 5.8. Периоды фоновых проверок, интерфейс отдельных порогов статуса/правил событий, сроки/бюджеты событий и аудита, технические детали обработки отказа аудита, схема событий и курсоров ещё открыты. Точка просмотра аудита в карте экранов также требует отдельного решения.

Источники: [FR-004.14 и FR-010.2](<../3. Функциональные требования.md>), [NFR-SEC-009](<../4. Требования безопасности.md>); [WorkManager](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work#schedule_periodic_work), [Doze/App Standby](https://developer.android.com/training/monitoring-device-state/doze-standby) и [разрешение уведомлений Android](https://developer.android.com/develop/ui/views/notifications/notification-permission). Доступность фоновой задачи и разрешение показа уведомлений — разные условия.

### 5.8. Сроки хранения журналов и сбой аудита

**Статус: принято пользователем после согласования всего пакета Р01–Р25.** Если Agent не может надёжно записать начало изменяющего действия в аудит, действие не начинается; мониторинг продолжает работать по возможности. Приняты сроки/бюджеты журналов и общая обработка отказа. Актуальная нормативная формулировка — AFR-036–AFR-040 и ASEC-010–ASEC-013. Раздел ниже сохраняет ход обсуждения; точные схемы и технические резервы ещё проектируются.

Предлагаемые начальные настройки серверных журналов:

| Журнал | Предельный возраст записей | Бюджет хранения |
|---|---|---|
| События мониторинга и безопасности | 7 суток | 32 МБ |
| Аудит управляющих операций | 30 суток | 64 МБ |

Это проектные значения по умолчанию, не норматив и не результат измерений. МБ означает 1 000 000 байт. Настройки общие для сервера и доступны в клиенте всем подключённым устройствам с принятыми одинаковыми правами. Реальный расход и достаточность значений нужно проверить на реализации.

**Очистка и отображение:** действуют оба ограничения: записи старше срока удаляются, а при достижении бюджета раньше срока вытесняются самые старые завершённые записи. Таким образом, 7/30 суток — верхняя граница возраста, а не обещание минимального покрытия. Клиент показывает фактический размер, доступный диапазон и сокращение покрытия из-за лимита. Уменьшение срока или бюджета с потерей записей требует подтверждения последствий; изменение политики само является аудируемой операцией. Бюджеты журналов не расходуют скрыто лимит истории метрик. В учёте нужно учитывать индексы; временный технический резерв ограничить и показывать отдельно, его размер и реализация пока не выбраны.

**Телефоны и активные проблемы:** ротация не ждёт, пока все телефоны прочитают журнал. При догрузке с устаревшей позиции Agent сообщает о пропуске и отдаёт доступные записи; отсутствующие записи не выдумываются. Текущее состояние активной проблемы хранится отдельно от истёкшей записи о её начале: ротация не должна изображать проблему устранённой. Сроки и бюджет локальной копии журналов на телефоне требуют отдельного согласования, серверные значения их автоматически не определяют.

**Поток событий:** повтор одной продолжающейся проблемы ограничивается и может объединяться с количеством повторов, временем первого и последнего наблюдения; возникновение и восстановление различаются. Аудит отдельных управляющих операций таким объединением не заменяется. Размеры записей, очереди и частота записи должны иметь ограничения; точные значения и механизм защиты от потока отказов ещё проектируются.

**Принятое правило и предлагаемые детали обработки отказа аудита:**

1. **Принято:** перед началом изменяющей операции должна быть надёжно сохранена запись о её начале. Если сохранить её нельзя, новое действие не начинается. Предлагаемые детали записи — идентификатор операции и инициатор; клиенту показывается понятная причина недоступности.
2. После выполнения сохраняется фактический результат. Если действие уже совершено, а результат записать не удалось, это не превращает действие в невыполненное. Клиенту сообщается известный результат и сбой аудита; при неопределённом результате показывается неопределённость, без автоматического повтора. После восстановления записи Agent пытается уточнить состояние по сохранённому идентификатору, если операция допускает проверку.
3. Метрики и доступное чтение продолжают работать по возможности; состояние аудита видно в ответах/состоянии Agent и не зависит только от записи события в тот же неисправный журнал. Сбой обычного журнала событий сам по себе не запрещает управляющие действия, если аудит исправен.
4. Достижение настроенного бюджета с успешной ротацией — штатный режим, не причина блокировки. Ошибка записи, повреждение хранилища, отсутствие места или прав — отказ. Ротация не должна удалять единственную запись о незавершённой операции; при невозможности обеспечить ограниченное хранение таких операций новые изменения приостанавливаются. Детали резерва и учёта состояния операций ещё открыты.
5. Минус этого выбора: при отказе аудита через клиент нельзя даже удалить файл ради освобождения места. Восстановление выполняется через SSH/локальное обслуживание с фактическими правами пользователя. Agent не повышает права автоматически и не обещает восстановить аудит внешних команд администратора. Такой отказ может временно лишить клиента управления сервером; это явный компромисс предлагаемой политики.

Источник: [OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html) рекомендует ограничивать расход ресурсов журналами, проверять отказы записи и сохранять работоспособность приложения при сбое логирования. Принятая приостановка новых управляющих действий — наш отдельный продуктовый выбор ради аудита, а не требование OWASP; мониторинг сохраняется по возможности, сохранение доступного чтения также предложено выше. Численные сроки и бюджеты источник не устанавливает.

## 6. Обновления: вопросы и плохие сценарии

Обновление запускается вручную. Системные модули разделяют процесс с ядром; дополнительные модули выполняются отдельно. Следующие пункты — вопросы реализации, а не утверждённый протокол обновлений:

| Риск или неоднозначность | Что предстоит определить |
|---|---|
| Новая версия модуля несовместима с ядром или клиентом | Версионирование контрактов, проверка совместимости до установки, условия согласованного обновления нескольких частей |
| Обновляется системный модуль | Предусмотреть возможный перезапуск всего Agent, восстановление API/WSS и отображение пропусков в истории; определить допустимую паузу |
| Обновляется дополнительный модуль | Определить обновление его процесса без перезапуска основного Agent и несвязанных дополнительных модулей |
| Идёт запись файла или другая изменяющая операция | Завершение текущих операций, отказ от новых, тайм-аут ожидания и поведение при принудительной остановке |
| Новая версия не запускается или зависает | Проверка работоспособности, ограничение перезапусков и возврат предыдущей версии |
| Модуль изменяет формат данных | Миграции, сохранение состояния и возможность отката после миграции |
| Обновление требует больше прав | Проверка совместимости и разрешений; штатная операция при недостатке прав отклоняется без автоматического повышения |
| Модуль потребляет общие ресурсы или имеет зависимости | Лимиты CPU/RAM/диска, зависимости между модулями и предотвращение влияния на остальные функции |
| Обновление вмешивается в сторонние библиотеки или системные пакеты | Отдельная упаковка зависимостей и границы изменений хоста |
| Источник пакета подменён или пакет повреждён | Подпись, целостность, доверенные источники и отзыв версий серверных модулей |

Отдельное обновление системного пакета и независимый перезапуск его функции — разные свойства. Формат поставки системных модулей, возможность менять их пакеты отдельно и связь их версий с версией Agent ещё не выбраны. Для дополнительных модулей сохраняется цель локализовать обновление в соответствующем процессе; изменение общего контракта может потребовать согласованного обновления нескольких частей.

### 6.1. Ручное обновление и восстановление

Статус: **принято пользователем** — ручное обновление через клиент/SSH либо серверную CLI, раздельное обновление совместимого дополнительного модуля, предварительная проверка и подготовка восстановления, автоматический возврат после провала проверки новой версии. Также приняты серверное выполнение независимо от связи с телефоном, отслеживание результата, запрет конфликтующих обновлений, сохранение идентичности/данных и запрет восстановления отозванных токенов при откате. Основание: FR-002.20, FR-009.13, требования безопасности к подлинности поставки и восстановлению после неудачного обновления. Конкретный формат выпуска, язык, СУБД, способ запуска утилиты и механизмы миграции/восстановления этим не выбираются.

| Что обновляется | Предлагаемый канал и область перезапуска |
|---|---|
| Agent и системные модули | Пользователь запускает обновление из клиента через SSH либо вручную через серверную CLI. Выпуск основного Agent меняется согласованно; требуется перезапуск основного процесса. Управляемые им дочерние модули также могут быть остановлены/перезапущены: независимость от перезапуска Agent не обещается |
| Дополнительный серверный модуль | Ручной запуск обновления через серверную CLI/установщик; возможность запуска из клиента через SSH предлагается как удобный канал обслуживания. При совместимых контрактах остановка/замена/запуск затрагивают только этот модуль. При изменении общего контракта или зависимостей заранее нужен согласованный план, а не обещание независимого обновления |
| Клиентский UI-пакет | Локальная установка новой проверенной совместимой версии после подтверждения пользователя; Agent и серверный процесс ради этого не перезапускаются. Версии пакета могут различаться между телефонами; совместимость проверяется для каждого сервера |

**Предлагаемый порядок:**

1. Определить текущие и целевые версии, фактическую ОС/архитектуру/зависимости, контракты клиента–Agent и Agent–модули, UI-контракты и схемы данных. Показать, что будет обновлено, какие функции прервутся и потребуются ли миграции/дополнительные права. Не обновлять несовместимые части молча и не включать автоматически отключённые модули.
2. До остановки работающей версии загрузить целевой выпуск в отдельное место, проверить подлинность/целостность и выполнить доступные проверки запуска/конфигурации. Наличие контрольной суммы без доверенного подписанного источника не доказывает подлинность. Предложение: клиент получает сведения о выпусках из доверенного каталога, серверный установщик повторно проверяет фактическую совместимость и артефакт перед заменой. Источник/модель доверия и частота проверки ещё не выбраны.
3. Проверить свободное место и права на новый выпуск, предыдущий выпуск и согласованную резервную копию изменяемых данных. Резерв обновления не должен незаметно вытеснять историю в обход её бюджета/подтверждённой политики. При недостатке места или невозможности подготовить восстановление не останавливать старую рабочую версию, сообщить причину.
4. Сохранить согласованное состояние и создать проверяемую консистентную копию данных, которые могут измениться при миграции. Остановить новые изменяющие операции и согласовать завершение уже начатых; длительные действия не повторять после тайм-аута без проверки результата. Остановить затрагиваемые процессы, применить миграцию и переключить выпуск. Атомарная смена указателя на код сама по себе не делает миграцию данных атомарной.
5. Запустить новую версию и проверить локальную работоспособность API, чтение настроек/истории и работу обязательных коллекторов; для модуля — согласование контракта и готовность его операций. Нормальное отсутствие GPU/стороннего сервиса не считать провалом выпуска. Клиент отдельно проверяет восстановление связи и совместимость. Потеря сети только на телефоне не является достаточным основанием для серверного отката.
6. Если проверка новой версии не проходит, выполнить заранее подготовленный возврат к проверенной предыдущей версии с совместимым состоянием данных. Если восстановление тоже не удалось, остановить бесконечные повторы, сохранить журнал и показать реальный либо неизвестный результат с инструкцией восстановления через SSH/CLI. Успех не объявляется только по факту запуска PID.

**Выполнение и конкуренция:** обновлением основного Agent должна управлять локальная утилита обслуживания вне обновляемого процесса; это не требует нового постоянного привилегированного сервиса. Предлагается сохранять на сервере идентификатор операции и этапы, обеспечить продолжение/восстановление после разрыва SSH/связи с телефоном и после перезапуска хоста. Способ запуска и восстановления утилиты ещё выбрать. Одновременно допускается одна конфликтующая операция обслуживания; остальные устройства видят состояние, а повторный запрос не начинает вторую замену. Пароль sudo и SSH-секреты остаются только в памяти клиента на время обслуживания. Повышение прав отдельно подтверждается/проверяется в SSH-сценарии; работающий Agent не получает постоянный helper.

**Граница отката:** сохранить файлы предыдущей версии недостаточно при несовместимой миграции. Для штатного обновления заранее требовать проверенный путь возврата: обратимую миграцию либо согласованное восстановление данных/переключение их подготовленной копии. Не обещать безопасный автоматический откат, если этот путь отсутствует. Конфигурация, история, идентичность Agent, TLS-ключи и устройства не должны теряться при успешном обновлении; повторный pairing не требуется. При возврате не восстанавливать отозванные токены и не отменять новые ограничения доступа. Состояние безопасности требует отдельного согласованного восстановления, не слепой замены всего каталога старой копией. Возможную потерю измерений между снимком и возвратом, срок проверки выпуска и время хранения резервов ещё определить. Внешние эффекты операций модуля, например изменения PostgreSQL, не откатываются автоматически возвратом его кода.

**Совместимость клиентов:** пока не выбран диапазон поддержки версий, нельзя обещать обновление всех телефонов без ограничений. До начала показывать известные несовместимости; порядок обновления клиентов/UI/Agent/модулей должен быть частью плана. Для давно отключённых телефонов нужны проверка при следующем подключении и понятное сообщение, а не гарантия знания их текущей версии.

**Подлинность и возврат версии:** автоматический возврат проверенного локального выпуска после ошибки — отдельный сценарий восстановления, не разрешение устанавливать любую старую версию из сети. Отозванные уязвимые выпуски, устаревшие метаданные и смена ключей издателя требуют политики. [TUF](https://theupdateframework.github.io/specification/latest/) описывает защиту от подмены, возврата к устаревшим версиям и замораживания метаданных; применение самой библиотеки/протокола пока не выбрано. [SQLite Backup API](https://www.sqlite.org/backup.html) иллюстрирует необходимость консистентного снимка активной БД; выбор SQLite этим не утверждается.

Принято: ручной запуск серверных обновлений из клиента через SSH либо CLI, отдельное обновление дополнительного модуля при совместимых контрактах, предварительная подготовка восстановления и автоматический возврат после провала проверки новой версии. Формат поставки, миграции, доверенные ключи, окно проверки/отката, хранение резервов и технический механизм продолжения/восстановления операции после разрыва связи или перезагрузки остаются открытыми.

## 7. Права мобильных устройств

**Принято в текущем диалоге:** все зарегистрированные мобильные устройства имеют одинаковые права и приоритет. Разделение телефонов на администратора и наблюдателя не выбирается.

Равенство прав не отменяет индивидуальные отзывные токены и идентификацию устройства для аудита. Оно также не означает, что любому устройству разрешено обходить ограничения ОС, модулей или серверной политики.

**Открыто:** кто и как разрешает новый pairing, как отзываются устройства и порядок конкурирующих изменений с одинаковым приоритетом. Все телефоны обращаются к одному Agent с одной серверной учётной записью исполнения; смена имени в локальной записи другого телефона не должна самовольно менять эту учётную запись.

## 8. Файловый доступ через пользователя Linux

**Принято, последнее решение пользователя:** весь основной процесс Agent запускается под существующим Linux-пользователем, указанным в клиенте при настройке сервера. Файловые операции выполняются в пределах прав этой учётной записи и ограничений службы; отдельный файловый исполнитель и отдельная служебная учётная запись ядра не выбираются.

**Критическая неоднозначность:** ввод имени пользователя сам по себе не подтверждает право действовать от его имени. Нельзя выдавать доступ root или другой учётной записи только по строке, переданной клиентом.

**Предложения по доверенной настройке выбранной учётной записи:**

- Учётная запись исполнения закрепляется на сервере при установке через SSH либо локальную CLI/конфигурацию. Передача её имени обычным API-запросом не должна менять пользователя запущенного процесса.
- При обычном SSH-подключении естественный кандидат — аутентифицированный пользователь установки. Выбор другой учётной записи нужно описать отдельно; root допускается с предупреждением в клиенте.
- Проверки файлового доступа выполняет ОС с учётными данными основного процесса; нельзя ограничиваться чтением отображаемых битов доступа.
- При недостатке файловых прав операция отклоняется с понятной причиной. Автоматическое повышение прав файлового менеджера не применяется.

**Принято по интерфейсу:** клиент предупреждает о рисках запуска Agent под root. Дополнительно предложено показывать выбранную учётную запись и предоставляемые права при настройке. Предупреждение не заменяет проверку доверия, авторизацию и ограничения операций.

**Открыто:** техническое подтверждение административных полномочий при выборе другой учётной записи; реализация подключения к готовому Agent по принятым правилам раздела 8.1; смена, удаление пользователя и переиспользование UID; обновление списка групп; реализация принятых ограничений корней и защиты собственных файлов Agent из раздела 8.2, включая взаимодействие с корзиной.

Ранее согласованное разделение ядра и файлового исполнителя отменено последним прямым решением пользователя. Обычные права пользователя и групп не равны автоматическому получению sudo или полного окружения его интерактивной сессии. Разрешённый запуск от root требует синхронизации с NFR-SEC-013.

### 8.1. Готовый Agent и несколько устройств

Статус: **принято пользователем** — правила первой установки, подключения дополнительных устройств, несовпадения пользователей и выделенной административной смены пользователя Agent. Решения об одном основном процессе, выбранной учётной записи исполнения и равных правах устройств сохраняются. Детали реализации ещё проектируются.

- При первой установке закреплять учётную запись исполнения на сервере. Обычный вариант — пользователь, прошедший SSH-аутентификацию; повышение для установки пакетов/службы само по себе не меняет выбранного пользователя исполнения на root. Отдельный выбор другой учётной записи требует подтверждённых административных полномочий.
- При подключении следующего телефона использовать существующий Agent и отдельный токен устройства. Все авторизованные устройства работают через тот же процесс с его фактическими правами, независимо от имени, введённого в новой форме. Имя SSH-пользователя не является персональной маской прав API.
- Если найден Agent под другой учётной записью, показывать фактического пользователя исполнения и последствия до завершения подключения. Не переустанавливать Agent и не менять владельца службы автоматически. При подтверждении доступа к существующему Agent и успешном доверенном pairing подключать устройство к нему; одной SSH-аутентификации произвольного пользователя сервера недостаточно для получения токена Agent.
- Смену пользователя работающего Agent считать отдельной административной процедурой через SSH/локальную CLI, с планом переноса прав конфигурации, TLS-ключей и истории и ожидаемым перезапуском. Не предлагать обычное поле профиля сервера как способ смены прав процесса. Детали миграции пока не определены.

Принято: при несовпадении SSH-пользователя и пользователя исполнения подключать к уже работающему Agent после явного подтверждения фактических прав и доверенного pairing. Разрешённые корни, защита файлов Agent, способ выдачи pairing-кода и техническая процедура административной миграции требуют отдельной детализации.

### 8.2. Область файлового доступа

Статус: **принято пользователем** — домашний каталог как начальная область, явно добавляемые корни с возможностью выбрать `/`, единая серверная политика для телефонов и защита собственных файлов Agent через API. Запуск Agent под выбранным пользователем, разрешённый root и отказ без автоматического sudo остаются принятыми решениями. Технические детали и полномочия изменения корней ещё проектируются.

Противоречие FR-007.2/FR-007.22 с общим принципом доступа по правам учётной записи Linux разрешено так: список корней дополнительно ограничивает область файлового менеджера, а ОС определяет допустимые операции внутри неё. Это принятое продуктовое ограничение, не выдающее прав сверх ОС. Персональные списки корней по пользователям ServerDeck в старых требованиях нужно заменить общей серверной политикой с учётом одного пользователя процесса и равных прав телефонов.

**Принятый вариант:** общая для сервера область файлового менеджера — настраиваемый список корней; первоначально домашний каталог пользователя Agent, дополнительные каталоги вроде `/srv` и `/var/www` добавляются администратором. Разрешить явный выбор `/` с предупреждением: тогда область охватывает файловую систему, но фактический доступ всё равно ограничен правами процесса и фиксированными запретами продукта. Политику хранить на сервере, а не отдельно на каждом телефоне. Кто и каким доверенным способом меняет список, ещё согласовать; список, который клиент свободно расширяет, не является независимым барьером против этого клиента.

**Принято по собственным данным Agent:** через общий файловый менеджер запретить чтение/скачивание TLS-ключей и секретов устройств, а также изменение/удаление исполняемых файлов и внутренней конфигурации/БД Agent; настройки и обновления выполняются предназначенными для этого операциями или через SSH/CLI. Защищать нужно объект и альтернативные пути доступа, не только текстовое имя каталога. В выбранной архитектуре это ограничения API, не гарантия изоляции от процессов с тем же UID или root. Полную защиту от администратора сервера не обещать.

**Пока открыто:** права изменения корней; точный список защищённых объектов; поведение при отсутствии или недоступности домашнего каталога; виртуальные ФС и специальные файлы; символьные/жёсткие ссылки, bind mounts и гонки пути. Старый FR-007 запрещает переход по символьным ссылкам; это правило не менять молча. Конкретный механизм безопасных операций по путям проектировать после выбора продуктовой политики и стека.

Техническое основание для дальнейшего проектирования: [Linux man-pages: openat2](https://www.man7.org/linux/man-pages/man2/openat2.2.html) описывает разрешение путей относительно каталога и ограничения переходов по ссылкам; это не выбор готовой реализации или гарантия защиты только проверкой строки пути.

## 9. Требования к ресурсам

**Принято в текущем диалоге:** численные требования к CPU, RAM и диску будут определены измерениями на готовом Agent. Общая цель — небольшое потребление ресурсов. Конкретные цифры пока не обещаются.

**Предложение:** измерять отдельно ядро, модули, сбор и хранение истории, активные подключения и передачу файлов. До получения измерений не назначать вымышленные минимальные требования; при проектировании всё равно предусматривать ограниченные очереди, размеры ответов и сроки хранения.

**Открыто:** детальные правила агрегации GPU/сети и пределы общего объёма истории. Глубина и временные уровни GPU/сети согласованы в разделе 9.1. Решение об измерении ресурсов не отменяет уже заданную политику CPU-истории.

### 9.1. Сбор, доставка и история метрик

Статус: **принято пользователем** — разделение сбора, доставки и хранения; работа основного сбора без телефонов; базовые интервалы из таблицы; уровни истории CPU/GPU/сети; отдельная свежесть блоков и отображение частичного отказа. Также согласованы явные пропуски в истории, сохранение записанной истории после перезапуска и сообщение о сбоях её записи. Детальные технические предложения и оставшиеся вопросы обозначены ниже. Основание: FR-005.9, FR-005.22, FR-010.3–010.4 и раздел 10 контекстного документа. Значения ниже — начальные настройки для проверки измерениями, а не обещание потребления ресурсов.

Разделить три независимые политики: измерение на сервере, передача текущих значений клиенту и сохранение истории. Основной сбор и история работают без подключённых телефонов. Несколько устройств получают результаты общих коллекторов; их запросы не запускают повторное измерение каждого ресурса. Настройка обновления на телефоне не меняет автоматически серверную частоту и историю. При запросе более частых обновлений сообщать фактическую частоту источника.

| Группа | Принятый базовый интервал сбора | Уточнения |
|---|---|---|
| Текущие CPU, RAM/swap, сетевые счётчики и динамические NVIDIA-метрики | 2 секунды | Общий сбор независимо от открытых экранов; способ и стоимость каждого источника проверить. Характеристики GPU и других устройств не перечитывать с той же частотой |
| Занятость файловых систем | 15 секунд | Изменения состава монтирований учитывать отдельно; медленная или недоступная ФС не должна блокировать общий ответ |
| Процессы для общего обзора и топов | 5 секунд | При открытом экране процессов или ресурса с топом — общий сбор не чаще раза в 2 секунды; возврат к обычному режиму после завершения подписок/ограниченного срока активности |
| Характеристики ОС, оборудования, интерфейсов и сводки сторонних сервисов | При запуске и раз в 60 секунд | При доступности дополнять уведомлениями об изменениях. Ошибка источника и восстановление проверяются отдельно с ограниченными повторами |
| Сетевые проверки latency/packet loss | Отдельная политика | Проверки по запросу и фоновые проверки не смешивать; фоновые цели, согласование между устройствами и частоту ещё определить |

Клиент по действующим требованиям получает карточки раз в 5 секунд, подробности раз в 2 секунды. Для HTTPS/WSS нужно согласовать смысл этих настроек, минимальную частоту и ограничения. На каждом блоке сохранять время успешного измерения, время последней попытки и причину недоступности; свежий ответ Agent не обновляет время старого значения. Принято считать регулярно обновляемый блок устаревшим после трёх пропущенных плановых обновлений; для источников по событиям/запросу нужны отдельные правила. Клиентский порог 60 секунд из FR-010.4 относится к доступности Agent и не заменяет свежесть источников. Принято отдельно показывать состояние «Agent доступен, но часть метрик устарела»; точные названия и правила сочетания клиентских статусов ещё согласовать.

**История:** действующее требование CPU сохраняется: точки за 15 секунд не менее часа, за минуту не менее суток, за 5 минут не менее 7 суток; не более 2000 точек на запрос одного CPU-графика. Для GPU и сети приняты такая же глубина и шаги, но собственные правила агрегации; пределы ответа для них ещё согласовать. Обязательная долговременная история RAM, файловых систем и каждого PID этим решением не добавляется. Точки за 15 секунд формируются из исходных измерений, а не из одного случайного снимка в конце окна.

**Детальные технические предложения для дальнейшего проектирования:**

- CPU: сохранить правила FR-005.9 — средние для нагрузки/состояний/PSI/частот, максимум температуры и throttling, последнее LA. При неполных окнах учитывать фактическое покрытие; средние объединять с весами по длительности/валидному покрытию, а не усреднять средние без весов.
- GPU: предложены средние utilization, мощности и занятой VRAM, а также максимумы температуры, мощности и занятой VRAM и признак наблюдавшегося throttling. Пиковый utilization и точный набор рядов ещё согласовать. Максимум означает максимум среди полученных измерений: пик между измерениями может остаться незамеченным.
- Сеть: хранить объём переданных/полученных байтов за валидные интервалы, длительность покрытия, среднюю и максимальную наблюдённую скорость, приращения ошибок/потерь. Среднюю скорость вычислять из объёма и длительности; накопительные счётчики не усреднять. Сбросы и смена экземпляра интерфейса разрывают последовательность, а не создают отрицательный трафик.
- По каждой метрике хранить полноту покрытия окна. Пропуски не заменять нулями и не скрывать соединением графика. После перезапуска Agent история остаётся; период простоя отмечается разрывом, для производных от счётчиков требуется новая исходная точка. Изменения системных часов не должны давать отрицательную длительность или незаметно склеивать интервалы; конкретный механизм времени ещё выбрать.

**Отказы и нагрузка:** ограничить очереди измерений, записи и доставки; при медленном клиенте текущий снимок заменять более новым, не накапливая бесконечную очередь. Аудит, события и результаты изменяющих операций требуют отдельной политики сохранения и не отбрасываются по правилу текущих снимков. При ошибке истории сохранять доступность текущих метрик и явно сообщать о деградации хранения. Переполнение/повреждение диска не считать успешной записью. Минимальную глубину истории нельзя обещать при недостаточном объёме: нужны оценка вместимости, настраиваемый бюджет, согласование приоритета сроков и лимитов и явное сообщение о нарушении покрытия. Не удалять защищённые настройки/ключи ради освобождения места. Предельную потерю ещё не записанных точек при аварийном завершении процесса определить отдельно.

**Открыто:** численные бюджеты диска и детальный порядок очистки; хранение событий/аудита; выбор хранилища; точные алгоритмы агрегации и обработки времени; пределы ответов GPU/сети; частота сетевых проверок; правила свежести источников по событиям/запросу; допустимая потеря ещё не записанных точек при аварии. Два бюджета через клиент и предупреждение о сокращении истории приняты в разделе 9.3. Базовые интервалы, уровни истории и отдельное отображение устаревших блоков уже приняты.

Технические основания: [статистика интерфейсов в документации ядра Linux](https://www.kernel.org/doc/html/latest/networking/statistics.html) описывает накопительные счётчики байтов/ошибок и различия источников; [рекомендации Prometheus по инструментированию](https://prometheus.io/docs/practices/instrumentation/) — стоимость сбора и ограничения числа рядов. Ссылки поддерживают технические принципы, а не предлагаемые интервалы или выбор Prometheus как зависимости.

### 9.2. Обсуждение истории на мобильном устройстве

Статус: пользователь согласился сохранить серверную историю и локальную копию полученных данных на клиенте после обсуждения ограничений хранения только на телефоне. Перенос всей истории исключительно на телефон не принят.

Хранение полученных данных на телефоне возможно и полезно для просмотра без связи. Однако хранение только на клиентах не обеспечивает непрерывную историю, если все устройства отключены, без сети или приложение не выполняет сбор. Пример: ночной перегрев нельзя восстановить утром, если в это время метрики нигде не сохранялись. Фоновый опрос не является надёжной заменой серверного хранения: Android Doze ограничивает сеть и фоновые задачи; периодические задания WorkManager имеют минимальный интервал 15 минут и неточное время запуска. Основания: [Doze и App Standby](https://developer.android.com/training/monitoring-device-state/doze-standby), [периодическая работа WorkManager](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work#schedule_periodic_work).

**Принятая общая схема:** сервер хранит согласованную историю независимо от телефонов, каждый клиент сохраняет локальную копию полученных диапазонов и при подключении запрашивает недостающие данные в пределах сохранённой сервером глубины. Постоянное мобильное соединение для накопления истории не требуется. При недоступности сервера клиент показывает только ранее загруженные данные с их временем и пропусками; неполную локальную копию нельзя представлять как полную историю. Новое устройство получает доступную серверную историю после авторизации, а не начинает её с нуля. Детали синхронизации ещё проектируются.

Вариант «короткий серверный буфер + более длинная история на телефоне» также возможен, но меняет гарантию: после отсутствия клиента дольше срока буфера пропуски не восстанавливаются из Agent. Несколько телефонов могут иметь разные покрытия локальной истории; подтверждение получения одним устройством не должно автоматически удалять данные, нужные другим. Удаление приложения/его данных лишает устройство локальной копии при отсутствии отдельного восстановления. Сроки и бюджет мобильного хранения, синхронизация, изменение агрегатов и удаление данных пока не выбраны.

### 9.3. Настраиваемый объём истории и предварительная оценка

**Принято пользователем после обсуждения:** в настройках клиента дать возможность выбрать два бюджета — историю на конкретном сервере и локальные копии на этом телефоне. Также приняты отображение использования/покрытия, вытеснение старейших точек при достижении бюджета, предупреждение о сокращении глубины меньше 7 суток и подтверждение последствий уменьшения лимита. Численные значения по умолчанию и детальные алгоритмы не выбраны.

**Принято по настройкам:** два явно обозначенных бюджета: история на диске конкретного сервера и локальная история на этом телефоне суммарно для добавленных серверов. Серверный бюджет хранится и применяется Agent, общий для всех устройств. Локальный бюджет действует только на конкретном телефоне. **Техническое предложение:** клиент отправляет именованную операцию изменения и показывает подтверждённое сервером значение; не выдавать локальное изменение за успешное изменение серверной настройки при отсутствии связи. Конкурирующие изменения с нескольких телефонов требуют проверки версии настройки; уведомление о конфликте предпочтительнее незаметной перезаписи. Контракт изменения настройки ещё не выбран.

В интерфейсе показывать: установленный лимит, фактическое использование, оценку объёма для согласованных сроков хранения, фактическое покрытие и пропуски. Численные значения по умолчанию определить после измерений. При увеличении бюджета прежние удалённые точки не восстанавливаются из воздуха; при уменьшении заранее показать последствия очистки и получить явное подтверждение удаления данных.

**Принято при достижении лимита:** вытеснять старейшие точки, сохраняя свежие, и сообщать о сокращении покрытия. Глубина 7 суток остаётся целевой согласованной политикой; слишком малый бюджет не позволяет гарантировать её. Предупреждать об этом и предлагать увеличить бюджет либо явно согласиться на сокращение глубины. При уменьшении лимита показывать последствия удаления данных и запрашивать подтверждение. **Техническое предложение:** сначала удалять точки старше заданного срока. Правила очистки между уровнями/рядами и между серверами на телефоне ещё выбрать. Прежнее предложение о штатной остановке записи при полном бюджете пересмотрено: сохранять свежую историю. Ошибка записи из-за реального заполнения ФС или её недоступности — отдельное состояние отказа.

**Расчётная иллюстрация, не измерения готового Agent:** при полном заполнении всех трёх уровней одна скалярная серия содержит `3600 / 15 + 86400 / 60 + 604800 / 300 = 3696` точек. Уровни считаются независимо, с перекрытием по времени. Серия — один числовой показатель одного объекта; среднее и максимум считаются разными сериями. Динамические характеристики CPU-ядер, GPU и интерфейсов увеличивают число серий. Количество серий пока не определено окончательным контрактом.

Для иллюстрации принять условную стоимость одной сохраняемой точки 32–64 байта. Это допущение для арифметики, не подтверждённая стоимость записи, не нижняя/верхняя граница фактического формата и не выбор СУБД. Формула: `3696 × число серий × байт на точку`.

| Условное число серий на сервере | Объём по модели 32–64 байта на точку |
|---|---|
| 100 | 11,8272–23,6544 МБ, округлённо 12–24 МБ |
| 500 | 59,136–118,272 МБ, округлённо 59–118 МБ |
| 2000 | 236,544–473,088 МБ, округлённо 237–473 МБ |

В этой таблице 1 МБ = 1 000 000 байт. Не включены отдельно события/аудит, постоянные метаданные, файлы Agent, корзина, исходные двухсекундные снимки и история каждого PID. Схема хранения может оказаться как компактнее, так и существенно больше модели. На телефоне объём зависит также от количества серверов, загруженных диапазонов и формата локальной БД; сумма серверных оценок — лишь ориентир для полных копий при том же формате и уровнях.

Лимит должен учитывать реально выделенные файлы истории и накладные расходы записи, а не только сумму полезных значений. Для иллюстрации: SQLite, если будет выбран, использует страницы, индексы и дополнительные файлы журнала/WAL; удалить строки недостаточно, чтобы гарантировать немедленное уменьшение размера файлов. До обещания жёсткого физического лимита определить резерв для транзакций/обслуживания, границу учёта и механизм ограничения. Основания: [формат файлов SQLite](https://www.sqlite.org/fileformat.html), [WAL](https://www.sqlite.org/wal.html). Выбор SQLite этим не утверждается. Измерения после реализации должны заменить условные байты на точку оценкой для фактической схемы и конфигурации сервера.

## 10. Сетевой доступ

**Статус:** общая схема принята пользователем после обсуждения. Конкретные параметры TLS, значения лимитов и формат протокола ещё не утверждены.

**Принято:** прямое HTTPS/WSS-подключение телефона к Agent по IP или домену. REST и WebSocket используют один настраиваемый TCP-порт; 8443 — возможный пример, а не выбранное обязательное значение. Обязательные VPN, reverse proxy и центральный relay не добавляются. По существующему VPN/локальной сети используется тот же протокол с внутренним адресом.

**Принятый общий процесс настройки:**

1. Клиент получает адрес, порт, пользователя и параметры SSH. Перед установкой проверяются SSH-идентичность, права и выбранный режим сетевого доступа.
2. Установщик создаёт индивидуальный TLS-ключ и самоподписанный сертификат Agent с явным доверием конкретному серверу в клиенте; обязательного домена нет. При стандартной проверке адреса IP/DNS должны соответствовать SAN сертификата.
3. По проверенному SSH-каналу клиент получает TLS-отпечаток и одноразовый pairing-код. При ручной установке сведения получают из CLI, отпечаток подтверждает пользователь.
4. Клиент проверяет HTTPS-доступность с телефона и совпадение TLS-идентичности до передачи pairing-кода или токена. Нельзя принимать любой сертификат или автоматически заменять закреплённое доверие.
5. Выполняются pairing, защищённое сохранение токена устройства и первый запрос метрик. После первого корректного снимка создаётся готовая запись сервера.
6. Дальнейшие REST/WSS-запросы используют токен конкретного устройства; равенство прав телефонов не означает общий токен.

Пункты о проверке SSH/TLS, pairing, токене и первом снимке также основаны на UC-001 и NFR-SEC-003/006/023. Самостоятельный выпуск сертификата и закрепление доверия согласованы как подход. Конкретное значение порта, срок сертификата, ротация и техническая реализация проверки доверия требуют детализации.

**Существующие режимы по FR-002.12 и NFR-SEC-024:** «Не открывать», «Только локальная сеть», «Любой адрес». По умолчанию — наиболее ограниченный режим. Открытие порта и изменение firewall выполняются только после явного выбора, режим «Любой адрес» сопровождается предупреждением. Последние решения о процессах и пользователях эти правила не отменяли.

**Предложение по firewall:** поддержать точечные изменения распознанной конфигурации UFW для Ubuntu/Debian; не включать, не отключать и не сбрасывать firewall автоматически. Сохранять сведения о созданных установщиком правилах, удалять только собственные изменения. Для неизвестной конфигурации или внешнего firewall провайдера показывать инструкцию, затем повторять проверку с телефона. Успех локальной команды не означает достижимость Agent извне. Учитывать IPv4 и IPv6.

**Плохие сценарии и открытые вопросы:**

- Режим «Не открывать» сейчас описан как прослушивание только localhost: телефон напрямую не подключится, мастер не получит первый снимок. Нельзя считать такую установку завершённым добавлением сервера; нужно явно определить дальнейшую настройку. VPN сам по себе не делает localhost сервера доступным телефону.
- Не определять доверенную локальную сеть автоматически по публичной подсети VPS; нужен явно выбранный интерфейс/диапазон.
- При NAT/CGNAT либо внешнем firewall открытие локального порта недостаточно; проброс, VPN или изменение внешних правил остаются действиями администратора, если отдельная автоматизация не согласована.
- Ротация/истечение сертификата, смена адреса, IPv6, параметры TLS, сроки pairing-кода и пределы запросов требуют детализации.
- HTTP API и WSS должны иметь одинаковые правила аутентификации; для проверки соединения не добавлять публичный диагностический API в обход NFR-SEC-006.
