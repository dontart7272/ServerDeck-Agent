# Модульная система, IPC и UI

Версия: 1.0, 12 октября 2026 года. Статус: специфицировано; реализация/испытания отсутствуют. Основания: AFR-003, AFR-005, AFR-051–AFR-059, AFR-070/071 и ASEC-009, ASEC-020–ASEC-024, ASEC-028. Связанные документы: [API](<3. API и форматы данных.md.md>), [конфигурация](<7. Пример конфигурации.md.md>), [архитектура](<8. Архитектура и обслуживание.md>).

## 1. Классы и доверие

Десять системных модулей компилируются в Agent; нельзя отключить/удалить их через реестр. Дополнительные модули — отдельные процессы с ручной доверенной регистрацией. Манифест не назначает системный статус и не даёт OS-права. Общий UID позволяет модулю вмешиваться в другие файлы/процессы этого UID; список capabilities ограничивает маршрутизацию честного ядра и не является sandbox.

Серверный модуль и клиентский UI имеют независимые версии/жизненный цикл. Приложение обнаруживает карточку после проверки реестра; установка UI требует отдельного подтверждения. Удаление интеграции не удаляет Docker/стороннее приложение. Непроверенный UI не получает доступа к секретам, системным экранам подтверждения и приватным API.

## 2. Манифест и регистрация

Формат JSON, [полная структурная схема](<contracts/module.schema.json>). `manifest_version=1`, SemVer для версии кода; совместимость — интервалы `{min_inclusive,max_exclusive}`, а не произвольные выражения. module_id/publisher_id — обратный DNS `[a-z0-9]` с точками/дефисами до 128 символов. Совпадение имени издателя не доказывает доверие к коду.

| Поле | Смысл и ограничения |
|---|---|
| module_id, publisher_id, version | Устойчивая идентичность, явная новая версия; зарезервированный `serverdeck.system.*` запрещён |
| compatibility | OS linux, architectures amd64/arm64; интервалы Agent, IPC major/minor, data schema |
| execution | mode managed/external; managed executable абсолютный и проверенный, args отдельным массивом, code_dir/data_dir; без shell/substitution |
| dependencies | module_id + диапазон версии + required bool; до 32, без циклов/самоссылок |
| reads, actions | id/schema/version/timeout; actions имеют effect/cancellation/confirmation/reconcile описания; до 64 каждого |
| series | id/unit/value_type/aggregation/interval_ms/max_cardinality/history_allowed; до 256 объявлений |
| ui | Необязательные package digest/size/version/publisher, диапазоны server schema/client UI; не URL произвольного сервера |
| resource_request | max_series, history_budget_bytes, желаемые CPU/RAM; регистрация не означает выдачу запрошенного |

В schema для параметров/data допускается ограниченный JSON Schema draft-07: object/properties/required/additionalProperties=false, scalar, enum, bounded array, min/max, local `$ref` только `#/definitions/Name` в корневые definitions документа (без вложенных pointer/escaped names), oneOf с discriminant. Remote refs, regex произвольной сложности, executable validation и рекурсивные ссылки запрещены; глубина схемы 16, общий размер включённых схем 256 КБ. E01 дополнительно ограничивает разворачивание DAG локальных ссылок 10000 посещений, проверяет неиспользуемые definitions и требует конечные maxLength/maxItems, min/max для чисел; arbitrary pattern/format/custom keywords отклоняются. Это защита декларативного входа, не доказательство доверия IPC или безопасности процесса. Семантический валидатор доказывает bounds каждого variable-size узла. Все вложенные схемы properties/items/additionalProperties проверяются также рядом с const/enum/oneOf, до компиляции, с общими лимитами глубины и посещений; содержимое значений const/enum остаётся данными. Это обязательная вторая проверка после структурной схемы манифеста.

Команда `serverdeckctl module register --manifest <path>` читает файл от владельца Agent/root через локальный доверенный канал. Проверяет владельцев/права кода и каждого родителя, symlink, digest code tree, совместимость/граф, схемы/namespace, бюджет и план разрешения запуска. Код не обязан находиться под `/opt/serverdeck`, но путь должен быть явно принят; расположение в чужом изменяемом каталоге — отказ. Реестр — критические таблицы БД, а не автоматическое исполнение появившегося JSON. Сохранение intent + новой регистрации атомарно в критической БД; наблюдатель читает revision, проверяет snapshot и активирует без полного restart. Ошибка проверки сохраняет предыдущую рабочую регистрацию, карточка показывает отказ новой версии.

Установка кодовых файлов/смена UID выполняются через SSH/CLI с фактическими правами. Сеть может менять только политику уже зарегистрированного кода/желаемое состояние и удалять собственные объекты при наличии прав. Подмена кода после регистрации обнаруживается перед стартом; без проверки нельзя запускать по одному имени executable.

## 3. Граф и жизненный цикл

`desired=enabled|disabled`, `process=stopped|starting|running|stopping|exited|unknown`, `ipc=disconnected|handshaking|ready|unresponsive`, `health=ok|degraded|error|incompatible`. Присутствующий PID не означает ready. Эффективные capabilities содержат `can_start/can_stop/can_remove`, `resource_isolation` и причины отказа.

Required dependency готова до запуска зависимого. Падение dependency делает зависимого degraded и запрещает только зависимые операции, не независимые функции. План отключения/удаления перечисляет транзитивно затронутые модули и версии; второй телефон, изменивший граф, инвалидирует план. Системные функции не зависят от дополнительных модулей.

Managed: отдельная process group, без daemonize/setsid потомков; перезапуск после аварии с задержками 1,2,4,8,16 секунд, не более пяти автоматических рестартов в скользящем окне 600 секунд. Счётчик сохраняется между рестартами Agent, не обнуляется ради обхода. После лимита — error до ручного запуска. Heartbeat 5 секунд, три пропуска — unresponsive; зависание не порождает параллельный экземпляр. Stop: IPC shutdown, до 15 секунд, затем SIGKILL управляемой группе/доступной cgroup, проверка отсутствия потомков. Результат неизвестной операции не становится failed только из-за убийства процесса.

Если доступна делегация cgroup v2, каждый managed module получает подгруппу с MemoryMax/CPUQuota/pids.max по выданному профилю; ядро размещается отдельно от домена детей по правилам cgroup v2. Если делегации нет — только bounded IPC/очереди/контроль жизненного цикла, `resource_isolation=unavailable`. Нельзя вводить RLIMIT_NPROC для всего UID. Уход потомка из группы недопустим по контракту и требует диагностики; process group не объявляется защитой от злонамеренного кода. Остановка основного unit завершает всю его cgroup, а не только известные PID.

Отключение сохраняет регистрацию/данные/настройки; удаление сохраняет данные по умолчанию, purge_data подтверждается отдельно. Отказ прав/аудита не превращается в успех и не удаляет чужой код. Обновление требует проверки нового графа, сохранения старой регистрации, quiesce, проверки совместимости данных и возврата; эффекты во внешнем приложении не откатываются сменой кода.

## 4. Framing и handshake IPC

AFR-054/057; ASEC-021/022. Unix `SOCK_STREAM`. Каждый frame: 4 байта unsigned big-endian длины payload, затем ровно N байт UTF-8 JSON; N=1..1 000 000. EOF в заголовке/payload закрывает канал без исполнения неполного сообщения. Глубина JSON <=32, duplicate keys запрещены. Один frame — одно сообщение JSON-RPC 2.0; batch не поддерживается. Поля `id` строковые до 64 символов, result/error взаимоисключающие. [Структурная схема](<contracts/ipc.schema.json>), JSON-RPC [официальная спецификация](https://www.jsonrpc.org/specification); framing/тайм-ауты — решения ServerDeck.

Agent создаёт runtime каталог 0700, socket 0600; для внешнего UID — отдельный socket с точечной ACL и защищённым родителем, без общего 0777. Managed instance получает по унаследованному read-only FD3 одноразовые registration_id, instance_id, secret 256 бит, endpoint и expiry; FD закрывается после чтения, env/argv секрет не содержат. Неиспользуемые FD и credentials закрываются до exec. Peer SO_PEERCRED должен совпадать с зарегистрированными UID и ожидаемым PID экземпляра. Secret в hello не журналируется.

Первое сообщение в течение 5 секунд — `hello {registration_id,module_id,instance_id,secret,ipc_min,ipc_max,capabilities,schema_digest}`. Agent атомарно потребляет секрет, сверяет действующую регистрацию/экземпляр/peer/version/digest и отвечает `welcome {session_id,ipc_version,grants,limits,agent_run_id}`. После этого все сообщения связаны с этой сессией. Старый secret, второй канал того же instance и неверный peer отвергаются. Secret действует 30 секунд и только на один handshake. Reconnect managed требует новой выдачи через доверенный канал и сверки живого экземпляра, а не replay прежнего hello.

Для external-process нельзя притворяться, что Agent может передать FD произвольному уже запущенному PID. Администратор регистрирует UID/endpoint и запускает внешний supervisor через доверенный launcher `serverdeckctl module external-session`: launcher, работающий с фактическими разрешёнными полномочиями, получает ограниченный одноразовый FD и передаёт его своему ребёнку. IPC pairing FD через отдельный локальный admin socket разрешён только ранее зарегистрированному UID/launch policy, не предоставляет сетевой токен или произвольную CLI. Точная выдача для другого UID требует проверенного OS-адаптера/ACL, без него канал недоступен; см. TECH-IPC в разборе готовности. Отдельный UID не даёт права Agent посылать сигнал/останавливать внешний unit.

## 5. Методы IPC и устойчивые действия

| Направление / метод | Params → result |
|---|---|
| module→Agent `hello` | Handshake выше → welcome |
| Agent→module `collect` | sample_id, requested_series, monotonic deadline → block, source observation timestamps, объявленные records/metrics |
| Agent→module `read` | read_id, typed params, request_id → typed data, observation/freshness |
| Agent→module `operation.prepare` | operation_id, action_id, typed params/digest → допустимость/фазы/отмена/план; без эффекта |
| Agent→module `operation.execute` | operation_id, action_id, typed params/digest, durable_intent_receipt → быстро accepted или known result |
| module→Agent `operation.report` | operation_id, revision, state, effect, safe result/error → durable receipt после commit |
| Agent→module `operation.reconcile` | operation_id, params_digest → известный результат либо unknown; не повторяет execute |
| Agent→module `operation.cancel` | operation_id/revision → подтверждённая отмена либо too_late |
| module→Agent `event.publish` | event_id, declared kind/resource, safe data → receipt/sequence после сохранения |
| оба `heartbeat` | session_id/sequence → liveness; notification без гарантий хранения |
| Agent→module `shutdown` | reason/deadline → stopping; отсутствие ответа не подтверждает остановку |

Обычный RPC <=10 секунд. execute возвращает accepted до долгой работы; все изменяющие методы имеют id и dedup, timeout не отменяет эффект. Ядро сохраняет intent до execute; модуль не выполняет действия по notification. Модуль хранит receipt/результат до подтверждения Agent с bounded outbox; при заполнении запрещает новые эффекты, сообщает degraded. После crash ядро вызывает reconcile, не execute вслепую. Неспособный обеспечить такой контракт модуль может иметь read-only capabilities, а не неподтверждённые изменяющие операции. receipt доказывает запись в Agent, не внешнюю транзакционность приложения. Токен/SSH-секрет телефона в params не передаётся; инициатор — безопасный id для корреляции, ядро остаётся авторизатором.

Лимиты на сессию: 8 in-flight RPC, 32 queued, 64 сообщения/с burst 128, outbox 1000 записей/4 МБ, до 256 активных numeric series на модуль, максимум 4096 суммарно по дополнительным. При сверхлимите typed `RESOURCE_EXHAUSTED`; после трёх нарушений за минуту канал закрывается, запуск ограничен restarts. collect не выполняется повторно параллельно зависшему вызову. Контент произвольных файлов через IPC не маршрутизируется; крупные объявленные данные разбиваются на порции, каждый chunk имеет seq/total/digest и общий bound.

JSON-RPC errors: -32700 parse, -32600 invalid request, -32601 unknown method, -32602 invalid params, -32603 internal; ServerDeck -32001 unauthorized, -32002 incompatible, -32003 unavailable, -32004 conflict, -32005 resource exhausted, -32006 audit unavailable. `error.data` содержит безопасный API code/effect/operation_id, без секретов. Неверный handshake получает только общий отказ и закрытие.

## 6. Ряды, расписание и история

Namespace `module.<module_id>.<series_id>.<schema_version>`. Agent выдаёт только согласованные серии/частоту/кардинальность/квоту; новые экземпляры ресурса проходят ограничение cardinality. Интервал 1000..3 600 000 мс, по умолчанию 5000; модуль не увеличивает общий системный сбор. Дополнительная история суммарно <=25% server history budget, квоты выдаются явно, по умолчанию 0. Недопущенные серии не сохраняются. Нечисловые строки не превращаются в историю метрик. Переход схемы/единиц создаёт новый ряд. Падение IPC оставляет last-good значения stale, не null/zero без причины. Активные проблемы не исчезают при отключении модуля: статус наблюдения source_unknown, восстановление только после валидной проверки.

## 7. UI-пакет v1

AFR-058/059, ASEC-023/024. ZIP с ровно `manifest.json`, `ui.json`, `signature.json`, ресурсами `assets/` и локализациями `locales/`. [UI schema](<contracts/ui.schema.json>) описывает подписываемый manifest и дерево ui. manifest содержит module_id/publisher_id/package_version/ui_schema/server_schema/client_components, inventory каждого файла (путь/size/SHA-256). signature.json содержит algorithm `Ed25519`, key_id и signature base64url. Подписываются точные UTF-8 bytes manifest.json с domain prefix `ServerDeck UI v1\n`; manifest перечисляет digest ui/resources/locales. Signature не подписывает саму себя. Не требуется неоднозначная пересериализация JSON. Клиент проверяет подпись доверенного отдельно ключа и все inventory bytes до активации; key из пакета не добавляется в trust store. Путь установки/backup защищён клиентом, рабочая версия переключается после всех проверок. Новая версия/старый подписанный пакет не принимаются автоматически без проверки совместимости и подтверждения.

Профиль ui-v1: архив <=5 МБ, распаковано <=20 МБ, <=256 файлов, отдельный JSON <=1 МБ, путь <=128 байт, глубина JSON <=32, дерево UI <=512 nodes/глубина 16, <=32 screens, до 16 locales; картинки только PNG/WebP без анимации, <=2048×2048 и суммарно <=16 млн decoded pixels. Нет ссылок/hard links/absolute paths/`..`, дубликатов ZIP entry/case-collision, encrypted ZIP или вложенных архивов. Размер проверяется фактически при распаковке, не по заголовку. Пакет с неизвестным компонентом целиком несовместим, безопасная общая карточка остаётся доступной.

Встроенные компоненты v1: `column`, `row`, `section`, `text`, `metric`, `status`, `chart`, `table`, `text_input`, `number_input`, `toggle`, `select`, `button`. Обязательны уникальные node_id; row/column/section содержат children; остальные не содержат произвольных children. Layout только численные bounds/предопределённые token IDs; HTML/CSS/JS/DEX/native libraries/URL загрузки отсутствуют. Text локализован по key, никакого eval. Binding — JSON Pointer в ответ зарегистрированного read_id/series, не файловый путь/код. Chart только разрешённые numeric series, table <=100 строк на страницу, <=16 колонок. Формы используют зарегистрированные типы/bounds, не произвольный шаблон запроса.

Button задаёт action_id, фиксированное отображение проверенных form fields и безопасные literal values, а не URL/HTTP method/shell. Сервер повторно валидирует параметры; доступность кнопки не является правом. Нативное приложение показывает prepare/confirmation, издатель не может скрыть последствия/подменить объект. UI не меняет trust, токены, SSH-настройки, серверные roots или системные диалоги через скрытый binding. Смежная Android-реализация и матрица компонентов обязательны для завершения, серверная проверка пакета их не заменяет.

## 8. Неисправности и проверки

Неверная регистрация/цикл/несовместимость — до запуска, предыдущая запись сохраняется. Нет IPC/слишком большой frame/flood — деградация конкретного модуля; ядро продолжает доступное чтение. Нет аудита — запрещены start/stop/policy/remove/actions и автоочистка, доступное наблюдение продолжается. Crash после effect/report — reconcile, unknown сохраняется. Нет прав external stop — routing disabled и process running/unknown отдельно. Нет cgroup delegation — отсутствие resource isolation объявлено. См. процедуры V-MODULE/V-UI в [плане](<9. План реализации.md>) и записи [журнала](<11. Журнал проверки требований.md>).

Официальные основания, проверено 12 октября 2026: [systemd kill v249](https://raw.githubusercontent.com/systemd/systemd/v249/man/systemd.kill.xml), [systemd service v249](https://raw.githubusercontent.com/systemd/systemd/v249/man/systemd.service.xml), [cgroup v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html), [Ed25519 RFC 8032](https://www.rfc-editor.org/rfc/rfc8032). Профиль ZIP/UI и локальный launcher — технические решения ServerDeck; не заявляют готовую изоляцию или проверенную реализацию.
