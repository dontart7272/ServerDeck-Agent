# API и форматы данных ServerDeck Agent

Версия спецификации: 1.0. Дата: 12 октября 2026 года. Статус: специфицировано в рамках AFR/ASEC; приложение не реализовано, совместимость и безопасность не испытаны. Новые продуктовые гарантии не вводятся. Неразрешённые границы отмечены в [разборе препятствий](<10. Противоречия и готовность.md>).

## 1. Источники и представление

Нормативная база: [AFR](<2. Функциональные требования.md>), [ASEC](<4. Требования безопасности.md>). Связанные спецификации: [модули/IPC/UI](<5. Модульная система.md.md>), [конфигурация](<7. Пример конфигурации.md.md>), [архитектура и хранение](<8. Архитектура и обслуживание.md>). Машиночитаемые ограничения — [контракт сообщений](<contracts/api.schema.json>); он описывает типы, таблицы ниже — семантику, права и порядок эффектов. Одного прохождения JSON Schema недостаточно для разрешения действия.

JSON UTF-8, media type `application/json`. Размеры считаются по фактическим несжатым байтам; сжатый вход не принимается. Дубликаты декодированных ключей, NUL, невалидный UTF-8/непарные UTF-16 surrogate escapes, NaN/Infinity, глубина более 32 и неизвестные поля запроса отклоняются. Корневой контейнер считается глубиной 1; число элементов массива и членов объекта <=4096, более строгие schema bounds сохраняются. JSON number должен быть конечным float64, без ненулевого underflow; экспонента -324..324 ограничивает стоимость точной арифметики валидатора. U64 передаётся строкой и этим float64-ограничением не ограничивается. Обычные запросы/ответы не более 1 000 000 байт; страница истории до 4 000 000 байт. Лимит проверяется до полной загрузки/разбора. Контент файлов передаётся отдельно.

`Id` — UUID v4 в нижнем регистре; `Version` — непрозрачная строка до 256 символов. `U64` — десятичная строка без знака/ведущих нулей, включая `"0"`, максимум 18446744073709551615, чтобы не терять точность в JSON-потребителях. Проценты/скорости/температуры — конечные JSON number. UTC timestamps — RFC 3339 с `Z`, до наносекунд; время клиента не служит основанием авторизации/истечения. `duration_ms` и размеры — целые числа в явно указанном диапазоне. UUID boot ОС и идентификатор запуска Agent независимы.

API major — в пути `/api/v1`; minor — поле `schema_version: "1.0"`. Новые необязательные поля ответа допускаются в minor; клиент игнорирует неизвестные поля ответа, но не неизвестный discriminant/enum. Новая обязательная семантика, изменение единиц/смысла поля или ослабление проверки требуют major. Поддерживаются текущая и предыдущая выпущенная major; у первой v1 предыдущей выпущенной major нет. В дальнейшем нужны отдельные адаптеры и одинаковые проверки безопасности для двух версий, а не механическая смена префикса. Несовместимость не запускает действие.

## 2. Bootstrap, авторизация и маршруты

AFR-011, AFR-060–AFR-065, AFR-071; ASEC-002–ASEC-008.

Доверенный CLI через проверенный SSH выдаёт ограниченный bootstrap: `agent_id`, адреса/SAN, порт, fingerprint SHA-256 DER сертификата, срок сертификата, поддерживаемые API majors, одноразовые `pairing_id`/`pairing_code`/`expires_at`. Код — 128 случайных бит, base64url без padding; в журнал/argv не попадает. Сертификат проверяется по закреплённому отпечатку, SAN и сроку; pin не отключает остальные проверки.

`POST /api/v1/pair` — единственное сетевое исключение без токена. Вход: `request_id`, `pairing_id`, `pairing_code`, `device_name` (1–80 символов). Выход после надёжного сохранения устройства/аудита: `agent_id`, `device_id`, `token`, `api_majors`, `created_at`. Токен — 32 случайных байта в base64url, хранится только проверочное SHA-256 значение, сравнение постоянного времени. Случайность токена делает перебор хеша непрактичным; пароли так хранить нельзя. Код хранится проверочным значением, одноразово потребляется вместе с устройством в одной критической транзакции. Повтор потерянного ответа не раскрывает тот же токен: требуется новый код через SSH, ненужное устройство можно отозвать. Исходный токен на сервере ради повторной выдачи не сохраняется.

До дорогого разбора проверяются TLS, размер, лимит соединений и rate limit. Неверный/использованный/истёкший pairing выдаёт одинаковый `PAIRING_REJECTED`. Пять неудачных попыток аннулируют конкретный код, не блокируют существующие телефоны. TTL 300 секунд, до трёх одновременно выданных кодов; лимиты IP/Agent дополнительно заданы конфигурационным профилем. Ошибка commit не выдаёт токен и не начинает новое изменение.

TTL кодов/планов/секретов IPC и простоя потоков отсчитывается монотонно, UTC expiry служит отображению и дополнительному запрету, не продлению при переводе часов назад. Перезапуск инвалидирует незавершённые pairing-коды/планы/tickets; связанные уже принятые операции остаются в durable state, staging сверяется/очищается по политике. Это не отзыв существующих телефонов и не сброс dedup.

Все остальные маршруты требуют `Authorization: Bearer <token>`, включая WSS upgrade, файлы, info, capabilities и продолжения. Секреты в URL, cookie и WebSocket subprotocol запрещены; Origin браузера не заменяет токен. Браузерный доступ/CORS по умолчанию выключен, WSS допускает отсутствие Origin у нативного клиента и отклоняет непустой Origin вне локального списка. Устройства имеют равные права; инициатор извлекается из токена. Каждый запрос сверяет актуальное состояние отзыва. Отзыв commit-ится до ответа, закрывает WSS; потоки проверяют авторизацию перед каждой порцией до 64 000 байт и не реже секунды. Уже отправленные байты не отзываются. Уже начатое необратимое действие не превращается в отменённое.

| Метод и путь | Назначение | Ответ |
|---|---|---|
| POST `/api/v1/pair` | Bootstrap, описанный выше | 201 или ошибка |
| POST `/api/v1/query` | Типизированное чтение по таблице раздела 4 | 200; JSON истории имеет отдельный предел |
| POST `/api/v1/prepare` | План/последствия подтверждаемого действия без исполнения | 200, `plan_id`, версии объектов, последствия, срок |
| POST `/api/v1/operations` | Одно именованное действие | 202, `Operation`; повтор может вернуть 200 |
| GET `/api/v1/operations/{operation_id}` | Состояние известной операции | 200 или 404; без автоматического выполнения |
| PUT `/api/v1/transfers/{transfer_id}/content` | Поток upload/edit для подготовленной операции | 200, байты/SHA-256; публикации ещё нет |
| GET `/api/v1/transfers/{transfer_id}/content` | Подготовленный download или текст | Поток с известной длиной/ограничением |
| GET `/api/v1/ui/{package_digest}` | Пакет, объявленный зарегистрированным модулем | Ограниченный поток; проверка доверия на телефоне |
| GET `/api/v1/stream` | WSS `serverdeck.v1` | Upgrade после авторизации |

Нет HTTP-метода установки выпуска, произвольного shell, выдачи локальных credentials или управления sudo. SSH-обслуживание имеет отдельный устойчивый идентификатор, наблюдаемый через CLI.

Запрос чтения: `{schema_version, request_id, query, params}`. Успех: `{schema_version, request_id, agent_id, served_at, query, data}`. Схемы `query` и `data` связаны discriminant. Для коллекций `items`, `next_cursor` (null в конце), `coverage`, `revision` обязательны; сортировка до пагинации, стабильный tie-break по id. Продолжение не меняет query/filter/sort. Неверный тип/действие возвращает ошибку, не пустой успех.

## 3. Общие типы измерений и идентичность

AFR-012–AFR-028, AFR-055; ASEC-019, ASEC-030.

`Metric = {key, resource_id, series_schema, unit, value, availability, freshness, measured_at, attempted_at, expected_interval_ms, source, reason}`. Availability: `available|absent|unsupported|permission_denied|source_error`; freshness: `fresh|stale|unknown`. Это две оси: последнее корректное значение может быть устаревшим при текущем отказе прав. `value`/`measured_at` могут сохранять последнее успешное измерение, но тогда `freshness=stale`; при отсутствии успешного значения оба null. Ноль допустим только как измеренное значение. `reason` — безопасный enum, не stderr; `source` — зарегистрированное имя адаптера. Для `collection_mode=on_demand|event` интервал null, возвращается время наблюдения; периодический блок stale при времени с последнего планового успеха >= 3 интервалов. Изменение режима процессов 2/5 секунд сохраняется в блоке и не переписывает старые timestamps.

Снимок: `{snapshot_id, agent_run_id, boot_id, segment_id, captured_at, blocks, partial}`. Каждый блок: `{block_id, collection_mode, observed_at, expected_interval_ms, metrics, records, availability, reason}`. Records — типизированные записи ресурса, без секретных cmdline/env. Глобальный captured_at не меняет возраст блоков. Недоступный блок остаётся в ответе с причиной, а не исчезает под видом пустого набора.

| Ресурс | Идентичность и поля |
|---|---|
| System | `agent_id`, boot-id, hostname, доступный machine-id, ОС/ядро/архитектура/timezone, uptime; machine-id не публичный ключ доверия |
| CPU | boot-id + logical-id + generation; модель, topology, metrics; hotplug разрывает производные |
| GPU | UUID + schema, driver/CUDA, PCIe; индексы только подписи; недоступность NVML отдельно от отсутствия GPU |
| Network | boot-id + netns + ifindex + generation; generation увеличивается при исчезновении/reuse/reset; адреса/MTU/routes/DNS/link отдельно от счётчиков |
| Filesystem | boot-id + mount namespace + mount-id + generation + device; точка монтирования не достаточна для идентичности |
| Process | boot-id + PID + starttime ticks + pid namespace; `process_ref` связывает все части; RSS/CPU/UID/name/state, parent_ref, threads, доступные cgroup/unit/container |

Единицы: `percent`, `byte`, `byte_per_second`, `packet`, `packet_per_second`, `count`, `second`, `hertz`, `celsius`, `watt`, `bit_per_second`, `ratio`, `bool`. Raw 64-битные счётчики/байты — U64, производные — number. Изменение единицы/формулы создаёт другую series_schema и ряд. Чувствительная полная командная строка, environment и произвольный текст журналов не экспортируются.

Формулы v1: CPU total = приращение user+nice+system+idle+iowait+irq+softirq+steal; guest/guest_nice повторно не прибавляются. Busy = 100×(total−idle−iowait)/total; iowait и steal отдельны, steal входит в busy. Первая точка, отрицательная компонента/total<=0 дают отсутствие производной, не clamp до нуля. Процесс CPU = 100×Δ(utime+stime)/(CLK_TCK×Δmonotonic_seconds), может превышать 100% на многопоточном процессе; `cpu_host_percent` дополнительно делится на число online CPU в том же окне. RAM used=Total−Available, без подмены Available на Free. Disk used=(blocks−bfree)×frsize, available=bavail×frsize; used_percent=100×used/(used+available), reserved отдельно; inode аналогично, нулевой знаменатель недоступен. Основной диск карточки — доступное монтирование `/`; при недоступности не выбирается случайный другой диск. Сводная сеть суммирует только объявленный набор интерфейсов без loopback, с `included_resource_ids` и предупреждением о возможном двойном учёте bridge/veth; API не утверждает, что это уникальный внешний трафик. Процент link=100×8×скорость_байт/link_bps только при известном link_bps.

История CPU/GPU/network использует агрегаты AFR-028. `Point={bucket_id, revision, segment_id, from, to, step_ms, covered_ms, sample_count, complete, statistics, gap_reason}`; статистики `mean|min|max|last|sum|observed_true` разрешаются реестром ряда. Mean взвешивается по валидной монотонной длительности; сетевые sum — валидные приращения, rate_mean=sum/covered_seconds, rate_max — максимум наблюдённых интервалов. Неполное окно может позднее обновиться по тому же bucket_id с большей revision. Отсутствующий источник не интерполируется нулём. Скачок часов >1 секунды относительно монотонного прогресса или обратный UTC открывает segment_id; boot/run/reset также разрывают базу производных. Это начальный порог обнаружения, не точность часов.

Окна каждого уровня выровнены по UTC внутри сегмента, `[from,to)`; пересекающий границу валидный интервал делится по длительности. Два успешных измерения с расстоянием не более трёх expected intervals дают покрытие между ними, scalar использует левое наблюдение, rate/counter — приращение пары. При source error/reset/более длинном разрыве этот интервал не заполняется удержанным значением; текущий last-good можно показывать stale отдельно. Max — по фактически наблюдённым значениям окна, last — последнее валидное наблюдение; интервал не продолжается за последний полученный sample ради complete=true. Clock segments не сливаются даже при одинаковом UTC.

Начальные ключи реестра v1 (поле Metric.key, все условно доступные источники сохраняют status): CPU `busy_percent/user_percent/nice_percent/system_percent/iowait_percent/steal_percent/idle_percent/irq_percent/softirq_percent` — percent, `load1/load5/load15` — count, `psi_some_percent/psi_full_percent` — percent по поддержке источника, `frequency_hz` — hertz, `temperature_c` — celsius, `throttled` — bool. Memory `total_bytes/available_bytes/free_bytes/used_bytes/swap_total_bytes/swap_used_bytes` — byte, `used_percent/swap_used_percent` — percent. Filesystem `total_bytes/used_bytes/available_bytes/reserved_bytes` — byte, `used_percent/inodes_used_percent` — percent, `inodes_total/inodes_available` — count. Network `rx_bytes/tx_bytes` — byte cumulative, `rx_rate/tx_rate` — byte_per_second, `rx_errors/tx_errors/rx_dropped/tx_dropped` — count cumulative, `link_load_percent` — percent. GPU `utilization_percent/memory_utilization_percent/fan_percent` — percent, `vram_total_bytes/vram_used_bytes` — byte, `temperature_c` — celsius, `power_w` — watt, `throttled` — bool; Process `cpu_percent/cpu_host_percent` — percent и `rss_bytes` — byte. Дополнительные доступные NVML/PSI/throttling поля регистрируются с version/unit/source отдельно, не добавляются неименованным массивом в публичный ряд. Network cumulative хранит sum valid deltas, CPU state/PSI/frequency mean, temperature max, throttled observed_true/last, GPU по AFR-028; обязательная history memory/filesystem/process не создаётся.

E04 technical detail (13 октября): реестр v1 дополнен CPU `throttle_events` (count cumulative), Process `uptime_seconds` (second). `cpu_summary={record_type,resource_id,logical_cpu_count}` связывает aggregate CPU с nullable count; `network_summary={record_type,resource_id,included_resource_ids,warning}` объявляет non-loopback sum и обязательный BRIDGE_VETH_DOUBLE_COUNT_POSSIBLE. CPU/network records допускают собственный observed_at для metadata60с; network.operstate — строка Linux ABI. Ограниченный Snapshot процесса summary top10/detail100 не подменяет полную ProcessPage: PAGE_REQUIRED/partial. Глобальный cache ≤32 различных process revisions/≤64 owners, кроме исходных ≤2 на устройство/TTL30с; отказ новых allocation — LIMIT_EXCEEDED без подмены уже выданной страницы. Форматы маршрутов, conditional sensor profiles и реальные ограничения — [METRICS](<../../agent/METRICS.md>); build-contracts.py/JSON/embedded copies согласованы.

## 4. Реестр чтений

В записи `?` означает необязательное поле; остальные обязательны. Общая страница — limit 1..100, по умолчанию 100. `cursor?` ограничен 2048 символами. Все response-типы определены в JSON Schema; строки внешних названий до 256 символов, сообщения до 512, массивы ограничены.

Процессные страницы относятся к одному сохранённому ограниченному снимку: TTL 30 секунд, максимум два снимка на устройство; по истечении `CURSOR_EXPIRED`, клиент начинает заново. Каталоги не обещают атомарный snapshot ФС: изменение revision даёт `OBJECT_CHANGED`, страницы разных revision не склеиваются. Raw имена файлов Linux — массив base64url-компонент в `Location={root_id, components}`; base64 здесь кодирует только имена, не контент. Компонент после декодирования 1..255 байт, не `/`, NUL, `.` или `..`; UI использует безопасный display_name без обратного преобразования в путь. Пустой массив означает корень. Передача имени одной неоднозначной path-строкой не допускается.

## 5. Изменения, подтверждение и устойчивость

AFR-038–AFR-050, AFR-056, AFR-064; ASEC-009–ASEC-018.

Вход OperationRequest: `{schema_version, request_id, operation_id, action, params, expected_version?, plan_id?}`. operation_id создаёт инициатор перед отправкой и сохраняет на телефоне. Сравнение повторов: инициатор из авторизации + action + канонические типизированные params + expected_version. Порядок JSON-ключей не влияет; чувствительные параметры сравниваются по HMAC с защищённым ключом, содержимое файлов — по digest и длине. plan_id — разрешение данного смысла и версии, не часть смысла повтора. Повтор существующего запроса возвращается до проверки срока старого плана, но после текущей авторизации. Чужой инициатор не может исполнить id другого; чтение результата доступно равноправным устройствам без секретов.

`prepare` принимает action/params/expected_version и operation_id, проверяет типы/права, возвращает последствия, требуемое предупреждение/подтверждение, привязанные версии и plan_id (случайные 128 бит, TTL 120 секунд). План ограничен по памяти, не производит изменение объекта. Все перечисленные ниже изменения, включая самостоятельный `process.kill`, требуют plan_id. Клиент показывает нативное подтверждение; пакет модуля не может заменить диалог. После срока/изменения объекта нужен новый план. Повтор HTTP-запроса к существующей операции не требует нового подтверждения. Системные автоочистка/правила используют идентичность `system`, заранее принятую политику и устойчивый id, а не подделывают телефонный plan_id.

| Action | Params / обязательные предварительные условия | Результат/необратимый шаг |
|---|---|---|
| `config.set` | `changes` только runtime-поля из конфигурации, expected_version | Новая revision; снижение retention/квот подтверждает потерю |

Operation: `{operation_id, revision, initiator, action, object_ref, state, phase, created_at, updated_at, effect_status, audit_status, cancellable, progress?, result?, error?, dedup_until?}`. States: `preparing`, `running`, `succeeded`, `rejected`, `failed`, `cancelled`, `unknown`. Effect: `none|applied|partial|unknown`; audit: `durable|result_pending|unavailable`. `failed` не подразумевает effect=none. `unknown` не терминальный для хранения; разрешается наблюдением либо явной локальной административной процедурой. `rejected` означает отсутствие побочного эффекта; `cancelled` допустим, только если заявленная отмена подтверждена. Partial result сообщает завершённые/неизвестные фазы и сохранённые объекты.

Result в schema выбирается по action: file/ticket, новая revision, trash_id, сигнал/наблюдаемое завершение, ICMP result, device revocation, module lifecycle result или typed module data. Произвольный JSON результата допускается только внутри объявленного module action со своей зарегистрированной схемой. Внутренние `system.trash.expire`, `system.storage.cleanup`, локальная `modules.register` и bootstrap `devices.pair`/`pairing.issue` и offline `storage.backup`/`storage.restore` имеют Operation/result для аудита, но не становятся разрешёнными HTTP action. Pairing token никогда не входит в сохранённый Operation/result.

Чистая семантика runtime общая для локального bootstrap и API: неверная ICMP-цель/фон без цели, некорректный clean absolute root/дубликаты root и edit_bytes>full_text_bytes отклоняются. ConfigChanges заменяет предоставленную группу целиком; поля внутри группы обязательны по схеме. Проверяются patch и полный результат объединения с текущей валидной revision (`contracts.ApplyRuntimeChanges`); чистая функция не сохраняет состояние и не подтверждает права ОС. Application layer повторяет проверку версии, политики/прав/preflight перед durable intent/commit; прохождение codec не подтверждает plan_id или разрешение действия.

Порядок: авторизация → lookup id → валидация/план → ограниченное ожидание конфликтующих locks → повторная проверка реального объекта → одна FULL-транзакция intent+operation → эффект → одна транзакция result+audit. Locks имеют стабильный порядок, перед фактическим эффектом проверяется внешнее изменение. БД, filesystem, IPC не имеют общей атомарной транзакции. При отказе записи начала эффект запрещён. После сохранённого intent и сбоя результата операция блокирует конфликтующий объект до сверки; в памяти можно сообщить известный эффект с audit_status=result_pending, но после перезапуска нельзя выдумать тот же успех без доказательства.

Ключи внутренней сериализации: settings revision group, module graph/registration, process_ref, file identity `(filesystem,mount generation,inode)` и directory/name для source/destination. Aliases одного объекта не получают независимые locks по строке пути. Root-policy change использует общий барьер допуска файловых mutations и повторную проверку generation; запущенный поток при сужении доступа прекращается на безопасной границе. Locks берутся в каноническом порядке ключей без ожидания внешнего RPC под DB-транзакцией. Это предотвращает внутренние гонки/дедлоки, но не превращает внешний SSH-writer в участника блокировки.

До четырёх изменяющих операций одновременно, включая фоновые изменения; transfer-сессия занимает один из двух transfer-слотов, не удерживает слот выполнения на всё ожидание upload. До 32 ожидающих операций, не более 8 на устройство, round-robin между готовыми очередями устройств, FIFO внутри; после 10 секунд ожидания до intent — `BUSY` без эффекта. Ни один телефон не получает постоянный приоритет. Отмена не используется для остановки нативного зависшего вызова. Незавершённые операции не вытесняются; 10 000 записей/64 МБ операционного состояния — начальный верхний предел, при исчерпании новые изменения блокируются. Завершённые результаты и dedup живут 7 суток, аудит отдельно 30 суток/64 МБ. Клиент не повторяет автоматически старый operation_id после dedup_until; отсутствие записи 404 не является доказательством неисполнения.

## 6. Файловые потоки и безопасный отказ

Ticket привязан к устройству, Agent, объекту/версии, режиму, размеру и digest, TTL простоя 300 с, общий срок до 3600 с. До двух активных потоков/стадированных передач суммарно; повтор upload с начала допускается только пока публикация не началась и staging заменяется безопасно, без повторного изменения оригинала. Продолжение с произвольного offset и многопоточная дозагрузка в v1 не поддерживаются; download можно заново подготовить по той же проверенной версии. TLS/токен проверяются заново. Range произвольного файла через URL отсутствует.

PUT принимает `application/octet-stream`, Content-Length обязателен и равен согласованному размеру; фактический лимит проверяется независимо. SHA-256 проверяется после завершения, временный файл закрывается/fsync-ится; это ещё не commit. Обрыв/отзыв/ENOSPC оставляет исходник, transfer получает failed/expired; staging очищается по ограниченной политике с аудитом, без аудита удерживается и блокирует новые передачи при лимите. Чужие временные файлы не удаляются. Download фиксирует fd/версию, проверяет объект до/после; изменившийся поток помечается transfer outcome `OBJECT_CHANGED`, клиент не считает его согласованной копией. Простой HTTP 200 не подтверждает digest/полноту полученного файла.

При commit expected_version — версия исходного файла для edit/replace, версия целевого родителя для upload без замены; обе привязки сохранены в Ticket/transfer state. Для conflict=replace replace_version обязателен, для fail запрещён; замену существующего target нельзя согласовать пустым token. Правила BLOCK-FS применяются одинаково к edit/upload/restore. Прежние UID/GID/mode/ACL и значимые security attributes не меняются неявно: проверяется возможность сохранить согласованный metadata profile без расширения доступа; при невозможности — отказ и конкретные последствия для отдельного плана, не скрытый chown/sudo. Готовность временного контента не даёт права заменить изменившийся target.

Полный/частичный текст передаёт bytes, отдельно сообщает BOM/encoding и версию. v1 редактирует только проверенный UTF-8/UTF-8 BOM без NUL; непонятная кодировка/бинарный файл доступны для download с объяснением отсутствия редактирования. BOM и переводы строк не меняются неявно. Tail читает ограниченные порции, <=1 МБ выдачи и <=8 МБ сканирования за запрос; строка длиннее лимита получает truncated, не бесконечный поиск. При более раннем cursor привязка к версии обязательна. Другие кодировки требуют отдельного специфицированного адаптера, не догадки.

Версия файла — серверный непрозрачный token, связывающий mount/identity, size, mtime/ctime ns и для редактирования SHA-256 прочитанного контента. Это обнаружение конфликтов, а не Linux CAS-примитив. Защита собственных объектов учитывает inode/aliases, mount и предков; symlink не разыменовываются, вложенные mounts требуют отдельной регистрации. Разрешение `/` не отменяет защиту. При невозможности доказать безопасность многошаговой записи/rename/restore возвращается `SAFETY_UNAVAILABLE`; ограничение отмечается в capabilities. Остаточная гонка с внешним writer не объявляется устранённой комбинацией stat+rename; критерий допуска находится в BLOCK-FS.

## 7. Курсоры, история и WSS

AFR-024, AFR-026–AFR-031, AFR-036–AFR-040; ASEC-013/028.

Курсоры непрозрачны, аутентифицированы HMAC; связывают agent_id, stream epoch, kind, query digest, position, schema, expiry. Токен устройства внутри не хранится; каждый запрос авторизуется отдельно. Позиция журналов — `(epoch, sequence U64)`, не timestamp. Для событий/аудита нет серверной очереди на каждый телефон: клиент хранит свою позицию. После удаления нужной позиции — `CURSOR_GAP` с earliest/latest и актуальными проблемами; клиент явно подтверждает новую точку и показывает пробел. Поворот ключа cursors/восстановление БД открывает новый epoch, не подделывает непрерывность. History cursor привязан к series/from/to/level/segment; bucket revision позволяет обновить незакрытое окно. После ротации — явная coverage/gap, не ложный пустой диапазон.

WSS-клиент отправляет `subscribe {request_id, subscriptions:[{id, topic, params, after?}]}`. Topics: `snapshot` (view summary/detail), `events`, `operations`, `problems`, `storage`. Не более 16 подписок на соединение; summary каждые 5 с, detail каждые 2 с. Server: `subscribed`, `snapshot`, `changes`, `gap`, `error`, `heartbeat`. Каждое сообщение имеет schema_version/type/subscription_id/server_time; changes — одну ограниченную страницу с cursor. Вход Agent проверяется только по `WssClientMessage`, вход клиента — по `WssServerMessage`; объединённая `WssMessage` служит карте типов и запрещена как target Go codec. `subscriptions[].id` уникальны внутри subscribe; сессия отдельно проверяет уже занятые id и общий предел 16. Params привязаны к topic: snapshot использует параметры snapshot.get (view обязателен, blocks/resource_ids необязательны); events — фильтры events.list без cursor/limit; operations — state из operations.list; problems/storage — пустой объект. after допускается только для сохраняемых изменений, не snapshot. В changes тип каждой записи data определяется topic, смешивание типов запрещено. Эти уточнения исправляют незавершённую подготовку первого, ещё не выпущенного v1; совместимость с реальным клиентом не заявляется.

Клиент подтверждает `ack {subscription_id,cursor}` только после сохранения страницы. Ack связан с текущей сессией/подпиской и точным cursor реально ожидающей подтверждения страницы; чужой, старый или неотправленный cursor не продвигает состояние. Авторизация пересматривается при обработке каждого сообщения. Перед выдачей следующей страницы — ack предыдущей; сервер не удаляет записи по ack. Для operations устойчивый change sequence хранится вместе с state; после ротации догружается актуальный список/unknown состояния, не пропавший прогресс.

Текущий снимок: один заменяемый pending на подписку. Сохраняемые изменения: до 16 непотверждённых страниц/4 МБ на соединение, максимум одна на подписку; при медленном клиенте закрытие 1013 с resume через HTTPS/WSS, а не бесконечная очередь. Предел WSS frame 1 МБ; большие history/UI/контент через HTTPS. Ping каждые 30 с, ожидание pong 10 с; permessage-deflate выключен. Переподключение клиентом 1,2,4,8,16,30 с с jitter ±20%, сброс backoff после минуты устойчивой связи. Отзыв — 1008, слишком большое сообщение — 1009; коды не заменяют причины typed error. Потеря соединения не отменяет операцию. Отдельный протокол догрузки аудита — query, WSS сообщает изменения счётчика/coverage без экспорта чувствительного потока по умолчанию.

## 8. Ошибки и ограничения

`ErrorEnvelope={schema_version,request_id,agent_id?,served_at,error:{code,message,retryable,operation_id?,details?}}`. message безопасное, <=512 символов; details только типизированные поля `field`, `current_version`, `earliest_cursor`, `latest_cursor`, `retry_after_ms`, `effect_status`. Нет контента/секретов/stack trace/сырого stderr. HTTP timeout/502 прокси не является таким подтверждением отказа и требует чтения operation_id.

| HTTP | Коды | Поведение |
|---|---|---|
| 400 | INVALID_REQUEST, INVALID_PATH, UNSUPPORTED_QUERY, UNSUPPORTED_ACTION | Исправить запрос, эффекта нет |
| 401 | UNAUTHORIZED, PAIRING_REJECTED | Восстановить доверие/доступ; не подбирать бесконечно |
| 403 | PERMISSION_DENIED, POLICY_DENIED, PROTECTED_OBJECT | Не повышать права автоматически |
| 404 | NOT_FOUND, OPERATION_NOT_FOUND | Не доказывает прошлое неисполнение |
| 409 | VERSION_CONFLICT, OBJECT_CHANGED, IDEMPOTENCY_CONFLICT, DEPENDENCY_CONFLICT, CURSOR_GAP, BUSY, PLAN_EXPIRED | Показать актуальное состояние/новый план; без слепого повтора |
| 410 | CURSOR_EXPIRED, TRANSFER_EXPIRED | Начать новое чтение/подготовку |
| 413 | LIMIT_EXCEEDED | Размер/лимит объявлен, потоки остановлены |
| 422 | INCOMPATIBLE_VERSION, INVALID_MANIFEST, UNSUPPORTED_ENCODING, SAFETY_UNAVAILABLE | До действия; capabilities объясняют причину |
| 429 | RATE_LIMITED | Retry-After, bounded backoff |
| 503 | AUDIT_UNAVAILABLE, STORAGE_UNAVAILABLE, SOURCE_UNAVAILABLE, MAINTENANCE, MODULE_UNAVAILABLE | Read по возможности; новое изменение запрещено при отказе intent |
| 507 | NO_SPACE, QUOTA_EXCEEDED | Сохранить исходник, восстановление без обхода аудита |
| 500 | INTERNAL_ERROR | Если intent уже существует — effect unknown/known через Operation, не ложный rejected |

Профили внутренних лимитов находятся в конфигурации. Возврат ошибки сам по себе не доказывает отсутствие эффекта уже принятой операции; Operation является источником состояния. Неавторизованный flood ограничивается до журналирования дорогих полей; диагностируется с bounded counters. Потерю возможности записать отказ видно в audit health, её нельзя назвать полным аудитом.

## 10. Официальные основания

Проверены 12 октября 2026 года. [Linux proc](https://www.kernel.org/doc/html/latest/filesystems/proc.html) задаёт источники CPU/процессов, но не гарантирует точность всех датчиков. [openat2](https://manpages.debian.org/bookworm/manpages-dev/openat2.2.en.html) и [renameat2](https://manpages.debian.org/bookworm/manpages-dev/renameat2.2.en.html) описывают разные операции; отсутствие compare-by-inode при замене — вывод о границе данной конструкции, а не заявленная готовая защита. [JSON-RPC](https://www.jsonrpc.org/specification) применяется только к IPC; HTTP envelope и WSS — контракт ServerDeck. Профили очередей/тайм-аутов являются техническими начальными решениями и требуют нагрузочной проверки.
