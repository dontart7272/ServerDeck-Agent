## 1. Структура Go-проекта

Создан один Go-модуль в `agent/`; пользователь подтвердил локальный module path `serverdeck.local/agent`. Git checkout/remote отсутствует; GitHub-домен не выдуман. В E01 существуют cmd, internal/app, internal/contracts, internal/config, tools и evidence. E02 добавляет internal/storage (embedded migrations) и internal/operations; остальные каталоги ниже остаются планируемыми. Фактическая структура, ограничения WAL/backup и CLI — [STORAGE](<../../agent/STORAGE.md>). Agent и CLI — два исполняемых файла, только Agent работает постоянно. Установщик использует CLI lifecycle-команды; не появляется постоянный привилегированный процесс.

```text
agent/
  go.mod, go.sum                    # закреплённый Go/cgo/зависимости после E01
  cmd/serverdeck-agent/             # сборка и вход основной службы
  cmd/serverdeckctl/                # локальный CLI/installer/recovery
  internal/app/                    # orchestration и application services
  internal/domain/                 # typed identities, availability, operations, events
  internal/transport/httpapi/       # API major adapters, auth, bounded codecs
  internal/transport/ws/            # подписки и resume, без собственного сбора
  internal/transport/local/         # CLI socket и SO_PEERCRED, отдельный от module IPC
  internal/auth/                    # pairing, devices, revoke, TLS bootstrap
  internal/operations/              # intent, dedup, locks, reconciliation
  internal/storage/                # SQLite repos, accounting, backup, migrations
  internal/metrics/                # E04 scheduler, shared snapshots и Linux read-only adapters
  internal/events/                 # rules, active problems, journal readers
  internal/modules/                # registry, graph, supervisor, IPC codecs
  internal/system/                  # system,cpu,gpu,memory,filesystems,network,
                                   # processes,files,docker,security — 10 внутренних модулей
  internal/linux/                   # openat2/pidfd/netlink/proc/sys/cgroup adapters
  internal/lifecycle/               # preflight, install/update/remove/recover
  migrations/                      # по БД, checksum и совместимость
  packaging/                       # unit template, release/TUF metadata templates
  tests/integration/               # изолированные Linux fault/race tests
  tests/compat/                    # API/IPC/UI/release fixtures
```

Это описание будущих каталогов, не инструкция создать пустые заглушки. Пакеты появляются вместе с работающим блоком. Domain не зависит от HTTP/SQL/NVML; adapters возвращают типизированные результаты/availability, без протекания raw errno/секретов в UI. Общий operation service используют HTTP, штатный CLI и системные cleanup workers. Модули не получают DB handles/phone tokens. Стандартные interfaces выделяются по проверяемым границам clock/fs/store/collector/IPC, не по числу пакетов.

Для E01 реально загружены Go1.27.2 и go-sqlite3 v1.14.52; добавлен ограниченный JSON Schema validator github.com/santhosh-tekuri/jsonschema/v5 v5.3.1 (Apache-2.0). Два Go-модуля закреплены в go.mod/go.sum и прошли mod verify, Windows/cgo tests. Для исторического E01 websocket/x/sys/NVML/TUF были кандидатами. В E03 реально подключён coder/websocket v1.8.15/ISC, закреплён origin commit/checksums/license; модульных зависимостей теперь три. x/sys/NVML/TUF ещё не импортируются. Ubuntu22.04 WSL2 amd64 cgo и arm64 cross-build проверены; native ARM smoke/race ещё не проверены; см. [notices](<../../agent/THIRD_PARTY_NOTICES.md>). В [заголовке SQLite выбранного тега](https://raw.githubusercontent.com/mattn/go-sqlite3/v1.14.52/sqlite3-binding.h) указана3.53.4, содержащая WAL-reset fix; E01 всё равно проверяет фактическую runtime-версию/сборку. `libsqlite3` build tag по умолчанию не используется, чтобы не подменить библиотеку старым системным пакетом.

Собственный код Apache-2.0; начальная инвентаризация: websocket ISC, x/sys BSD-3-Clause, go-nvml Apache-2.0, go-sqlite3 MIT + SQLite public domain, go-tuf Apache-2.0. Проверены [websocket license](https://raw.githubusercontent.com/coder/websocket/v1.8.15/LICENSE.txt), [NVML license](https://raw.githubusercontent.com/NVIDIA/go-nvml/v0.13.4-1/LICENSE), [TUF license](https://raw.githubusercontent.com/theupdateframework/go-tuf/v2.4.2/LICENSE); остальные и транзитивные notices перепроверяются по загруженным pinned sources в E01. Это не юридическое заключение и не завершённый SBOM. Сборочный baseline Ubuntu22.04/glibc2.35, cgo=1; динамические ELF зависимости измеряются для каждого target, не угадываются по примеру release.json. Новые уязвимости/несовместимость до старта E01 требуют пересмотра pins с записью причины, не автоматического latest.

Фактический E04 размещён в internal/metrics: types/engine/Linux adapter/platform stub и поведенческие tests, без пустых domain/collection/system пакетов. Query/WSS/native orchestration остаются в существующем internal/app; [METRICS](<../../agent/METRICS.md>) описывает limits и ownership snapshots. Планируемые каталоги выше не объявляются существующей реализацией.

Scheduler → bounded collector (один активный вызов на источник) → immutable last-good snapshot → event evaluator / aggregator / HTTP/WSS views. Несколько телефонов читают общий snapshot; HTTP не запускает независимый CPU/NVML сбор. Process detail subscription/ограниченный query lease 10 секунд повышает сбор до 2 секунд, disconnect/expiry возвращает 5 секунд. Общие метрики/история собираются без клиентов.

Aggregator → bounded history writer; rules → event state+event journal; operation service → critical intent → Linux/module effect → critical result. Storage health доступен в RAM snapshot даже при сломанной event DB. Нет зависимости успешного мониторинга от успешной записи audit/history, но источники, требующие записи собственных курсоров, объявляют degraded/gaps. Обработанный collector error локален; fatal Go/cgo crash может завершить основной процесс и все системные функции.

Native NVML: один ограниченный worker на источник, timeout ожидания лишь ставит source_error/stale, не освобождает зависший вызов и не запускает бесконечные goroutines. Watchdog ядра проверяет progress scheduler/API/storage control, а не требует успеха недоступного GPU. Зависший NVML может потребовать ручного restart всей службы; out-of-process GPU как новая архитектура не вводится молча. Встроенный nvidia-smi fallback запускается лишь когда нет занятого зависшего native вызова и проверен поддерживаемый машиночитаемый профиль; не shell.

## 3. Базы и таблицы

Локальная ФС, отдельные database/sql pools/очереди, один writer на БД; `foreign_keys=ON`, `busy_timeout=1000`, page_size=4096, WAL с проверкой действительного journal_mode, bounded readers/checkpoint. Обязательна проверенная SQLite с WAL-reset fix 3.51.3 либо официальным backport, а не версия драйвера по имени. `sqlite_version()`, compile options и source id записываются в release evidence.

| БД | Таблицы/ключи/важные связи | Durability и учёт |
|---|---|---|
| critical.db | identity(agent_id); devices(device_id,token_hash,revoked_at,revision); pairing(code_hash,expires,attempts); settings(revision,typed_document); rules(id,revision); module_registry(id,revision,digest,policy); operations(id PK,actor,action,params_hmac,state,phase,effect,result,revision,expires); operation_changes(epoch,seq,id,revision); audit(epoch,seq,operation_id,kind,safe fields); transfer_state(id,object/version,digest,phase); trash_index(id,fs/object/original location,expiry); schema_migrations | WAL/FULL, intent+operation+audit в одной транзакции. Аудит логически 64 МБ, critical state/operations отдельно до64 МБ; индексы и общий WAL учитываются консервативно, не «бесплатно» |
| events.db | active_problems(id,rule/resource,state,last observation); events(epoch,seq,problem_id,kind,count,time,safe data); source_offsets(source,boot/inode,cursor,coverage); schema_migrations | WAL/FULL, state transition+event+offset одной транзакцией. Events32 МБ/7 суток; active state до8 МБ/10000, отдельно от ротации событий |
| history.db | series(id,module,resource,generation,unit,schema); segments(id,boot,clock mapping,reason); buckets(series,segment,level,start PK,revision,weighted accumulators,coverage); gaps(series,segment,range,reason); schema_migrations | WAL/FULL, batch каждые<=5 секунд; queues bounded. 256 МБ по умолчанию включая indexes/WAL/SHM/резерв, дополнительные<=25% |

UUID хранится binary16 либо каноническим TEXT с CHECK в первой миграции; U64 counters сохраняются без переполнения signed SQLite INTEGER (TEXT decimal либо fixed binary8, определённый адаптером). Seq/revision — положительный signed64, при исчерпании новый epoch/revision namespace, не wrap. Времена UTC — integer microseconds + монотонный offset/segment для вычислений, nanos исходного file version отдельно. Не сохранять файл content в audit/operations. Сравнение requests использует HMAC от канонической типизированной сериализации, ключ в защищённом отдельном файле; утрата ключа не разрешает replay.

Секреты TLS/HMAC и security-floor journal находятся вне history и защищены как critical state. В critical audit таблице tombstone/intent до сверки операции не удаляются вместе с завершённым audit stream. Events DB не атомарна с critical.db: operation result содержит безопасный outbox id для события; доставка в events идемпотентна, отметка отдельно. Отказ события не отменяет уже сохранённый результат. Automatic retention/history write являются обслуживанием собственного хранилища по принятой политике; не обходным пользовательским delete. Изменение политики и удаление корзины требуют intent; rotation audit производится контролируемой транзакцией с сохранением единственного operation state.

## 4. Место, квоты и отказ

Preflight учитывает основной файл, indexes, WAL/SHM, операционное состояние, staging, корзины, backup и выпуск отдельно. Free-space check — оценка до записи, не резерв места от других приложений. ENOSPC возможен после него; каждое действие обязано иметь обработку частичной записи. Page quota/journal_size_limit не объявляются жёстким общим ограничителем WAL: применяются bounded batches, read deadlines, checkpoint, admission по фактическому allocated bytes и запасу. Нет forced VACUUM на заполненном диске.

History default: резерв min(8 МБ,10% бюджета) внутри бюджета; WAL hard8 МБ, DB allocation не более budget−reserve−текущие sidecars, следующий worst-case batch проверяется до записи. Cleanup сначала удаляет истёкшие окна, затем старейший временной диапазон по всем уровням, сохраняя свежие диапазоны каждого разрешённого ряда; module quota применяется отдельно. Страницы reuse/incremental vacuum и bounded checkpoints применяются при наличии места, не обещают немедленно вернуть bytes ОС. При невозможности вписать очередной batch — gap/quota warning, последние снимки продолжаются. Нарушение hard limit из-за внешнего заполнения/непредвиденной write amplification — readiness defect до релиза, не разрешение выйти за лимит бесконтрольно.

History writer очередь <=5с/8 МБ, заполнение отбрасывает незаписанные метрики с отмеченным диапазоном потери, не audit/operations. События/active problems не угадываются после отказа DB; engine продолжает bounded RAM observations, показывает lost coverage. Critical writer отказ до intent → новый эффект запрещён, в том числе file cleanup/обычный revoke/CLI. После effect отказ commit → известный effect + result_pending в RAM, после crash unknown до reconciliation. Технический резерв не гарантирует восстановление при отказе ФС/устройства. Клиент не может очистить пользовательский файл через обход аудита ради свободного места.

После обнаруженного скачка часов retention не использует новый wall clock как доказательство истечения 7-дневной dedup-защиты/срока корзины: temporal expiry приостанавливается до проверки времени, в рамках загрузки используется elapsed monotonic. Бюджет истории/завершённых журналов по-прежнему ограничивает хранение по устойчивому порядку, unknown операции/активные проблемы защищены. Если консервативное сохранение dedup исчерпало операционный предел, admission блокируется, а не преждевременно удаляет защиту. Неверное/недостоверное время не допускает установки TUF-пакета с пропуском expiry. После restart отсутствующая монотонная база не восстанавливается из одной wall-time догадки.

## 5. Filesystem и процессы

Корни открываются как directory FD и связываются с mount identity. openat2 `RESOLVE_BENEATH|RESOLVE_NO_SYMLINKS|RESOLVE_NO_MAGICLINKS` и запрет незарегистрированных crossings; для данного root используется RESOLVE_NO_XDEV, отдельный зарегистрированный mount становится своим root. EAGAIN при доказательстве пути — ограниченный повтор только чтения/подготовки, затем SAFETY_UNAVAILABLE. Нет fallback realpath+open.

Собственные secret/DB/runtime/config/code/registry/backup объекты и aliases индексируются по identities; секреты запрещены к чтению, рабочие объекты и необходимые предки к изменению. Корзина/staging того же filesystem выбирается в доверенно созданном закрытом каталоге, не в чужом каталоге по строковой догадке. Root privileges не отменяют guards. nlink/unknown overlay/mount identity и невозможность проверки alias означают отказ спорному действию, не исключение. Файловые mutation-примитивы имеют отдельный gate BLOCK-FS: pathname операции после FD-проверки не становятся автоматически устойчивыми к внешнему rename/write. При переносе между ФС сохраняется источник до verified target и отдельного trash intent; unknown сохраняет обе стороны для сверки.

pidfd_open + повторная проверка starttime/boot + pidfd_send_signal связывают signal с экземпляром. Если нужные безопасные вызовы недоступны, управление процессом недоступно, мониторинг остаётся. Отсутствие процесса после сигнала/проверки сообщает отдельно, timeout не означает failure отправки. Защищены PID1, ядро и managed processes с собственным lifecycle.

## 6. Локальный CLI и systemd

`serverdeckctl` для штатных операций соединяется с `/run/serverdeck/admin.sock` (0600/0700), SO_PEERCRED разрешает владельца Agent/root. Нет доверия произвольному SSH-login, request actor=`local:<uid>` из peer, а не argv. Не передаёт сырой SQL/shell; вызывает те же named application services/audit guard. Offline maintenance/recovery требует реальных прав, эксклюзивный lock и остановленную службу; отсутствующий процесс не автоматически превращает все CLI-команды в audit bypass.

Проектируемый основной unit, не установленный файл:

```ini
[Unit]
Description=ServerDeck Agent
After=network.target
StartLimitIntervalSec=600
StartLimitBurst=5

[Service]
Type=notify
User=<selected-existing-user>
Group=<selected-existing-primary-group>
ExecStart=/opt/serverdeck/current/serverdeck-agent --config /etc/serverdeck/server.json
WorkingDirectory=/var/lib/serverdeck
RuntimeDirectory=serverdeck
RuntimeDirectoryMode=0700
UMask=0077
Restart=on-failure
RestartSec=5s
WatchdogSec=30s
NotifyAccess=main
TimeoutStartSec=60s
TimeoutStopSec=30s
KillMode=control-group
SendSIGKILL=yes
LimitCORE=0

[Install]
WantedBy=multi-user.target
```

Подстановки здесь — placeholders документа, установщик валидирует user/group и генерирует literal unit без shell. READY=1 только после проверки БД/путей/политики, listen/auth и запущенного планировщика; отсутствие GPU/ограниченные права — degraded sources. WATCHDOG=1 не посылается без контроля progress ядра; частичный source failure не заставляет бесконечно перезапускать всё. Shutdown запрещает admission, завершает безопасные фазы/запись, отмечает unknown, останавливает children; systemd завершает оставшуюся cgroup.

Нельзя без проверки включить ProtectHome/PrivateDevices/ProtectProc/PrivateNetwork/ProtectSystem=strict: они могут скрыть согласованные файлы, GPU, процессы или запись в разрешённые roots. Hardening профиль выбирается после проверки реальных функций; базовый unit не обещает sandbox. NoNewPrivileges влияет на ping с file capabilities, поэтому не включается незаметно с обещанием работоспособного ICMP; точечный выбранный профиль проверяется на хосте. Никакой автоматической выдачи CAP_NET_RAW/CAP_SYS_ADMIN/групп. Delegation — отдельный план при установке, отсутствие отображается. Основной unit один; временная maintenance task не постоянный helper.

## 7. Установка и обслуживание

CLI команды проектируются как структурированные plan/apply/status: `install`, `update`, `uninstall`, `runtime-user change`, `tls rotate`, `backup`, `recover`. Plan содержит maintenance_id, installation_id, версии/пользователя/место/порт/dependencies/firewall diff/действия с возможными потерями и digest. apply принимает этот план и проверяет реальные условия повторно. Секреты вводятся через защищённый канал/stdin, не argv/логи. Идемпотентный maintenance_id в защищённом installer state; flock/install lock исключает второй установщик.

До существования Agent первичная установка ведёт локальный bounded журнал фактических шагов/неопределённостей, не заявляет наличие ещё не созданного аудита. После создания критической БД штатные изменения обязаны использовать intent. Работа продолжается локальной transient systemd task `serverdeck-maintenance-<id>` с Type=oneshot и действительными полномочиями SSH-сценария; не привязана к stdin/жизни SSH-сессии. Повтор после разрыва читает state и наблюдает ту же задачу. Состояния preflight/staging/quiescing/backup/migrating/switching/healthchecking/rolling_back/succeeded/failed/unknown; каждое переключение сохраняется/синхронизируется до продолжения.

Установка: проверенный bootstrap/подписи → OS/syscalls/cgo libs/runtime user → место/порт → план точечных packages/firewall → staging verified release → paths/ownership/TLS/identity/config → основной unit → local health → phone reachability/pair/первый snapshot. Localhost оставляет установку, но не готовую запись телефона. Повтор не сбрасывает identity/devices/TLS. Смена user и TLS — SSH-only план, экспорт текущего доступа/проверка прав/перезапуск/проверка доверия каждого телефона. SAN не дописывается без ротации сертификата.

## 8. Миграции, backup и безопасный откат

Каждая БД имеет `schema_migrations(version,checksum,release_id,applied_at)` и manifest `read_min/read_max/write_version`. Миграции нумерованные, проверяют исходную схему/checksum, выполняются в транзакции там, где SQLite допускает; неатомарный filesystem шаг записан отдельно. Dirty/incomplete migration блокирует normal write, не «автовосстанавливает» пустую БД. Последовательность между БД контролируется maintenance state, не объявляется одной транзакцией. v1 первая миграция создаёт таблицы; будущие конкретные миграции добавляются вместе с изменением схемы и rollback fixture, не выдумываются сейчас.

Backup через SQLite backup API либо полностью остановленную и корректно закрытую БД; никогда один живой `.db` без WAL. Для согласованного набора: admission закрыт, операции сверены/unknown сохранены, writers остановлены, quiescence barrier, snapshot каждой БД и защищённых файлов, manifest installation_id/schema/digests/security_generation, fsync; тест restore/quick_check. Если quiesce не достигнут, backup помечен несогласованным и не годится для автоматического rollback. Резерв один предыдущий рабочий, размер/место показаны отдельно; staging следующего выпуска bounded, резерв нельзя удалить до гарантированного нового пути возврата.

Security floor хранит текущие revocations, policy revision/ограничения и TUF trusted metadata вне возвращаемого snapshot. Штатный revoke/config-security commit сначала атомарен с intent в critical.db; security-floor export обновляется до разрешения обслуживания. Во время обслуживания новые изменения/выдача pairing запрещены, поэтому floor стабилен. После crash, если актуальность export относительно critical generation не доказана, rollback не включает старые токены. Это не обещание атомарной записи двух файлов: maintenance gate сверяет generations, при неопределённости fail-closed и SSH recovery. Старый бинарник должен читать актуальную floor schema и соблюдать не более широкую политику; иначе запрещён как автоматическая цель rollback. При невыразимой новой политике требуется отдельный maintenance plan. При потере достоверного доступа все токены backup остаются неактивными до доверенного recovery.

Обновление: проверить TUF/архив/совместимость до остановки → disk budget/конфликты → quiesce/security floor/backup → stage → migrations → атомарно заменить ссылку current + fsync родителя → restart → 60 секунд локального health. Проверяются защищённый API локальными credentials, чтение состояния/планировщик/ожидаемые sources, не только наличие PID. Health credentials краткоживущие через FD/local socket, не публичный bypass и не старый телефонный токен. GPU absent/permission denied допустимы, unexpected loss ранее доступного источника диагностируется. Неудача → проверенная предыдущая неотозванная версия + согласованный data snapshot + текущая floor; полная папка безопасности никогда не восстанавливается вслепую. Провал rollback оставляет failed/unknown и SSH-инструкцию, не бесконечное переключение версий.

## 9. Поставка и удаление

Release manifest [schema](<contracts/release.schema.json>): version/release_id/os/arch/kernel/glibc/cgo libs/Agent API majors/IPC range/UI schema/DB read-write versions/security_floor_version/rollback targets/files digests. TUF target подписывает digest/длину manifest и archive как отдельных targets. Начальная реализация go-tuf/v2 и toolchain выбраны выше; E01 проверяет pinned source/provenance/licenses, собственная «упрощённая TUF» не пишется. Trusted root поставляется с проверенным installer/client; transport GitHub Releases не является trust anchor. TUF state/metadata versions/expiry сохраняются через rollback, часы не обходятся флагом ignore. Offline archive включает нужную подписанную цепочку metadata; просроченные metadata требуют доверенного обновления, не отключения проверки.

Удаление: plan → надёжный intent штатно либо явно обозначенный emergency external maintenance → stop unit/cgroup → снять только учтённые свои firewall rules → удалить только проверенные installation-owned code/unit/registry objects. Данные/config/ключи сохраняются по умолчанию, full purge отдельно подтверждает список; symlink и изменившийся владелец не дают удалить чужое. Docker/драйверы/packages/сторонние приложения не удаляются. Частичный отказ перечисляет сохранённые/неизвестные объекты. Recovery при неработающем Agent не зависит от HTTP; требует фактических прав и отдельной записи пробела/шагов, не обещает аудировать произвольный SSH.

## 10. Официальные основания и пределы

Проверены 12 октября 2026 года: [SQLite WAL](https://www.sqlite.org/wal.html) — локальность, отсутствие общей атомарности WAL-БД, WAL-reset fix; [synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous) — FULL commit durability при исправной ОС/диске; [backup](https://www.sqlite.org/backup.html) — согласованная копия одной БД, общий barrier является решением ServerDeck. [systemd v249 service](https://raw.githubusercontent.com/systemd/systemd/v249/man/systemd.service.xml), [exec](https://raw.githubusercontent.com/systemd/systemd/v249/man/systemd.exec.xml), [kill](https://raw.githubusercontent.com/systemd/systemd/v249/man/systemd.kill.xml) — исходная версия для проверки старшего целевого Ubuntu, не доказательство установленной версии хоста. [Go cgo](https://pkg.go.dev/cmd/cgo), [go-sqlite3](https://github.com/mattn/go-sqlite3), [NVML](https://docs.nvidia.com/deploy/nvml-api/latest/), [go-nvml](https://github.com/NVIDIA/go-nvml) — зависимости сборки/native API, не полная статичность/изоляция падения. [TUF](https://theupdateframework.github.io/specification/latest/) — доверие metadata, не транзакция rollback пользовательских данных.
