# ServerDeck Agent — функциональные требования

Версия: 1.0. Дата оформления и проверки: 12 октября 2026 года.
Статус: базовые требования по согласованной архитектуре и принятому пользователем пакету Р01–Р25. Реализация и испытания ещё не выполнены.

## 1. Назначение и применение

Документ определяет поведение основного Agent, его CLI/установщика и серверной интеграции дополнительных модулей. Связанные обязанности Android-клиента помечены отдельно. Все требования обязательны в пределах указанного условия применимости; отсутствие оборудования или прав отражается состоянием доступности, а не вымышленными данными.

Основания: [описание проекта](<1. Краткое описание.md>), [согласованные Р01–Р25](<Предложения по оставшимся вопросам.md>), [рабочие решения](<Рабочие заметки и решения.md>) и [контекст клиента](<0. Контекст и потребности клиента.md>). Проверки безопасности определены в [ASEC](<4. Требования безопасности.md>).

Префикс AFR отличает требования Agent от клиентских FR. Предварительные EX-001–EX-040 служат трассировкой потребностей, не именами URL. Схемы JSON, маршруты, полный манифест, конфигурация и SDK оформляются отдельно до реализации соответствующих контрактов. Порядок разработки не сокращает согласованный продукт.

## 2. Среда, исполнение и установка

### AFR-001. ОС и ядро

Целевая матрица обязательных проверок: Ubuntu 22.04/24.04/26.04 LTS, Debian 12/13 на x86-64. Первый реальный стенд — Ubuntu 22.04 VPS. Управляемая установка требует systemd; файловая защита требует Linux не ниже 5.6 и доступных нужных вызовов. Другие дистрибутивы допускают ручную установку с диагностикой.

**Приёмка:** установщик сообщает обнаруженное окружение и несовместимости до изменений; статус проверенной поддержки присваивается только по испытаниям.

### AFR-002. Архитектуры и GPU

x86-64 обязателен. Для ARM64 выпускается сборка, статус поддержки определяется проверками; ARM32 не обещается. Поддержка NVIDIA обязательна при совместимых оборудовании и драйвере. Матрица GPU/драйверов отдельна; Jetson/MIG/vGPU не считаются проверенными автоматически. AMD относится к последующему развитию.

**Приёмка:** неподходящая архитектура/драйвер диагностируются; отсутствие GPU не блокирует остальные функции.

### AFR-003. Модель процессов и системных модулей

Один основной systemd-unit запускает один процесс ядра и десяти системных модулей. Системные модули нельзя отключить/удалить; их код поставляется общим бинарником. Дополнительные модули работают отдельно. Изменение системного кода может перезапустить все основные функции.

**Приёмка:** нет отдельной службы на каждый системный модуль и обещания его горячего независимого обновления; частичный отказ источника отличается от аварии процесса.

### AFR-004. Пользователь и права

Agent работает под существующим выбранным пользователем, включая root по явному выбору с предупреждением клиента. Обычные операции используют права процесса/групп и серверную политику. Автоматические sudo, постоянный helper и автоматическое создание отдельной учётной записи не применяются.

**Приёмка:** sudo при установке не меняет runtime-пользователя на root; недостаток прав даёт понятный отказ, без обхода ограничений ОС.

### AFR-005. Стек и сборки

Agent/CLI реализуются на Go; HTTP/TLS/JSON — стандартная библиотека, WSS — coder/websocket, Linux API — golang.org/x/sys/unix, NVIDIA — NVIDIA/go-nvml, SQLite — database/sql и mattn/go-sqlite3. Версии toolchain/зависимостей закрепляются и проверяются. Системные пакеты кода компилируются в общий бинарник; произвольные Go-plugin/.so как системные модули не загружаются.

**Приёмка:** релиз воспроизводимо собирается для заявленных целей с учётом cgo/glibc; компилятор на сервер не требуется.

### AFR-006. Размещение установки

Выпуски размещаются в /opt/serverdeck/releases с переключением current; конфигурация — /etc/serverdeck, данные — /var/lib/serverdeck, runtime — /run/serverdeck. Код, данные и конфигурация разделены. Необходимые рабочие права выдаются выбранному пользователю; каталоги выпуска обслуживает установщик.

**Приёмка:** обновление кода сохраняет идентичность, устройства и данные; пути и владельцы доступны для диагностики и защищены по ASEC.

### AFR-007. Установка по SSH

Клиент проверяет SSH-доверие, загружает проверенный выпуск и запускает установщик. Предварительно проверяются ОС/архитектура, пользователь, доступные sudo-действия, место, порт и существующий Agent; показывается план изменений. SSH/sudo-секреты используются в памяти на время обслуживания.

**Приёмка:** неверный пароль или недостаточные полномочия не дают ложного успеха; ошибка сообщает фактически выполненные и неизвестные последствия.

### AFR-008. Повтор установки и неполное добавление

Установщик идемпотентен и распознаёт существующую установку, выбранного пользователя и незавершённое обслуживание. Повтор не сбрасывает TLS, устройства или данные. Закрытие незавершённой формы очищает клиентские параметры/секреты, но не удаляет автоматически уже установленный Agent.

**Приёмка:** повтор после обрыва показывает текущее состояние и продолжает допустимый шаг; запись готового сервера создаётся только после доверенного подключения и первого корректного снимка.

### AFR-009. Зависимости

Основные данные читаются через /proc, /sys, netlink и системные вызовы. htop/top, sysstat, lm-sensors, Prometheus/exporter, Docker и CUDA Toolkit не являются обязательной установкой. Для ICMP предлагается iputils-ping; journalctl используется при наличии/доступности. Для выбранного способа доставки проверяются загрузчик, распаковка и CA.

**Приёмка:** устанавливаются только нужные недостающие пакеты по показанному плану; sensors-detect, смена драйвера, групп, sysctl и загрузка модулей ядра не выполняются незаметно.

### AFR-010. Существующий Agent и смена пользователя

Новый телефон подключается к действующему Agent и получает его реальные права. Несовпадение SSH-пользователя и runtime-пользователя показывается, не вызывает автоматическую переустановку. Смена runtime-пользователя выполняется через SSH/CLI с переносом прав/состояния и ожидаемым перезапуском.

**Приёмка:** изменение имени в клиентском профиле не меняет пользователя процесса; разрешённое подключение использует доверенный pairing.

### AFR-011. Готовность и общие сведения Agent

Авторизованный клиент получает идентичность/версию Agent, поддерживаемые версии контрактов, capabilities, runtime-пользователя, доступность источников, ограничения и состояние хранения/аудита. До pairing нет публичного API метрик или полного описания прав.

**Приёмка:** совместимость проверяется через доверенный SSH-bootstrap и разрешённый pairing; свежий ответ не маскирует старое измерение.

## 3. Системные модули

### AFR-012. Сведения о системе

Предоставляются hostname, Machine ID при доступности, ОС/версия, ядро, архитектура, часовой пояс, uptime и характеристики. Идентичность экземпляра Agent отделена от IP, hostname и загрузки ОС.

**Приёмка:** смена адреса не создаёт новый сервер автоматически; перезагрузка/смена идентичности не склеивает несовместимые ряды.

### AFR-013. CPU

Предоставляются характеристики/число CPU, общая и покомпонентная нагрузка, user/system/iowait/steal/idle и доступные дополнительные состояния, load average, PSI, частоты, температуры и throttling. Процессные топы переиспользуют общий сбор.

**Приёмка:** расчёт выполняется по валидным приращениям счётчиков, первая/сброшенная точка не выдаётся за достоверный процент; методика общего процента и нормализации фиксируется в контракте единообразно; недоступные датчики имеют причину.

### AFR-014. NVIDIA GPU

Обнаруживаются GPU, UUID, драйвер/CUDA при применимости, PCIe, utilization, VRAM, температура, мощность, вентиляторы и доступные GPU-процессы. NVML — основной источник, nvidia-smi — диагностика/ограниченный машиночитаемый резерв. Драйвер автоматически не заменяется.

**Приёмка:** различаются отсутствие GPU, библиотека/драйвер, права и неподдерживаемое поле; номер GPU не служит устойчивой идентичностью; ошибка NVIDIA не подменяется нулём.

### AFR-015. RAM и swap

Предоставляются Total, Available, Free, используемая RAM как Total минус Available, объёмы и проценты swap. Отсутствие swap — нормальное состояние; недоступный Available не заменяется без объявления другой методики.

**Приёмка:** Free и Available различаются; знаменатель не бывает нулевым; обязательная долговременная история RAM не добавляется.

### AFR-016. Файловые системы и диски

Предоставляются источник/точка монтирования/тип, общий/занятый/доступный объём, inode и доступность. Корневая / показывается при доступности даже для overlay/squashfs; остальные псевдо/служебные ФС скрыты по умолчанию. Ошибка одной ФС не скрывает остальные.

**Приёмка:** недоступные inode имеют отдельный статус; смена монтирования учитывается. Выбор основного диска карточки закрепляется отдельным правилом контракта, а не случайным порядком. SMART/форматирование/разделы и обязательная история дисков не добавляются.

### AFR-017. Сеть

Предоставляются интерфейсы/тип, адреса, MTU, маршруты/gateway/DNS, RX/TX, ошибки/dropped, доступные link speed/duplex. При неизвестной пропускной способности процент загрузки канала не выдумывается. Публичный IP не определяется обращением к навязанному внешнему сервису.

**Приёмка:** сброс счётчика и смена экземпляра интерфейса разрывают вычисление, а не дают отрицательный трафик; недоступный источник не делает сервер OFFLINE.

### AFR-018. Список и подробности процессов

Предоставляются PID/идентичность экземпляра, имя/владелец/состояние, CPU/RSS, время запуска/uptime, родитель, потоки и доступные связи systemd/Docker/cgroup. Поиск/сортировка выполняются до пагинации; страница содержит не более 100 процессов. Топы используют те же результаты.

**Приёмка:** ограниченная видимость обозначена; аргументы команд, окружение и полная чувствительная командная строка не выдаются.

### AFR-019. Файловый менеджер

Предоставляются корни, каталог с продолжением, метаданные/доступные действия, полный/частичный текст, создание, сохранение, upload/download, rename/move, корзина, восстановление и ручной PURGE по AFR-042–AFR-050.

**Приёмка:** клиент получает фактические права и конфликты; операция не расширяет доступ за счёт пользователя SSH или скрытого sudo.

### AFR-020. Docker-обзор

Через существующий Docker API предоставляются наличие/версия/доступность Engine, состояния и количества контейнеров, проблемные/активные контейнеры, доступные CPU/RAM и Compose-метаданные. Rootless-сокет задаётся явно; версия API согласуется.

**Приёмка:** «не установлен», «daemon недоступен» и «нет прав» различаются; Docker ради обзора не устанавливается; start/stop/remove контейнеров не добавляются.

### AFR-021. Мониторинг безопасности

Читаются доступные сведения firewall, SSH-сессий/входов, Fail2ban/jail/блокировок. Journal/auth-логи распознаются адаптерами ОС, с позицией чтения и учётом ротации; события классифицируются фиксированными документированными правилами.

**Приёмка:** неполное покрытие обозначено; успешный вход сам по себе не считается предупреждением. Автонастройка firewall/Fail2ban, блокировки адресов и универсальный log viewer не добавляются.

## 4. Сбор, передача и история

### AFR-022. Качество и доступность значений

Показатель содержит единицу, идентичность объекта, время успешного измерения/последней попытки, доступность и безопасную причину. Различаются отсутствует, не поддерживается, нет прав, ошибка, устарел и валидное нулевое значение.

**Приёмка:** клиент может показать частичный результат; смена смысла/единицы ряда не смешивается с прежней историей.

### AFR-023. Расписание общего сбора

| Данные | Интервал |
|---|---|
| CPU/RAM/network/NVIDIA, динамика | 2 секунды |
| Занятость ФС | 15 секунд |
| Процессы/топы | 5 секунд; при активных потребителях 2 секунды |
| Статические характеристики и сводки | При старте и 60 секунд |
| Включённая фоновая ICMP-диагностика | 60 секунд |

**Приёмка:** сбор/история продолжаются без телефонов; несколько устройств не умножают сбор. После завершения подписок или ограниченного срока активности процессы возвращаются к 5 секундам.

### AFR-024. Доставка снимков и подписки

Клиентские карточки получают данные раз в 5 секунд, подробности — раз в 2 секунды, переиспользуя общий снимок. Сбор, доставка и история независимы. Медленному клиенту текущий снимок заменяется свежим, без бесконечной очереди.

**Приёмка:** аудит/события/операции не отбрасываются по правилу заменяемых снимков; WSS-переподключение имеет задержку и догрузку сохраняемых данных.

### AFR-025. Свежесть

Регулярный блок устаревает после трёх пропущенных плановых обновлений. Для источников по запросу/событию возвращаются время наблюдения, режим и состояние; к ним механически не применяется таймер периодического коллектора.

**Приёмка:** новый ответ не обновляет timestamp старого значения; клиент различает доступный Agent с устаревшими данными и недоступный Agent. Итоговые статусы карточки остаются клиентскими.

### AFR-026. Время и идентичность рядов

Длительности измеряются монотонными часами, отображаемое время — UTC. Учитываются boot-id, экземпляр ресурса и схема ряда. Перестановка системных часов открывает новый сегмент с явным признаком, не создаёт отрицательные длительности и скрытое слияние.

**Приёмка:** перезапуск/сброс требует новой исходной точки производных; повторы догрузки не создают дубликаты и не теряют сегменты.

### AFR-027. Уровни истории

Для CPU/GPU/сети целевые уровни: шаг 15 секунд за последний час, 1 минута за последние 24 часа, 5 минут за последние 7 суток. Поддерживаются запросы диапазонов 15 минут/1/6/24 часа/7 дней. Фактическое покрытие зависит от бюджета, доступности и отказов.

**Приёмка:** пользователь видит доступный диапазон/шаг/пропуски; сокращение целевой глубины предупреждается. Обязательная история RAM/дисков/каждого PID не вводится.

### AFR-028. Агрегация

CPU: средние нагрузки/состояний/PSI/частот, максимум температуры/throttling, последнее LA. GPU: средние utilization/мощности/VRAM, максимумы температуры/мощности/VRAM и наблюдённый throttling. Сеть: приращения объёмов/ошибок, длительность покрытия, средняя и максимальная наблюдённая скорость.

**Приёмка:** средние объединяются с весами покрытия; накопительные счётчики не усредняются. Точки 15 секунд используют исходные измерения окна. Максимум не обещает поймать пик между измерениями.

### AFR-029. SQLite и запись

SQLite размещается на локальной ФС; критическое состояние/аудит/операции отделены от частой истории. Критические записи надёжно commit-ятся до действия; история записывается пакетами не реже раза в 5 секунд, с возможной потерей незаписанного пакета. Используется исправленный поддерживаемый SQLite, включая WAL-reset fix 3.51.3 или официальный backport.

**Приёмка:** WAL/checkpoint/длительные чтения ограничены, NFS/SMB не используются; копия БД согласованная. Независимые БД не считаются одной атомарной транзакцией.

### AFR-030. Бюджет истории

Серверный бюджет по умолчанию 256 МБ, общ для телефонов и настраивается версионированной аудируемой операцией. Дополнительным модулям суммарно доступно не более 25% этого бюджета с явным распределением. Индексы/WAL/технический резерв учитываются и показываются, резерв ограничен.

**Приёмка:** вытесняются старейшие диапазоны при сохранении свежей многоуровневой истории; снижение лимита с потерей данных подтверждается; покрытие менее 7 суток предупреждается; ключи/настройки не удаляются ради истории.

### AFR-031. Выдача истории

Не более 2000 точек на ряд для CPU/GPU/сети; размер страницы истории не более 4 МБ. Число рядов и продолжение ограничиваются общим размером. Ответ содержит фактический шаг, покрытие и признаки неполного окна.

**Приёмка:** большой запрос агрегируется/разбивается предсказуемо, а не молча усекается; клиент может обновить ранее полученный неполный агрегат.

### AFR-032. Локальный кэш клиента

Смежное требование Android: бюджет 128 МБ суммарно по серверам включает метрики и журналы, настраивается отдельно от серверного. Клиент показывает распределение/покрытие, сохраняет доступное для offline и догружает пропуски в пределах серверного хранения.

**Приёмка:** очистка кэша не удаляет токены/профили; чтение одним телефоном не удаляет серверные записи для других; серверные лимиты не меняются локальным ползунком без подтверждённого запроса.

## 5. События, аудит и операции

### AFR-033. Серверные события

Agent формирует/сохраняет события независимо от телефонов. Общие правила задают объект/метрику, порог, длительность, восстановление и повторы. Активная проблема хранится независимо от истёкшего события о начале.

**Приёмка:** потеря источника не изображает восстановление; история событий не подменяет текущее состояние.

### AFR-034. Начальные правила

| Правило | Возникновение | Восстановление |
|---|---|---|
| Недостаток доступной RAM | Менее 10% 2 минуты | Более 15% 2 минуты |
| Недостаток места или inode | Менее 10% 5 минут | Более 15% 5 минут |
| Высокая CPU/GPU-загрузка | Выключено, задаёт пользователь | По пользовательскому правилу |
| Температура GPU | Порог устройства либо явный пользовательский | По объявленному правилу устройства/пользователя |
| Недоступный регулярный источник | Порог устаревания AFR-025 | Валидное измерение |
| Неудачные SSH-входы | Отключаемое правило: 5 с одного адреса за 5 минут при распознанном источнике | По схеме события/окна |

**Приёмка:** правила редактируемы и отличаются от локальных порогов цвета; неудачи SSH не объявляются доказанной атакой.

### AFR-035. Повторы и реакция

Уведомления о начале/восстановлении различаются; повтор продолжающейся проблемы не чаще раза в час. Повторы могут объединяться с количеством и временем первого/последнего наблюдения. Аудит отдельных управляющих действий так не объединяется.

**Приёмка:** нет бесконечного потока одинаковых уведомлений и автоматического убийства процессов/блокировки адресов/перезапуска приложений по порогу.

### AFR-036. Хранение журналов

События: до 7 суток и 32 МБ. Аудит: до 30 суток и 64 МБ. Оба ограничения действуют совместно, фактическая глубина показывается; старейшие завершённые записи вытесняются при достижении объёма. Бюджеты отдельны от метрик; ротация не ждёт все телефоны.

**Приёмка:** уменьшение срока/объёма с потерей записей подтверждается; активная проблема и единственное состояние незавершённой операции не удаляются обычной очисткой; устаревший курсор получает явный разрыв.

### AFR-037. Уведомления телефона

Смежное требование Android: foreground использует HTTPS/WSS, фон — WorkManager 15 минут по умолчанию, варианты 30/60/отключение. У каждого устройства свой курсор и настройки показа/звука. После offline старые события объединяются в сводку с подавлением дублей. Просмотр событий/аудита — отдельные вкладки раздела сервера «События и действия».

**Приёмка:** показывается последнее успешное обращение; нет гарантии срока доставки при Doze/force-stop/нет сети. Телефон без сети не утверждает, что сервер выключен.

### AFR-038. Аудит и отказ записи

Все управляющие операции/отказы фиксируют устройство или локального/системного инициатора, идентификатор операции, время, безопасный объект и результат. До изменяющего действия сохраняется надёжная запись начала. Если это невозможно, действие не начинается. Мониторинг/доступное авторизованное чтение продолжаются по возможности.

**Приёмка:** сбой аудита виден в текущем состоянии; метрики не засоряют аудит. Ошибка записи результата после побочного эффекта не превращает его в невыполненное и не вызывает слепой повтор; восстановление выполняется через SSH/CLI с обозначением пробелов. Штатный CLI применяет ту же политику аудита; первичная установка до появления Agent и аварийное внешнее обслуживание отдельно описаны в ASEC-031 и не являются обходным HTTP/IPC-методом.

### AFR-039. Состояние и повторы операций

Изменение имеет устойчивый id, привязку к инициатору/действию/параметрам и состояния подготовки/выполнения/успеха/отказа/отмены/неизвестного результата. Повтор с тем же id в пределах срока возвращает состояние, другой набор параметров отклоняется. Завершённые результаты/защита повторов сохраняются 7 суток.

**Приёмка:** после истечения срока защита от дублей не обещается, старое действие не повторяется автоматически. Незавершённые состояния сохраняются до проверки/административного разрешения; при невозможности ограниченного хранения новые изменения приостанавливаются.

### AFR-040. Конкуренция и отмена

Настройки и файлы имеют версии; конфликт возвращает актуальное состояние. Конфликтующие действия объекта сериализуются, до четырёх изменяющих операций Agent одновременно. Устройства равноправны; очередь не даёт постоянного приоритета. Отмена гарантируется до необратимого шага либо для объявленной поддерживающей её операции.

**Приёмка:** второй телефон не затирает изменение молча; SSH-вмешательство обнаруживается проверкой текущего объекта, а не только внутренним lock.

### AFR-041. Завершение процесса

TERM и KILL — отдельные именованные подтверждаемые действия. Проверяется экземпляр процесса, права и защита PID 1; используется pidfd при поддержке. Успешная отправка сигнала не равна подтверждённому завершению.

**Приёмка:** PID reuse не направляет сигнал другому процессу; TERM не превращается автоматически в KILL; собственное ядро/управляемые модули обслуживаются через предусмотренный жизненный цикл.

## 6. Файловые операции

### AFR-042. Разрешённые корни

По умолчанию доступен home пользователя Agent. Доверенные равноправные устройства через общую аудируемую настройку могут добавить другие корни, включая / с предупреждением. Корень имеет идентификатор, пути относительны; политика не расширяет права ОС.

**Приёмка:** корень другого смонтированного раздела допустим, вложенные монтирования включаются явно; смена политики конфликтует по версии.

### AFR-043. Ссылки и защищённые объекты

Работа идёт через дескрипторы каталогов и защищённое разрешение путей; symlink/magic-link не разыменовываются. Ссылки могут отображаться как объекты без чтения целей. Спецфайлы/сокеты/устройства и виртуальные /proc,/sys,/dev не обслуживаются как обычные файлы. Собственные секреты/рабочие объекты/предки Agent защищаются по ASEC.

**Приёмка:** обход через traversal, aliases, hard links, mounts и гонки не даёт доступа; при невозможности безопасной операции возвращается отказ.

### AFR-044. Текстовый просмотр

Полный текст по умолчанию до 1 МБ, редактирование полного текста до 512 КБ. Частичный просмотр поддерживает последние 100/500/1000 строк и более ранние порции, ограниченные по байтам. Кодировка и версия сообщаются; постоянный tail-f не добавляется.

**Приёмка:** лимиты настраиваемы/объявлены; бинарный или слишком большой текст не выдаётся как полный редактируемый. КБ = 1000 байт; МБ = 1 000 000. Контент может передаваться потоком, чтобы JSON-экранирование не ломало поддерживаемый размер.

### AFR-045. Передачи файлов

Upload по умолчанию до 50 МБ, download до 100 МБ, если явно не настроено иначе. До двух передач одновременно; контент потоковый, без base64 в управляющем JSON. Проверяются место, границы путей, размер, временный файл и конфликт имени.

**Приёмка:** лимит контролируется по фактическим байтам, не только заявленному размеру; незавершённая передача не выдаётся за готовый файл и очищается по ограниченной политике.

### AFR-046. Создание и сохранение

Создание/rename/редактирование проверяют имя, права, ожидаемую версию и текущую идентичность объекта; готовый файл публикуется атомарно там, где это возможно. Неудача записи/нехватка места не повреждает исходник молчаливой частичной заменой.

**Приёмка:** конфликт не теряет чужие изменения; существующий объект не заменяется без подтверждённой политики; точные версии/кодировки оформляются в контракте.

### AFR-047. Корзина

Удаление через файловый менеджер перемещает объект в закрытую доступную корзину на той же ФС. Срок по умолчанию 7 суток, бюджет 1 ГБ на ФС, настраиваемые. При заполнении новые перемещения отклоняются с вариантами очистки/увеличения; свежие записи ради бюджета не удаляются незаметно.

**Приёмка:** невозможность корзины не превращает удаление в необратимое; исходный путь/инициатор/время/срок доступны; ГБ = 1 000 000 000 байт.

### AFR-048. Окончательное удаление

Ручной PURGE разрешён только для объектов корзины и требует отдельного явного необратимого подтверждения. Автоочистка выполняется по серверному сроку, через те же проверки и аудит.

**Приёмка:** обычное удаление не вызывает PURGE, объект/последствия подтверждения определены; при невозможности аудита очистка не обходит AFR-038. Это заменяет противоречивое исключение из клиентского FR-007.21.

### AFR-049. Восстановление

Объект восстанавливается в разрешённый исходный/выбранный каталог с правами пользователя. При занятом имени нужно новое имя или отдельное разрешение замены.

**Приёмка:** исходное имя не даёт обход корней; занятый объект не перезаписывается молча, восстановление может сообщить частичный результат/отказ.

### AFR-050. Перенос между ФС

Межфайловое перемещение — отслеживаемое копирование, проверка результата и отдельное перемещение источника в корзину. Оно не объявляется единым атомарным rename.

**Приёмка:** при неопределённости сохраняется источник и показывается частичный результат; незавершённый target/копия не означает безопасное удаление оригинала. Архивирование/исполнение файлов этим требованием не добавляются.

## 7. Дополнительные модули и UI

### AFR-051. Ручная регистрация

Установщик модуля явно регистрирует через CLI JSON-манифест: id/издатель/версия, совместимость ОС/архитектуры/Agent/IPC, capabilities/схемы действий, зависимости, команда/аргументы, пути к коду/данным. Agent обнаруживает реестр без полного перезапуска, проверяет и показывает карточку.

**Приёмка:** произвольный executable не запускается автоматически, системный статус не назначается манифестом; запуск разрешается доверенной установкой.

### AFR-052. Зависимости

Дополнительные зависимости описываются графом, циклы и несовместимость диагностируются до запуска/обновления. Системные функции не зависят от удаляемого дополнительного модуля.

**Приёмка:** отключение/удаление необходимого модуля показывает зависимые и требует подтверждения последствий; независимые модули продолжают работу.

### AFR-053. Управляемые процессы

Желаемое состояние, существование процесса и готовность IPC раздельны. Максимум пять рестартов за десять минут с возрастающей задержкой, затем ручной запуск. Остановка: запрос, до 15 секунд ожидания, затем принудительная остановка управляемой группы с сообщением результата.

**Приёмка:** бесконечных рестартов/потомков нет; при остановке основного unit завершается его cgroup, после старта разрешённые модули запускаются заново; неизвестные операции остаются обозначенными.

### AFR-054. IPC

Unix stream socket, JSON-RPC 2.0, UTF-8 JSON с framing длиной сообщения. Handshake проверяет регистрацию, экземпляр, версии/capabilities и секрет запуска из унаследованного канала; peer credentials — дополнительная проверка. Обычный RPC ожидается до 10 секунд, длительное действие возвращает operation-id; управляющее сообщение до 1 МБ.

**Приёмка:** до handshake действия не маршрутизируются; токен телефона модулю не передаётся; timeout не означает отмену побочного эффекта.

### AFR-055. Данные/история модулей

Agent согласует расписание/лимиты, переиспользует снимки и сохраняет разрешённые ряды через общий механизм с бюджетом AFR-030. У модуля пространство имён/версия схемы/единицы и ограничение числа рядов; CPU-интервалы ко всем рядам автоматически не применяются.

**Приёмка:** новые ряды/единицы не подменяют старые; неизвестный/неразрешённый ряд не расходует хранилище без согласования.

### AFR-056. Отключение и удаление

Отключение управляемого модуля останавливает процесс/сбор/действия, сохраняя данные/настройки. Обычное удаление удаляет код/регистрацию, сохраняя данные; полная очистка отдельно подтверждается. Обновление возможно отдельно при совместимости.

**Приёмка:** отсутствие прав не изображается успехом; удаление интеграции не удаляет само стороннее приложение; независимые функции сохраняются.

### AFR-057. Внешний запуск

Внешний процесс, включая другого пользователя, допускается при доверенной регистрации канала/прав/протокола. Agent различает наблюдение и полномочия запуска/остановки/удаления. Supervisor не должен незаметно восстанавливать модуль, считающийся отключённым.

**Приёмка:** отключение маршрутизации не выдаётся за подтверждённую остановку недоступного процесса; недостаток полномочий сообщается без повышения прав.

### AFR-058. Декларативный UI

Смежное требование клиента: подписанный версионированный JSON-пакет со статическими ресурсами, id/издателем/совместимостью и действиями. Только встроенные нативные компоненты. До совместимого UI — общая карточка состояния/версии/доступного управления.

**Приёмка:** модуль автоматически появляется после серверной регистрации; новые страницы возможны без APK, новые типы компонентов требуют обновления клиента; исполняемые Android/JS-компоненты не загружаются.

### AFR-059. Установка UI

Пакет получается через Agent или импортом; клиент проверяет подпись доверенного издателя, целостность, идентичность, схему/размеры/совместимость и запрашивает отдельное подтверждение. Новому ключу из самого пакета автоматически не доверяет. Сохраняет рабочую версию до успешной замены.

**Приёмка:** UI/серверный модуль имеют независимый жизненный цикл; повреждённый UI не ломает остальные экраны; удаление UI не удаляет модуль сервера.

## 8. Подключение, устройства и обслуживание

### AFR-060. Транспорт

HTTPS JSON обслуживает именованные команды/настройки/снимки/историю/операции, WSS — подписки. Один TCP-порт, по умолчанию 8443, настраиваемый; нет обязательного relay/VPN/reverse proxy. Обычный JSON не более 1 МБ, история до 4 МБ; потоковые файлы отдельно.

**Приёмка:** HTTP/WSS имеют одинаковую авторизацию, секрет не в URL; занятый порт диагностируется; большие ответы имеют ограничение и продолжение.

### AFR-061. Доступ и firewall

Режимы: localhost «Не открывать», явно выбранная LAN/VPN-область, внешний доступ с предупреждением. Ограниченный режим по умолчанию. Из localhost нельзя завершить добавление готового сервера без доступного маршрута и первого снимка. UFW меняется точечно по плану, без reset/enable/disable; другие неизвестные firewall — инструкции.

**Приёмка:** проверяются IPv4/IPv6 и достижимость с телефона; не определяется «локальная сеть» по публичной подсети VPS; сохраняются только собственные firewall-изменения.

### AFR-062. ICMP-цель

Один общий server target, IP/домен, включая частные/VPN-адреса; по умолчанию отсутствует. Запрос — максимум пять пакетов и десять секунд, по первому пределу; фон после явного включения раз в 60 секунд. DNS/экземпляр цели связаны с результатом, смена цели создаёт другой ряд.

**Приёмка:** используется проверенный ping с массивом аргументов без shell; URL/сканирование/произвольные флаги не принимаются; отказ ICMP не равен OFFLINE.

### AFR-063. Pairing и устройства

Одноразовый криптографически случайный pairing-код действует 5 минут, выдаётся через доверенный SSH/CLI, имеет ограниченные попытки. Устройства равноправны, имеют отдельные id/токены/последнюю активность. Новый телефон не получает доверие только из произвольного SSH-логина.

**Приёмка:** истёкший/использованный код не работает; первый снимок после pairing использует уже полученный токен без повторной установки.

### AFR-064. Токены и отзыв

Токен устройства — случайный 256-битный, действует до отзыва; сервер хранит проверочное значение, клиент — защищённое хранилище. Устройства могут отзывать друг друга с подтверждением; закрываются активные WSS и новые запросы отозванного устройства.

**Приёмка:** утрата всех телефонов восстанавливается через SSH/CLI; при недоступном аудите штатный отзыв не обходит блокировку, аварийные внешние действия/пробелы обозначаются.

### AFR-065. TLS и адрес

TLS не ниже 1.2, предпочтительно 1.3. Самоподписанное доверие/отпечаток проверяются через SSH, включая DNS/IP-идентичность и срок. Сертификат 365 дней, предупреждение за 30; ручное обновление через SSH/CLI, каждый телефон проверяет новый отпечаток.

**Приёмка:** смена адреса проверяет тот же Agent и сертификат, не отключает проверку; истёкшее/неожиданное доверие требует восстановления через SSH.

### AFR-066. Выпуски и совместимость

Подписанные архивы по архитектуре с манифестом и TUF-метаданными. Доверенные ключи поставляются проверенным клиентом/установщиком, GitHub Releases — транспорт. Совместимость включает ядро/glibc, Agent/API/IPC/UI/схемы. Клиент проверяет не чаще раза в сутки, с отключением; установка только вручную. Доступен локальный подписанный архив.

**Приёмка:** неподписанный/несовместимый/отозванный выпуск отклоняется до остановки; ранее отключённый телефон проверяется при возвращении.

### AFR-067. Выполнение обновления

Через SSH/CLI предварительно проверяются место, подписи, зависимости и операции, готовится согласованное восстановление, затем локально выполняется замена. Установщик — временная задача обслуживания systemd, переживающая разрыв SSH; повтор наблюдает существующее состояние, не начинает второе обновление.

**Приёмка:** основной Agent не получает постоянного helper; дополнительный модуль обновляется отдельно при совместимости, системный код может перезапустить ядро; данные/идентичность не теряются штатно.

### AFR-068. Проверка, миграция и откат

60 секунд проверяются процесс, защищённый API, чтение состояния, планировщик и ожидаемые доступные источники. Отсутствующий GPU/права не считаются провалом выпуска сами по себе. При провале автоматически возвращаются проверенный выпуск и согласованное состояние. Один предыдущий рабочий выпуск/резерв хранится до следующего успешного обновления или явной очистки.

**Приёмка:** несовместимая миграция без проверенного возврата требует отдельного плана обслуживания; отозванные токены не возвращаются, новые ограничения не отменяются. Известно отозванный выпуск не выбирается для автоматического возврата. Если актуальный учёт доступа восстановить достоверно нельзя, старые токены из резервной копии не активируются автоматически: требуется доверенное восстановление через SSH. Внешние изменения стороннего приложения не обещаются к откату.

### AFR-069. Удаление и восстановление

Обычное удаление Agent через SSH/CLI останавливает его/управляемые процессы и сохраняет данные; полная очистка отдельно подтверждается. Удаляются только принадлежащие установке объекты/правила; системные пакеты, драйверы, Docker и сторонние приложения не удаляются автоматически.

**Приёмка:** отчёт показывает сохранённые/удалённые/неудалённые объекты; восстановление доступа/повреждения не требует работающего публичного API.

## 9. Устойчивость, ограничения и проверка

### AFR-070. Частичный отказ и контроль ресурсов

Обработанный отказ коллектора/IPC/истории не останавливает остальные доступные функции. Очереди/сложность JSON/размеры/частота/параллельность ограничены. Для модулей при доступных делегированных cgroup задаются CPU/RAM-лимиты; отсутствие изоляции явно показывается. Для ядра применяются watchdog и ограниченные рестарты.

**Приёмка:** зависший нативный вызов не размножает параллельные попытки; глобальные UID-лимиты не мешают другим приложениям; фатальный сбой ядра не объявляется изолированным отказом модуля.

### AFR-071. Версии и измеряемые параметры

Публичный API поддерживает текущую и предыдущую major-версию; IPC-диапазон объявлен манифестом. Полные JSON-схемы и профили ограничений закрепляются до выпуска. Потребление CPU/RAM, очереди и резервные объёмы измеряются; версия SQLite и зависимости проверяются.

**Приёмка:** несовместимость видна до действий; численные бюджеты не выдаются за RAM-требования/производительность; release notes содержат проверенные окружения и ограничения.

### AFR-072. Документация, лицензия и испытания

Собственный код — Apache-2.0 с проверкой лицензий зависимостей/notices. Оформляются API/IPC/UI, модульная система, конфигурация, обслуживание и восстановление. Испытываются ordinary/root, недоступные источники, реальная NVIDIA, обрыв SSH/сети, конкуренция, переполненный/повреждённый диск, отказ аудита, перезапуск операции, миграция/откат, подмена пакетов и обход файловых корней.

**Приёмка:** результаты привязаны к AFR/ASEC и целям релиза; исходные клиентские противоречия перечислены и не используются для отмены последних решений.
