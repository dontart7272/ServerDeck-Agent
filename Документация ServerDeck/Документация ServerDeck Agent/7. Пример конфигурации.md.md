# Конфигурация Agent

Версия: 1.0, 12 октября 2026 года. Статус: специфицировано, не применено к реальному серверу. Основания: AFR-004–AFR-011, AFR-023–AFR-040, AFR-042–AFR-047, AFR-051–AFR-071; ASEC-001–ASEC-031 в применимой части. [Структурная схема](<contracts/config.schema.json>), [полный пример](<contracts/examples/config.json>), [API](<3. API и форматы данных.md.md>), [обслуживание](<8. Архитектура и обслуживание.md>).

## 1. Источники и изменение

`/etc/serverdeck/server.json` — bootstrap/параметры запуска, root-managed; owner/group/ACL выдаются только выбранному существующему пользователю. `runtime_initial` используется только при первичной инициализации, потом источником runtime-настроек служит critical.db с revision. Изменение файла не перетирает решения телефонов при restart. CLI `config export` выдаёт redacted effective runtime; `config import` применяет тот же аудит/versions/confirmation, что HTTP. Файл не содержит паролей/токенов/ключей, только ссылки на защищённые объекты. Не допускаются env substitution, include удалённого файла или shell expansion.

Чтение: strict JSON UTF-8, <=1 МБ, неизвестные поля/дубли/неверный тип/границы — отказ до сетевого listen. Проверяются абсолютность путей, владельцы/родители, отсутствие symlink/небезопасных ACL, локальность DB, OS-механизмы. При ошибке runtime-фрагмента в БД используется последняя валидная revision только если её подлинность/целостность проверены; иначе read-only recovery через SSH, без старой слабой политики. Переменные окружения не переопределяют безопасность. В примере `operator` — существующая учётная запись, не команда создать пользователя.

Все размеры — десятичные bytes, интервалы в ms, TTL в seconds, retention в days. `null` для отсутствующей цели/источника; `0` не означает бесконечный лимит. Начальные лимиты ресурсов — технический профиль, не измеренный минимум RAM/CPU.

## 3. Runtime-поля и согласованные числа

API `config.set` принимает typed `changes` с непустым подмножеством ключей ниже и expected_version. Значения bounds фиксируются schema. Defaults не считаются результатами измерений. Нельзя менять интервалы/срок dedup или ослаблять TLS через произвольный JSON patch.

| Ключ runtime | Default / допустимый диапазон v1 | Поведение |
|---|---|---|
| history.budget_bytes | 256000000 / 16000000..16000000000 | Включает DB/index/WAL/SHM/резерв; уменьшение с потерей данных подтверждается |
| history.module_share_percent | 25 / 0..25 | Суммарный потолок, не автоматическая выдача квоты |
| events.retention_days/budget_bytes | 7/32000000; 1..365 / 1000000..1000000000 | Оба ограничения совместно; уменьшение подтверждается |
| audit.retention_days/budget_bytes | 30/64000000; 1..365 / 4000000..2000000000 | Завершённые записи ротируются, intent операции сохраняется отдельно |
| files.full_text_bytes/edit_bytes | 1000000/512000; 1000..1000000 / 1000..512000 | edit<=full; v1 hard maxima совпадают с defaults, снижение допускается |
| files.upload_bytes/download_bytes | 50000000/100000000; 1000..1000000000 / 1000..2000000000 | Настраиваемые лимиты, фактические bytes контролируются |
| files.roots | home выбранного user при установке | Список root_id/path/mount identity, max32; расширение с предупреждением, `/` отдельно |
| trash.retention_days/budget_bytes_per_fs | 7/1000000000; 1..365 / 1000000..100000000000 | При переполнении отказ новым moves; без тайного PURGE свежих |
| icmp.target/background_enabled | null/false | IP/домен <=253 символов, без URL/flags; одна общая цель |
| modules.grants | пусто | Назначения registered ids и history quota; ОС-права не изменяет |

Модульные grants изменяются только через `modules.policy.set`, а не дублирующую запись config.set. Roots API передаёт как параметры общей политики; физические mount identity фиксирует сервер, клиент не может подделать id файловой системы. Rules имеют отдельные versioned records/операции, см. следующий раздел. В schema runtime_initial отсутствуют grants до ручной регистрации.

Остальные согласованные интервалы/ограничения v1 неизменяемы сетевым config.set: динамика CPU/RAM/GPU/сети 2000, ФС 15000, процессы 5000/2000 при активном потребителе, характеристики 60000, ICMP фон 60000; доставка 5000/2000; stale 3 периода; история 15000/час, 60000/сутки, 300000/7 суток; batch write<=5000; dedup 7 суток; 4 одновременных изменения, 2 передачи; история <=2000 точек/ряд/4 МБ, обычный JSON/IPC <=1 МБ; процессная страница <=100; RPC 10000; stop модуля 15000; рестарты 5/600 с; сертификат 365/30 дней; pairing 300 с/токен 256 бит; health-check 60000. Изменение этих контрактных constants требует новой версии профиля и проверки требований, а не скрытой настройки.

Клиентские 128 МБ кэша, фон 15/30/60 мин/off и проверка обновления раз в 24 часа — обязанности Android, не server.json и не таймер Agent. У Agent нет обязательного обращения к облаку для уведомлений/публичного IP.

## 4. Начальные event rules

Rule: id/version/enabled/kind/resource_selector/metric/comparison/threshold/duration_ms/recovery_comparison/recovery_threshold/recovery_duration_ms/repeat_ms. Numeric threshold должен иметь unit совместимую с зарегистрированным рядом, duration 0..86400000, repeat>=3600000. До 256 правил; редактирование версионированное/аудируемое. Recovery не подтверждается отсутствием источника.

| ID/kind | Начальная политика |
|---|---|
| memory.available / threshold | available_percent<10 непрерывно 120000 мс; recovery>15 120000; repeat 3600000 |
| filesystem.available / threshold | available_percent<10 300000; recovery>15 300000; inode отдельное правило |
| filesystem.inodes_available / threshold | Те же 10/15 и 300000; неподдерживаемые inode не ноль |
| cpu.busy / threshold | disabled; пользователь задаёт порог/длительность/recovery |
| gpu.utilization / threshold | disabled; пользователь задаёт параметры |
| gpu.temperature / device_threshold | Только когда источник предоставляет сопоставимый порог/recovery; иначе inactive_requires_config |
| source.unavailable / source_stale | После 3 периодов; recovery после валидной точки; repeat час |
| ssh.failures / ssh_window | enabled при распознанном доступном источнике: >=5 неудач с одного адреса за 300000 мс; после окна без новых неудач recovery, это затихание наблюдений, не доказательство безопасности |

Разрывы/рестарт не продолжают выдуманный непрерывный threshold-duration: pending duration сбрасывается, active problem остаётся source_unknown до валидного состояния. У device_threshold при отсутствии documented recovery нельзя угадывать универсальную температуру — пользователь задаёт правило. Дедуп SSH учитывает journal cursor/source boot или inode+offset, bounded ключи адресов; при переполнении состояние покрытия неполное, а не потеря без признака.

Лимиты CPU/RAM модуля становятся выданными только по проверенной регистрации/делегации, не вводятся глобально для UID. Нет гарантии, что 64 соединения или 4096 рядов помещаются в конкретный VPS: превышение CPU/RAM корректируется профилем после измерений, не обещанием поддержать максимумы одновременно. При нехватке ресурса — typed отказ/coverage, а не отключение защиты. Аудит достигший quota ротируется внутри guarded транзакции; недостаток физического места/резерва не обходится очисткой пользовательских файлов по HTTP.

## 6. Валидация и применение

Структурная JSON Schema не проверяет владельца, существование пользователя, SAN, no-symlink, локальность ФС, реальную поддержку syscall, сумму grants<=25%, edit<=full, IPv4/IPv6 routing, подпись выпуска или долговечность commit. Эти semantic checks выполняются до listen/эффекта, включены в V-CONFIG/V-BOOT/V-AUDIT/V-FILE/V-UPDATE.

Runtime changes: прочитать текущую revision → prepare последствия/потери → повторно сверить revision/политику и права → intent+новое состояние в critical.db → применять effects/retention workers → result. Частичная очистка после снижения лимита даёт новую конфигурацию + наблюдаемый cleanup operation, не ложное обещание мгновенного освобождения физических страниц. При отказе result commit используется unknown/result_pending, не повтор политики вслепую. Рост лимита не восстанавливает удалённую историю.


Уточнение API-аудита 13 октября 2026: Runtime/ConfigChanges и config.set prepare/execute используют общий pure semantic validator с bootstrap. Группы патча заменяются целиком; helper `contracts.ApplyRuntimeChanges` проверяет исходный snapshot, patch и merged result без изменения аргумента/хранилища. Version guard, OS preflight и аудит принадлежат будущему application layer и не заменяются этой проверкой.

## E04: фиксированный collection profile

E04 не добавляет runtime/bootstrap полей или способа отключить системные источники. Коллекция2/5/15/60с, delivery2/5с и query lease10с — согласованный fixed profile; HTTP view/blocks/resource_ids выбирают выдачу, не включают отдельный collector. Реальные resource/page/native-call bounds, timeout статуса и SOURCE_BUSY — [METRICS](<../../agent/METRICS.md>). Ограниченный snapshot/process cache не считается history DB и не меняет её budget. Runtime seed E03/critical settings не переписываются.


## Применение E05

Runtime config.set сейчас исполняет группы history/events/audit/icmp/files через E02 audited plan/version service. При уменьшении физического бюджета сохраняется новая политика, ограниченная очистка может закончиться unknown/partial: это не означает откат политики или отсутствие удаления. Повтор той же операции не выполняет изменение заново. Events journal budget отделён от active allowance8МБ; физический размер включает DB/WAL/SHM/резерв, подробнее [HISTORY](<../../agent/HISTORY.md>). Остальные группы ожидают соответствующие этапы и не рекламируются capabilities как реализованные.


Уточнение завершения15 октября2026 (прогоны именованы по UTC14 октября): config.set при незавершённом уменьшении budget/retention возвращает новую version и cleanup_operation_id, равный ID текущей операции, со статусом unknown/partial/CLEANUP_PENDING. Это та же наблюдаемая операция применения политики и очистки, а не потерянное фоновое действие. До подтверждения результата сохранённый intent/lock не удаляется; повтор не запускает очистку заново. По правилам E02 требуется сверка и штатное административное resolve после проверки остатка/health; неизвестный исход автоматически не объявляется успехом. При пустом журнале уменьшение срока завершается succeeded и cleanup_operation_id=null. Calendar cleanup не обходит консервативные clock guards. Это ограничение доступности при неопределённости, не ложный failed/none и не откат принятой политики.

## Уточнение E07: процессы и ICMP

[Фактическая техническая реализация](../../agent/PROCESS-DIAGNOSTICS.md): process.term/kill используют существующий process_ref и раздельный подтверждённый план, только pidfd без fallback. signal_sent не равен exit_observed. config.set.icmp меняет общую target/background_enabled через CAS и аудит. diagnostics.icmp возвращает последний результат; diagnostics.icmp.run — manual operation через общий service. Opaque target_version включает agent_run_id/runtime revision/hash группы, старые результаты/планы не подходят новой revision. До5пакетов/10s, один probe, интервал между началами≥15s; фон только явно включённый, каждые60s, stale180s. Фон — мониторинг по уже аудированной настройке (AFR-038/ASEC-011), не одна изменяющая операция каждую минуту; manual probe аудируется. Существующие schemas/messages/enums не меняются. Недоступные syscall/ping/права не отключают остальные метрики. Исторический объём E07 не включал E08/E09; актуальное файловое поведение описано ниже.

## Применение E08 —16 октября2026

config.set.files применяет общую группу roots/byte limits/trash retention через plan/CAS/audit. Полная группа проходит contracts validator; root `/` не отменяет fixed protections. Production shared-root guard допускает обычный home на общей ФС в согласованной модели обслуживания, при актуальном inventory. config path сам по себе не доказывает безопасный доступ; roots/actions сообщают отказ и права. [FILES](../../agent/FILES.md) определяет runtime guards, лимиты и recovery.

Лимиты transfer/trash применяются при admission; уменьшение budget не разрешает немедленный PURGE свежих данных. Deadline trash сохраняется для каждой записи при создании. Фоновая очистка проходит отдельный audit, после рестарта ожидает консервативный полный retention interval uptime и не повторяет unknown. Runtime revision меняется при config.set: ticket со старой revision не публикуется. Собственные bootstrap/state/TLS/runtime/code и private staging/trash не становятся доступными после смены roots.
