# ServerDeck Agent — требования безопасности

Версия: 1.0. Дата оформления и проверки: 12 октября 2026 года.
Статус: базовые требования по решениям, принятым пользователем, включая Р01–Р25. Документ задаёт требования к реализации; испытания безопасности ещё не выполнены.

## 1. Область и связанные документы

Требования относятся к основному Agent, CLI/установщику, серверным модулям, хранилищам и границе с клиентом. Обязанности Android отмечены явно. Префикс ASEC отличает их от клиентских NFR-SEC.

Основания: [описание](<1. Краткое описание.md>), [AFR](<2. Функциональные требования.md>), [принятый пакет Р01–Р25](<Предложения по оставшимся вопросам.md>) и последние прямые решения пользователя. Старые запреты root и постоянный helper из клиентского NFR-SEC-013 не действуют как актуальная архитектура Agent.

Безопасность не означает обещание неограниченной доступности, неизменяемого аудита или полной изоляции модулей. Все проверки обязательны для применимых функций, включая запуск от root. Неопределённые в этом документе точные JSON-схемы/профили лимитов должны быть закреплены и проверены до выпуска.

## 2. Активы и границы доверия

Защищаются TLS/private keys, pairing-коды, токены/проверочные значения устройств, идентичность и настройки Agent, состояние операций, аудит, метрики/история, пользовательские файлы, код/метаданные выпуска и доверенные ключи издателей.

| Участник или граница | Принятая модель |
|---|---|
| Неавторизованный сетевой клиент | Недоверенный; не получает метрики, файлы или управляющие действия |
| Сеть между телефоном и сервером | Недоверенная; проверяемый TLS и авторизация |
| Сопряжённое устройство | Доверенный равноправный оператор; действия ограничены API, политикой и правами ОС |
| Пользователь SSH/CLI | Административные полномочия определяются реальными правами; SSH-login сам по себе не даёт токен |
| Дополнительный модуль под общим UID | Код, которому администратор доверил права пользователя; полноценной sandbox-изоляции нет |
| Внешний модуль/IPC | Отдельная доверенная регистрация и проверка канала, без доверия одному module-id |
| Root и злонамеренный код под UID Agent | Могут вмешиваться в процесс/файлы в пределах полномочий; предотвращение этого не гарантируется |
| Пакеты и метаданные из сети/от Agent | Недоверенные до проверки подписи, источника, совместимости и ограничений |
| UI-пакет | Декларативные недоверенные данные до проверки; подпись не разрешает исполнение кода |

Честный Agent должен противостоять неавторизованному клиенту, подмене сервера/пакета, неверным параметрам, случайным ошибкам доверенного оператора и ограниченным по ресурсам потокам запросов. Злонамеренный доверенный телефон уже обладает согласованными правами оператора; журнал помогает расследованию, но не отменяет эти права.

## 3. Исполнение, доверие и авторизация

### ASEC-001. Пользователь и отсутствие скрытого повышения

Основной процесс работает под явно выбранным существующим пользователем. Root допустим с предупреждением; отдельный пользователь автоматически не создаётся. Доступ проверяется по фактическим credentials/группам, серверной политике и ограничениям службы. Наличие sudo у пользователя не разрешает Agent применять его в обычном API.

**Проверка:** запустить root/ordinary; попытка недоступной операции ordinary получает отказ. Вызов не запускает sudo/helper, не меняет группы/credentials и не использует привилегии SSH-сеанса.

### ASEC-002. Установщик и SSH-доверие

Клиент проверяет SSH host key до передачи секретов/запуска обслуживания. Установщик предварительно показывает план, проверяет разрешённые действия sudo, окружение/пути/место/выпуск. Полученный по SSH runtime-пользователь не заменяется root из-за sudo. Временная задача обслуживания имеет только реальные предоставленные административные права.

**Проверка:** изменённый host key, недостаточные sudo-права, частичная установка и повторный запуск не дают ложного доверия/успеха; прекращение клиента не обещает откат уже выполненного.

### ASEC-003. Секреты SSH и bootstrap

Пароль SSH, sudo-пароль и разблокированный секрет ключа находятся в памяти клиента только на время сценария; незавершённая форма/закрытие/завершение освобождают их. Секреты не попадают в логи, ошибки, аргументы запуска или постоянный черновик. Доверенные сведения первого подключения получают через проверенный SSH/CLI.

**Проверка:** после отмены/сбоя в конфигурации/логах нет секретов; новый телефон с произвольным SSH-login не получает токен без разрешённого pairing.

### ASEC-004. Единая авторизация HTTP/WSS

Каждая операция, история, файл, аудит, capabilities и подписка требуют действующего устройства. Исключение — минимальный ограниченный pairing-bootstrap без публичных метрик/полных прав. Авторизация выполняется на сервере до дорогостоящих действий и на продолжениях потоков/страниц; скрытые кнопки клиента не являются контролем доступа.

**Проверка:** без токена и после отзыва недоступны те же данные по HTTP, WSS, повторному подключению и передаче файлов. Продолжение мониторинга при сбое хранения не открывает публичный обход авторизации.

### ASEC-005. TLS и идентичность сервера

TLS не ниже 1.2, предпочтительно 1.3. Клиент проверяет закреплённое через SSH доверие, срок и DNS/IP-идентичность. Самоподписанность не разрешает принять любой сертификат. Идентичность Agent не равна адресу.

Сертификат — 365 дней, предупреждение за 30. Ротация ручная SSH/CLI; каждый телефон проверяет новый отпечаток. Неожиданная замена/истечение/подозрение на компрометацию требуют доверенного восстановления, без выключения TLS-проверки.

**Проверка:** MITM, неправильное имя/IP, чужой/истёкший сертификат отклоняются; изменение адреса не подменяет сервер. Ключи не выдаются через API.

### ASEC-006. Pairing

Код криптографически случайный, одноразовый, действует 5 минут, привязан к конкретному Agent и доверенно разрешённому сценарию. Выдача через CLI доступна владельцу Agent или администратору с фактическими полномочиями; наличие любого SSH-login не является разрешением. Попытки, параллельность и частота ограничены; истечение/использование аннулирует код. Код не раскрывается через общедоступную диагностику/логи.

**Проверка:** replay, использованный/истёкший код, поток подбора и неверная привязка не выдают токен и не создают неограниченное состояние. Конкретные лимиты попыток фиксируются в конфигурационном профиле до выпуска.

### ASEC-007. Токены и равноправие устройств

Каждому устройству выдаётся отдельный случайный 256-битный токен до отзыва. Сервер хранит проверочное значение, не исходный токен; клиент — защищённое Android-хранилище. Токены не передаются в URL, модули, UI-пакеты или сообщения ошибок. Идентичность аудит-инициатора выводится из авторизации, не из произвольного device-id в запросе.

**Проверка:** устройства имеют равные права/приоритет, но разные секреты; подмена заявленного device-id не меняет инициатора и не позволяет использовать чужую регистрацию.

### ASEC-008. Отзыв и утрата доступа

Подтверждённый отзыв равноправным оператором прекращает новые запросы и действующие WSS-сессии отозванного устройства; активные потоки пересматривают авторизацию в предусмотренных безопасных точках. SSH/CLI позволяет восстановиться при утрате всех телефонов.

**Проверка:** отзыв не теряется из-за кэша/перезапуска/отката. При отказе аудита обычный API отзыва подчиняется ASEC-011; аварийное SSH-действие и пробел аудита обозначаются, не выдаются за полностью записанные.

### ASEC-009. Именованные действия и валидация

API принимает только зарегистрированные операции с типизированными схемами, bounds и серверной проверкой состояния/прав. Не допускаются произвольные shell-команды/скрипты, подстановка команд и произвольные исполняемые пути. Внешняя утилита вызывается проверенным executable и массивом аргументов без shell. Доверенная ручная установка модуля — отдельное разрешение исполнения его кода с правами пользователя, а не произвольный shell-endpoint.

**Проверка:** метасимволы/опции в имени файла, ICMP-target или параметре не становятся командой. Неверное поле/тип/объём даёт ограниченную безопасную ошибку.

## 4. Аудит, повторы и состояние

### ASEC-010. Содержание аудита

Управляющие действия и отказы фиксируют время, авторизованное устройство/локального/системного инициатора, operation-id, действие, безопасный объект и результат. Нет токенов, паролей, ключей, содержимого файлов/чувствительных аргументов/окружения. Чтение текущих метрик не заполняет аудит.

**Проверка:** негативные сценарии оставляют корректную идентичность и результат без секретов. Поля недоверенного ввода ограничены/экранированы, не создают поддельные записи.

### ASEC-011. Запрет новых изменений без записи начала

До первого побочного эффекта изменяющей операции надёжно сохраняется начало. Невозможность записи запрещает начало, включая управление модулями, настройки, файловые действия и штатную очистку корзины. Штатный CLI не обходит это правило. Первичная установка до появления рабочего Agent и отдельное аварийное внешнее обслуживание относятся к ASEC-031. Мониторинг и доступное авторизованное чтение продолжаются по возможности. Отказ виден в текущем состоянии независимо от записи события в сломанный журнал.

**Проверка:** заполненный диск, отказ прав, повреждение/отказ commit не приводят к изменению объекта. Штатная ротация с успешной записью ничего не блокирует. При отказе через клиент нельзя даже очистить файл ради места; восстановление — SSH/CLI.

### ASEC-012. Результат после побочного эффекта

Ошибка сохранения результата не превращает уже выполненное действие в невыполненное. Известный результат и сбой аудита сообщаются отдельно; при неопределённости возвращается неизвестный результат. Автоматический повтор запрещён. Проверка/безопасное завершение уже начатой операции определяется её схемой.

**Проверка:** crash/lost reply между побочным эффектом и ответом не вызывает второе выполнение. Надёжный стартовый intent не считается доказательством успеха.

### ASEC-013. Повторы, конфликты и ротация

Operation-id привязан к инициатору/действию/параметрам; повтор в пределах срока возвращает состояние, несовпадающие параметры отклоняются. Завершённые результаты/защита повторов — 7 суток; после истечения нельзя обещать exactly-once или слепо повторять. Файлы/настройки проверяются по версии, конфликтующие действия сериализуются.

Аудит — до 30 суток/64 МБ, события — до 7 суток/32 МБ. Ротация не удаляет единственные сведения незавершённой операции: они сохраняются в операционном состоянии до проверки/административного разрешения. При невозможности ограниченного хранения новые изменения приостанавливаются.

**Проверка:** перезапуск, два телефона, ротация и внешнее SSH-изменение не превращают неизвестное состояние в ложный успех; старый cursor сообщает разрыв.

## 5. Файлы, процессы и источники

### ASEC-014. Разрешённые корни и путь

Все файловые операции используют id разрешённого корня и относительный путь. Проверка строкового префикса/realpath с поздним открытием недостаточна. Используются дескрипторы и защищённое разрешение openat2 с запретом выхода за корень, symlink/magic-link. Двойное декодирование, NUL, traversal и неоднозначный путь не должны расширять доступ.

**Проверка:** чтение/запись/upload/download/move/restore/PURGE одинаково ограничены. Подмена промежуточного каталога, ссылки и гонки не обходят политику; без нужного безопасного механизма — отказ.

### ASEC-015. Mounts, aliases и собственные файлы

Вложенное монтирование включается явно как разрешённая область. Hard links/bind mounts и альтернативные имена не обходят защиту собственных объектов: учитываются файловые идентичности и безопасные операции с родителями. TLS-ключи/токены не читаются через файловый API; код/конфигурация/БД/runtime/реестр/резервы Agent и необходимые предки защищены от разрушительного изменения через него.

**Проверка:** / с root не отменяет фиксированных запретов. Проверяются aliases, смена mount/inode и rename предка. API-защита не заявляется изоляцией от root/того же UID.

### ASEC-016. Типы и содержимое файлов

Спецфайлы/устройства/сокеты и виртуальные /proc,/sys,/dev не читаются как обычный файл. Контент потоковый и ограничен по фактическим байтам: полный текст 1 МБ, редактирование 512 КБ, upload 50 МБ, download 100 МБ по умолчанию. Частичный текст ограничен строками и байтами. Неограниченный read/декодирование/память запрещены.

**Проверка:** неизвестная длина, чрезмерная строка, бинарный/неверно закодированный текст и обрыв потока не исчерпывают память/диск. Имена/контент не исполняются, секреты не попадают в технические ошибки.

### ASEC-017. Сохранение, корзина и PURGE

Запись проверяет исходную версию/идентичность и публикует готовый результат атомарно, где возможно; не расширяет права файла незаметно. Корзина закрытая на той же ФС, 7 суток/1 ГБ по умолчанию; недостаток места не превращает удаление в PURGE. Ручной PURGE только корзины и после отдельного необратимого подтверждения. Восстановление/замена имени имеют явную политику.

**Проверка:** занятой target не перезаписывается молча; меж-ФС операция при неопределённости сохраняет источник. Свежие объекты не удаляются ради квоты; автоматическая очистка не обходит аудит.

### ASEC-018. Идентичность процесса и сигналы

Перед сигналом проверяются boot-id/PID/время старта/текущий экземпляр и права, с pidfd при поддержке. PID 1 защищён при root. TERM/KILL отдельны и подтверждаемы; обычный TERM не эскалирует автоматически. Собственное ядро и управляемые модули обслуживаются по специальному жизненному циклу.

**Проверка:** PID reuse, исчезновение процесса и race не посылают сигнал другому объекту; успешный send не выдаётся за подтверждённое завершение. Аргументы/окружение процессов не экспортируются.

### ASEC-019. Docker и журналы безопасности

Docker-сокет/журналы используются только при существующих реальных правах, без автоматического добавления в docker/adm/systemd-journal. Обзор Docker не предоставляет клиенту сырой прокси всего Docker API и не добавляет управление контейнерами. Чтение security-источников идёт по проверенному адаптеру и показывает неполноту.

**Проверка:** недоступный socket/journal не запускает sudo; неподдерживаемый формат не означает отсутствие угроз. Дополнительные права выдаёт администратор с объяснением фактического охвата.

## 6. Модули, IPC и UI

### ASEC-020. Доверие к серверному модулю

Ручная установка явно регистрирует и разрешает код. Проверяются манифест/id/издатель/пути/совместимость/зависимости, циклы и подмена регистрации. Модуль не назначает себя системным; появление executable не является разрешением запуска. Системные функции не зависят от удаляемого модуля.

**Проверка:** чужая/неверная регистрация не запускается. Администратору объясняется, что код под общим UID получает его права; подпись и capabilities не являются sandbox. Для внешнего процесса состояние управления не преувеличивается.

### ASEC-021. Аутентификация IPC

Unix stream socket защищён правами каталога/сокета. Handshake связан с доверенной регистрацией и экземпляром запуска; одноразовый секрет передаётся унаследованным каналом/FD, не аргументами команды. Peer credentials проверяются дополнительно; одного UID или заявленного module-id недостаточно. Токены телефонов не передаются.

**Проверка:** другое соединение/старый экземпляр/повтор секрета не получает маршрутизацию. Проверка не заявляется защитой от злонамеренного root/кода под тем же UID.

### ASEC-022. Ограничения IPC и процессы

Framing длиной и UTF-8 JSON проверяются до выделения чрезмерной памяти; управляющее сообщение до 1 МБ, глубина/очередь/частота/число запросов ограничены. Обычный RPC — 10 секунд, длительный возвращает operation-id. Максимум пять рестартов за десять минут; управляемая остановка до 15 секунд, затем предусмотренное принудительное завершение.

**Проверка:** повреждённый length/JSON, flood, зависание, исчезновение socket и старые сообщения не ломают ядро/остальные модули. Timeout не означает отмену уже выполненного действия.

### ASEC-023. Подлинность UI-пакета

Android-клиент проверяет подпись отдельно доверенного издателя, целостность, id, схемы/версии/возможности и получает подтверждение установки. Ключ из того же пакета не создаёт доверие автоматически. Получение через уже доверенный Agent не заменяет доверие к издателю.

**Проверка:** подмена пакета/модуля/ключа/версии отклоняется до активации; рабочий UI сохраняется до проверенной замены; установка UI не устанавливает серверный код.

### ASEC-024. Декларативность и сложность UI

Разрешены только встроенные нативные компоненты и объявленные именованные действия. JavaScript, DEX, native Android-библиотеки и исполняемые сценарии не загружаются. Архив до распаковки проверяется на traversal/ссылки/число файлов/распакованный размер; изображения и глубина/сложность дерева ограничены профилем.

**Проверка:** zip-bomb, огромная картинка, неверная binding/action и неизвестный компонент не выполняют код/чужие операции и не ломают остальные экраны. Сервер повторно проверяет параметры даже после клиентской валидации.

## 7. Поставка, данные и доступность

### ASEC-025. Подписи и совместимость выпуска

Бинарники/архивы/манифесты и метаданные проверяются по доверенным ключам и TUF-политике: целостность, роли/версии/срок, отзыв и совместимость. Ключи приходят с проверенным bootstrap/клиентом, не из произвольного скачанного файла. GitHub Releases/HTTPS-транспорт сами по себе не доказывают подлинность; checksum с того же источника недостаточен.

**Проверка:** повреждённый/чужой/несовместимый/отозванный/устаревший выпуск отвергается до остановки. Неверные часы не разрешают пропустить проверку срока/подписи.

### ASEC-026. Обновление, миграция и откат

До замены проверяются место, зависимости, конфликтующие действия, резерв и путь возврата данных. Без проверенного возврата после несовместимой миграции требуется отдельный план обслуживания. Health check 60 секунд оценивает действительные ожидаемые функции, не отсутствие необязательного оборудования. Автовозврат допускает только проверенный предыдущий выпуск и согласованное состояние.

**Проверка:** разрыв SSH/перезапуск не начинает второе обновление; откат не возвращает отозванные токены/устаревшие разрешения и не заменяет всё состояние безопасности слепым snapshot. Известно отозванный выпуск не выбирается автоматически; отсутствие безопасного пути возврата показывается явно. Если актуальное состояние доступа утрачено и не может быть проверено, старые токены из backup не активируются автоматически — применяется доверенное восстановление через SSH. Внешние эффекты модуля не обещаются обратимыми.

### ASEC-027. Хранение и резервные копии

Каталоги состояния/секретов и файлы получают минимально необходимые права; приватные ключи/секретное состояние не доступны посторонним. Токены в серверной БД представлены проверочными значениями. SQLite локальный, исправленный поддерживаемый выпуск с WAL-reset fix; WAL/SHM/backup/временные файлы защищены не слабее исходного состояния. Копии согласованные, независимые БД не считаются общей атомарной транзакцией.

**Проверка:** история не вытесняет идентичность/ключи/настройки. Резерв защищён от чтения через файловый API. Шифрование всех данных на диске и защита от администратора хоста не обещаются этой моделью.

### ASEC-028. Защита ресурсов и частичная работоспособность

Запросы, JSON/frames, страницы, передачи, очереди/частота/время обработки ограничиваются до дорогой работы. Общий JSON до 1 МБ, история до 4 МБ/2000 точек на ряд, процессы до 100 на страницу, до двух файловых передач и четырёх изменений одновременно. Состояние handshake/операций и резервы также ограничены. Снимки заменяемы; сохраняемые события/аудит/операции имеют свою политику.

**Проверка:** slow client, большие запросы и массовые ошибки не создают бесконечные очереди/логи. При делегированных cgroup применяются модульные лимиты, иначе отсутствие изоляции видно; глобальные UID-лимиты не мешают другим приложениям. Watchdog не обещает изоляции нативного падения ядра.

### ASEC-029. Сетевая диагностика и firewall

ICMP-target — явно выбранный общий IP/домен, включая частные сети; без shell/произвольных флагов/URL/port scan. Максимум пять пакетов и десять секунд по первому пределу, фон раз в 60 секунд после включения. DNS/реальный адрес/время связаны с результатом. CAP_NET_RAW/sysctl автоматически не выдаются/не меняются.

Firewall меняется лишь точечным согласованным планом поддерживаемого адаптера. Нельзя автоматически reset/enable/disable UFW, менять чужие правила или принимать публичную подсеть VPS за LAN.

**Проверка:** target не становится командой; ошибка ICMP не означает OFFLINE. IPv4/IPv6/NAT/внешний firewall проверяются фактическим маршрутом с телефона.

### ASEC-030. Ошибки, логи и фоновые ограничения

Ошибки типизированы, ограничены и не раскрывают ключи/токены/пароли/содержимое файлов/чувствительную командную строку. Нет рекурсивного бесконечного логирования сбоя самого журнала. События не запускают автоматическое исправление. Уведомления без внешнего сервиса зависят от телефона; его offline не доказывает остановку сервера.

**Проверка:** malicious input не подделывает событие/лог, значения отсутствия не заменяются нулями, недоступный source не объявляется безопасным состоянием. WorkManager/Doze/force-stop не подменяются обещанием доставки за 15 минут.

### ASEC-031. Аварийное обслуживание и удаление

SSH/CLI восстанавливает доступ/аудит/установку с фактическими административными правами. Штатные команды работающего Agent сохраняют правила авторизации/аудита; отдельный режим аварийного обслуживания требует реальных локальных административных полномочий и не доступен через обходной публичный API/IPC. Первичная установка до существования аудита и внешние аварийные действия описывают фактически выполненные шаги/пробелы. Agent не обещает контролировать все SSH-команды. Обычное удаление сохраняет данные, полная очистка отдельно подтверждается; только собственные объекты/правила удаляются.

**Проверка:** восстановление не отключает TLS/авторизацию и не создаёт скрытый постоянный helper. Удаление интеграции/Agent не удаляет автоматически Docker/драйверы/системные пакеты/стороннее приложение. Частичный отказ удаления не выдаётся за успех.

## 8. Приёмка безопасности

Для выпуска обязательны негативные проверки и фиксация результата по ASEC/AFR:

| Сценарий | Требования |
|---|---|
| Ordinary/root, sudo при установке, несовпадение пользователей | ASEC-001–ASEC-003 |
| Запрос без токена, подмена устройства, отзыв WSS/потоков | ASEC-004, ASEC-007, ASEC-008 |
| MITM, смена адреса/сертификата, истечение, pairing replay/flood | ASEC-005, ASEC-006 |
| Командная инъекция, неподдерживаемые действия | ASEC-009, ASEC-029 |
| ENOSPC/нет прав/повреждение БД до и после действия | ASEC-010–ASEC-013, ASEC-027 |
| Два телефона, потерянный ответ, crash/expiry/replay | ASEC-012, ASEC-013 |
| Traversal/symlink/hard link/bind mount/rename race | ASEC-014, ASEC-015 |
| Большой файл/строка, конфликт/обрыв записи, меж-ФС move, PURGE | ASEC-016, ASEC-017 |
| PID reuse/PID 1/потеря процесса | ASEC-018 |
| Недоступный Docker/journal/изменённый формат источника | ASEC-019 |
| Ложный module-id/экземпляр, сломанный framing, зависание/рестарт | ASEC-020–ASEC-022 |
| Подменённый UI, архив/картинка/дерево чрезмерного размера | ASEC-023, ASEC-024 |
| Подмена/отзыв выпуска, обрыв обновления, миграция/rollback | ASEC-025, ASEC-026 |
| Чтение секретов/backup, WAL-growth, медленный клиент/flood | ASEC-027, ASEC-028, ASEC-030 |
| Утрата всех телефонов, отказ аудита, частичное удаление | ASEC-031 |

Значения глубины JSON, числа соединений, скорости запросов, лимитов pairing, UI-архивов/изображений, внутреннего резерва и cgroup-профилей задаются в версиях контрактов/конфигурации и проверяются нагрузкой до выпуска. Неограниченное значение по умолчанию недопустимо; требования к CPU/RAM публикуются после измерений.

## 9. Источники и пределы их применения

- [OWASP Logging](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html): состав/защита логов, ограничение ресурсов и проверка отказов. Запрет новых изменений при отказе аудита — отдельное принятое решение ServerDeck, не обязательное предписание источника.
- [RFC 9525](https://www.rfc-editor.org/rfc/rfc9525.html): проверка идентичности сервиса TLS; [Android security config](https://developer.android.com/privacy-and-security/security-config): клиентское доверие.
- [openat2](https://manpages.debian.org/bookworm/manpages-dev/openat2.2.en.html): защищённое разрешение пути; не готовое доказательство безопасности всей многошаговой операции.
- [Docker Linux post-install](https://docs.docker.com/engine/install/linux-postinstall/): административный охват доступа к docker.
- [SQLite WAL](https://www.sqlite.org/wal.html), [Backup API](https://www.sqlite.org/backup.html): локальность WAL, durability, исправления и согласованные копии.
- [TUF](https://theupdateframework.github.io/specification/latest/): модель доверия поставки и метаданных.
- [systemd.service](https://github.com/systemd/systemd/blob/main/man/systemd.service.xml), [systemd.kill](https://github.com/systemd/systemd/blob/main/man/systemd.kill.xml): watchdog и завершение процессов службы.
- [Android WorkManager](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work): ограничения периодической фоновой работы.

Приведённые продуктовые сроки, бюджеты и допустимые права согласованы пользователем; источники не заменяют эти решения и не доказывают готовность реализации. Формальные тесты/аудит кода проводятся после её появления.
