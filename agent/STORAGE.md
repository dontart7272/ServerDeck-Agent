## Файлы и границы

- `internal/storage/migrations/001.sql`: первая embedded миграция critical.db; SHA256 текста, release_id, applied_at, user_version=1 и application_id. Созданы только таблицы работающего E02: identity, settings, devices/security_policy для направленных floor-fixtures, operations/object_locks/operation_changes, audit/storage_meta, schema_migrations. Pairing, rules, модули, transfer/trash и независимые events/history DB появятся со своими этапами и миграциями.
- `internal/storage/store.go`, `platform_linux.go`: открытие, совместимость реальной схемы и checksum, quick_check, локальная ФС, права, flock, один writer/соединение, ограниченный доступ и RAM health. Windows отказывает critical storage, сохраняя прежние offline contract-команды.
- `internal/storage/operations.go`, `resolve.go`: FULL-транзакции intent/operation/audit/locks, результаты, ротация, cursor gap, административное разрешение unknown.
- `internal/storage/backup.go`: SQLite backup API, защищённые manifest/digest и текущий security floor; восстановление в новый каталог.
- `internal/operations/`: один application service, compiled handlers, планы, дедупликация, очередь, cancellation boundary и maintenance barrier. ConfigHandler проверяется на реальной БД, но не зарегистрирован в offline CLI: OS preflight/применение всей runtime-политики и local socket относятся к зависимым этапам.
- `internal/app/state.go`: конечный CLI использует этот service; нет raw SQL, shell, HTTP или IPC bypass.

## Открытие и запись

Каталог 0700, файлы 0600, собственный UID, nlink=1; каждый компонент открывается no-follow, directory FD удерживается. Writable ancestors запрещены, кроме root-owned sticky временного каталога. Поддерживаемая здесь allowlist локальных ФС: ext4, tmpfs, XFS, Btrfs; наличие в allowlist не означает проверенную матрицу выпуска. NFS/SMB/Windows mount отказываются. Shared UID/root не считаются изолированными злоумышленниками. Owner-lock удерживается весь срок жизни Store. Offline maintenance запускается от владельца состояния; root может обслуживать root-owned состояние, автоматически менять пользователя/права CLI не умеет.

page_size=4096, foreign_keys=ON, synchronous=FULL, реальный journal_mode=WAL; busy timeout/read/write transaction deadline 1000 ms. ConnectHook задаёт настройки на каждом соединении: cache_spill=OFF, cache_size=-8192 KiB, temp_store=MEMORY, trusted_schema=OFF, autocheckpoint=0, journal_size_limit=0, statement cache отключён. Для checkpoint явно используется `main.wal_checkpoint(TRUNCATE)`: общий checkpoint включает TEMP и при memory TEMP приводил к SQLITE_LOCKED; это исправлено и перепроверено. До транзакции нужен успешный TRUNCATE; внешний длительный reader даёт ограниченный BUSY.

WAL hard 8000000 bytes обеспечивается консервативным admission: после TRUNCATE максимум страниц `(WALBytes−65536−32)/4120`, cache spill отключён, одна транзакция может записать каждую dirty page в WAL один раз. Growth ограничен max_page_count. Поэтому v1 допускает БД примерно до 7,9 МБ и может отказать раньше логических квот state/audit по 64 МБ. Это намеренный ранний отказ, а не обещание использовать весь номинальный бюджет. Для расширения полезной ёмкости нужен отдельно проверенный bounded-page writer; лимиты WAL нельзя ослаблять молча. Physical allocation DB/WAL/SHM и free space проверяются отдельно с запасом WAL+65536; проверка не резервирует место от чужих приложений. Реальный ENOSPC после эффекта всё равно обрабатывается. VACUUM на заполненном диске не запускается.

По умолчанию операции ограничены 10000 записями/64000000 bytes, на запись резервируется 32768 bytes с учётом результата <=16384 и locks/index overhead. Аудит резервирует консервативные 2048 bytes/запись; runtime audit retention/budget читаются из settings перед записью. Общая физическая граница также ограничивает выделение страниц и sidecars. Внутренняя writer-очередь <=32, read pages<=100; весь SQL фиксирован, значения параметризованы.

## Порядок операций

Инициатор создаётся доверенным адаптером; Local берёт euid, не argv. В E03 Device-инициатор создаётся только из проверенного непрозрачного Credential; HTTP/WSS и local socket повторяют авторизацию/политику перед intent/running. Параметры strict JSON <=65536 bytes, неизвестные поля проверяет compiled handler; канонизация упорядочивает ключи и нормализует конечные числа float64 (большие U64 остаются строками). HMAC-SHA256 включает actor/action/expected_version/params; request/plan ID не входят в смысл. Ключ `request.key` не регенерируется при потере существующей БД. В БД нет исходных параметров/содержимого файлов.

План: случайные 128 бит, 120 секунд, <=128 всего/8 на инициатора. План не меняет объект. Execute сначала возвращает существующий результат после проверки actor/action/HMAC, затем проверяет план, ждёт очередь и повторяет lookup/проверку реального объекта. Отказ до intent не исполняет эффект. При перегрузке конкурентных запросов до создания intent возможен BUSY; повтор существующего ID возвращает состояние, не запускает работу заново.

До четырёх активных эффектов; очередь32/8 на инициатора/10 секунд. Готовые очереди вращаются между инициаторами, FIFO внутри. Ключи конфликтов валидированы и сортируются; durable object_locks создаются в одной FULL-транзакции с operation+audit intent. Перед эффектом объект проверяется снова и сохраняется running/effect. Internal lock не защищает внешний объект от SSH: будущий адаптер обязан использовать подходящий атомарный version-aware примитив; файловые гарантии E08/BLOCK-FS этим блоком не закрыты.

Отмена через context работает до intent; после intent Service.Cancel может выиграть до входа в effect phase. После входа произвольный native effect не прерывается, отключение клиента его не отменяет. Panic/неопределённый результат дают unknown. При отказе result commit RAM сохраняет известный эффект с result_pending; durable lock остаётся. После restart preparing/running становятся unknown/reconcile_required, callbacks не запускаются. Unknown не вытесняется, блокирует конфликтующий объект до проверки/административного разрешения.

Завершённые результаты защищены семь суток; при рестарте нет доказанного elapsed времени, поэтому temporal eviction консервативно ждёт полный retention-интервал в текущем запуске. Скачок wall clock >1 секунды относительно monotonic приостанавливает temporal expiry. Audit age cleanup аналогично ждёт свой интервал; объёмная ротация работает независимо, сохраняет operation state. При исчерпании защищённого состояния новые изменения запрещены. Audit seq/floor дают CURSOR_GAP, epoch сохранён в storage_meta. Health — фиксированное RAM-состояние/counter без рекурсивного журнала и сырых ошибок.

## Backup, floor и восстановление

Штатные backup/restore требуют durable running operation соответствующего действия и maintenance barrier: новых операций/планов нет, активные эффекты завершены. Backup API копирует согласованный critical.db, включает committed WAL; он не копирует одну живую `.db` без WAL и не обещает атомарность нескольких БД. Manifest пишется последним: фактическая schema1/2/3 (текущая3 послеE05), installation_id, security_generation, digest/length/consistent и HMAC. Директория назначения должна отсутствовать; незавершённую копию повтор не перезаписывает.

Текущий floor хранится отдельно от возвращаемого snapshot, защищён ключом текущего состояния. E02 floor v1 содержит installation/generation, revoked device IDs, deny_actions/max_changes. Это направленный механизм для проверки границы E03/E11, не полный формат TUF/authorization policy. Export сверяется с живой critical generation и содержимым; отсутствие/повреждение актуальной authority останавливает restore. При запуске старый critical.db под более новым floor или утрата обязательного floor запрещены.

Restore не заменяет действующую БД: новый private каталог, marker restore-incomplete, проверка manifest/HMAC/digest/schema/quick_check, overlay текущих отзывов и union запретов/min параллелизма. Актуальные operations/object_locks/operation_changes/audit/storage_meta переносятся из quiesced текущей authority, чтобы не потерять dedup и единственное unknown-состояние после старого snapshot. Это read-only чтения источника и одна destination-транзакция, не общий commit двух БД. Revision восстановленных settings увеличивается выше обеих прежних версий, исключая ABA. Audit получает новый случайный epoch; AuditPage отказывает старому epoch с CURSOR_GAP, E03 обязан привязывать к нему публичный курсор. После этого — fsync и complete marker. Незавершённый restore не открывается. Потеря ключа/floor/доказательства актуальности означает SAFETY_UNAVAILABLE, без активации токенов backup. Переключение службы/подписи/миграции будущих версий — E11. Полное восстановление при уничтоженной текущей authority потребует отдельного доверенного SSH recovery, а не выбора старого export вслепую.

Floor-fixtures допускают до32 отозванных IDs и128 deny_actions; исчерпание даёт fail-closed. Это описание границы исторического E02. В E03 floor v2 хранит полный текущий ограниченный registry active verifiers, Agent identity и policy; последние32 revoked metadata можно удалить без resurrect токенов, поскольку restore заменяет backup registry текущим целиком. Pairing/token/revoke реализованы в E03, TUF остаётся E11. Ошибка floor после registry commit даёт unknown/partial и отдельный RAM health flag, не повтор эффекта. Детали и проверки — AUTH-TRANSPORT.

`state-resolve ... applied|none --confirm` — явное наблюдение локального владельца, не автоматическое доказательство успеха. Service пишет audit gap с фактическим local UID и ADMIN_RESOLUTION и только затем освобождает durable lock/назначает dedup_until в той же транзакции. Никакой эффект не повторяется. Нельзя использовать `none` как догадку по потерянному ответу.

Официальные основания проверены 13 октября 2026: [SQLite WAL](https://www.sqlite.org/wal.html), [PRAGMA](https://www.sqlite.org/pragma.html), [backup API](https://www.sqlite.org/backup.html), [закреплённый драйвер](https://github.com/mattn/go-sqlite3/tree/v1.14.52). FULL предполагает исправный fsync/носитель; process-crash и ENOSPC тесты не моделируют отключение питания или всю матрицу ФС.
